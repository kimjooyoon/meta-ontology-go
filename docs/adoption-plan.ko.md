# Gooo를 다른 팀이 실제로 쓰게 만드는 계획

업데이트: 2026-10-30. 아래 기준은 실제 사용에서 개발 우선순위를 고르기 위한 것입니다.
공개 예제와 자체 소비자의 실행 기록을 제공하고 있으며, 외부 고객의 반복 사용과 지불 의사는 미관측입니다.

## 먼저 제공할 작업

**작은 업무 규칙을 바꾸고, 달라진 결과를 설명하고, 선택한 프로그램을 다시 쓰는 흐름**에 집중합니다.
첫 대상은 조건식·변수 대입·함수 호출로 표현할 수 있고 요구사항 변경이 반복되는 Go 백엔드 작업입니다.
큐 배치 크기, 재시도 계산, 진단 분류 같은 좁은 함수를 기존 프로그램 옆에서 시험할 수 있게 만듭니다.
Go로 직접 작성한 함수와 테스트가 비교 기준이며, 초기 Gooo 선언과 사례 작성 시간도 비용에 포함합니다.
[동일한 규칙의 Go 함수](../examples/workflow-outcome-delta/referencego/batch.go)와
원래 입력 20개를 읽는 검사를 함께 제공합니다. 이 검사는 의미가 같은 비교 대상을 준비하며,
작업 시간이나 고객의 비용 절감은 실제 사용에서 별도로 측정합니다.

Gooo 선언에는 허용할 선택지와 기대 결과가 있고, 자체 소형 결정 모델은 후보의 순서를 제안합니다.
컴파일러는 고른 경로를 Go로 만들고 실제 결과를 저장합니다. 모델을 생략하면 같은 후보를
결정론적으로 탐색합니다. 저장한 프로그램은 새 추론 없이 다시 실행할 수 있습니다.
설계도, 조립한 부품, 시험 기록을 함께 전달하는 작은 공방처럼 사용 흐름을 설명합니다.

현재 [배치 규칙 예제](../examples/workflow-outcome-delta/README.md)는 한도를 16에서 32로 바꿉니다.
[저장된 관측](research/workflow-outcome-delta-20261011/README.md)의 열 입력 그룹 중
다섯 그룹에서 기대값과 출력이 함께 바뀌고, 나머지 다섯은 같은 기대값을 충족합니다.
이를 [변경 보고서](workflow-outcome-delta.md#share-a-change-report)로 공유할 수 있습니다.
한 예제의 관측 범위를 그대로 표시하고, 팀별 편익은 실제 사용에서 측정합니다.

현재는 에이전트가 실행 결과를 읽고 다음 입력을 정한 뒤 다시 실행하는 과정도 지원합니다.
[작업 세션](language/workspace-sessions.md)은 한 실행 파일을 보유하면서 매 요청의 소스와 입력을
다시 확인하고 실제 프로그램을 두 번 실행합니다. 이전 실행의 성공 판정은 재사용하지 않습니다.
이 기능은 [소비자 요청 #1855](https://github.com/kimjooyoon/meta-ontology-go/issues/1855)에서 출발했고,
[PR #1860](https://github.com/kimjooyoon/meta-ontology-go/pull/1860)으로 `dev`에 병합됐고,
[0.6.39-dev 릴리스](releases/0.6.39-dev.md)에 포함됐습니다.
별도의 [공개 예제 #264](https://github.com/kimjooyoon/gooo-go-ports/pull/264)는 세션으로
저장된 테스트 관측을 해석합니다. 기존 ports 검증기의 개별 실행·재실행 경로에 세션을
연결하는 작업은 #1855의 여섯 번째 완료 조건으로 남아 있습니다.

## 최근 피드백에서 바꾼 우선순위

기여한 프로젝트에서 받은 반응은 문제의 재현 여부와 사용자의 필요를 함께 봐야 함을 보여줍니다.

- [pflag 유지관리자](https://github.com/spf13/pflag/pull/529#issuecomment-6495441754)는
  실제 사용자 수요가 불분명한 드문 결함의 수정이 다른 중요한 작업의 검토 시간을 가져간다고 지적했습니다.
  넓게 결함을 찾아 PR을 늘리는 작업을 줄이고, 보고된 사용자 문제와 기존 수정 요청부터 처리합니다.
- [githealthcheck의 검사 요청](https://github.com/Git-Hospital/githealthcheck/pull/47#pullrequestreview-5691267324)은
  유지관리자가 직접 실행하고 구현을 잘못 바꿔 검사가 실패하는지도 확인한 뒤 병합됐습니다.
  이런 독립적인 반례 확인을 활용하고, 상대가 실행한 검사 횟수는 상대의 관측으로 표시합니다.
- [Rugsnare의 데이터 손실 수정](https://github.com/Paraphern/rugsnare/pull/15#issuecomment-6476450927)은
  읽기 실패를 데이터 부재로 처리해 저장 내용을 덮어쓰는 실제 문제를 해결했습니다.
  Gooo에서도 읽지 못한 출처와 비어 있는 출처를 구분하고, 불완전한 관측을 성공으로 바꾸지 않습니다.
- [Goldmark의 답변](https://github.com/yuin/goldmark/issues/612#issuecomment-6501156861)은
  URL 처리의 모호한 경우에 기존 설정 확장점을 사용하도록 안내했습니다.
  문서화된 동작과 원하는 동작이 다른 경우에는 해당 사용처의 설정과 계약부터 확인합니다.

이 반응은 기여의 유용성을 판단할 자료입니다. 각 프로젝트에서 Gooo를 채택했다는 뜻으로 세지 않습니다.
PR·병합·스타·코드 줄 수와 함께 실제 사용자의 요청, 재현 입력, 독립 검증과 후속 사용을 구분해 기록합니다.
새 기여를 만들기 전에 기존 담당 작업과 다른 기여자의 수정이 있는지도 확인합니다.

## 도입 효과를 판단할 지표

| 질문 | 기록할 값 | 현재 상태 |
| --- | --- | --- |
| 해결할 구체적인 문제가 있는가? | 요청 출처, 사용자가 겪은 실패, 기대 동작, 기존 담당 작업 | 자체 소비자의 세션 요청 확인; 외부 Gooo 고객 수요는 미관측 |
| 처음 실행하기 쉬운가? | 설치 시작부터 자기 입력의 첫 결과까지 걸린 시간, 실패한 단계 | 기존 Go 1.27.3 환경의 새 폴더에서 0.6.39 아카이브·라이브러리 생성·진단 흐름 자체 확인; 외부 사용 시간은 미관측 |
| 다음 규칙 변경이 쉬워졌는가? | 같은 작업의 Go+테스트 기준 대비 전체 수정 시간; 초기 선언 비용 포함 | 미관측 |
| 무엇이 바뀌었는가? | 전체 입력 그룹, 같은 기대값의 회귀, 변경된 요구, 미관측·중복 충돌 | 저장 결과 비교 구현 |
| 모델을 붙일 이득이 있는가? | 같은 후보·예산에서 시도 수, 완성/부분 결과, 준비·추론·전체 실행 시간 | 좁은 자체 예제별 기록 |
| 계속 쓰는가? | 외부 팀의 두 번째 실제 변경, 재실행 횟수, 중단 이유 | 미관측 |
| 검토 부담을 줄였는가? | 변경 범위, 독립 재현 방법, 수정 요청과 재검토 횟수 | 피드백 확인; 비용 절감은 미관측 |
| 비용을 내고 해결할 문제인가? | 담당자가 제시한 반복 비용, 원하는 지원 범위, 유료 도입 의사 | 미관측 |

분모가 없으면 미관측으로 남깁니다. 회귀율의 분모는 같은 기대값을 이전에 충족한 그룹입니다.
원하는 결과가 바뀐 입력은 별도로 셉니다. 모델의 첫 추천, 탐색 후 충족 결과, 새 입력 결과도
각각 기록합니다. 추론 시간에 모델 로딩·컴파일 시간을 섞어 속도 개선을 주장하지 않습니다.
금액으로 환산하려면 실제 요금이나 사용 팀이 제공한 시간당 비용과 기간이 필요합니다.

## 다음에 확인할 것

1. 실제 ports 소비자를 지원되는 작업 세션에 연결합니다. 현재 입력과 새 실행 결과,
   실행 파일 재사용, 원본 출처와 자원 정리를 각각 확인합니다. 그 후에 소비자 버전을 갱신합니다.
2. 처음 쓰는 에이전트가 고정된 공개 버전으로 설치부터 자기 입력의 첫 결과까지 도달하는지 확인합니다.
   필요한 파일, 지원 환경, 실패한 단계와 표현할 수 없는 조건을 함께 남깁니다.
3. 실제 작업에서 두 번째 변경이 발생하면 처음 선언을 준비한 비용까지 포함해 Go+테스트와 비교합니다.
   저장 재실행이나 데모 한 번을 팀의 반복 사용으로 세지 않습니다.
4. 외부 사용자가 구체적인 문제와 지원 범위를 제안하면 그 작업을 우선합니다.
   유료 파일럿은 반복 사용과 지불 의사가 확인된 요구에 맞춰 설계합니다.

외부 모집과 인터뷰, 대외 연락은 실제 실행 여부를 구분해 기록합니다.
판매 가능성은 설치·연동 지원, 팀의 변경 기록 관리, 반복 검증 운영에서 확인할 수 있습니다.
호스팅, 접근 제어, SLA, 요금제는 실제 요청과 운영 비용이 확인된 뒤 구체화할 후보입니다.
공개 언어·컴파일러·소형 모델과 재현 가능한 예제를 계속 제공하면서 비용을 낼 작업을 찾습니다.

## Jev에서 참고할 부분

[TypeSafe의 공식 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev)는
Jev의 출력을 사전에 정한 타입으로 제한하고 스키마 일치를 보장한다고 설명합니다.
[공식 문서](https://docs.typesafe.ai/introduction)는 좁은 질문을 나누고 그 답을 코드로 조합하는 방식을 제안합니다.
Gooo에서는 이 아이디어를 허용된 조립 선택지, 명시적인 기대 결과, 수정 전후 실행 기록에 연결해 연구합니다.
업무적으로 올바른 선택인지와 어떤 입력까지 관측했는지는 추가로 측정할 항목입니다.

[a16z의 2026-10-09 발표](https://www.a16z.news/p/investing-in-typesafe)에서 TypeSafe 투자 관계를 확인했습니다.
Gooo의 투자 가능성과 매출은 별도의 고객 증거가 필요한 미관측 항목으로 둡니다.
특정 업체의 전용 제품이나 제휴를 표방하려면 실제 연동과 고객 요구부터 확보해야 합니다.
현재 개발 우선순위는 자체 결정 모델, Go 실행 경로, 재사용 가능한 언어 표현과 변경 설명입니다.
