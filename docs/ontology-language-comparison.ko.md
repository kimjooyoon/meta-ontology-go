# 관련 언어에서 배우는 Gooo의 다음 과제

2026-10-13 기준으로 공식 문서와 Gooo 소스를 함께 살펴본 기록이다.
공통 프로그램의 실행 속도나 정답률을 비교한 결과는 아직 없다.
여기서는 언어가 문제를 표현하는 방식과 Gooo에서 실제로 발견한 빈틈을 연결한다.

## 비교할 언어

| 언어 | 참고할 표현 방식 | Gooo에서 이어갈 작업 |
| --- | --- | --- |
| TypeQL / TypeDB 3 | 데이터 모델과 추론 함수를 구분하고, 인자와 반환값으로 계산 방향을 드러낸다. | 조건식의 원래 입력과 후보 결과를 구분하고, 보조 활동을 호출하는 방향을 설명한다. |
| Nemo | 사실과 규칙으로 관계를 선언한다. 재귀 관계, Unicode와 IRI 이름, 여러 데이터 형식을 다룬다. | 기존 활동 ID와 조건식의 호출 관계를 읽어 변경의 영향을 보여준다. |
| Scallop | 사실에 붙은 태그를 provenance semiring으로 전파한다. 확률적 추론도 이 구조에 포함된다. | 후보 점수, 허용된 선택지, 조건식, 실제 실패 사례를 함께 읽을 수 있게 한다. |
| OML / openCAESAR | 모듈의 namespace, import, 멤버 IRI로 참조 범위를 정한다. | import 별칭과 활동 ID를 따라 파일 사이의 참조를 해석하고 리팩토링 범위를 정한다. |

근거: [TypeQL 함수와 규칙](https://typedb.com/docs/typeql-reference/functions/functions-vs-rules/),
[Nemo 언어 안내](https://knowsys.github.io/nemo-doc/intro/tour/),
[Scallop provenance](https://www.scallop-lang.org/doc/probabilistic/provenance.html),
[OML 명세](https://opencaesar.io/oml/).
TypeQL과 Nemo는 현재 개발 비교 대상으로, Scallop과 OML은 관련 원리를 읽는 대상으로 두었다.
최근 커밋이나 별 개수만으로 성장 가능성과 사용성을 판단하지 않는다.

### 최근 변경에서 고른 두 가지

[TypeDB 3.13.6](https://github.com/typedb/typedb/releases/tag/3.13.6)은
2026-09-22에 공개됐고, 내장 함수를 `std::math::round`처럼 한정한 이름으로
호출하는 방식을 추가했다. Gooo에서도 파일별 import 범위를 타입과 호출에
일관되게 적용해야 사용자가 이름 충돌을 추측하지 않아도 된다.

[Nemo 0.10.1](https://github.com/knowsys/nemo/releases/tag/v0.10.1)은
2026-08-01에 공개됐다. 규칙의 projection을 import 쪽으로 옮길 때 조건 필터가
무시되던 문제를 수정했고, 유도한 사실 전체의 trace를 출력하는 옵션도 추가했다.
여기서 Gooo에 적용할 과제는 변환 전후의 조건을 보존하고, 결과가 따라온 소스 경로를
읽을 수 있게 하는 것이다. 소스 carrier 보존과 실제 실행 결과의 일치는 각각 확인한다.
두 변경에서 이름의 소유권과 변환 후 조건 보존을 이번 작업의 기준으로 삼았다.

## Gooo에서 이미 이어지는 흐름

Gooo 소스는 만들 수 있는 선택지와 지켜야 하는 조건을 선언한다.
구성 과정은 그 범위에서 후보를 만들고, 관찰 기록은 어느 소스와 선택으로 나온 결과인지 남긴다.
지원하는 프로필에서는 소형 결정 모델이 선택지를 고를 수 있고, 결정론적 선택 경로도 유지한다.

이 흐름을 도면과 작업 기록에 비유할 수 있다. 활동의 이름은 도면의 표지이고,
활동 ID는 같은 부품을 계속 가리키는 번호다. 조건식은 맞춰야 하는 치수이며,
관찰은 실제로 조립한 결과다. 표지를 바꿨다고 부품 번호까지 바뀌면 변경 이력을 따라가기 어렵다.

현재 구현의 비교할 만한 지점은 소스의 선택, 조건, 활동 ID와 관찰을 연결하는 방식이다.
이 방식이 다른 언어보다 유리한지는 같은 작업을 수행한 자료가 더 필요하다.
새 Integer 조건식 그래프를 읽는 작은 결정 모델과 컴파일러 연결을 개발하고 있다.
표현을 내보내는 기능과 모델이 이를 읽고 판단하는 기능의 진행 상태는 각각 기록한다.

## 이번 비교에서 이어진 개발

1. 활동 이름을 바꿀 때 같은 파일의 호출과 조건 참조를 함께 바꾸고 ID를 유지한다.
   소스 변경 제안과 원본·결과 해시를 남기는 기능은
   [PR #1511](https://github.com/kimjooyoon/meta-ontology-go/pull/1511)에서 CI 34개를 통과해
   개발 브랜치에 병합됐다.
2. [호출 위치 리팩토링 PR #1512](https://github.com/kimjooyoon/meta-ontology-go/pull/1512)는
   escaped 문자열과 한국어 이름의 소스 위치를 다룬다. 새 예제에서는 호출 두 개와 선언을
   세 편집으로 갱신하고 원본을 유지했다. 원래 CI의 의미 검사와 저장소 투영 검사에서
   같은 보조 함수 추출 문제가 발견돼 병합하지 않았다. 호출 수 계산을 작은 함수로
   분리한 수정안을 [PR #1513](https://github.com/kimjooyoon/meta-ontology-go/pull/1513)으로
   제출했고, 원래 PR은 병합하지 않고 닫았다. 새 PR은 자신의 CI 27개와
   해당 소스의 증거를 확인한 뒤 개발 브랜치에 병합됐다.
   파일 간 rename과 에디터의 실제 동작 관찰은 후속 과제다.
3. [조건식 의존 관계](source-criteria-dependencies.md)는 이미 준비한 호출 정보를 읽어
   후보 소유 활동 → 고정 조건식 → 보조 활동의 경로를 보여준다.
   예제의 세 연결과 두 보조 활동은 소스 분석으로 확인했다.
   [PR #1514](https://github.com/kimjooyoon/meta-ontology-go/pull/1514)는
   자신의 CI 27개를 통과해 개발 브랜치에 병합됐다.
4. 별도 워크스페이스 구현에서는 명시한 활동 ID가 호출 보고서에서 이름 기반 ID로
   다시 계산되는 문제를 찾았다. 원본과 내부 변환 후의 보고서가 선언 ID를 유지하도록 수정하고,
   실행 전 호출 관계를 읽는 `package inspect`를
   [PR #1515](https://github.com/kimjooyoon/meta-ontology-go/pull/1515)로 공개했다.
   자신의 CI 27개 중 두 실행에서 도움말 표의 분리 한계를 발견해 병합 없이 닫았다.
   도움말 내용은 그대로 두고 표를 작은 선언으로 나눈
   [수정안 #1516](https://github.com/kimjooyoon/meta-ontology-go/pull/1516)은
   자신의 CI 27개와 소스에 연결된 산출물을 확인한 뒤 개발 브랜치에 병합됐다.

2026-10-13 작성 시점에 호출 위치 변경과 의존 관계는 개발 브랜치에 병합됐으며,
워크스페이스 수정안 #1516도 개발 브랜치에 병합됐다.
개발 브랜치에 병합된 기능과 설치 가능한 릴리스의 범위도 따로 확인한다.
예제의 소스 분석은 프로그램 실행과 모델 예측을 수행하지 않았다.
각 변경은 자신의 CI 결과와 소스에 연결된 증거를 확인한 뒤 공개 흐름에 반영한다.

## 비교 원리를 소스 사용성으로 옮기는 예

OML에서 참고한 점은 멤버 이름을 어떤 모듈에서 읽는지 명시하는 방식이다.
Gooo의 후속 개발본은 같은 `Amount` 이름을 서로 다른 패키지가 써도
`청구.Amount`의 파일별 import와 entity ID로 구분하도록 구성했다.
새 소스 준비 결과에서 입력·결과 참조 네 개가 의도한 ID 네 개와 일치했다.

또한 참조를 잘 읽어도 편집 결과에서 import나 본문이 없어지면 작업을 이어갈 수 없다.
새 포맷 예제에서 기존 경로가 이 요소를 빠뜨리는 문제를 관찰했고,
전체 소스 carrier를 비교하는 후속 수정안을 준비했다.
별도 예제에서는 import 1개, 계산 본문 4개, bind 1개, 조립 선언 1개와
한정 타입 참조 4개를 보존하는 변경 제안을 확인했다.
두 관찰 모두 프로그램을 실행하거나 모델을 평가하지 않았으며 원본 파일을 유지했다.
레코드 소스에서는 패키지 실행과 포맷 경로의 필드 지원 차이도 찾았다.
같은 명시적 V4 프로필을 포맷 경로에 연결한 뒤, 별도 소스에서 필드 3/3개와
필드의 ID·이름·타입 표기·필수 여부·개수·순서를 보존했다.
이 소스의 import 1개, 계산 본문 2개와 bind 1개도 남았고 원본 변경과 실행·모델 예측은 0이다.
이렇게 비교에서 가져온 원리를 작은 Gooo 작업의 표현과 편집 문제에 적용한다.

이 모듈 해석과 포맷 변경은 [PR #1517](https://github.com/kimjooyoon/meta-ontology-go/pull/1517)의
원래 CI 23개와 해당 소스의 증거를 확인한 뒤 개발 브랜치에 병합됐다.
위 소스 관찰은 각각 수행 당시의 생산자에 연결해 보존한다.
필드 타입의 한정 참조와 실제 에디터의 파일 간 탐색은 후속 작업이다.

## 먼저 보완할 약점

- **모듈 사용성:** 초기 예제에서 타입 서명의 `rules.Integer`가 거절되는 문제를 확인했다.
  개발 브랜치의 [파일별 import 타입](qualified-activity-types.ko.md)은 별칭과 entity ID를 해석한다.
  같은 별칭이 두 파일에서 서로 다른 타입 ID를 고르는 새 소스 예제를 준비했다.
  필드 타입의 한정 표기와 에디터의 모듈 탐색은 후속 과제다.
- **변경 범위:** 단일 파일 rename과 entry 호출 집합만으로 전체 워크스페이스의
  소비자 참조가 갱신됐다고 판단할 수 없다. 참조 범위와 미해결 부분을 드러낸다.
- **결정 모델 입력:** [SDK #79](https://github.com/kimjooyoon/gooo-decision-runtime/pull/79)는
  원래 입력과 후보 결과를 구분한 소스 전용 패킷을 구현하고 기존 CI 두 실행을 통과해 병합됐다.
  저장한 조건식 예제의 14개 노드를 1,838바이트의 canonical 패킷으로 준비했다.
  수치 특징 규약은 [SDK 0.2.50-experimental](https://github.com/kimjooyoon/gooo-decision-runtime/releases/tag/v0.2.50-experimental)로
  공개했다. 별도 새 소스의 조건식 17개 노드와 1개 선택지를 원래 입력·후보 결과 역할을
  구분한 특징으로 준비했다. 이 준비 과정의 모델 예측·조건 실행은 각각 0회이며,
  평가 정답은 입력에서 제외한다.
  [SDK #83](https://github.com/kimjooyoon/gooo-decision-runtime/pull/83)은
  이 특징을 읽는 18,626개 파라미터의 소형 수치 결정 런타임이다.
  새 API 테스트 5개는 합성 파라미터로 수치 예측 7회를 확인했다.
  자신의 CI 두 실행과 산출물 확인을 거쳐
  [SDK 0.2.51-experimental](https://github.com/kimjooyoon/gooo-decision-runtime/releases/tag/v0.2.51-experimental)로 공개됐다.
  [컴파일러 연결 개발본](scalar-source-model.ko.md)은 같은 수치 입력으로 허용된 조합을
  정렬하고, 기존 구성 흐름이 실제 Gooo 조건식을 평가한다. 새 API 검사 5개와 별도 CLI 관찰에서 합성 가중치
  예측 8회를 확인했다. 첫 소스의 선택 조건 2/2와 별도 조건 1/1, 병렬 소스 네 개의
  요청별 선택 조건 2/2와 별도 조건 1/1은 각각 기록한다. 모델을 연결하지 않은 별도
  소스는 조건 2/2를 확인했다. 이 수치를 학습 모델의 정답률로 해석하지 않는다.
  실제 학습 가중치와 소스 계열을 분리한 평가가 후속 과제다.
- **관계 데이터 연동:** 표준 형식으로 내보낼 때 보존되는 ID·관계·출처와 손실되는 요소를
  명시한다. 먼저 하나의 작은 업무 흐름에서 필요한 교환 범위를 정한다.

Scallop의 확률 태그 전파, Gooo의 PROV 이력, 후보 모델 점수는 의미가 서로 다르다.
또한 Nemo에서 사실이 없는 상태와 Gooo에서 아직 실행을 관찰하지 않은 상태도 각각 해석한다.
이 경계를 유지해야 비교 자료가 구현 방향을 제대로 안내할 수 있다.

## 강점 후보와 보완 순서

| 관점 | Gooo에서 현재 확인한 요소 | 남은 약점과 다음 작업 |
| --- | --- | --- |
| 의도를 계산으로 옮기기 | 소스가 허용한 경로와 고정 조건을 함께 선언하고 유한 후보를 구성한다. | 지원 타입과 선택 형태가 제한돼 있다. 실제 업무 프로그램에서 표현되는 요구와 외부 코드가 필요한 요구를 센다. |
| 변경 추적 | 활동 ID를 유지한 단일 파일 rename과 조건 의존 경로가 개발 브랜치에 들어갔다. | 파일 간 rename·참조 탐색이 남아 있다. 대상 참조와 갱신된 참조를 구분한다. |
| 모듈과 편집 | 한정 타입 참조 4/4개와 별도 포맷의 필드 3/3개를 소스 관찰로 확인하고 #1517을 개발 브랜치에 병합했다. | 필드 타입의 한정 참조와 실제 에디터 사용을 이어서 확인한다. |
| 모델 선택 설명 | 소스 전용 수치 입력과 작은 런타임을 구현하고 후보 점수와 조건 결과를 구분한다. | 실제 Gooo 조건 평가에 모델 순위를 연결한 개발본을 준비했다. 학습된 가중치와 소스 계열을 분리한 평가가 남아 있다. 첫 선택과 탐색 후 선택의 결과를 각각 센다. |
| 관계 데이터 교환 | stable ID, 소스 관계와 PROV 기록을 사용하는 흐름이 있다. | TypeQL·Nemo와 같은 과제를 실행한 자료와 표준 형식의 손실 내역이 부족하다. 작은 교환 예제 하나부터 작성한다. |

이 표의 강점 후보는 현재 구현의 성격을 가리킨다. 다른 언어보다 낫다는 판단은
공통 과제에서 같은 기준으로 얻은 관찰이 쌓인 뒤에 할 수 있다.

## 같은 과제로 확인할 항목

요금 조건, 승인 이유, import 활동 rename, 규칙 변경의 영향, 모델 후보 선택,
저장한 결과의 재사용을 공통 과제로 둔다. 과제마다 다음을 남긴다.

- 선언할 수 있는 요구 수 / 시도한 요구 수, 필요한 외부 언어 코드와 설정 단계
- 유지한 ID, 갱신한 해석된 참조 수 / 대상 참조 수, 무관한 소스의 변경 여부
- 선택용 입력과 별도 평가 입력 각각의 실제 일치 수 / 실행한 입력 수
- 미해결·미관찰 항목과 그 이유

속도와 메모리를 비교한다면 언어 버전, 입력, 기기, 초기화와 실행 범위를 맞춘다.
아직 측정하지 않은 항목은 미관찰로 남기고, 언어 전체의 완전성 백분율로 합치지 않는다.

## 연결 개발본의 한계

연결의 대상은 Integer 입력 한 개와 Integer 결과, 이진 선택지 1~6개, 고정 Boolean
조건식 1~8개다. 관계 질의·재귀 규칙·온톨로지 교환은 별도 소스 과제로 범위를 정하고
구현해야 한다. TypeQL의 함수, Nemo의 규칙과 같은 과제를 적을 때 필요한 외부
코드와 미표현 요구를 먼저 기록한다. Gooo의 모델 점수는 시도 순서를 정하며,
조건식의 실제 결과와 Scallop의 provenance 태그 전파는 각자의 의미를 가진다.

모델 제안이 틀리는 새 두 예제에서는 첫 후보의 점수가 약 95.3%여도 조건은
0/2였다. 예산 2는 다음 허용 후보의 조건 2/2와 별도 조건 1/1을 확인했고,
예산 1은 조건 0/2와 별도 조건 0/1을 불완전 상태로 남겼다. 이렇게 점수와
실제 조건 결과를 함께 읽는 것이 현재 Gooo 비교의 한 가지 소스 과제다.

## 복합 선택에서 확인한 비교 과제

Scallop의 태그 전파를 읽으면서 Gooo에서도 여러 선택의 점수를 하나의 조합으로
읽어야 하는지 검토했다. 현재 소형 런타임은 허용된 전체 조합을 정렬하고,
각 후보의 Gooo 조건 결과를 따로 남긴다. Gooo의 후보 점수와 Scallop의
provenance semiring은 각각의 의미와 계산 규칙으로 해석한다.

새 [복합 선택 소스](../examples/scalar-source-model-multichoice/README.md)는
할당 대상과 실행 순서 두 선택으로 네 조합을 만든다. 모델 예측 1회에서 첫 제안은
조건 0/2였고, 두 번째 조합은 조건 2/2와 별도 입력 조건 1/1을 만족했다.
소스의 선언 순서, 활동 ID와 각 후보의 실제 결과도 확인했다.
가중치는 합성이며, 경쟁 언어 실행과 학습 모델 평가는 수행하지 않았다.

같은 방향의 [요금 분기 과제](../examples/scalar-source-model-fee-shared-inputs/README.md)는
음수 입력 0, 두 배 계산과 상한 90을 고정 조건식 두 개로 표현한다.
첫 제안의 조건 4/8 뒤에 선택 조건 8/8과 별도 입력 조건 8/8을 확인했다.
이 과제의 입력은 조건식들이 공유한다. 조건마다 입력을 반복한 앞선 별도 소스는
중복 오류로 멈췄으며, 안내에 이 규칙을 추가했다. 요구를 적는 방식의 작은 혼동도
사용성 보완 항목으로 기록한다.

별도 [호출 예제](../examples/scalar-source-model-native/README.md)는 모델이 고른 `Fee`
본문을 `Main`에서 호출해 실제 생성 프로그램으로 실행했다. 구성 예측 1회와
선택 조건 2/2·별도 조건 3/3 뒤에 네이티브 호출자 기대값 3/3을 확인했다.
실행 단계의 추가 예측은 0회였고, 기존 실행기의 두 프로세스 출력도 일치했다.
이로써 모델 제안부터 Gooo 조건 평가와 프로그램 실행까지 이어지는 작은 범위를
확인했다. 다른 언어와 같은 과제를 실행한 비교와 학습된 모델 품질은 이어서 관찰한다.

이 결과에서 이어갈 작업은 세 가지다.

1. **TypeQL에서 참고한 계산 방향:** 원래 입력·후보 결과·보조 활동을 같은 작은
   업무 조건으로 표현하고, 사용자가 별도 코드를 써야 하는 요구를 센다.
2. **Nemo에서 참고한 규칙의 재사용:** 기존 조건식 호출 그래프가 다루는 관계와
   여러 사실을 질의하는 관계를 나눠 작은 과제를 작성한다. 현재의 유한 함수 평가에서
   재귀 관계 질의는 별도 표현·실행 범위를 설계하고 관찰한다.
3. **OML에서 참고한 모듈 경계:** 한정 활동 서명 다음으로 필드 타입과 파일 간
   리팩토링에 같은 ID·별칭 규칙을 적용한다. 전체 대상 참조와 실제 갱신 참조를 기록한다.

모델 연결 초안 [#1518](https://github.com/kimjooyoon/meta-ontology-go/pull/1518)의
과거 작업 진척 조회에서는 GitHub 서버 오류로 한 항목이 미관찰 상태가 됐다.
원래 실패 기록은 유지하고, 추가 소스 관찰과 문서 수정은 별도 변경으로 제출한다.
공개된 변경, CI가 확인한 변경, 개발 브랜치에 병합된 변경을 구분해 기록한다.
