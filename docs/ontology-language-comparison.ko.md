# 관련 언어에서 배우는 Gooo의 다음 과제

2026-10-13 기준으로 공식 문서와 Gooo 소스를 함께 살펴본 기록이다.
공통 프로그램의 실행 속도나 정답률을 비교한 결과는 아직 없다.
여기서는 언어가 문제를 표현하는 방식과 Gooo에서 실제로 발견한 빈틈을 연결한다.

## 비교할 언어

| 언어 | 참고할 표현 방식 | Gooo에서 이어갈 작업 |
| --- | --- | --- |
| TypeQL / TypeDB 3 | 데이터 모델과 추론 함수를 구분하고, 인자와 반환값으로 계산 방향을 드러낸다. | 조건식의 원래 입력과 후보 결과를 구분하고, 보조 활동을 호출하는 방향을 설명한다. |
| Nemo | 사실과 규칙으로 관계를 선언한다. 재귀 관계, Unicode와 IRI 이름, 여러 데이터 형식을 다룬다. | 기존 활동 ID와 조건식의 호출 관계를 읽어 변경의 영향을 보여준다. |
| Mangle | Go에 내장할 수 있는 Datalog 확장으로 도메인 관계와 결과의 근거를 표현한다. | Gooo 결과에 실제 조건 값·활동 ID·투영의 위치를 붙이는 개발본을 구현했다. 원래 Gooo 위치와 조건 필드 ID를 직접 연결하는 범위가 남아 있다. |
| Scallop | 사실에 붙은 태그를 provenance semiring으로 전파한다. 확률적 추론도 이 구조에 포함된다. | 후보 점수, 허용된 선택지, 조건식, 실제 실패 사례를 함께 읽을 수 있게 한다. |
| OML / openCAESAR | 모듈의 namespace, import, 멤버 IRI로 참조 범위를 정한다. | import 별칭과 활동 ID를 따라 파일 사이의 참조를 해석하고 리팩토링 범위를 정한다. |
| egglog | 선언한 동치 규칙으로 여러 표현을 같은 것으로 묶고, 그 집합에서 표현을 추출한다. | 코드 조립에서 선언된 동치와 유한 사례의 일치를 구분한다. 도입 전 검토 대상이다. |

근거: [TypeQL 함수와 규칙](https://typedb.com/docs/typeql-reference/functions/functions-vs-rules/),
[Nemo 언어 안내](https://knowsys.github.io/nemo-doc/intro/tour/),
[Mangle 공식 설명](https://github.com/google/mangle),
[Scallop provenance](https://www.scallop-lang.org/doc/probabilistic/provenance.html),
[OML 명세](https://opencaesar.io/oml/),
[egglog equality saturation 안내](https://egraphs-good.github.io/egglog-tutorial/01-basics.html).
TypeQL과 Nemo는 현재 개발 비교 대상으로, Scallop과 OML은 관련 원리를 읽는 대상으로 두었다.
최근 커밋이나 별 개수만으로 성장 가능성과 사용성을 판단하지 않는다.
TypeQL은 데이터베이스 질의, Nemo·Scallop은 관계·논리 추론, OML은 모델링,
egglog는 동치 기반 변환에 초점이 있다. 각 언어와 Gooo의 겹치는 과제를 골라 비교한다.

### 최근 변경에서 고른 두 가지

[TypeDB 3.13.6](https://github.com/typedb/typedb/releases/tag/3.13.6)은
2026-09-22에 공개됐고, 내장 함수를 `std::math::round`처럼 한정한 이름으로
호출하는 방식을 추가했다. Gooo에서도 파일별 import 범위를 타입과 호출에
일관되게 적용해야 사용자가 이름 충돌을 추측하지 않아도 된다.

[Nemo 0.10.1](https://github.com/knowsys/nemo/releases/tag/v0.10.1)은
2026-08-01에 공개됐다. 규칙의 projection을 import 쪽으로 옮길 때 조건 필터가
무시되던 문제를 수정했고, 유도한 사실 전체의 trace를 출력하는 옵션도 추가했다.
여기서 Gooo에 적용할 과제는 변환 전후의 조건을 보존하고, 결과가 따라온 소스 경로를
읽을 수 있게 하는 것이다. 소스 carrier 보존과 실제 실행 결과의 일치는 각각 확인한다.
두 변경에서 이름의 소유권과 변환 후 조건 보존을 이번 작업의 기준으로 삼았다.

## Gooo에서 이미 이어지는 흐름

Gooo 소스는 만들 수 있는 선택지와 지켜야 하는 조건을 선언한다.
구성 과정은 그 범위에서 후보를 만들고, 관찰 기록은 어느 소스와 선택으로 나온 결과인지 남긴다.
지원하는 프로필에서는 소형 결정 모델이 선택지를 고를 수 있고, 결정론적 선택 경로도 유지한다.

이 흐름을 도면과 작업 기록에 비유할 수 있다. 활동의 이름은 도면의 표지이고,
활동 ID는 같은 부품을 계속 가리키는 번호다. 조건식은 맞춰야 하는 치수이며,
관찰은 실제로 조립한 결과다. 표지를 바꿨다고 부품 번호까지 바뀌면 변경 이력을 따라가기 어렵다.

현재 구현의 비교할 만한 지점은 소스의 선택, 조건, 활동 ID와 관찰을 연결하는 방식이다.
이 방식이 다른 언어보다 유리한지는 같은 작업을 수행한 자료가 더 필요하다.
새 Integer 조건식 그래프를 읽는 작은 결정 모델과 컴파일러 연결을 개발하고 있다.
표현을 내보내는 기능과 모델이 이를 읽고 판단하는 기능의 진행 상태는 각각 기록한다.

## 이번 비교에서 이어진 개발

1. 활동 이름을 바꿀 때 같은 파일의 호출과 조건 참조를 함께 바꾸고 ID를 유지한다.
   소스 변경 제안과 원본·결과 해시를 남기는 기능은
   [PR #1511](https://github.com/kimjooyoon/meta-ontology-go/pull/1511)에서 CI 34개를 통과해
   개발 브랜치에 병합됐다.
2. [호출 위치 리팩토링 PR #1512](https://github.com/kimjooyoon/meta-ontology-go/pull/1512)는
   escaped 문자열과 한국어 이름의 소스 위치를 다룬다. 새 예제에서는 호출 두 개와 선언을
   세 편집으로 갱신하고 원본을 유지했다. 원래 CI의 의미 검사와 저장소 투영 검사에서
   같은 보조 함수 추출 문제가 발견돼 병합하지 않았다. 호출 수 계산을 작은 함수로
   분리한 수정안을 [PR #1513](https://github.com/kimjooyoon/meta-ontology-go/pull/1513)으로
   제출했고, 원래 PR은 병합하지 않고 닫았다. 새 PR은 자신의 CI 27개와
   해당 소스의 증거를 확인한 뒤 개발 브랜치에 병합됐다.
   파일 간 rename과 에디터의 실제 동작 관찰은 후속 과제다.
3. [조건식 의존 관계](source-criteria-dependencies.md)는 이미 준비한 호출 정보를 읽어
   후보 소유 활동 → 고정 조건식 → 보조 활동의 경로를 보여준다.
   예제의 세 연결과 두 보조 활동은 소스 분석으로 확인했다.
   [PR #1514](https://github.com/kimjooyoon/meta-ontology-go/pull/1514)는
   자신의 CI 27개를 통과해 개발 브랜치에 병합됐다.
4. 별도 워크스페이스 구현에서는 명시한 활동 ID가 호출 보고서에서 이름 기반 ID로
   다시 계산되는 문제를 찾았다. 원본과 내부 변환 후의 보고서가 선언 ID를 유지하도록 수정하고,
   실행 전 호출 관계를 읽는 `package inspect`를
   [PR #1515](https://github.com/kimjooyoon/meta-ontology-go/pull/1515)로 공개했다.
   자신의 CI 27개 중 두 실행에서 도움말 표의 분리 한계를 발견해 병합 없이 닫았다.
   도움말 내용은 그대로 두고 표를 작은 선언으로 나눈
   [수정안 #1516](https://github.com/kimjooyoon/meta-ontology-go/pull/1516)은
   자신의 CI 27개와 소스에 연결된 산출물을 확인한 뒤 개발 브랜치에 병합됐다.

2026-10-13 작성 시점에 호출 위치 변경과 의존 관계는 개발 브랜치에 병합됐으며,
워크스페이스 수정안 #1516도 개발 브랜치에 병합됐다.
개발 브랜치에 병합된 기능과 설치 가능한 릴리스의 범위도 따로 확인한다.
예제의 소스 분석은 프로그램 실행과 모델 예측을 수행하지 않았다.
각 변경은 자신의 CI 결과와 소스에 연결된 증거를 확인한 뒤 공개 흐름에 반영한다.

## 비교 원리를 소스 사용성으로 옮기는 예

OML에서 참고한 점은 멤버 이름을 어떤 모듈에서 읽는지 명시하는 방식이다.
Gooo의 후속 개발본은 같은 `Amount` 이름을 서로 다른 패키지가 써도
`청구.Amount`의 파일별 import와 entity ID로 구분하도록 구성했다.
새 소스 준비 결과에서 입력·결과 참조 네 개가 의도한 ID 네 개와 일치했다.

또한 참조를 잘 읽어도 편집 결과에서 import나 본문이 없어지면 작업을 이어갈 수 없다.
새 포맷 예제에서 기존 경로가 이 요소를 빠뜨리는 문제를 관찰했고,
전체 소스 carrier를 비교하는 후속 수정안을 준비했다.
별도 예제에서는 import 1개, 계산 본문 4개, bind 1개, 조립 선언 1개와
한정 타입 참조 4개를 보존하는 변경 제안을 확인했다.
두 관찰 모두 프로그램을 실행하거나 모델을 평가하지 않았으며 원본 파일을 유지했다.
레코드 소스에서는 패키지 실행과 포맷 경로의 필드 지원 차이도 찾았다.
같은 명시적 V4 프로필을 포맷 경로에 연결한 뒤, 별도 소스에서 필드 3/3개와
필드의 ID·이름·타입 표기·필수 여부·개수·순서를 보존했다.
이 소스의 import 1개, 계산 본문 2개와 bind 1개도 남았고 원본 변경과 실행·모델 예측은 0이다.
이렇게 비교에서 가져온 원리를 작은 Gooo 작업의 표현과 편집 문제에 적용한다.

이 모듈 해석과 포맷 변경은 [PR #1517](https://github.com/kimjooyoon/meta-ontology-go/pull/1517)의
원래 CI 23개와 해당 소스의 증거를 확인한 뒤 개발 브랜치에 병합됐다.
위 소스 관찰은 각각 수행 당시의 생산자에 연결해 보존한다.
이후 [한정 필드 타입](language/package-qualified-field-types.ko.md)과
[한정 레코드 생성자](language/package-qualified-record-constructors.ko.md)를 개발 브랜치에 반영했다.
실제 에디터의 파일 간 탐색은 후속 작업이다.

## 먼저 보완할 약점

- **모듈 사용성:** 초기 예제에서 타입 서명의 `rules.Integer`가 거절되는 문제를 확인했다.
  개발 브랜치의 [파일별 import 타입](qualified-activity-types.ko.md)은 별칭과 entity ID를 해석한다.
  한정 필드 타입과 한정 레코드 생성자도 개발 브랜치에 반영했다.
  같은 별칭이 두 파일에서 서로 다른 타입 ID를 고르는 예제와 실제 생성 실행을 기록했다.
  중첩 레코드와 에디터의 모듈 탐색은 후속 과제다.
- **변경 범위:** 단일 파일 rename과 entry 호출 집합만으로 전체 워크스페이스의
  소비자 참조가 갱신됐다고 판단할 수 없다. 참조 범위와 미해결 부분을 드러낸다.
- **결정 모델 입력:** [SDK #79](https://github.com/kimjooyoon/gooo-decision-runtime/pull/79)는
  원래 입력과 후보 결과를 구분한 소스 전용 패킷을 구현하고 기존 CI 두 실행을 통과해 병합됐다.
  저장한 조건식 예제의 14개 노드를 1,838바이트의 canonical 패킷으로 준비했다.
  수치 특징 규약은 [SDK 0.2.50-experimental](https://github.com/kimjooyoon/gooo-decision-runtime/releases/tag/v0.2.50-experimental)로
  공개했다. 별도 새 소스의 조건식 17개 노드와 1개 선택지를 원래 입력·후보 결과 역할을
  구분한 특징으로 준비했다. 이 준비 과정의 모델 예측·조건 실행은 각각 0회이며,
  평가 정답은 입력에서 제외한다.
  [SDK #83](https://github.com/kimjooyoon/gooo-decision-runtime/pull/83)은
  이 특징을 읽는 18,626개 파라미터의 소형 수치 결정 런타임이다.
  새 API 테스트 5개는 합성 파라미터로 수치 예측 7회를 확인했다.
  자신의 CI 두 실행과 산출물 확인을 거쳐
  [SDK 0.2.51-experimental](https://github.com/kimjooyoon/gooo-decision-runtime/releases/tag/v0.2.51-experimental)로 공개됐다.
  [컴파일러 연결 개발본](scalar-source-model.ko.md)은 같은 수치 입력으로 허용된 조합을
  정렬하고, 기존 구성 흐름이 실제 Gooo 조건식을 평가한다. 새 API 검사 5개와 별도 CLI 관찰에서 합성 가중치
  예측 8회를 확인했다. 첫 소스의 선택 조건 2/2와 별도 조건 1/1, 병렬 소스 네 개의
  요청별 선택 조건 2/2와 별도 조건 1/1은 각각 기록한다. 모델을 연결하지 않은 별도
  소스는 조건 2/2를 확인했다. 이 수치를 학습 모델의 정답률로 해석하지 않는다.
  실제 학습 가중치와 소스 계열을 분리한 평가가 후속 과제다.
- **관계 데이터 연동:** 표준 형식으로 내보낼 때 보존되는 ID·관계·출처와 손실되는 요소를
  명시한다. 먼저 하나의 작은 업무 흐름에서 필요한 교환 범위를 정한다.

Scallop의 확률 태그 전파, Gooo의 PROV 이력, 후보 모델 점수는 의미가 서로 다르다.
또한 Nemo에서 사실이 없는 상태와 Gooo에서 아직 실행을 관찰하지 않은 상태도 각각 해석한다.
이 경계를 유지해야 비교 자료가 구현 방향을 제대로 안내할 수 있다.

| 의도를 계산으로 옮기기 | 소스가 허용한 경로와 고정 조건을 함께 선언하고 유한 후보를 구성한다. | 지원 타입과 선택 형태가 제한돼 있다. 실제 업무 프로그램에서 표현되는 요구와 외부 코드가 필요한 요구를 센다. |
| 변경 추적 | 활동 ID를 유지한 단일 파일 rename과 조건 의존 경로가 개발 브랜치에 들어갔다. | 파일 간 rename·참조 탐색이 남아 있다. 대상 참조와 갱신된 참조를 구분한다. |
| 모듈과 편집 | 파일별 한정 타입·필드 타입·레코드 생성자를 선언 ID에 연결하고 새 네이티브 사례를 기록했다. | 중첩 레코드와 실제 에디터의 모듈 탐색·편집을 이어서 확인한다. |
| 실행 설명 | 개발본은 실제 `if`의 참·거짓과 활동 ID, 순수 투영의 위치, 레코드 입출력을 함께 기록한다. | 원래 Gooo 본문 위치와 조건의 필드 ID를 직접 연결하고, 설명 기록을 언어의 판단 입력으로 읽는 기능이 남아 있다. |
| 모델 선택 설명 | 소스 전용 수치 입력과 작은 런타임을 구현하고 후보 점수와 조건 결과를 구분한다. | 실제 Gooo 조건 평가에 모델 순위를 연결한 개발본을 준비했다. 학습된 가중치와 소스 계열을 분리한 평가가 남아 있다. 첫 선택과 탐색 후 선택의 결과를 각각 센다. |
| 관계 데이터 교환 | stable ID, 소스 관계와 PROV 기록을 사용하는 흐름이 있다. | TypeQL·Nemo와 같은 과제를 실행한 자료와 표준 형식의 손실 내역이 부족하다. 작은 교환 예제 하나부터 작성한다. |

이 표의 강점 후보는 현재 구현의 성격을 가리킨다. 다른 언어보다 낫다는 판단은
공통 과제에서 같은 기준으로 얻은 관찰이 쌓인 뒤에 할 수 있다.

## 같은 과제로 확인할 항목

요금 조건, 승인 이유, import 활동 rename, 규칙 변경의 영향, 모델 후보 선택,
저장한 결과의 재사용을 공통 과제로 둔다. 과제마다 다음을 남긴다.

- 선언할 수 있는 요구 수 / 시도한 요구 수, 필요한 외부 언어 코드와 설정 단계
- 유지한 ID, 갱신한 해석된 참조 수 / 대상 참조 수, 무관한 소스의 변경 여부
- 선택용 입력과 별도 평가 입력 각각의 실제 일치 수 / 실행한 입력 수
- 미해결·미관찰 항목과 그 이유

속도와 메모리를 비교한다면 언어 버전, 입력, 기기, 초기화와 실행 범위를 맞춘다.
아직 측정하지 않은 항목은 미관찰로 남기고, 언어 전체의 완전성 백분율로 합치지 않는다.

## 연결 개발본의 한계

연결의 대상은 Integer 입력 한 개와 Integer 결과, 이진 선택지 1~6개, 고정 Boolean
조건식 1~8개다. 관계 질의·재귀 규칙·온톨로지 교환은 별도 소스 과제로 범위를 정하고
구현해야 한다. TypeQL의 함수, Nemo의 규칙과 같은 과제를 적을 때 필요한 외부
코드와 미표현 요구를 먼저 기록한다. Gooo의 모델 점수는 시도 순서를 정하며,
조건식의 실제 결과와 Scallop의 provenance 태그 전파는 각자의 의미를 가진다.

모델 제안이 틀리는 새 두 예제에서는 첫 후보의 점수가 약 95.3%여도 조건은
0/2였다. 예산 2는 다음 허용 후보의 조건 2/2와 별도 조건 1/1을 확인했고,
예산 1은 조건 0/2와 별도 조건 0/1을 불완전 상태로 남겼다. 이렇게 점수와
실제 조건 결과를 함께 읽는 것이 현재 Gooo 비교의 한 가지 소스 과제다.

## 복합 선택에서 확인한 비교 과제

Scallop의 태그 전파를 읽으면서 Gooo에서도 여러 선택의 점수를 하나의 조합으로
읽어야 하는지 검토했다. 현재 소형 런타임은 허용된 전체 조합을 정렬하고,
각 후보의 Gooo 조건 결과를 따로 남긴다. Gooo의 후보 점수와 Scallop의
provenance semiring은 각각의 의미와 계산 규칙으로 해석한다.

새 [복합 선택 소스](../examples/scalar-source-model-multichoice/README.md)는
할당 대상과 실행 순서 두 선택으로 네 조합을 만든다. 모델 예측 1회에서 첫 제안은
조건 0/2였고, 두 번째 조합은 조건 2/2와 별도 입력 조건 1/1을 만족했다.
소스의 선언 순서, 활동 ID와 각 후보의 실제 결과도 확인했다.
가중치는 합성이며, 경쟁 언어 실행과 학습 모델 평가는 수행하지 않았다.

같은 방향의 [요금 분기 과제](../examples/scalar-source-model-fee-shared-inputs/README.md)는
음수 입력 0, 두 배 계산과 상한 90을 고정 조건식 두 개로 표현한다.
첫 제안의 조건 4/8 뒤에 선택 조건 8/8과 별도 입력 조건 8/8을 확인했다.
이 과제의 입력은 조건식들이 공유한다. 조건마다 입력을 반복한 앞선 별도 소스는
중복 오류로 멈췄으며, 안내에 이 규칙을 추가했다. 요구를 적는 방식의 작은 혼동도
사용성 보완 항목으로 기록한다.

별도 [호출 예제](../examples/scalar-source-model-native/README.md)는 모델이 고른 `Fee`
본문을 `Main`에서 호출해 실제 생성 프로그램으로 실행했다. 구성 예측 1회와
선택 조건 2/2·별도 조건 3/3 뒤에 네이티브 호출자 기대값 3/3을 확인했다.
실행 단계의 추가 예측은 0회였고, 기존 실행기의 두 프로세스 출력도 일치했다.
이로써 모델 제안부터 Gooo 조건 평가와 프로그램 실행까지 이어지는 작은 범위를
확인했다. 다른 언어와 같은 과제를 실행한 비교와 학습된 모델 품질은 이어서 관찰한다.

이 결과에서 이어갈 작업은 세 가지다.

1. **TypeQL에서 참고한 계산 방향:** 원래 입력·후보 결과·보조 활동을 같은 작은
   업무 조건으로 표현하고, 사용자가 별도 코드를 써야 하는 요구를 센다.
2. **Nemo에서 참고한 규칙의 재사용:** 기존 조건식 호출 그래프가 다루는 관계와
   여러 사실을 질의하는 관계를 나눠 작은 과제를 작성한다. 현재의 유한 함수 평가에서
   재귀 관계 질의는 별도 표현·실행 범위를 설계하고 관찰한다.
3. **OML에서 참고한 모듈 경계:** 한정 활동 서명·필드 타입·레코드 생성자에
   같은 ID·별칭 규칙을 적용했다. 파일 간 리팩토링의 대상 참조와 실제 갱신 참조를 기록한다.

## 결과의 이유에서 실제 실행 조건까지

[새 조건 경로 예제](../examples/native-condition-evidence/README.md)는
소스가 선택한 승인 레코드와 실제 `if` 평가를 같은 활동 ID에 연결한다.
CLI의 여섯 입력에서 기대값 12/12, 조건 평가 10건, 두 위치의 참·거짓 4/4 쌍을 관측했다.
별도 중첩 호출 소스의 기대값은 4/5였고 산술 실패 1건도 남겼다.
각 분모를 유지하며, 이 관찰을 언어 전체의 완전성이나 다른 엔진보다 높은 성능으로 환산하지 않는다.

이 기능은 Mangle의 근거 연결을 읽고 고른 작은 공통 과제에서 이어졌다.
현재 위치는 순수 Go 투영을 가리킨다. 원래 Gooo 본문과 조건 필드의 ID까지 연결하는
[다음 범위](language/native-condition-evidence.ko.md)를 명시했다.

첫 공개 구현의 원래 CI에서 반복문 설명이 결과 통신 한도를 넘는 문제를 찾았다.
[수정한 새 관찰](../examples/native-condition-transport/README.md)은 결과와 설명 파일을 분리한다.
새 반복 소스의 기대값 80/80과 기록 65,536건·누락 16,108건 `PARTIAL`을 각각 보여 준다.
설명의 한도가 실행 결과를 막지 않도록 고치고, 기록되지 않은 근거도 수로 드러낸다.

모델 연결 초안 [#1518](https://github.com/kimjooyoon/meta-ontology-go/pull/1518)의
과거 작업 진척 조회에서는 GitHub 서버 오류로 한 항목이 미관찰 상태가 됐다.
원래 실패 기록은 유지하고, 추가 소스 관찰과 문서 수정은 별도 변경으로 제출한다.
공개된 변경, CI가 확인한 변경, 개발 브랜치에 병합된 변경을 구분해 기록한다.

## 모듈 원리에서 이어진 워크스페이스 리팩토링

OML의 import 범위를 읽고 전체 워크스페이스의 이름 변경에서 확인할 기준으로 삼았다.
새 CLI 소스에서 entry 밖 소비자를 포함한 대상 참조 5/5개를 갱신하고,
같은 이름의 다른 패키지와 다른 import를 쓰는 파일의 내용을 유지했다.
이름에서 ID를 얻던 별도 entry 소스에서는 기존 ID를 선언에 기록하고 entry와
소비자 참조 1/1개를 함께 갱신했다. 전체 PROV 그래프와 외부 API 소비자는 별도 범위다.

또한 Gooo의 고정 조건식과 추가 질문의 기준 활동 사이에 한정 이름 지원 차이를 찾았다.
`observe oracle`도 한 파일의 import 별칭을 해석하도록 보완한 새 과제에서는
기준 활동 ID와 참조 1/1개를 유지했다. 추가 질문 1회가 유한 후보를 구분했고,
순위 기록 2개와 기준 활동 평가 2회를 남겼다. 선택 후 별도 입력의 일치는 1/1이었다.
이 수치는 서로 다른 역할의 분모를 유지한다. 모델 예측과 네이티브 실행은 0회다.

[워크스페이스 리팩토링 안내](language/workspace-activity-refactoring.ko.md)는
이 변경 제안의 범위와 각 관찰의 생산자를 설명한다. 다른 언어의 rename을 실행한
비교 자료는 아직 없다. 이번 결과는 같은 업무 과제로 비교할 Gooo 쪽의 작은 사용성 개선이다.

## 후보 본문까지 이어가는 모듈 리팩토링

[워크스페이스 리팩토링 #1520](https://github.com/kimjooyoon/meta-ontology-go/pull/1520)은
모든 공급 소스의 참조를 패키지와 활동 ID로 따라가는 공개 변경이다.
모델 경로 연결 [#1519](https://github.com/kimjooyoon/meta-ontology-go/pull/1519)은
자체 CI 33개의 성공과 원래 소스 검증 후 개발 브랜치에 병합됐다.

OML의 파일별 import 범위를 참고한 후속 과제는 `source_fill` 후보의 호출이었다.
표현만 분리하면 지역 변수와 import 별칭을 구분하기 어려워, 직접 선언한 후보를
실제 빈자리에 넣은 본문에서 해석하고 원래 소스 위치와 연결했다.
새 후보 3개·hole 2개의 소스에서 참조 6/6개를 갱신하는 제안을 확인했다.
별도 소스에서는 같은 범위의 지역 변수가 별칭을 가려 변경 제안 없이 오류를 반환했다.
모델 예측·후보 점수 계산·프로그램 실행은 각각 0회이며,
[구체적인 지원 범위](language/workspace-source-fill-refactoring.ko.md)를 따로 기록한다.

현재의 강점 후보는 소스가 허용한 여러 경로를 같은 활동 ID로 추적하며 편집할 수 있는 점이다.
보완할 부분은 자동 파생 경로의 위치 정보, 한정 필드 타입, 관계 질의와 편집 적용이다.
TypeQL·Nemo의 관계 계산과 같은 업무 과제를 실행한 비교는 아직 없다.
이름 변경 참조 수, 후보 일치 수, 학습된 모델 품질을 각각의 분모로 계속 기록한다.

## 파생 경로에서 분모를 나누는 이유

Gooo의 고정 문법에서 값·조건 후보를 파생하면, 활동 호출은 원래 본문과 같은 ID를 가리킨다.
새 per-hole 소스에서 이름을 바꾼 뒤 전용 fill API로 구성해 참조 2/2, 선택 입력 1/1과
별도 입력 1/1을 확인했다. 문법 표현은 13개 중 4개를 유지했고, 유지한 표현의 조합은
4/4개를 구성했다. 조합 완전성과 문법 표현 범위는 다른 분모다.
[구체적인 관찰](language/workspace-derived-fill-refactoring.ko.md)은 원래 생산자와 한계를 함께 기록한다.

이 과제는 Gooo의 경로 구성과 편집을 다룬다. Nemo의 관계 질의나 Scallop의 확률 태그 전파,
TypeQL의 데이터 계산과 공통 실행 성능을 비교한 결과는 아직 없다. 여러 표현을 생성할 수
있는 범위, 실제 선택 결과와 관계 데이터 교환 능력을 각각 확인하는 방향으로 이어간다.

## 비교를 다음 개발로 옮기는 기준

각 언어가 집중하는 문제부터 맞춘다. TypeQL은 데이터와 관계를 질의하는 언어,
Nemo는 사실에서 새 관계를 유도하는 규칙 언어, Scallop은 확률 태그를 포함한 추론 언어,
OML은 온톨로지의 모듈과 개념을 기술하는 언어다. 추가로 살펴본
[egglog](https://github.com/egraphs-good/egglog)는 Datalog와 equality saturation을 결합한다.
Gooo에서는 이들의 원리를 작은 소스 구성·변경 과제로 옮겨 확인한다.

| 비교 관점 | Gooo에서 확인한 강점 후보 | 현재 약점 | 다음 개발의 관찰 기준 |
| --- | --- | --- | --- |
| TypeQL의 계산 방향 | 입력, 후보 결과와 보조 활동을 고정 조건식으로 연결한다. | 관계 데이터의 질의와 재귀 계산을 표현할 실행 범위가 부족하다. | 같은 업무 요구 중 Gooo 선언으로 표현한 수와 별도 구현이 필요한 수를 기록한다. |
| Nemo의 사실·규칙·trace | 기존 활동과 조건식의 의존 경로를 실행 전에 읽는다. | 관계 질의와 사실의 유도 과정 전체를 설명하는 기능은 별도 과제다. | 작은 조건 변경에서 직접·간접 영향을 받은 ID와 근거 소스 위치를 각각 기록한다. |
| Scallop의 태그 전파 | 모델 제안의 점수와 실제 조건 결과를 함께 기록한다. | 현재 합성 가중치 관찰은 학습된 모델의 품질을 알려주지 않는다. | 제안 순위, 선택 입력 일치, 별도 입력 일치, 미관찰 조건을 분리한다. |
| OML의 모듈과 IRI | 명시한 활동 ID를 유지하면서 파일 간 표시 이름을 바꾼다. | 중첩 레코드, 외부 소비자, 에디터에서의 편집 적용은 아직 빈틈이다. | 대상 참조 전체 중 수정한 참조, 유지한 ID, 관련 없는 파일의 보존을 센다. |
| egglog의 동치 표현 탐색 | 버전이 정해진 값 문법의 성질을 이용해 파생 경로 안의 원래 참조를 유지한다. | 유한 사례의 일치에서 일반적인 의미 동치를 얻는 기능은 없다. | 문법 범위, 유지한 표현의 조합, 실제 입력 일치와 동치 근거를 각각 기록한다. |

이 표의 다음 기준은 개발 계획이다. 다른 언어를 같은 조건에서 실행한 성능 순위는
아직 없다. 비교 대상을 선택할 때는 현재 읽을 수 있는 명세, 실제 예제와 개발 기록을
우선 보고, 작은 업무 요구를 해결하는 데 필요한 선언과 별도 구현을 함께 읽는다.

### 이름, 동일성, 동치는 서로 다른 역할이다

[OML의 멤버 IRI](https://opencaesar.io/oml/#315-member)는 namespace와 멤버 이름을
이어 구성한다. Gooo의 명시한 활동 ID는 표시 이름과 별도로 선언한다.
현재의 워크스페이스 이름 변경은 이 명시 ID를 유지하고, 이름에서 ID를 얻던 선언은
변경 전 ID를 선언에 기록한다. 이는 Gooo 소스의 식별 방식에서 비교할 만한 차이다.
OML 도구의 실제 rename 동작이나 마이그레이션 지원 여부는 따로 관찰해야 한다.

두 활동이 몇 개 입력에서 같은 값을 냈더라도 두 활동의 ID를 합치지 않는다.
[egglog 튜토리얼](https://egraphs-good.github.io/egglog-tutorial/01-basics.html)은
규칙의 선언, 규칙 실행과 표현 추출을 구분한다.
[관련 연구](https://arxiv.org/abs/2304.04332)는 Datalog와 동치 표현 탐색의 결합을 다룬다.
여기서 Gooo에 적용할 원리는 제안된 표현과 확인된 성질을 구분하는 것이다.
이번 파생 문법의 참조 성질은 활동 호출과 지역 바인딩을 만들지 않는다는 범위이며,
활동 본문의 전체 의미 동치와는 별도 근거다.

### 가까운 개발 순서

1. **진행 중인 리팩토링을 마무리한다.** 직접 선언한 후보의 실제 hole 범위와
   버전이 정해진 파생 문법의 원래 본문 참조를 다룬다. 각각의 소스 관찰과 CI를 기록한다.
2. **모듈 타입의 사용성을 보완한다.** 활동 서명의 한정 타입 다음으로 필드 타입의
   해석과 진단 범위를 검토한다. 현재 V4 필드는 단일 기본형 중심이며, 중첩 레코드와
   여러 값은 새로운 표현·생성·실행 관찰이 필요하다.
3. **같은 작은 업무 과제로 비교한다.** 요금 분기, 승인 이유, import 뒤 이름 변경을
   공통 요구로 삼는다. 지원하지 않는 요구도 그대로 남기고, 환경과 별도 구현량을 기록한다.
4. **자체 결정 모델의 근거를 보강한다.** Gooo가 선언한 선택지와 조건을 학습·판단
   대상으로 유지한다. 후보 순위와 별도 입력 결과를 읽고, 전체 언어의 완성률로 합치지 않는다.

이 순서는 언어의 표현과 실제 사용 범위를 넓히는 개발 계획이다.
현재 단계의 비교에서는 큰 외부 실행기나 모델을 설치하지 않았고,
과거 소스·모델 관찰을 다시 실행하지 않았다.

## 비교에서 이어진 모듈 사용성 개발

OML의 모듈과 로컬 prefix를 살펴본 뒤, Gooo 필드 타입의 파일별 import 해석을
보완했다. 같은 `data.Count`라는 표기도 파일의 제공 패키지에 따라 정수와 불리언으로
다르게 읽힌다. 원래 표기·필드 ID·제공 패키지·기본 타입 ID·소스 범위를 함께 남긴다.
같은 패키지의 별도 파일에 선언한 활동도 원래 `bind` 범위와 활동 ID를 유지하며 연결한다.

[필드 타입 가이드](language/package-qualified-field-types.ko.md)와
[예제 관찰](../examples/package-qualified-field-types/README.md)에 producer와 범위를 적었다.
새 native 관찰은 3개 필드 참조 중 3개 해석, 파일 간 연결 1개 유지, 입력 3개의 활동
출력 6개 중 6개 일치를 보였다. 별도 CLI 소스에서도 참조 3/3와 연결 1개를 읽었다.
모델 호출은 0회이며, 기존 V4의 단일 기본형 범위다. 전체 언어의 완성률이나 다른
언어 대비 성능으로 이 분모를 확대하지 않는다.

별도 한글 field352 프로그램에서도 `자료.값`과 `자료.문장`의 참조 바이트 범위 3/3,
파일 간 연결 1개를 유지했다. 입력 2개의 출력 4/4와 반복 결과가 같았다. 이 관찰은
앞선 field270의 입력·출력 분모와 별도로 기록한다. 이름을 여러 언어로 표현할 때도
ID와 원본 위치를 함께 읽을 수 있도록 만드는 방향이다.

다음 비교 과제는 작은 업무 요구의 표현 범위와 변경 이유의 추적이다. TypeQL의
계산과 데이터 구분, Nemo의 유도 근거, Scallop의 확률 태그, egglog의 확인된 동치
규칙을 각 과제에서 필요한 만큼 검토한다. Gooo 소스가 소유한 의도와 선택지,
실제 관찰 결과가 계속 연결되도록 만드는 것을 기준으로 삼는다.

## 같은 구조의 값에 다른 업무 의미를 붙이는 과제

2026-10-13에 TypeQL의 데이터·계산 구분, Nemo의 규칙 표현,
Scallop의 provenance 태그와 OML의 모듈 명세를 공식 문서에서 다시 확인했다.
현재 공개 릴리스도 TypeDB 3.13.6과 Nemo 0.10.1로 확인했다.
최근 개발 기록과 읽을 수 있는 예제를 비교 대상 선정의 근거로 사용한다.

이번 Gooo 과제는 가격과 수량처럼 구조가 같은 정수를 업무상 구분하는 것이다.
기본형 별칭은 동일한 정수 타입을 가리키므로, 서로 다른 명시 ID를 가진
한 필드 레코드로 가격과 수량을 선언했다. 새 소스에서 연결 2개가 구분됐고,
수량을 가격 포트에 연결한 1개는 실행 전에 거절됐다. 입력 사례 2개의 출력 6/6과
서로 다른 내부 생성 이름을 확인했다. 모델 호출은 0회다.
[업무 타입 안내](language/domain-record-identity.ko.md)는 원래 생산자와 한계를 설명한다.

Gooo에서 더 다듬을 강점 후보는 표시 이름과 별개인 업무 ID,
소스가 정한 계산·선택 경로, 그 결과의 관찰을 함께 따라가는 것이다.
보완할 약점은 관계 질의, 중첩 레코드, 외부 데이터의 단위·출처 선언과 실제 에디터 연동이다.
다음에는 가격·수량 구분, 승인 이유, import 뒤 이름 변경을 같은 요구로 맞춰
표현한 요구 수와 외부 구현량을 비교한다. 위 6/6 결과의 분모는 두 입력 사례의 출력이다.

필드 타입 구현 [#1523](https://github.com/kimjooyoon/meta-ontology-go/pull/1523)은
공개 후 CI의 저장소 목록 단계에서 한글 경로를 읽는 오류가 발견됐다.
Git이 표시용으로 escape한 경로를 실제 파일명으로 읽던 부분을
NUL로 구분한 원본 경로 읽기로 수정했다. 별도 새 경로 4개에서 한글·공백·따옴표를
포함한 파일 목록과 줄 수를 확인했으며, 기존 전체 포트폴리오를 로컬에서 재실행하지 않았다.
수정 제출의 호환성과 전체 CI 성공 여부는 해당 제출의 원래 실행에서 확인한다.

## 모듈의 개념을 실제 값 생성까지 이어가기

필드·업무 타입 수정안 [#1524](https://github.com/kimjooyoon/meta-ontology-go/pull/1524)은
자신의 원래 CI 23개와 소스·산출물 연결을 확인해 개발 브랜치에 병합됐다.
실패한 #1523의 원래 실행과 소스는 그대로 보존했다.

다음 작은 사용성 과제는 `import money ...` 뒤 `money.Value{...}`로 실제 값을 만드는 것이다.
원래 새 constructor612 테스트에서 서명은 해석됐지만 본문에 import 별칭이 남는 문제를 찾았다.
OML의 파일별 prefix 관점에서 참고할 원리를 값 생성자와 후보 조립에도 적용했다.
해당 파일의 import·제공 entity ID·실제 빈자리의 변수 범위를 함께 읽는 수정안을 준비했다.

별도 constructor641 소스는 같은 별칭을 두 파일에서 다른 업무 타입으로 해석하고,
생성자 위치 3개와 실제 출력 8/8을 확인했다. constructor687의 소스 후보는
선택 1/1, 별도 평가 1/1, 다른 실제 입력의 출력 2/2를 기록했다.
새 CLI716에서도 모듈 값 생성과 후보 조립을 함께 사용해 실제 출력 8/8을 확인했다.
모델·외부 provider 호출은 0회이며 각 생산자와 분모는 따로 보존한다.
[구체적인 표현과 범위](language/package-qualified-record-constructors.ko.md)를 기록했다.

이 과제에서 비교할 점은 온톨로지에 붙인 이름과 ID가 실제 계산과 변경에도 이어지는가다.
Gooo 쪽의 강점 후보를 다듬는 동시에 관계 질의, 중첩 레코드, 단위·출처와 에디터 연동을
다음 요구로 유지한다. 다른 언어에서 같은 업무 과제를 실행한 비교 자료는 후속 작업이다.

## 강점을 키우고 약점을 보완할 순서

2026-10-13에 위 공식 문서와 두 공개 릴리스 내용을 다시 확인했다.
자료를 읽고 고른 개발 판단은 다음과 같다. 실행한 비교 실험의 결과와 구분한다.

| 참고 대상 | 현재 Gooo에서 비교할 지점 | 보완할 작업 | 적용 상태 |
| --- | --- | --- | --- |
| OML | 표시 이름이 바뀌어도 명시 ID를 유지하며 실행·관찰과 연결한다. | import의 같은 의미가 서명·필드·본문·후보에 이어지게 한다. | 서명·필드 해석은 개발 브랜치에 반영. 이번 생성자 수정안은 새 관찰을 마쳤다. |
| TypeQL | 소스의 허용 후보와 사례가 계산 구현의 선택에 참여한다. | 관계·집합·여러 반환값을 쓰는 업무 요구의 지원 범위를 먼저 확인한다. | 현재 native 레코드 범위는 평면 구조다. 더 넓은 표현은 후속 설계 대상. |
| Nemo | 활동의 ID와 호출·관측 기준으로 변경 영향을 따라간다. | 재귀 관계 질의와 결과 하나의 유도 이유를 사용자가 읽을 형태로 만든다. | 기존 의존 관계 출력과 규칙 엔진의 fact trace는 범위가 다르다. 이유 출력은 별도 요구로 유지. |
| Scallop | 모델 선택과 사례의 실제 결과를 각각 기록한다. | 모델 점수가 뜻하는 것, 모호함, 미관측 후보를 설명한다. | 현재 점수에 확률 의미가 확인되지는 않았다. semiring·미분 추론 지원은 미구현. |
| egglog | 소스가 조립 경로와 조건을 소유한다. | 어떤 변환이 선언된 동치인지, 어떤 변환은 사례만 맞는지 명시한다. | 원리 검토 단계. 임의의 동치 규칙을 컴파일러에 추가하지 않았다. |

큰 추론 엔진을 한 번에 붙이기보다, 다음 세 업무를 작은 프로그램으로 맞춘다.
가격·수량을 혼동하지 않는 계산, 승인 결과와 그 이유, 모듈 이름 변경 후 의미 유지다.
먼저 Gooo로 표현하는 과정에서 막힌 부분을 고친 뒤 다른 언어의 같은 과제를 준비한다.
관계 질의와 데이터 연결에서는 TypeQL·Nemo가 가진 표현을 참고할 부분이 많다.
Gooo에서 계속 다듬을 지점은 개념 ID, 허용 구현, 확인 기준과 조립 결과를 한 소스에서 이어가는 흐름이다.

### 공통 과제에서 기록할 값

| 값 | 분모와 기록 방법 |
| --- | --- |
| 요구 표현 | 미리 정한 요구 중 언어 소스에서 표현한 수 / 전체 요구 수. 외부 코드가 맡은 요구는 별도 표시. |
| 의미 유지 | 변경 전후 유지한 ID·참조 수 / 변경 영향을 받는 ID·참조 수. 해석되지 않은 참조도 표시. |
| 결과 일치 | 같은 입력의 실제 출력 일치 수 / 전체 확인 출력 수. 선택·별도 평가·실제 호출은 따로 기록. |
| 설명 가능 범위 | 결과에 소스·조건·선택 또는 규칙 경로를 연결한 수 / 확인한 결과 수. 경로 누락을 숨기지 않는다. |
| 표현 비용 | 업무 소스와 외부 구현의 파일·줄 수, 필요한 실행 환경. 자동 생성 파일은 구분한다. |

아직 실행하지 않은 언어·과제의 값은 미관측으로 둔다. 위 값을 단일 종합 점수로 합치면
각 언어가 맡는 역할과 부족한 요구가 가려질 수 있다. 이번 8/8도 두 입력 사례의 활동 출력에 대한 결과다.
자체 소형 모델은 Gooo가 정한 선택지의 판단을 계속 담당하며, 모델 없는 실행도 같은 요구로 확인한다.

## 결과의 이유를 공통 과제로 삼기

추가 비교 대상으로 Mangle의 현재 공식 문서와 개발 소스를 읽었다.
Go 구현, 관계·구조 표현과 질의할 수 있는 provenance가 Gooo의 남은 설명 요구와 연결된다.
[구체적인 분석](language/mangle-and-source-decisions.ko.md)에 읽은 근거와 도입 범위를 적었다.

먼저 Gooo로 재고 요청의 승인 여부·이유·요청 번호를 함께 반환하는 새 프로그램을 만들었다.
선택 1/1, 별도 평가 1/1, 실제 입력 6개의 활동 출력 12/12를 기록했다.
그 안의 결정 레코드 6개와 필드 값 18개도 원래 결과의 좁은 분모로 따로 읽을 수 있다.
승인 여부가 같아도 이유가 틀린 후보는 선택되지 않았다. 모델·provider 호출은 0회다.
[소스와 관찰](../examples/source-decision-reasons/README.md)은 실제 공개 개발 소스 bbfcaebb를 생산자로 유지한다.

Gooo에서 다듬을 강점은 이런 업무 조건과 구현 선택을 소스에 함께 적는 흐름이다.
보완할 부분은 직접 적은 이유를 실제 입력·성립한 조건의 근거 경로까지 연결하는 것이다.
Mangle의 실행 비교와 자동 분기 설명은 아직 수행하지 않았다.
