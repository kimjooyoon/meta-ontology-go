# `.gooo` language sketch

The surface language starts with four declarations:

```gooo
package billing
namespace billing

entity Order id "billing://entity/order"
entity PaymentMethod id "billing://entity/payment-method"
entity Payment id "billing://entity/payment"

activity PayOrder(Order, PaymentMethod) -> Payment
```

The compiler deterministically derives PROV-inspired facts:

- `PayOrder` is an `Activity`;
- inputs are `Entity` nodes used by `PayOrder`;
- the result is an `Entity` generated by `PayOrder`;
- each declaration retains a source span and semantic identity.

The initial grammar is intentionally narrow. Future syntax may add explicit relations,
constraints, capabilities, assertions, handwritten slots, and projection options. A
new syntax feature must define whether it is authoritative, derived, or a candidate.

## Identity and namespaces

An identity is an absolute, stable URI-like string. Names are scoped by namespace and
never become identity by string coincidence. Renaming a declaration is safe when its
semantic ID remains unchanged.

## Bidirectional contract

The compiler exposes two directions:

1. parse and lower `.gooo` to semantic IR;
2. analyze Go symbols that carry a registered semantic identity and lift deterministic
   facts back to IR deltas.

The implementation must preserve these laws:

- **Get-Put:** generating Go and lifting it does not create a new semantic fact without
  a source-backed delta;
- **Put-Get:** an accepted Go semantic delta is visible in the next DSL/IR projection;
- **Round-trip:** `DSL -> IR -> Go -> lifted IR` is semantically equivalent to IR;
- **Locality:** an implementation-only Go edit does not rewrite unrelated generated
  regions or unrelated DSL declarations.

Textual equality is not required; semantic equivalence and stable generated regions are.
