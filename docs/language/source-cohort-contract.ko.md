# 관찰하기 전에 평가할 작업 정하기

작업 목록에서 실패한 항목을 지운 뒤 비율을 계산하면 결과가 좋아 보일 수 있습니다.
Gooo의 평가 집합은 입력이 요구한 작업과 소스에 선언한 종료 작업으로 먼저 정합니다.
결과가 도착하는 과정에서는 이 집합을 유지합니다.

예를 들어 입력 작업 하나와 종료 작업 두 개가 있으면 예상 집합은 세 개입니다.
그중 두 개의 결과만 연결됐을 때 분모는 세 개로 남습니다. 같은 입력 작업이 두 번
등장해도 작업 정체성이 같으면 한 번 포함합니다.

## Gooo가 소유하는 선언

[registry.gooo](../../internal/meta/metricprogram/registry.gooo)의 개발 소스는
`CohortTerminalDeclaration` 레코드와 `CohortTerminalCount`, `CohortTerminalAt`
본문으로 두 종료 작업을 표현합니다. 각 레코드는 대상 `Subject`, 실행 담당 `Carrier`,
판단 계열 `Family`와 `Trilemma`를 보관합니다.

`terminate-at-fixed-point`의 실행 담당은 `replay-counterfactual`입니다.
두 값의 이름이 다르다는 점도 소스에 남습니다. 안정 ID는 표시 이름과 별도로 유지합니다.
Go의 두 생산 경로는 같은 생성 결과를 읽으며, 별도의 검증 커널은 기존 의미를 독립적으로
재구성합니다. 집합의 합치기·정렬과 전송은 Go가 수행합니다.

이 경로는 Gooo 선언에 따라 결정론적으로 구성됩니다. 생성된 세 파일의 전체 목록과
선언 ID, 해시는 묶음 명세에 남습니다. 기존 작업·엔티티를 생성한 두 파일은 이 개발
변경에서 바이트가 같고, 새 종료 선언은 세 번째 파일에 들어갑니다.

## 실제 생산 결과에서 반례 만들기

개발 소스의 `metric-cohort-counterexamples` 실행기는 기존 CI 생산자가 업로드한
정확한 결과 묶음을 받도록 연결했습니다. 원래 저장소·커밋·실행 회차·결과물 ID와
압축 파일 해시를 대조하고, 실제 선언과 입력에서 예상 작업 집합을 구성합니다.
실행기 기록에는 실제 코드 체크아웃과 워크플로 정의의 커밋, 실행 회차·잡·Go 환경도
남습니다. PR 코드와 워크플로 정의의 커밋은 각 역할로 보관합니다.
아래 16개 사례를 실행 전에 선언해 둡니다.

| 범위 | 사례 |
| --- | --- |
| 관찰 입력 | 예상 관찰 누락, 관찰 교체, 알 수 없는 관찰 추가, 중복된 바인딩 |
| 결과 기록의 집합 | 예상 대상 삭제 후 재해시, 대상 교체 후 재해시 |
| 기원 | 다른 커밋, 재해시한 프로그램, 다른 원본 해시, 프로그램 원본 변경, 다른 레지스트리 기원, 다른 입력 커밋 |
| 입력·권한 | 결과 기록 누락, 생산 입력 누락, 저장소 쓰기 주장, 승격 권한 주장 |

관찰 입력을 바꾼 사례는 생산자를 다시 호출해 충족 개수와 미확인 상태를 기록합니다.
이때 다시 해시한 입력은 반례용 입력이라는 표시를 유지하며, 원래 생산자가 검증한
출처로 취급하지 않습니다. 모든 사례는 실제 readiness 소비자를 호출해 거부된 단계와
전체 오류 내용을 남깁니다. 예상한 전체 오류 내용과 실제 거부 이유를 대조합니다.
실행 개수는 소비자를 실제로 호출한 사례 수입니다. 보고서의 `PASS`는 선언한 반례가
모두 예상 경로로 거부된 결과를 뜻합니다. 작업 충족률과 미확인 개수는 각 생산 결과에
보관합니다.

알 수 없는 추가 관찰의 실행 담당은 등록된 작업으로 유지합니다. 예상 집합의 작업은
모두 연결된 상태에서, 집합 밖의 관찰이 추가된 경로를 살피기 위한 사례입니다.
기존 분류기의 `AMBIGUOUS` 경로와 후속 처리 지시를 기록하도록 구성했습니다.
충족률과 미확인 개수는 각각 보관합니다.

바뀐 입력만 별도 파일로 저장하고, 같은 입력은 원래 결과물의 멤버·해시를 참조합니다.
없어진 입력도 별도 상태로 남깁니다. 각 사례의 실행 시간과 준비 시간은 반례 관찰
보고서에 따로 보관합니다.

## 이전 개발 단계에서 확인한 범위

새 Gooo 선언과 집합 구성의 새 단위 사례 9개가 로컬에서 통과했습니다. 결과물 전달과
해시 표기, 입력 참조에 대한 새 프로토콜 사례도 별도로 확인했습니다. 이전 제안 #1613의 원래 CI에서는
16개 반례를 실제 실행해 모두 예상 경로로 처리했습니다. 누락·치환은 9개 중 8개,
추가 미확인 관찰은 9개 중 9개 충족과 미확인 1개를 함께 기록했습니다. 실행 구간은
준비를 포함해 약 4.32초였고, 컴파일·프로세스 시작·최종 보고서 저장·전체 CI 시간은
제외합니다. [원래 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/38852243934)의
커밋·회차·결과물 정체성은 관찰 파일에 보존합니다.

그 제안의 PR 전용 CodeQL 분석에는 세 경고가 남았습니다. 기존 ZIP 허용 목록 검사는
유지하면서 파일 접근에 선언된 고정 이름을 사용하도록 전송 경계를 정리했고, 생산자와
독립 검증기의 불필요한 용량 덧셈을 제거했습니다. 새 경계 사례 19개는 통과했습니다.
이 후속 소스의 수용 여부는 별도의 원래 CI와 CodeQL 결과에서 확인할 단계입니다.

전체 언어 평가는 24개 항목을 유지합니다. 기존 양성 경로의 다른 23개 상태·이유 비교는
기존 CI 단계에 남습니다. 거부된 반례의 다른 23개 항목 상태는 미관찰로 남습니다.

[이슈 #791](https://github.com/kimjooyoon/meta-ontology-go/issues/791)의 원래 여섯 조건은
그대로 유지합니다. 새 원래 실행에서 나온 소스·실행·결과물의 연결과 각 거부 이유를
검토한 뒤 완료 여부를 판단합니다.

## 2026-10-17: 예상 집합과 관측 데이터의 수신 경로

기존 16개 반례에서 알 수 없는 관측을 추가한 사례는 등록된 실행 담당을 유지하고
관측 ID를 바꿉니다. 생산자가 계산한 `9/9 + 미확인 1`과, 수신자가 독립 전략
재구성 단계에서 거부한 사실을 구분해야 합니다. 이 사례만으로 미등록 연산의 관측이
정상적인 소스 검증을 통과한 뒤 미해결 판정에 도달했다고 주장할 수 없습니다.
별도 상류 사례는 미등록 연산을 실행 목록에 요구해 프로그램 구성이 거부된 경우이며,
관측 데이터에 알 수 없는 항목이 섞인 경우와 역할이 다릅니다.

새 연결은 [Gooo 예제](../../examples/source-owned-cohort-observations/main.gooo)의
`AssessDeclared`를 사용합니다. 예상 집합은 기존 원문·프로그램에서 복원하고,
관측 파일은 별도로 전달합니다. 관측의 누락·중복·추가는 예상 집합을 수정하지 않습니다.
알 수 없는 관측 ID는 실행할 활동으로 등록되지 않고 원본 데이터에 남습니다.

- 기존 생산자 영수증의 형식과 검증 경로를 보존합니다. 기존 영수증이 검증되지
  않았으면 새 관측으로 충족 상태를 만들 수 없습니다.
- 새 `gooo/observed-concept-operation-binding/v1`은 기존 영수증 전체와 선언 집합의
  해시, 관측 파일의 원본 바이트 해시, Gooo 원문·투영·활동 ID를 연결합니다.
  지표 ID는 기존 `gooo.metric.meta.concept-operation-binding-bps.v1`을 사용합니다.
- 등록된 예상 작업의 관측은 기존 생산자가 만든 바인딩과 정확히 일치해야 합니다.
  집합 밖 관측은 실행 바인딩을 주장할 수 없습니다.
- Gooo가 결합 수·미확인 수·비율·미해결 사유와 다음 작업을 정합니다. 순수 함수
  평가기는 기존 타입 검사·본문 평가기를 사용하며 모델이나 외부 프로세스를 호출하지
  않습니다. 이 평가와 별도 네이티브 실행의 출처를 구분합니다.
- 수신자는 기존 전략·프로그램의 독립 재구성을 수행하고, 저장소의 현재 Gooo 원문과
  전달받은 원문을 대조한 뒤 관측 영수증을 다시 계산합니다. 관측 입력이 있는데
  기존 형식 영수증으로 되돌아가 이를 무시하는 경로도 거부합니다.

기존 readiness 명령의 입력 디렉터리에는 `operation-observations.json`과
`observation-policy.gooo`가 함께 들어갑니다. 둘 다 없으면 기존 경로를 사용하며,
하나만 있으면 입력 누락으로 처리합니다. 새 영수증에 관측 입력이 없으면 거부됩니다.

원래 CI 실행기에 정상·미등록 관측 추가·누락·교체·중복·빈 관측의 여섯 사례를
연결했습니다. 예상 집합의 크기는 원래 생산 결과에서 읽습니다. 별도로 작성한 기대값을
같은 Gooo 원문을 컴파일한 두 번의 네이티브 실행과 대조하도록 구성했습니다.
정상 사례에서는 기존 24개 항목과 다른 23개의 상태·이유를 비교하고, 나머지 사례에서는
소스 재구성 후 준비도 수신자가 미검증 상태를 거부하는 전체 이유를 비교합니다.
기존 16개 반례와 상류 미등록 요청 한 개는 별도 모집단으로 유지합니다.

새 원문은 메타 소스 목록의 기존 순서를 보존하며 추가합니다. 물리적인 `.gooo` 원문은
150개에서 151개, 메타 소스 역할 목록은 11개에서 12개가 됩니다. 언어 사례 131개와
준비도 항목 24개는 그대로입니다. 원문 재고 검사는 각 파일의 경로·해시·행 수와 전체
누락 여부를 독립적으로 대조합니다. 원문 추가 때마다 고쳐야 했던 파일 수 상수는
이 대조가 담당하며, 등록되지 않은 원문에 대한 거부는 유지합니다.

이 절은 CI 수용 전 개발 소스의 구현 설명입니다(2026-10-17 작성). 작성 시점에는 새
소스의 원래 CI와 네이티브 결과를 관찰하지 않았고, #791을 완료로 판정하지 않습니다. 원본 바이트 해시와 재계산은
입력의 연결을 확인하며, 외부 관측 내용 자체의 사실성을 인증하지는 않습니다.

### 후속 관측과 등록 경계 수정

PR #1637의 원래 실행
[38947813155](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/38947813155)에서
새 관측 여섯 사례에서 소스 재계산과 준비도 수신의 예상 결과를 확인했습니다. 같은 Gooo
판정의 네이티브 실행 두 번에서 여섯 행, 출력 필드 값 60개가 독립 기대값과 맞았습니다.
실행에 사용한 예상 집합은 이 생산 프로그램의 아홉 작업입니다.

미등록 관측 추가 사례는 `9/9`, 미확인 `1`, 커버리지 `10000`, 상태
`FAIL_CLOSED`를 함께 보존했습니다. 수신자는 소스를 재계산한 뒤
`concept-operation evidence is not verified`로 준비도 반영을 거부했습니다.
기존 16개 반례와 상류 미등록 요청 한 개도 별도로 유지됐습니다. 정상 관측에서는
다른 23개 항목이 동일했고, 모델 호출은 없었습니다. PR 전체의 수용과 #791 완료
판정에는 남은 검사의 해결이 필요합니다.

원래 네이티브 기록의 `producer_source_sha`는 `UNBOUND_LOCAL_SOURCE`였습니다.
그 기록의 출처는 원래 CI의 정확한 체크아웃·실행·회차와 일치하는 Gooo 원문 바이트를
통해 연결했습니다. 원래 기록은 그대로 보존합니다. 후속 소스는 빌드의 VCS 정보를
기록하고 네이티브 생산자 커밋과 체크아웃을 직접 대조하도록 구성합니다.

같은 PR의 다른 원래 검사에서는 등록 엔진이 물리 파일 수의 정수 리터럴을 반드시
찾는 문제가 드러났습니다. 후속 경로는 `DeclaredSourceCount()`로 명시적 등록 목록의
고유 경로 수를 구합니다. 관측 파일 수는 이 기대값을 정의하지 않습니다. 등록 엔진은
관측 인자가 없는 해당 커널 호출과 실제 모듈 import를 확인해 그대로 보존합니다.
예전 정수 리터럴을 가진 입력은 기존 추가·메타 소스 승격 변환을 유지합니다.
파일·해시·행 수의 독립 대조와 언어의 의미 분모 검사는 계속 수행합니다.

후속 소스의 원래 CI 결과는 별도로 확인해야 합니다. 누락된 의미 검사, 관측을 분모로
사용하는 식, 다른 모듈의 호출은 새로운 경계의 반례로 작성했습니다.

검토했습니다. 전체 `main` 병합 후 검사와 #791 완료 판정은 각각 별도입니다.

여섯 사례는 관측 내용의 분류를 확인합니다. 새 관측 영수증의 다른 커밋·프로그램·
예상 집합·해시, 바인딩 변경, 쓰기·승격 주장까지 모두 확인한 수로 사용할 수는

이를 보완하는 새 실행 경로는 같은 원래 생산 입력으로 정상 관측 영수증을 만들고,
준비도 수신자가 그 영수증을 반영하는지 먼저 확인합니다. 이어서 다음 13개 변형을
선언한 뒤 각각 소스 수신자와 두 번의 준비도 수신자에 전달합니다. 세 경로의 전체
거부 이유가 독립적으로 작성한 예상 문자열과 같고 결과·준비도 반영이 없어야 합니다.

| 범위 | 새 관측 영수증의 사례 |
| --- | --- |
| 관측 기원 | 다른 커밋, 다른 프로그램, 다른 예상 집합 |
| 바인딩 | 알려진 작업의 값 변경, 집합 밖 관측의 실행 바인딩 주장 |
| 권한 | 재해시한 저장소 쓰기 주장, 재해시한 승격 주장 |
| 내용·전달 | 다른 해시, 재해시한 원문 출력 값, 원문 바이트 변경, 관측 바이트 변경 |
| 입력·형식 | 관측 입력 쌍 누락, 관측을 둔 채 이전 영수증 형식으로 되돌리기 |

원본 아카이브의 출처와 새로 만든 관측 영수증의 출처를 구분합니다. 새 영수증·관측·
정책 파일은 변경 멤버로 보관하고, 그대로인 상류 입력은 원본 멤버를 참조합니다.
보고서는 정상 관측 영수증의 식별 해시와 각 변형 입력의 바이트 해시를 남깁니다.
기존 실행기와 CI를 사용하며, 13개는 여섯 분류 사례·기존 16개·상류 한 개·언어
131개 사례·24개 준비도 항목에 더하지 않습니다.

단위 입력은 변형·보관의 기계적 동작만 확인하고, 실제 생산자·수신자 관찰을 대신하지
