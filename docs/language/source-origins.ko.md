# Gooo의 출처와 기원

Gooo에서 중요한 질문은 “이 동작은 어디서 시작됐나?”다. 주문 수량이라는 개념을
선언하고, 처리 규칙의 후보를 고르고, 실행 가능한 코드로 바꾸는 사이에 처음의
출처를 따라갈 수 있어야 한다. 프로그램에 붙은 여행 기록처럼 읽을 수 있게 만들고 있다.

이 문서는 개발 소스의 조건식 연결을 설명한다. 설치 안내에 고정된 0.6.33 릴리스는
별도 버전이며, 이번 기능을 사용하려면 이 변경을 포함한 개발 소스가 필요하다.

## 현재 연결되는 것

| 연결 | 남기는 정보 | 활용 |
| --- | --- | --- |
| 실제 조건 → 선택된 Gooo 본문 | 본문·전체 소스 해시, 바이트 위치, 변환 전 조건식 | 실행된 조건을 선언된 코드에서 찾기 |
| 조건 → activity 선언 | 안정된 ID, 선언 이름과 위치 | 이름이 바뀐 뒤에도 같은 개념을 따라가기 |
| 조건의 필드 참조 → field 선언 | entity·field ID, 선언 위치 | 수량과 금액처럼 모양이 같은 값의 도메인 구별하기 |
| 변환된 패키지 → 원본 파일 | 패키지·파일 이름, 원본 해시와 위치 | import 호출·생성자 이름 변경을 거슬러 읽기 |
| 출처 기록 → Gooo 활동 | 평평한 typed record | 출처를 언어 안에서 분류하고 후속 동작의 입력으로 사용하기 |

본문의 `let`을 정규화하기 전후에는 바이트 길이가 유지된다. 조건의 AST 노드를
분기·반환 구조 변환 동안 이어 전달하고, 생성된 함수 안의 순번으로 대응시킨다.
한국어 이름과 문자열의 이스케이프는 실제 소스 리터럴의 바이트 위치로 변환한다.
원본 파일과 선택된 소스는 각각의 해시와 위치를 가진다.

같은 보조 activity가 두 호출 루트에 생성되면, 두 실행 위치는 구별되고 선언의
기원은 공유된다. 출처 주석을 추가해도 순수 투영에 기반한 실행 위치의 ID는 유지된다.

필드 목록은 조건식이 정적으로 참조한 선언을 뜻한다. 실제 입력에서 단락 평가로
읽힌 피연산자는 실행 경로의 별도 관찰 범위다.

## 결과에서 읽는 위치

저장한 패키지 실행 기록은 `gooo package origins --receipt execution.json`으로
읽을 수 있다. [조회 안내](recorded-origin-queries.ko.md)는 후보에서 조건·반환식으로
이어진 정적 경로와 최초 파일·조립 입력의 위치를 설명한다.

`gooo package execute --json --cases cases.json gooo.workspace.json` 결과의
`runtime.condition_sites[].source`에서 선택된 본문의 출처를 찾는다.

- `source_sha256`, `start_byte`, `end_byte`: 선택된 Gooo 소스의 위치
- `declaration`: 조건을 선언한 activity의 ID와 위치
- `fields[].declaration`: 참조한 필드의 ID와 선언 위치
- `input_source`: 원본 패키지 파일의 해시·위치와 activity 선언
- `status`, `reason`: 연결된 범위와 미해결 이유

`composition.steps[].generation.report`에는 이미 후보 선택, 생성 경로,
본문 채우기의 기록이 있다. 이 기록과 조건의 activity ID를 함께 읽으면 어떤
구성 단계를 거쳐 현재 본문이 됐는지 살펴볼 수 있다. 모델이 사용되는 프로필에서는
제안 순서와 선택 기록을 남기며, 모델 경로를 비우면 결정론적으로 구성한다.

원본 본문에 없던 조건이나 본문 전체가 바뀐 경우는 `UNMAPPED`와 이유를 남긴다.
선택된 소스까지 연결되고 원본 조각이 미해결인 상태도 각각 읽을 수 있다.
예전 저장 기록에 출처가 없으면 그 부재를 유지한다.

저장 기록을 지금의 소스와 비교할 때도 이 경계를 유지한다. 예전 기록에
`condition_origins`가 없으면 해당 부가 정보만 제외하고 프로그램을 비교한다.
이미 담긴 출처, 본문, 진입점, 패키지 이미지와 나머지 구성 정보는 계속 대조한다.
이번에 새로 알아낸 위치를 과거 기록에 소급해서 적지는 않는다.

URI의 의미가 같은 ID를 서로 다른 대소문자로 쓴 경우에는 같은 필드 소유자로
해석한다. 작성한 ID 표기와 선언 위치는 소스에 남는다.
[ID 표기 사례](../../examples/source-owner-identity/README.md)에서 두 표현을 함께 읽을 수 있다.

## Gooo가 자신의 출처를 읽기

[작은 메타프로그램](../../examples/condition-origins/README.md)은 실행 위치별 출처를
typed record로 받고, 다음 문자열을 반환한다.

- `source-retained`: 원본 파일·선택된 본문·선언의 연결이 남아 있음
- `selected-source`: 선택된 본문과 선언까지 연결됨
- `origin-unresolved`: 해석에 필요한 연결이 부족함

Go 어댑터는 링크 유무와 개수를 옮긴다. 의미를 정하는 조건문은 `.gooo`에 있다.
이 구조를 이용하면 출처가 부족한 결과를 모아 질문하거나, 같은 기원을 공유하는
코드를 함께 살펴보는 메타프로그래밍으로 확장할 수 있다.

## 본문을 조립한 조각의 기원

`source_fill`은 빈칸에 들어갈 후보를 고른 뒤 조립 선언을 결과 소스에서 제거한다.
이때 조립 전 원문을 가리키는 `generation.report.body_fill.source_origin`을 남긴다.
원문 해시, activity ID, 의도와 후보의 위치, 빈칸 선언, 조립 전후 조각의 위치가 들어 있다.
패키지 실행에서 먼저 채운 본문은 `body_fills[].generation.report.body_fill.source_origin`에
기록되며, 최종 조건으로도 연결된다. 저장한 구성을 다시 읽을 때는 그 단계의 출처를 이어 쓴다.

조각은 다음 세 가지 기원으로 이어진다.

| 조각 | 원문에서 따라갈 위치 |
| --- | --- |
| `retained_template` | 템플릿에서 이어받은 본문 |
| `declared_candidate` | 선택한 후보의 `fill` 표현식과 빈칸 선언 |
| `derived_grammar` | 표현식을 만든 문법과 빈칸 선언 |

같은 표현식을 여러 후보에 써도 선택한 후보 ID와 위치를 유지한다. 문법으로 만든
표현식에는 실제로 작성된 표현식의 위치가 없으므로 `expression_source`를 붙이지 않는다.
문법 위치, 조립 입력과 계획의 해시를 통해 생성 경로를 읽는다.

실행한 조건의 `runtime.condition_sites[].source.construction`에는 해당 조건과
겹치는 조각들이 연결된다. 여기에 있는 `selected_source` 위치는 그 조립 단계의
출력 해시를 기준으로 한다. 여러 activity를 차례로 조립한 최종 파일은 별도 해시를 갖는다.
템플릿 조각은 조건 바깥까지 포함할 수 있으며 범위를 그대로 보여 준다.

[`ConditionFillOriginFacts`](../../internal/bodyexecution/condition_fill_origin_facts.go)는
이 연결을 평평한 기록으로 옮긴다. [Gooo 예제](../../examples/source-fill-origins/README.md)는
기록을 입력으로 받아 직접 선언된 후보, 문법 유도, 템플릿 유지를 구별한다.
선택과 출처를 언어의 다음 동작에서 다룰 수 있는 작은 연결이다.
[명령행 사례](../../examples/source-fill-origins/README.md#패키지-명령행)에서도 이 연결을 읽을 수 있다.

`assembly_input`은 **그 조립 단계에 들어온 Gooo 문서**다. 그 안의
`construction.input_source`는 **최초 패키지 파일**을 가리킨다. import 호출과
내부 이름 변경을 거쳐도 activity·후보·빈칸 ID로 원래 표현식을 찾는다.
템플릿의 위치는 생성자와 호출 이름 변경을 역으로 따라간다. 치환된 이름의 중간에
걸친 경계는 미해결로 남기고, 연결된 조각과 이유를 함께 보여 준다.

[원본 파일 예제](../../examples/workspace-fill-origins/README.md)에서 단계별 문서와
최초 파일을 함께 읽을 수 있다. `ConditionFillInputFacts`는 이 최초 파일의 조각을
Gooo에 전달한다. 파일을 옮겨 다시 읽을 때도 최초 파일명은 기록에 유지된다.
파일명은 기록된 표기이며 내용의 대응은 소스 해시와 선언·조각 위치로 읽는다.

기존 본문 채우기는 각 빈칸의 본문 출현을 한 번으로 제한한다.
반복 빈칸은 후속 범위다. [지역 변수의 기원](../../examples/value-origins/README.md)은
선택한 후보가 대입을 거쳐 조건에 쓰이는 관계와 본문의 반환식 노드를 기록한다.
`data_flow`의 `inputs`와 `controls`로 값의 입력과 제어 조건을 읽으며,
조건의 조각에는 직접 참조와 정적 의존 관계를 구별해 남긴다.
다른 함수 내부, 별칭, 일부 제어 경로는 부분 분석과 이유를 표시한다.

## 개발 중 확인한 범위

서로 다른 새 소스를 한 번씩 실행한 기록과 생산자 해시는
[예제 관찰](../../examples/condition-origins/observations.json)에 남긴다.
원본 파일 연결, 한국어·이스케이프 위치, 여러 호출 루트의 공통 기원,
선택된 템플릿의 조건 위치, 예전 기록의 출처 부재를 각각 살폈다.
실패한 진입점 지정과 예약어 필드 이름도 함께 남겼다.
공개 전 관찰의 생산자는 기존 컴파일러 커밋과 해당 임시 변경 해시다.
공개 커밋에서 얻는 CI 기록은 그 소스에 별도로 연결된다.

## 이어서 필요한 작업

출처를 연결하는 목적은 개발 중 다음 질문에 답하는 것이다.

- 이 계산은 어떤 개념과 작성자의 규칙에서 시작됐나?
- 이 조건은 직접 작성했나, 후보에서 골랐나, 어떤 변환으로 생겼나?
- 같은 선언에서 갈라진 코드들은 어디에 있나?
- 규칙을 고쳤을 때 다시 살펴볼 구성과 소비자는 무엇인가?

작은 결정 모델도 이 흐름 안에서 사용한다. 어떤 선택 공간을 받았고 어느 후보를
제안했는지 남기면, 이후의 코드와 모델의 제안을 함께 따라갈 수 있다.
검사 결과는 그 출처에 연결된 관찰로 읽는다. 출처가 있다는 사실만으로 동작의
정확성이 정해지지는 않으며, 결과가 맞았다는 사실로 기원을 추정하지도 않는다.

1. **원문 연결의 범위:** 최초 파일의 후보·hole·intent 연결을 더 다양한 생성자와 변환 조합으로 확장한다.
   채워진 조건은 `construction.input_source`에서 조각별 기원을 읽는다.
2. **값의 이동:** 구현된 지역 대입·조건·반환식 연결을 바탕으로 함수 간 호출과 bind 입력까지 확장한다.
3. **변경 영향:** 하나의 선언 ID에서 시작해 어떤 구성과 소비자가 영향을 받는지 찾는다.
4. **모델의 기원:** 소형 결정 모델의 버전·입력·제안을 구성 기록과 연결하고 소스의 선택 공간을 유지한다.

우선 질문 하나에 쓸 수 있는 연결부터 구현한다. 전체 프로그램의 기원이 한 번에
완성됐다는 가정 없이, 연결이 남은 범위와 이어야 할 부분을 함께 보여준다.

개선 정도도 이 질문에 맞춰 살핀다. 출처를 찾을 수 있는 구성의 비율,
변환을 거친 뒤에도 남아 있는 연결, 끊긴 연결의 이유를 따로 기록한다.
작성자가 애초에 출처를 적지 않은 경우와 컴파일러가 변환 중 잃은 경우를 구별해야 한다.
출처 비율의 집계와 함수 사이의 값 이동은 다음 구현 범위다.

## 참고한 연구와 구현

[W3C PROV-O](https://www.w3.org/TR/prov-o/)는 자료와 활동, 생성과 유도의 관계를
표현하는 공통 어휘를 제공한다. Gooo의 선언·변환·결과를 이어 보는 설계에 참고한다.
이번 조건 위치 자료는 JSON으로 전달한다.

[Mangle provenance](https://mangle.readthedocs.io/en/latest/provenance.html)는 유도된
사실을 규칙·변수 대입·입력 사실과 연결한다. Gooo에서는 그 연결 방식을 소스의
조건·선언·구성 경로에 적용하는 방향을 탐색한다.
[OML/openCAESAR](https://opencaesar.io/oml/)의 모듈과 온톨로지 표현도
개념의 ID와 사용 위치를 유지하는 언어 설계를 비교하는 데 참고한다.

[AgentMesh 조사](../research/agentmesh-origin-and-decision.ko.md)는 제공자의 기원과
모델 판단 내용의 기원을 연결하는 후속 설계를 정리한다. 외부 네트워크 연동은 아직 설계 단계다.
