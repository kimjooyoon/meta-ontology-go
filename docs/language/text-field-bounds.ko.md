# 원문이 정하는 Text 필드의 바이트 범위

이 문서는 V6의 원문 계약과 수용 기준을 설명합니다. 실행 성공 여부는 해당 소스
버전의 CI 원본과 릴리스 기록에서 함께 확인합니다.

EntityFields V6는 필드의 안정 ID에 `max_utf8_bytes` 조건을 붙입니다.
[실행 예제](../../examples/bounded-text/main.gooo)는 1,024바이트 입력에 6바이트
접두사를 붙여 1,030바이트 결과를 돌려주는 문제를 다룹니다.
[등록 조각 예제](../../examples/scope-fragments/README.md)는 같은 기능으로 파일 목록을
JSON·Go·Markdown으로 옮기며, 입력의 최대 크기에서 출력 필드의 바이트 상한을 구합니다.

```gooo
entity Expanded id "gooo://examples/bounded-text/expanded" fields {
    field value id "gooo://examples/bounded-text/expanded/value"
        type string required one max_utf8_bytes "1030"
}
```

조건은 관측과 모델 선택 전에 원문에 고정합니다. 입력 사례·기대 결과·표시용
렌즈·용량 힌트를 바꾸어 수용 범위를 넓힐 수 없습니다. 새로운 범위가 필요하면
원문의 선언을 바꾸고 그 의미 식별값과 출처를 새로 남깁니다.

## 값·전달·표시의 경계

- 단위는 JSON을 디코딩한 값의 UTF-8 바이트입니다.
- 단독 Text 입력과 조건을 생략한 필드는 기존 실행 프로필의 제한을 유지합니다.
- 명시한 `"0"`은 빈 Text만 허용합니다. 미선언과 다른 값입니다.
- `optional`의 생략과 `many`의 원소 수는 독립 조건입니다. `many`의 바이트 범위는
  각 원소에 적용하며, 기존 256개 원소 제한을 유지합니다.
- Gooo의 레코드 수신·전달·반환 경계에서 값을 검사합니다. 함수 내부의 임시 문자열
  크기를 정적으로 추론하는 기능은 별도 과제입니다.
- 전체 JSON, 네이티브 출력, 출처 페이지와 저장 영수증의 예산도 각각 적용합니다.

숫자는 기존 관측 예산 문법처럼 정규 십진 문자열로 씁니다. 범위는
`"0"`부터 `"4294967295"`까지입니다. 음수·소수·범위 초과·중복 조건과 Text 이외
타입의 선언은 오류로 남깁니다. 큰 선언을 해도 전체 전송 예산이 함께 늘어나지는
않습니다.

## 같은 결정을 전달하기

조건은 구문 필드에서 BX 모델·의미 IR·투영·패키지 인터페이스·실행 레코드로
전달됩니다. 전체 필드의 원문 범위와 안정 ID가 기원을 가리킵니다. 표시 이름이
바뀌어도 같은 ID의 바이트 조건을 보존하며, 조건 자체가 바뀌면 의미 해시가 달라집니다.
패키지 사이에서 같은 ID의 레코드를 합칠 때도 조건을 비교합니다. 서로 다른 조건은
충돌로 남기고 한쪽의 범위로 조용히 대체하지 않습니다. 별도 영수증 구조 프로필 V1은
값의 크기 조건을 지원하지 않으므로 해당 선언을 받으면 명시적으로 거부합니다.

Go 구조체에는 `gooo_max_utf8_bytes` 설명 태그를 남기고, Gooo 실행 경로가 실제
값의 수용 여부를 판정합니다. 내부 표현은 8바이트 값 하나로 미선언과 명시한 0을
구분합니다. 필드마다 별도 조건 객체를 할당하지 않습니다. 메모리·속도 개선율은
후속 측정 대상으로 둡니다.

JSON 이스케이프 해석은 기존 `internal/meta/textinput/escapes.gooo`의 정책을
공유합니다. 해석기·네이티브 수신·레코드 전달이 원래 바이트에서 잘못된 서로게이트와
중복 키를 확인합니다. Go 호스트 패키지 이동은 생성 영역의 바이트를 보존하며,
과거 `generation-origin.json`은 원래 생성 기록으로 유지합니다.
명시한 조건이 있는 필드의 네이티브 값도 JSON 변환 전에 UTF-8을 검사합니다.
바이트 슬라이스로 잘린 문자를 JSON 인코더가 대체한 뒤 수용하는 경로를 막습니다.

## 기대값 없이 실행하기

`package execute --inputs`는 입력과 실제 결과를 연결하는 관측 경로입니다.
성공 영수증의 `decision`은 `OBSERVED`이고, `inputs_digest`가 입력 원문을
가리킵니다. `cases_digest`와 전달 결과의 `expected`, `passed`는 생략합니다.
기대값을 제공하지 않았으므로 `finite_total`, `finite_passed`는 모두 0이며,
별도 평가와 입력이 겹치지 않는지에 대한 상태도 `UNKNOWN`으로 유지합니다.

외부 검사는 이 실제 결과를 독립 기대값과 비교할 수 있습니다. 그 기대값을 실행기에
전달한 것으로 기록하거나, 실행 영수증에 정답률 점수를 만들어 넣지는 않습니다.
같은 필드 조건과 안정 ID를 사용하는 `--cases` 비교와 각각의 입력 출처를 보존합니다.

작업공간 영수증의 `result.program.lowered_gooo_source`는 여러 원문을 합쳐 이름을
내린 초기 Gooo 소스입니다. `result.execution_source_sha256`는 그 소스에 본문 채우기를
적용한 뒤 실행 구성에 전달하는 바이트를 가리킵니다. 본문을 채웠다면 초기 소스와
다를 수 있습니다. `inputs_digest`는 제공한 입력 파일을,
`result.runtime.producer_source_sha`는 실행한 컴파일러의 빌드 기원을 가리킵니다.
입력 파일·원문 선언·본문을 구성한 소스·컴파일러 빌드의 단계를 함께 읽습니다.

`result.program.workspace_image.packages[].sources[].source_digest`는 해당 소스
문자열을 Go `json.Marshal`로 직렬화한 값의 해시입니다. 따옴표와 이스케이프가
포함되므로 원본 파일의 바이트 해시와 직접 비교하지 않습니다. 패키지 경로와
파일명, 전체 필드 경로를 함께 사용합니다. [첫 실행 안내의 해시 대상 표](../getting-started.md#read-a-digest-with-its-full-field-path)에
각 입력의 대상을 정리했습니다.

## 수용할 관측

이 기능을 처음 등록할 때 구문 사례 한 개를 추가했습니다. 당시 선언 분모는
132개(언어 기능 130, 거버넌스 2), 물리적 Gooo 원문 152개였습니다. 12개 메타 원문
역할과 24개 준비도 의무는 각각 유지합니다. 아래 네이티브 관측은 별도 집합입니다.
구문 기능 분모는 v94에서 130으로 이행하며, 과거 v93의 129개와 원본 바이트는
그대로 보존합니다. 다른 다섯 경계와 13개 연결 의무는 바꾸지 않습니다.

원래 CI에서 다음을 확인하도록 검사를 작성합니다.

1. 공개 `package execute`의 1,030바이트 결과와 1,025바이트 단독 입력의 거부.
2. 1,031바이트 출력 거부와 원문 조건을 1,031로 바꾼 경우의 수용.
3. 한글·NUL·명시한 0·선택 필드 생략·반복 원소의 정확한 값.
4. #1620 원본 13필드 자료의 그대로인 1,007바이트 zone과 1,030바이트 canonical.
5. 같은 안정 ID의 이름 변경, 형식 왕복, BX 법칙과 조건 변경의 의미 해시.
6. 원래 CI 소스에 묶인 공개 CLI의 두 네이티브 실행과 독립 기대값.
7. 원소 256개가 각각 필드 조건을 만족해도 전체 네이티브 출력 예산을 넘으면 거부.

실행 원본은 기존 CI 작업의 `command-origins-*` 산출물 안
`text-bound-native/`에 남깁니다. 원본 13필드의 기대값 없는 성공 경로는
`text-bound-input-only/`에 별도로 남기며, 원래 작업공간·입력 파일의 바이트와
필드 순서·안정 ID·타입·값을 확인하도록 작성합니다. 입력 1,024바이트와 zone
1,007바이트를 유지하고, 두 네이티브 실행의 출력을 비교합니다. 이 검사는 기존
언어 사례·준비도 분모와 별개입니다. 검사 작성·구현 설명과 실제 CI 수용은 별도로
읽습니다. 원본 이슈의 주소 파서 전체 구현은 별도 생태계 작업으로 이어집니다.
