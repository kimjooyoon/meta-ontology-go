# Gooo를 실제로 쓰는 언어로 발전시키기

2026-10-17 개발 방향. 아래의 우선순위와 목표는 앞으로 확인할 작업이다.
기존 예제의 성공 횟수를 외부 사용자의 경험으로 환산하지 않는다.

Gooo를 사용하는 에이전트가 작은 도구를 만들고, 다른 프로젝트에서 가져다 쓰고,
요구가 바뀌면 원문을 고쳐 다시 실행할 수 있어야 한다. 사람은 같은 소스와 결과를
읽을 수 있는 설명을 선택한다. 그 과정에서 개념과 계산이 어디서 왔는지 이어 보는 것이 Gooo의 가치다.
프로그램의 부품에 원래의 설계도와 교체 이력이 함께 따라오는 모습을 지향한다.

## 개발 순서

개발 변경안의 [순서 있는 목록](ordered-collections.ko.md)은 `many` 필드,
`for … in`, 원본 위치 연결과 패키지 호출을 함께 다룬다. 후보 선택용 사례와
별도 보류 사례, 네이티브 실행을 구분해 관찰하고 있다.
새로 만든 목록도 [생성 표현과 원소별 계산](../observations/construction-origins/README.md)을
기록한다. [기원 입력](native-origin-inputs.ko.md)은 저장된 읽기·생성·원소·연결을
Gooo 레코드로 전달하며, [네 가지 설명 프로그램](../../examples/native-origin-reader/README.md)이
빈 목록과 중단, 외부 입력과 생성한 원소의 연결을 해석한다.
계산 중 읽기와 전체 데이터 의존성은 관찰 범위를 나눠 표시한다.

### 1. 모델 없이 작은 프로그램을 끝까지 만들기

입력 읽기 → 계산 → 결과 쓰기까지 한 작업을 고른다. 예를 들어 여러 항목의 금액과
수량을 받아 합계와 처리 이유를 반환하는 도구다. 이미 있는 스칼라 계산과 레코드,
패키지 호출을 조합하고, 여러 항목을 표현할 때 막히는 지점을 다음 언어 기능의
요구사항으로 삼는다. 개발 소스는 스칼라 목록과 두 단계의 컬렉션 순회를 지원하며,
각 목록의 길이와 중첩 작업량을 제한한다. 실행 본문에서 레코드 안의 레코드와 중첩 목록은
추가 설계가 필요한 영역이다. 구체 범위는 [목록 안내](ordered-collections.ko.md)를 따른다.

각 기능은 `.gooo` 표현, 타입과 의미, Go 생성, 실행, 진단, 포맷과 이름 변경까지
같이 살핀다. 잘못된 입력에서 어느 소스 위치를 고쳐야 하는지도 사용성에 포함한다.
모델과 API 키를 설정하지 않은 상태에서도 이 경로가 동작하도록 유지한다.

### 2. 다른 프로젝트에서 재사용하고 바꾸기

두 패키지 사이의 데이터와 함수 연결, 이름 변경, 버전 변화에 따른 진단을 개선한다.
새 의존성을 추가할 때 어떤 기능과 개념을 가져오는지 읽을 수 있어야 한다.
현재의 소스 파일·워크스페이스 배포 방식을 출발점으로 삼는다.

### 3. 출처를 일상적인 개발 도구로 쓰기

“이 값은 어디서 왔나”, “이 규칙을 바꾸면 어디를 살펴봐야 하나”에 답하도록 만든다.
원본 선언의 ID, 파일과 범위, 변환, 선택된 후보를 이어 붙인다. 개발 소스의 [활동 사이 기원 조회](value-origins-across-activities.ko.md)는
activity 사이의 반환값과 bind 입력, 반환식만 있는 본문의 원본 파일 연결까지 다룬다.
반복 종료 경로와 중첩 데이터의 정밀한 연결은 후속 범위다.
이미 있는 변경 영향 조회와 연결해 같은 선언을 다시 찾을 수 있게 한다.

출처 정보와 실행 관찰은 각각의 의미를 유지한다. 원본이 남아 있는 비율과 테스트
입력의 결과 일치 비율은 다른 질문에 답하므로 별도로 기록한다.

### 4. 작은 결정 모델을 필요한 선택에 붙이기

소스가 선언한 유한한 후보 안에서 먼저 시도할 경로를 제안하도록 한다.
선택 공간, 실제 요청, 제공자, 모델 파일과 버전, 제안, 최종 구성의 연결을 보존한다.
연결이 없으면 결정론적 후보 순서를 사용한다. 모델의 기여는 같은 작업에서의
시도 수, 지연과 메모리, 별도 입력의 기능 결과로 비교한다.
[AgentMesh 조사](../research/agentmesh-origin-and-decision.ko.md)의 제공자 식별과
어댑터 경계도 이 범위에서 참고한다.

## 에이전트의 기본 작업과 고객 CI

기본 경로는 **버전을 고정해 설치 → `.gooo` 수정 → 실행 → 결과 읽기 → 재실행**이다.
[첫 프로그램 안내](../getting-started.md)의 공개 릴리스와 개발 소스 예제를 구별한다.
모델을 설정하지 않아도 이 경로를 끝낼 수 있어야 한다. 모델은 소스가 허용한
후보의 시도 순서를 제안하고, 이미 선택한 프로그램의 재사용에는 새 제안이 필요하지 않다.

- 기계 소비에는 기존 `--json` 결과와 종료 코드를 함께 쓴다. 종료 0인 `PROGRESS`도
  사례 일치 실패로 다룰 수 있도록 [CI 결과 읽기](../getting-started.md#use-results-from-an-agent-or-ci)를 안내한다. 실행 오류, 사례 불일치,
  기대값 없이 얻은 관측을 각각 읽는다. 명령 인자 오류는 JSON 대신 사용법을
  stderr에 쓰는 경로도 있으므로 빈 stdout을 성공 결과로 해석하지 않는다.
- `--cases`의 `finite_total`은 각 행의 `expected`에 적힌 기대 출력 항목 수이며,
  `finite_passed`는 전체 JSON 값이 일치한 항목 수다. 필드가 여럿인 레코드 기대값도
  한 항목으로 센다. 입력 행 수와 선언한 필드값 수는 별도로 남긴다. `--inputs`는 실제 입력에 대한
  관측이며 기대값이 없으므로 정답률을 만들지 않는다.
- 저장한 receipt는 선택과 출처를 재사용하는 입력이다. `package replay`는 원본과의
  연결을 확인하고 새 입력을 실제로 실행한다. 저장된 출력이 새 실행 결과를 대신하지 않는다.
- 소스를 고치면 기존 receipt가 거부될 수 있다. 예전 소스와 receipt는 함께 남기고,
  새 소스에는 `package execute`로 새 기록을 만든다.
- 사람용 렌즈, 별칭과 설명 선호는 보조 정보다. 이를 읽지 못해도 계산의 의미와
  안정 ID, 실행 선택이 바뀌지 않도록 유지한다.

고객 CI의 검사 대상은 고객이 사용하는 소스·계약·고정한 컴파일러와 실행이다.
컴파일러 저장소의 여섯 정식 검사와 모든 내부 실험 워크플로를 고객 프로젝트의
기본 의무로 복제하지 않는다. 사용한 패키지의 사례와 독립 기대값을 검사하고,
변경의 소비자 관계를 확정할 수 없으면 검사 범위를 넓혔다는 이유를 남긴다.
컴파일러의 실제 검사 의무와 승격 정책은 그대로 유지한다.

현재의 [인과적 검사 선택](../causal-ci-selection.md)은 계획과 실제 실행을 구별한다.
범위를 계산했다는 이유만으로 고객의 검사를 생략하는 기능으로 안내하지 않는다.
공개 partial/test reuse, 요청 안의 parse/probe cache도 각자의 입력·수명·소비 경계가
있다. 기존 계약에서 빠진 연결을 확인한 뒤 필요한 경계만 수선한다.

### 공유 산출물과 재시도 설계

중복 생산 작업을 줄이는 후속 설계에서는 선택 범위와 생산자·소비자의 기원을 함께 보존한다.
현재 두 symbolic-invocation 워크플로는 같은 생성 스크립트를 호출하지만 `dev` 실행 조건과
runner 설정이 다르다. 공유 전에 이 차이와 소비자가 필요한 입력을 명시해야 한다.

- 미선택, 대기, 실패, 취소, 완료 후 산출물 누락을 구분한다. 필수 산출물을 얻지 못하면
  제한된 대기 뒤 검증 불가로 종료하고 첫 원인과 다음 행동을 남긴다.
- 소비자의 재시도는 유효한 원래 산출물을 다시 읽을 수 있다. 생산자를 새로 실행했다면
  새 run·attempt·job으로 기록하고, 원래 결과와 소비자의 실행 시도도 각각 보존한다.
- 전송 장애의 제한된 재다운로드와 생산 작업의 재실행을 구별한다. 원본·계약·완료 목록·
  digest 불일치는 별도로 다룬다. 보조 측정 누락만으로 완료한 작업을 재실행하지 않는다.
- 소비자는 자신의 입력과 독립 기대값으로 결과를 판단한다. 환경의 호환 범위와 기존
  검사 선택을 유지하면서 중복 생산 작업량과 전체 완료 지연을 각각 측정한다.

`dev`의 `04ffab2c`에 대한 [원본 CI 한 번](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39022807070)에서는
의미적 일관성 검사 단계가 22분 5초, race 검사가 19분 4초, 일반 테스트가 9분 22초였다.
병렬 단계의 시간을 합산하지 않는다. 의미적 일관성 검사는 변환한 작업공간도 검사하므로
원문 테스트와 같은 작업으로 간주해 생략할 수 없다. 이 명령의 기존 예측은 약 25분 2초,
명령 관측은 약 22분 2초였으며, 변경한 줄 수에 비례하는 예측은 아직 확인하지 못했다.
다음 개선에서는 기존 실행 기원에 비싼 하위 작업의 입력과 시간을 연결하고,
소스 정규화를 앞세울 때 정상 작업의 추가 지연과 실패 작업의 절약량을 함께 살핀다.
이 한 번의 기록으로 성능 개선율이나 고객 CI의 예상 시간을 만들지 않는다.

다음 작업은 아래 순서로 고른다. 각 단계의 결과를 보고 다음 범위를 정한다.

1. **실패 후에도 실제 관측을 읽는다.** [#1663](https://github.com/kimjooyoon/meta-ontology-go/pull/1663)은
   부분 실행 결과와 출처를 보존하고 저장 보고서끼리 비교하는 변경이다. 출력 회수 경계도
   부모 프로세스의 종료, 스트림 끝, 보존된 바이트를 각각 다룬다. 에이전트는 완료 범위를
   읽고 다음 행동을 고르며, 관측의 누락만으로 작업을 다시 실행하지 않는다.
2. **보조 비용 이력의 책임을 좁힌다.** 과거 시간 표본, 현재 실행의 중복 예약, 예측의
   가용성을 구분하는 CI 도메인 변경을 설계한다. 이력 읽기 실패 시 명시적으로 예측 미상으로
   처리할 범위를 정하고, 현재 실행 의무와 기록 저장 실패는 원래 결과와 함께 보존한다.
3. **같은 유형의 규칙 한 개를 원문으로 바꾼다.** 기존 API 정책에 비어 있지 않은 사용자
   식별 조건을 추가하는 내부 사례를 다음 비교 후보로 삼는다. 기존 거부 순서와 9개 입력·
   15개 출력 계약을 유지하며 Gooo 본문, Go 연결, 독립 기대값의 변경량을 각각 센다.
4. **거부 지점을 에이전트가 바로 읽게 한다.** 기존 오류의 종류와 단계에 안정 코드를 붙이는
   작은 변경부터 시작한다. 명시적으로 선택한 구조화 stderr와 기존 성공 stdout·종료 코드의
   호환성을 살핀다. 진단이 후속 실행을 허용하는 범위는 각 작업의 원문 정책에서 정한다.
5. **실제 사용으로 다음 확장을 고른다.** 생태계는 고정 버전의 설치·예제·배포와 소비자 CI를,
   엔진은 의미·기원·실행 경계를 맡는다. 최초 사용과 같은 사용자의 두 번째 작업에서 막힌
   입력·단계·사람 개입을 남기고, 반복해서 드는 비용이 확인된 부분을 다음 언어 기능으로 고른다.

2026-10-17 엔진 개발과 생태계 개발 대화가 이 순서에 합의했다. 생태계에서 외부
에이전트의 최초 실행·활성화와 가장 큰 막힘은 아직 측정하지 못했다. ports 내부
observer의 시간 한도 도달과 고객의 기본 CI는 각각의 범위에서 기록한다. 실제
외부 재현이 들어오면 가장 작은 소스·명령·첫 진단부터 엔진 개선에 연결한다.

### 생태계와 합의한 다음 실제 작업

첫 경로는 **API·자동화 정책 한 규칙 편집 → 같은 입력의 전후 결과 비교 → 각 소스의
저장 기록으로 공식 replay**다. 생태계의 [공개 예제](https://github.com/kimjooyoon/gooo-go-ports/blob/584dd4a8cf5cf2836f3e73f001a4c76708f69ee1/examples/editable-api-policy/README.md)는
9개 스칼라 사실, 15개 결과 필드, 1–3개 입력 행의 오프라인 작업을 다룬다.
엔진은 실제 거부 지점의 기계 판독 코드와 원본 연결을 제공하고, 생태계는 고정 버전의
설치와 이 작업의 소비자 안내를 담당한다. 내부 실험과 엔진 전체 CI를 고객에게 복제하지 않는다.

사용자는 자신의 기존 Go·OPA·Cedar 등의 절차와 반복 업무를 설명하고 실제 편집·비교·
replay를 끝낸다. 줄어든 구체 작업을 특정했을 때 효용을 관찰한 것으로 기록한다.
같은 사용자의 두 번째 실제 작업은 재사용 관찰로 남긴다. 2026-10-31까지 3회 시도,
2회 완료, 1회 재사용은 실험 목표이며 현재 성과가 아니다.

지원 범위 안에서 완료한 실제 작업 세 번 모두 반복 이득이 없다면 이 정책 예제의
확장을 멈추고 사용처를 다시 고른다. 설치 실패는 첫 재현 장애를 먼저 수정한다.
무응답, 설치 실패와 사용 후 이득 부재를 같은 결과로 집계하지 않는다.
현재 독립 외부 사용자의 반복 업무 절감은 미검증이다.

내부 개선도 같은 방식으로 범위를 정한다. 현재 generated-test reuse 실험에서는
실행 입력 세 파일과 공개 자료 묶음의 경계부터 고친다. 누락된 관찰을 채운 뒤 안정된
의미 결정을 타입이 있는 Gooo 입력·조건으로 옮긴다. 프로토콜이나 Go 코드의 추가만으로
새 언어 표현력이 생겼다고 집계하지 않는다. 요청당 파싱과 필드 조회의 개선 역시 실제
사용자가 절약한 작업과 별도로 보고한다.

### 판단을 언어가 맡았는지 확인하기

이번 재검토에서 test reuse의 `.gooo`는 결과표를 담고 있었고, 실제 분기를 선택하는
부분은 Go에 남아 있었다. [#1657](https://github.com/kimjooyoon/meta-ontology-go/pull/1657)의
수정을 반영한 `main`은 타입이 있는 관측을 `AssessOriginal`과
`AssessReplay`에 전달하고, Gooo가 조건문과 함수 호출로 판단·이유·다음 행동을 만든다.
기존 순수 값 평가기를 사용한다. 판정 소스는 기존 메타 정책의 배치 방식대로
별도 `.gooo` 파일에 두고 평가기에 포함한다. 테스트할 프로그램과 판정 정책의
원본을 따로 보존하여 예제의 과거 등록·읽기 프로필을 유지한다. Go에는 파일 읽기, 성공한 실행 기록 확인과 실제
재사용 직전의 입력 비교를 남긴다. 관측과 판단이 만나는 위치를 소스에서 읽을 수 있다.

실행 도구의 출처도 같은 비교에 들어간다. `execution_tool_inputs`에는 실제로 고른
Go 실행 파일의 경로·바이트 해시·빌드 버전·플랫폼과 고정한 자식 환경의 해시를 남긴다.
실행은 관측한 절대 경로와 같은 환경을 사용하고, 파일 변경과 재사용 직전의 환경
변경을 확인한다. 환경은 프로세스·캐시 위치와 명시한 Go 설정으로 제한하며,
원래 환경의 비밀 값이나 모델 설정을 기록에 복사하지 않는다.
과거 v2 receipt의 검사 프로그램 버전만으로는 이 기원을 채울 수 없으므로,
Gooo는 `EXECUTION_TOOL_INPUTS_UNOBSERVED`와 다음 행동을 반환한다.
새 receipt는 v3, 보고서는 v4로 구분한다. 이 범위는 선택한 `cmd/go`와 자식 환경이며,
SDK 전체 파일·전이 모듈·테스트의 외부 효과가 닫혔다는 뜻은 아니다. 해당 의존성
감사는 계속 열려 있다. GNU time 포장 대신 같은 Go 파일을 직접 실행하고,
기존 Linux·macOS 프로세스 관찰 코드에서 peak RSS를 읽는다. 측정이 지원되지 않는
플랫폼은 미확정 오류를 반환한다. 재사용 프로세스도 실제 운영체제 값을 읽으며,
관측 실패를 `1 KiB`로 채우던 처리를 제거했다. `peak_rss_subject`는 JSON·요약·
읽기용 문서에 측정 대상을 남긴다. 최초 실행은 완료된 Go 명령들의 최대 RSS,
재사용은 현재 관측 프로세스의 RSS다. 이 설명 필드는 재사용 결정을 바꾸지 않는다.
서로 다른 대상을 측정한 수치로 메모리 절감률을 계산하지 않으며, 새 구현의 실제
검증 결과는 해당 소스에서 확인한다.

작은 규칙 변경의 기준은 “Gooo 조건과 독립 기대값을 바꿨을 때 기존 연결 코드로
실행되는가”다. 입력 프로필 조건만 바꾸는 회귀 사례가 이 경계를 확인한다. 첫 연결에
드는 Go 코드, 테스트와 다음 규칙의 변경량을 각각 센다. 전체 줄 수의 감소나 Gooo
비율 상승만으로 개발 비용이 줄었다고 판단하지 않는다. 초기 Gooo 분류기 반영 결과는
[실제 main의 원본 CI](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39026277458)에서
확인했다. 새 명령이나 고객 필수 검사 단계는 추가하지 않았다.

에이전트가 읽는 결과에는 실제 관측, 안정 activity ID, 원본 소스와 평가된 형태의
해시, 반환한 판단을 같이 남긴다. `UNKNOWN`에는 막힌 입력과 다음 행동이 있다.
사람용 설명은 이 기록을 읽는 보조 표면으로 둔다. 아직 실행하지 않은 초안과 실제
원본 실행의 완료 상태도 구별한다.

### 외부 자동화의 이력을 다루는 순서

AutoBot의 [과거 결정 보존 요구](https://github.com/mrveiss/AutoBot-AI/issues/18650)와
[판단 당시 정책·설정 연결 요구](https://github.com/mrveiss/AutoBot-AI/issues/18651)는
우리가 다룰 출처 문제를 구체적으로 보여준다. 요청, 적용한 규칙, 빠져 있던 값과
그때 사용한 기본값, 결정 및 후속 실행의 연결을 보존해야 한다. 이는 현재 요구에
대한 자료이며 독립 사용자의 도입이나 절감 성과는 아직 확인 대상이다.

생태계 작업과는 기존 고정 버전으로 표현 가능한 오프라인 정책부터 검토하기로 했다.
과거 기록 읽기, 보존된 당시 정책 평가, 현재 정책의 새 평가는 각각의 동작으로
설명한다. 현재 `package replay`는 새 실행을 하므로 이력 조회 안내에 대신 넣지 않는다.
당시 정책을 찾지 못하면 그 누락을 남기고 현재 규칙으로 과거 기록을 덮어쓰지 않는다.
새 평가에는 새 기록을 만들고 앞선 요청·정책·결정의 기원과 연결한다. 보존 자료의
내용 일치와 외부 권한·사실의 진위는 각각 필요한 출처로 판단한다.

검증 결과의 재사용 범위는 명시된 동일 입력 계약으로 정한다. 외부 적용 시점에는
현재 정책·권한·리소스 버전을 확인해야 한다. 예를 들어 v1 리소스의 과거 평가가
성공해도 v2에 쓰는 권한이 되지는 않는다. 후속 외부 연동은 이 확인과 변경을
조건부 쓰기나 CAS로 결합하는 경계를 설계한다. 현재 세 파일 재사용 정책과 순수
측정 설명 예제가 외부 효과까지 보장하는 것으로 해석하지 않는다.

### 관측으로 전략을 고치는 방법

[#1660](https://github.com/kimjooyoon/meta-ontology-go/pull/1660)·
[#1661](https://github.com/kimjooyoon/meta-ontology-go/pull/1661)의 진단 안내와
[측정 메타데이터 예제](../../examples/measurement-metadata/README.md)는
[#1662](https://github.com/kimjooyoon/meta-ontology-go/pull/1662)로 `main`에 반영됐다.
예제의 Gooo 조건은 명시된 측정 범위·단위·환경을 비교하고, 알려진 차이와 빠진 값을
보존한다. 수치가 좋아졌다는 결론에는 실제 값과 비교 설계가 추가로 필요하다.

같은 `d13f7bc` 트리를 검사한 원본 PR #1661과 승격 #1662의 race 명령은 각각
15분 44초와 23분 38초였다. [첫 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39032624595)과
[승격 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39036235050)은
서로 다른 실행 문맥이며 둘 다 시간 예측을 사용할 수 없었다. 같은 코드만으로
소요 시간을 고정할 수 없다는 관측이다. 두 실행의 차이를 개선율로 해석하려면
runner·캐시·입력 조건을 맞춘 비교가 필요하다. 다른 정식 검사를 기다리는 단계의
시간도 실제 계산 시간과 나눠 읽는다.

이후의 비용 이력 개선은 기존 관측과 실행 기록을 사용한다. 현재 이력 경계에는
과거 비용과 중복 실행 예약이 함께 들어 있어, 캐시 공유만 넓히면 새 검사가 과거
실행으로 오인될 가능성이 있다. 이는 고정 소스 검토에서 발견한 통합 위험이며
현재 CI에서 그 오인이 발생했다는 관측은 없다. 각 기록의 역할을 먼저 구분하고,
현재 계약에서 비교 가능한 이력만 예측에 쓰는 순서로 진행한다.

자체 소형 모델은 원문이 허용한 유한 선택을 정렬하는 역할로 발전시킨다. 자연어
요청의 표현과 Gooo 의미 입력, 선택과 실제 실행은 각각의 출처를 남긴다. 모델이
없는 순서도 계속 사용할 수 있어야 한다. 모델별 문서의 버전·사례 집합·단위가
다르므로 정확도나 작은 가중치 크기를 전체 실행 성능으로 합치지 않는다.
다음 모델 변경은 동일한 프로그램 계열을 학습·평가 양쪽에 넣지 않은 사례에서
고정 순서와 비교한다. 이번 진단·출력·문서 작업에서 새 모델 실행은 하지 않았다.

### 실행 도구 조건도 Gooo 계약에 쓰기

재사용 예제의 개발 계약 `v4`는 `execution-tool-inputs`를 원문에 선언한다.
Go 어댑터는 실제 선택한 실행 파일·버전·환경을 관찰하고, Gooo 정책은 출처가
빠진 과거 기록을 `UNKNOWN`으로 분류한다. 선언 목록에서도 이 조건을 빠뜨리면
현재 계약을 읽는 단계에서 오류가 난다. 패키지 입력과 실행 도구 입력을 함께
선언하므로 에이전트가 원문에서 필요한 관찰을 찾을 수 있다.

기존 계약 `v1`~`v3`과 과거 실행 기록은 당시의 범위를 유지한다. 현재 구현에
자동으로 승격하지 않으며, SDK 전체·전이 의존성·외부 효과의 출처 연결은 남아 있다.
이 계약 변경은 개발 소스이며 공개 `0.6.36`에는 포함되지 않는다.

부분 테스트 재사용도 개발 계약 `v2`에서 같은 실행 도구 관찰을 요구한다.
각 테스트 영역이 계약을 선언하고, 빌드와 테스트는 관찰한 실행 파일과 환경을
공유한다. 선택 직전의 관찰이 이전 기록과 다르면 Gooo가 재사용을 보류한다.
도구 정보가 없던 과거 기록은 `UNKNOWN`과 필요한 출처를 반환한다.
현재 고정 사례는 두 테스트 영역이며, 실행 중 모든 파일의 원자적 스냅샷이나
임의 프로젝트의 의존성 폐쇄를 보장하지 않는다.

## GitHub Linguist 준비

[Linguist 공식 기여 안내](https://github.com/github-linguist/linguist/blob/main/CONTRIBUTING.md#adding-a-language)를
2026-10-13에 확인했다. 새 언어에는 언어 정의, 호환되는 강조 문법과 라이선스,
대표적인 실제 코드 샘플, ID 생성, GitHub 사용 근거가 필요하다.
[사용량 기준](https://github.com/github-linguist/linguist/blob/main/CONTRIBUTING.md#language-extension-and-filename-usage-requirements)은
보통 확장자에 대해 최근 1년 내 색인된 파일 2,000개 이상이며 fork를 제외한다.
사용자와 저장소의 분산도 살피고, 특정 작성자가 차지하는 비중이 높으면 제외해 평가할 수 있다.

현재 Gooo의 외부 색인 파일 수와 독립 사용자 수는 이 작업에서 측정하지 않았다.
TextMate 문법은 이미 있으므로 실제 문법과의 일치, 라이선스, 대표 샘플의 원본과
이용 조건을 정리하면서 준비한다. 사용량을 확인한 뒤 등록 PR 시점을 판단한다.
샘플이나 저장소의 수를 인위적으로 늘려 이 기준을 채우는 작업은 하지 않는다.

`.gooo`를 `linguist-language=Go`로 덮어쓰면 GitHub 통계와 강조가 Go 기준이 된다.
현재 컴파일러 저장소의 `.gitattributes`에는 이 설정을 추가하지 않는다.
Gooo를 작성하는 편집기 경험은 기존 `source.gooo` 문법으로 제공한다.

우선순위는 작은 도구의 완성, 재사용, 변경 가능한 코드, 출처 연결이다.
그 사용이 쌓이는 과정에서 언어 등록을 준비한다.
