# 미해결 연산의 출처

등록되지 않은 연산이 들어왔을 때도 요청한 ID와 출처를 남기는 작업을 진행하고
있습니다. `internal/meta/metricprogram/unresolvedpolicy/policy.gooo`의 세 활동이
해상도, 이유, 다음 단계의 이름을 정합니다. Go는 받은 요청과 원본 스냅샷을 담아
전달합니다.

| 등록 여부 | 출처 기록 | 해상도 | 다음 단계 |
| --- | --- | --- | --- |
| 등록됨 | 있음 | `exact_operation` | `CONTINUE_SOURCE_OPERATION` |
| 미등록 | 있음 | `invariant_only` | `DECLARE_SOURCE_OPERATION` |
| 등록됨 | 빠짐 | `invariant_only` | `CAPTURE_OPERATION_ORIGIN` |
| 미등록 | 빠짐 | `invariant_only` | `CAPTURE_OPERATION_ORIGIN` |

출처 기록은 저장한 문맥의 존재를 뜻합니다. 실제 원본과의 일치는 독립적인 소비
단계에서 확인할 사항입니다. 반환되는 거부 기록은 요청한 연산과 지표 ID, 저장소와
커밋, 레지스트리 원본·투영의 경로와 다이제스트, 판단 규칙의 원본을 함께 담습니다.
프로그램 구성기는 실제로 받은 전략·검증 입력의 바이트 해시도 각각 기록합니다.
준비도 점수나 저장소 쓰기·승격 권한은 부여하지 않습니다.

## 현재 구현 범위

규칙 세 개를 Gooo에서 Go로 생성했고, 원본과 생성 묶음의 연결을 검증합니다.
새 로컬 검사 7개는 네 입력 조합, 생성 코드의 원본 일치, 오류를 감싸고 JSON으로
옮긴 뒤에도 요청과 권한 경계가 유지되는지를 확인했습니다. 분류는 정해진 분기로
실행하며 외부 모델을 호출하지 않습니다.

프로그램 구성기의 미등록 연산 거부 지점에 연결했습니다. 기존 등록 연산의
상태·증거·증명 계열 오류는 각자 기존 거부 경로를 유지합니다.
기존 컴파일러의 등록 제약과 16개 반례 집합은 유지합니다. 이 단계로 이슈 #791을
완료 처리하지 않습니다.

`metric-meta-program`은 이 거부 기록을 표준 출력의 JSON으로 전달합니다. 실패 종료와
오류 메시지를 유지하며 성공한 프로그램 산출물은 만들지 않습니다. 새 명령 경계
검사 5개는 영문·한글 ID, 입력 서식, 부분 출력과 출력 오류를 확인했습니다.
앞서 끝난 로컬 검사 단계들은 재실행하지 않았습니다. [원래 CI](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/38872091272)의 race 로그에서
최종 소스의 전체 64개 사례를 확인했습니다. 소스는
`9c1b231522b01a1dbcb414591c184967f6f7a745`이고, dev 병합은
`6963179807ed305c09478090d8eb54e825cdbb40`입니다.

## 소비자가 원본을 확인하는 방법

`metricprogram/verify.VerifyOperationRefusal`은 요청의 원본 바이트, 저장소 이름과
커밋, 실제 저장소 파일을 받습니다. 입력 해시와 연산·지표 ID를 다시 구성하고,
레지스트리와 판단 규칙의 원본·생성 묶음을 대조합니다. 생산자의 분류 함수를 다시
호출하는 대신 독립된 호환 기준으로 해상도·이유·다음 단계를 비교합니다.

검증 결과는 `VERIFIED_SOURCE_ORIGIN_REFUSAL`입니다. 이는 이 요청의 출처가
주어진 입력과 저장소 내용에 맞는다는 뜻입니다. 상위 작업의 실행 검증은
`UNASSESSED`로 남고, 준비도·쓰기·승격 권한은 모두 거짓입니다. 저장소 커밋은
호출자가 지정한 문맥이며 이 함수가 Git의 HEAD를 조회하지는 않습니다.
소스에 선언된 연산을 소비자가 아직 지원하지 못하면
`COMPATIBILITY_KERNEL_UNSUPPORTED`로 구분합니다.

## 상위 입력에 낯선 연산이 들어오면

기존 반례 16개와 별도로, 원래 CI의 상위 입력 원장에 새로운 연산을 추가하는
사례를 연결했고, [원래 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/38872091280)에서 확인했습니다.
그 원장에서 예상 작업 집합을 먼저 구한 뒤 실제 전략 생성과
독립 재구성, 프로그램 구성, 거부 기록의 소비를 이어갑니다. 예상 집합은 원래
집합에 새 연산 한 개를 더한 값이며, 기존 항목과 두 종료 작업을 보존합니다.

이 입력은 원본 실행 결과물에서 만든 공격적 변형입니다. 다시 계산한 해시가
상위 작업의 실제 실행을 증명하지는 않습니다. 이 사례는 실행 가능한 프로그램이나
준비도 기록을 만들지 않습니다. 전체 작업의 수행률은 관찰하지 않아 `coverage_bps`를
`null`로 남깁니다. 기존 16개 사례의 분모도 바꾸지 않습니다.

새 소비자 경계 25개, 상위 입력과 관찰 형식 13개, 예상 집합의 개수 경계 3개를
추가로 확인했습니다. 각 로컬 단계는 당시 소스의 관찰로 보관합니다. 후속 개수
검사를 추가한 뒤 먼저 끝난 단계를 재실행하지 않았습니다.

새 Gooo 원본은 기존 `RegisterSyntaxCapability`로 등록했습니다. 생성된 9개
파일을 그대로 적용하고 v90 기록을 보존한 채 v91을 추가했습니다. 읽기 전용
목록에서 원본 147개, 미등록·누락 0개를 확인했습니다. 이것은 원본 등록 상태이며
언어 전체의 완성을 뜻하지 않습니다.

## 남은 범위

규칙이나 레지스트리 자체를 읽을 수 없을 때는 일반 거부 오류를 반환합니다.
확인된 미등록 상태와 구분되는 구조화된 원본 이용 불가 기록은 후속 범위입니다.
일부를 실행한 프로그램, 원래 예상 집합의 100% 관찰과 추가 미지 항목이 함께 있는
경우의 정량 의미, 상위 원장의 실제 실행 권한 검증도 이번 진단 기록만으로 해결되지
않습니다. 이슈 #791은 열어 둡니다.
