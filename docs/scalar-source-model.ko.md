# Gooo가 선언한 선택과 조건을 모델에 연결하기

Gooo의 소스는 만들 수 있는 경로와 지켜야 하는 조건을 선언한다. 작은 결정 모델은
이 경로의 시도 순서를 고른다. 후보를 조립한 뒤 실제 조건을 평가하는 책임은
컴파일러의 기존 구성·평가 흐름이 가진다.

이 변경을 포함한 개발 소스는 SDK `v0.2.51-experimental`의
`gooo/scalar-criteria-model/v1` 아티팩트를 읽는다. 대상은 `Integer -> Integer` 활동의
이진 선택지 1~6개와 고정 Boolean 조건식 1~8개다. 조건식에는 원래 입력과 후보 결과의
Integer 역할 두 개가 들어간다. 보조 활동의 소스 그래프도 기존 흐름에서 읽는다.

## 한 요청의 진행

1. 소스의 타입, 후보 경로, 고정 조건과 시도 예산을 준비한다.
2. 모델을 연결하면 소스의 선택지와 조건식 그래프로 수치 특징을 만든다.
3. 요청의 scratch 배열에서 모델을 한 번 호출해 최대 64개 조합의 순서를 받는다.
4. 선언한 예산만큼 전체 후보를 조립하고, 소스가 가진 입력과 조건으로 평가한다.
5. 선택한 Gooo 소스, 생성 코드와 실제 조건 결과를 함께 기록한다.

이미 명시한 관찰 흐름이 순서를 확정한 경우에는 그 결과를 사용하고 모델 호출은 0이다.
모델이 없거나 소스가 수치 입력 프로필에 들어가지 못하면 결정론적 순서를 유지한다.
연결한 모델 파일 자체가 유효하지 않으면 로딩 오류를 반환한다.

`body-codegen --path-model`과 구성 흐름의 `--model`이 같은 보유 모델을 사용한다.
모델은 생성자에서 한 번 읽고, 요청마다 입력·scratch·순위·관찰을 따로 둔다.
이 경로는 요청을 기다리는 큐, 네트워크 모델 호출과 가중치 변경을 만들지 않는다.
후보 구성은 기존 취소와 시간 제한을 따른다. 대기 중인 비동기 작업을 추가하지 않았다.

## 선택 입력과 실제 평가

수치 특징에는 허용된 선택지의 구조·의도와 고정 조건식 그래프가 들어간다.
유한 평가 입력, 기대 결과, 별도 평가 입력과 관찰 답은 수치 특징에서 제외한다.
소스·계약·후보 계획 해시는 어떤 선언에서 나온 입력인지 연결하는 메타데이터다.
ID와 선택지 이름도 수치 행과 구분해 보존한다.

`body-context --model`은 같은 입력 준비 함수를 사용해 `scalar_features`와 호환 상태를
내보낸다. `READY_FOR_RANKING`은 해당 모델 계약으로 입력을 준비한 상태다.
이 명령의 모델 예측과 후보 평가는 각각 0회다. `--include-plan`으로 출력하는
유한 선언은 모델의 수치 특징과 별도 필드에 남는다.

순위에는 소스 입력·계획·실제 수치 행·모델 메타데이터·가중치 해시가 붙는다.
점수의 softmax와 선택지 주변 확률은 같은 조합 분포에서 계산한다.
점수가 같은 조합은 mask 순서로 정한다. 확률의 보정 상태는 학습 모델별 평가가 필요하다.

## 저장 결과와 변경

저장한 결과를 재사용할 때에는 원래 소스의 입력을 다시 준비한다. 특징 해시,
허용 조합, 순위, 점수의 유한성, 확률 정규화와 주변 확률을 확인한 뒤
기존 구성 흐름이 후보와 조건 결과를 다시 평가한다. 모델 파일을 읽거나
새 예측을 요청하지 않는다. 기록된 점수는 당시의 관찰로 보존한다.
수치 일관성 확인은 모델의 판단 품질이나 기록의 외부 서명을 증명하지 않는다.

정책으로 작업을 이어가는 경우에는 원래 모델 관찰을 복사하고 최초 소스와 연결한다.
변경한 의존 활동의 결과는 기존 정책·시도 예산 안에서 다시 평가한다.

## 이번 개발본에서 확인한 범위

[예제](../examples/scalar-source-model/README.md)와 새 API 검사 5개와 별도 CLI 소스 관찰 1개를 사용했다.
합성 파라미터로 모델 예측 1회, 선택 입력 조건 2/2개, 별도 입력 조건 1/1개를 확인했다.
모델 없는 별도 소스는 두 후보를 시도해 조건 2/2개를 만족했다.
세 번째 소스의 보조 활동 1개와 수치 행 준비는 예측·후보 평가 0회로 확인했다.
새 JSON 결과의 재구성과 특징 해시 변경 거절도 검사했다.

이 결과는 서로 다른 분모로 기록하며 학습 모델의 정답률로 합치지 않는다.
별도 새 검사에서 서로 다른 소스 요청 네 개를 같은 모델에 동시에 보냈다.
각 요청의 예측 1회, 선택 조건 2/2개, 별도 입력 조건 1/1개와 서로 다른 기록을 확인했다.
이미 취소된 요청은 취소 오류를 반환했다. 이 PC에서 기록한 요청별 예측 시간은
16,417~20,791나노초, 준비·구성 시간은 2,569,208~7,015,709나노초였다.
이는 합성 가중치와 작은 입력 네 개의 관찰이며 장시간 병렬 부하를 평가하지 않았다.

학습은 0회이고, 실제 학습 모델의 첫 선택 품질·별도 소스 계열 일반화·CPU 사용률·
전체 프로세스 메모리와 큰 입력의 지연 시간은 후속 관찰 항목이다. 파라미터 74,504바이트와
수치 scratch 1,792바이트는 런타임 배열의 크기이며 전체 프로세스 메모리는 별도로 센다.

## 높은 점수와 조건 결과를 함께 읽기

새 예제 두 개에서는 합성 모델이 조건을 만족하지 못하는 후보에 약 95.3%의
조합 확률을 줬다. 첫 후보의 실제 조건 일치는 두 예제 모두 0/2였다.

| 소스의 시도 예산 | 선택한 결과의 조건 | 별도 입력 조건 | 구성 상태 |
| --- | --- | --- | --- |
| 2 | 다음 허용 후보에서 2/2 | 1/1 | COMPLETE_FINITE |
| 1 | 첫 후보에서 0/2 | 0/1 | PARTIAL_FINITE |

점수, 첫 후보의 관찰, 최종 선택의 관찰과 사용한 예산을 각각 남긴다.
선택 조건과 별도 입력 조건도 각자의 분모를 유지한다.

일반 `body-codegen` 출력에서는 생성 코드와 함께 stderr에 위 상태를 표시한다.
별도 새 CLI 소스는 선택 조건 0/2, 별도 조건 0/1, 시도 1/1, 모델 호출 1회를
표시했고 원본은 유지했다. 이 관찰은 생성된 Gooo 프로그램을 실행하지 않았다.
CLI와 합성 아티팩트 제작 도구는 각각 한 번 실행했으며, 만든 모델 파일은
관찰 후 삭제했다. JSON 모드는 구조화된 기존 기록을 내보낸다.
