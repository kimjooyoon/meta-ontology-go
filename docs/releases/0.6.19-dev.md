# Gooo 0.6.19 development guide

This candidate lets a tool read a Gooo workspace's declared types and activities
through the compiler. The result includes record fields, stable identities and
ordered function arguments. The ecosystem workbench uses that view to compare
two versions and run Gooo rules describing the changes.

Think of the interface as a parts list: it records which inputs fit where and
which pieces are required. Executing caller examples then shows how those pieces
behave together. Both views are useful when a program is being assembled or
changed.

The [release page](https://github.com/kimjooyoon/meta-ontology-go/releases) records
published versions and exact sources. `gooo version --build --json` identifies
the installed binary. This candidate uses Go 1.27.2 and optional decision runtime
v0.2.26-experimental.

## Read a package's declared structure

From the compiler checkout:

```sh
go build -trimpath -o .gooo ./cmd/gooo
./.gooo package interface examples/package-optional-record-flow/gooo.workspace.json
./.gooo package interface --json examples/package-optional-record-flow/gooo.workspace.json
```

The example has `example/domain` and `example/app`. The domain owns `Profile`
with optional `note`, `complete` and `count` fields. `Submit` and the importing
`Main` activity both refer to the same Profile ID. The compiler resolves imports
and types before emitting the view; reading it does not execute activity bodies.

The JSON receipt is `gooo/package-workspace-interface-receipt/v1`. Its interface
contains source digests and source-owned declarations, including:

- type/field IDs, names, aliases, field order, type IDs, requiredness and cardinality;
- record versus nominal shape, including an explicitly empty record;
- activity inputs in declaration order, including repeated types, and its output;
- the package/source that owns each declaration and a digest for the full view.

Explicit entity and field IDs survive display-name changes. Activity IDs currently
come from the compiler's namespace/name convention, so renaming an activity changes
its ID. [Package interface details](../language/package-interface.md) describe the
supported projection and failure cases.

## Let Gooo explain an API change

In an [ecosystem workbench](https://github.com/kimjooyoon/gooo-ecosystem-workbench)
checkout, point `--compiler` at the absolute path of the new compiler:

```sh
go run ./cmd/workbench api-diff --compiler /absolute/path/to/gooo \
  --before examples/api-evolution/before/gooo.workspace.json \
  --after examples/api-evolution/after/gooo.workspace.json --out out/api-diff
```

Go joins matching identities and retains the original and new values. The
workbench's `recipes/api-changes.gooo` owns classification, priority and the next
operation. Its example returns three observations:

| Change | Classification | Next operation |
| --- | --- | --- |
| Input count becomes required | `input-tightened` | Supply the required input |
| Output count becomes optional | `output-weakened` | Handle missing output |
| Optional output note is added | `field-added` | Check record construction |

These actions are data that another tool or developer can consume. Source edits
remain a separate operation. External consumers and runtime behavior require
their own observations. A body-only change can keep the same declarations; the
report retains the changed source identity and suggests observing that behavior.

Omitting `--model` uses deterministic order. Supplying the workbench's existing
compatible model lets it order the declared assembly choices. The Gooo rules and
authored examples still constrain selection. Saved execution reuses the selected
program with zero new inference. The report separates the 17 authored selection
cases (51 field checks), actual changes with no supplied correctness labels, and
the number of changes receiving a known rule. Their denominators describe those
finite observations.

## Observe native startup and execution separately

Native records include host Start time, Wait time, remaining caller deadline and
the context at Start's return. The new two-second wait budget begins after Start
succeeds. The original enclosing caller deadline includes creation, compilation,
queueing and execution, and an earlier cancellation/deadline remains in effect.
`wait_limit_ns` records the applied boundary. Observed Wait can include runtime
startup, pipe handling and cancellation cleanup as well as generated code.

Older observations keep their original budget interpretation. The
[process guide](../native-process-observations.md) retains the Windows example
where host Start consumed the old shared budget and explains the new fields.

The [0.6.18 guide](0.6.18-dev.md) covers constructing packages, executing unlabelled
inputs, preserving partial history and evaluating a saved program later.
