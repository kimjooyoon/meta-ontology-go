# Gooo 0.6.18 development guide

This candidate lets a constructed package program run on inputs that have no
expected answers. Construction still uses its declared caller examples. Later
input execution keeps actual values and failures, and a separate evaluation can
add expected answers when they become available.

The [release page](https://github.com/kimjooyoon/meta-ontology-go/releases)
records published versions and their exact source. Check `gooo version --build
--json` for the installed revision. This candidate requires Go 1.27.2 and keeps
the optional decision runtime at v0.2.26-experimental.

## Construct once, then supply actual inputs

Build from this source and use the two-package example:

```sh
go build -trimpath -o .gooo ./cmd/gooo
./.gooo package construct --json \
  --construction-cases examples/package-caller-construction/construction-cases.json \
  --inputs examples/package-caller-construction/inputs.json \
  --attempts 6 examples/package-caller-construction/gooo.workspace.json \
  > /tmp/gooo-package-observed.json
```

The input file names the entry activity and supplies ordinary values. Its four
rows produce `3`, `-10`, `-9007199254740994` and `1`. No expected answers are
added to the receipt: its decision is `OBSERVED`, and its evaluation counts stay
zero. The original construction decision and every attempted helper remain
available, including local rejections and the reached division-by-zero fault.

Plain output is convenient when another program only needs those values:

```sh
./.gooo package construct --receipt /tmp/gooo-package-observed.json \
  --inputs examples/package-caller-construction/inputs.json \
  examples/package-caller-construction/gooo.workspace.json
```

Each actual value occupies one line. An unavailable or faulted entry returns a
nonzero exit status; `--json` retains the runtime detail. Saved replay verifies
every original construction attempt against the current source, executes the
selected program on the supplied inputs, and makes zero new model calls.

If rechecking an earlier attempt fails, `result.evaluation.replay_failure` keeps
its index, execution/comparison stage and current runtime observation. The new
evaluation stays unexecuted, and the saved construction history remains intact.
Failed native processes retain their underlying error and bounded diagnostic
bytes alongside exit/timeout status and output digests.

## Evaluate the same saved program later

```sh
./.gooo package construct --json --receipt /tmp/gooo-package-observed.json \
  --cases examples/package-caller-construction/evaluation-cases.json \
  examples/package-caller-construction/gooo.workspace.json
```

This produces a separate evaluation of the four labelled rows. The program and
construction history stay unchanged. Supply exactly one of `--inputs` or
`--cases`: each command binds the supplied file to its own digest.

Five construction attempts preserve a partial choice. It can still run on
actual inputs; this example then produces `3`, `-20`, `9007199254740995` and `1`.
Those values describe what ran. They do not imply that the caller's obligations
were satisfied. The public [ecosystem workbench](https://github.com/kimjooyoon/gooo-ecosystem-workbench/tree/a0152116bba110d6ef4f6a7404d8d954ff7ef8d8)
uses Gooo rules to distinguish missing evaluation answers, exhausted budgets
and faults during unscored execution. Its
[retained observations](https://github.com/kimjooyoon/gooo-ecosystem-workbench/tree/a0152116bba110d6ef4f6a7404d8d954ff7ef8d8/publication/package-input-diagnosis-20261009)
include the original compiler receipts and the resulting diagnoses.

## Optional model and finite evidence

Without a model, construction uses deterministic source order. An existing
compatible model can rank declared record choices through `--model`; saved
replay requires no model. The own graph QAT experiment retained the same program
after 41 attempts, compared with 48 in fixed order, for one related three-package
example. Its later unscored inputs and labelled evaluation made no new
predictions. This single related example does not measure transfer to new tasks.

## Native release profile

Each platform candidate runs eight JSON observations: partial construction,
complete construction, scored replay, partial input execution, fresh input
execution, input execution from a scored receipt, repeated input execution and
later labelled evaluation. A ninth command checks plain values exactly.

The witness checks original package sources, selected code, saved history,
input digests, process completion and integers above 2^53. Input-only receipts
must retain zero evaluation counts and omit expected/pass labels. The test's
known-value comparisons remain outside those user receipts. These checks have
their own finite scope; the structural release profile remains 26 cases.
