# PROV graph query model

Status: research proposal. This document does not add query syntax to `.gooo` or
change the semantic implementation. It defines a small, standard-library-only
query boundary that can be implemented after the current graph and provenance
contracts are stable.

## 1. Design decision

The query layer is a read projection over the semantic graph. It must not become a
second business source of truth, and it must not silently promote an observation
from Go analysis to business meaning.

| Concept | Meaning | Default query behavior |
| --- | --- | --- |
| deterministic fact | Source-backed, type-valid triple | included |
| candidate fact | Evidence-backed observation without authority | excluded |
| derived fact | Rule result with support facts | included when `derive` is enabled |
| inverse view | A read-only direction change such as `used` to `usedBy` | available without storing a new fact |
| zoom view | Bounded resolution/perspective projection | available only through an explicit view adapter |

`derived` is an origin, not a third replacement for the existing deterministic /
candidate status. A rule-derived result may be deterministic as a computation, but
it is still not canonical business intent. It carries a rule identifier and a
proof of support and is materialized only for the query result or a reconstructable
cache.

This separation follows the repository's authority boundary: `.gooo` declarations
and explicit assertions own business intent; the normalized IR owns the current
semantic graph; observations retain their evidence; and search is a projection.

## 2. Graph and fact semantics

The canonical graph uses stable semantic IDs. Names and aliases are lookup aids and
must always be namespace-qualified. A query that uses an unqualified display name
is invalid rather than a best-effort cross-namespace search.

The initial PROV-inspired relation directions are:

| Canonical predicate | Subject | Object | Query-local inverse |
| --- | --- | --- | --- |
| `used` | Activity | Entity | `usedBy` |
| `wasGeneratedBy` | Entity | Activity | `generated` |
| `wasDerivedFrom` | Entity | Entity | `derived` |
| `wasAssociatedWith` | Activity | Agent | `associated` |

The canonical triple is always stored in this direction. An inverse is an indexed
or computed query view and never changes the graph fingerprint. When a result is
serialized as PROV, the adapter should use the corresponding PROV property rather
than treating a local alias as a new ontology predicate.

Returned matches carry an origin: `declared` for facts lowered from `.gooo` or an
assertion, `observed` for candidate facts, `derived` for named-rule results, and
`inverse` for a canonical edge reversed only for this query.

`declared` and `inverse` results can share the same deterministic status. `derived`
results must expose their derivation trace. `observed` results remain candidates
even when a query happens to find them. A deterministic fact with the same triple
shadows a candidate for normal graph reads, while the candidate observation remains
part of append-only evidence.

The engine must not infer `wasDerivedFrom` merely because one Activity used an
Entity generated by another Activity. PROV describes derivation as an Entity-to-
Entity relation, and the conditions for a domain derivation are not supplied by
the generic usage pattern. A `.gooo` assertion or a trusted rule must state that
meaning explicitly.

## 3. Query model

The smallest useful query is a set of triple patterns evaluated against a selected
fact universe. A term is either a stable ID or a variable beginning with `?`.

```text
Pattern  = Term Predicate Term
Term     = stable-id | ?variable
```

The proposed Go boundary is intentionally small and parser-neutral. The names are
illustrative; they are not current exported APIs.

```go
type Query struct {
	Focus       []ID
	Patterns    []Pattern
	Rules       []Rule
	Perspective Perspective
	Resolution  Resolution
	Include     IncludeSet // deterministic, derived, candidate
	Derive      bool
	MaxDepth    int
	MaxFacts    int
}

type Pattern struct {
	Subject   Term
	Predicate Predicate
	Object    Term
}

type Match struct {
	Fact   FactKey
	Status FactStatus
	Origin Origin
	Proof  []Support
}

type Result struct {
	Bindings []Binding
	Matches  []Match
}

func (e Engine) Query(ctx context.Context, query Query) (Result, error)
func (r Result) Trace(fact FactKey) []Support
```

The implementation can use only `context`, ordinary Go maps, slices, and `sort`.
A compiled query may index facts by subject, predicate,
and object; the index is a cache, never an authority. A query must:

1. normalize IDs, predicates, variables, limits, and the query text;
2. select the fact universe before evaluating rules;
3. evaluate patterns with set semantics;
4. apply allowed rules to a fixed point or the configured bound;
5. attach origin and support evidence to every returned match;
6. sort bindings and matches by stable canonical keys before returning them.

The default universe is deterministic canonical facts. `include derived` adds
rule results. `include candidate` adds candidates as visibly marked results, but
does not make them rule inputs. A separate, explicit `derive from candidates`
option may be considered later; its outputs must be tainted as candidate-dependent
and must never be accepted as deterministic semantic changes.

The first rule evaluator should support positive conjunctions only. Every variable
in a rule head must occur in a positive body atom, and every predicate must have a
declared type signature. Negation, aggregation, unbounded path search, and
side-effecting predicates are out of scope for the first version. A rule program
must have a stable canonical form and hash so a derived-result cache can be keyed
by:

```text
semantic IR hash + rule program hash + canonical query + view configuration
```

The cache may be discarded and rebuilt. It must not replace append-only provenance
or durable evidence.

## 4. Rules and derived facts

Rules are Datalog-like positive implications over named predicates. The syntax below
is a proposal for query files, not an addition to the business DSL.

```text
rule usedBy(entity, activity) <=
    used(activity, entity)

rule contextDependsOn(owner, dependency) <=
    belongsTo(activity, owner),
    used(activity, entity),
    belongsTo(entity, dependency),
    owner != dependency
```

`usedBy` is a convenient inverse view. `contextDependsOn` is an application query
predicate, not a new PROV assertion. `belongsTo` must come from an explicit domain
fact or an approved projection; a name-prefix convention is insufficient.

Each derived match has a proof record conceptually equivalent to:

```text
derived fact: billing://context/billing contextDependsOn billing://context/ordering
rule:         context-depends-on/v1
supports:     billing://activity/pay-order belongsTo billing://context/billing
              billing://activity/pay-order used billing://entity/order
              billing://entity/order belongsTo billing://context/ordering
```

The evaluator uses set semantics and monotonic positive rules. A recursive program
stops when no new fact keys are produced or a configured limit is reached. The
result must report a limit error rather than returning a partial result as if it
were complete. Multiple proofs for one triple are retained in deterministic order
up to a configured proof limit; the first proof must not depend on map iteration
order.

A rule cannot promote a candidate, mutate the canonical graph, or manufacture a
source span. Rule output is query evidence. Promotion remains a separate,
source-backed reconciliation operation governed by the semantic layer.

## 5. Small query DSL

The smallest readable surface should be enough for search, inverse traversal, and a
bounded derived relation. A proposed query block is:

```text
query billing_dependencies {
    focus billing://context/billing
    match ?activity used ?entity
    derive contextDependsOn(?owner, ?dependency) <=
        belongsTo(?activity, ?owner),
        used(?activity, ?entity),
        belongsTo(?entity, ?dependency),
        ?owner != ?dependency
    view business context
    include deterministic derived
    limit 50
}
```

The minimum grammar is:

```text
query Name {
    focus ID*
    match Term Predicate Term
    derive Predicate(Variable*) <= Atom (, Atom)*
    view Perspective Resolution
    include deterministic|derived|candidate|inverse*
    limit Integer
}
```

`match` may be repeated. `derive`, `view`, and `include` are optional. A query
without `limit` receives a safe engine default; an explicit zero means no rows.
The parser should reject duplicate options, unsafe variables, unknown predicates,
unknown perspectives/resolutions, and IDs outside the namespace rules.

The textual and programmatic forms must have identical canonical plans and result
ordering, making fixtures useful for both a future CLI and Go-level conformance
tests.

## 6. Zoom-in and zoom-out

Zoom is a bounded view operation over the same semantic identity graph. It is not a
transitive closure switch and it does not create facts. A view has two independent
coordinates:

| Coordinate | Initial vocabulary |
| --- | --- |
| perspective | business, architecture, provenance, security, verification, runtime |
| resolution | system, context, activity, relation, code, execution, evidence |

The proposed request shape is:

```go
type ZoomRequest struct {
	Focus      []ID
	Perspective Perspective
	From, To   Resolution
	Direction  Direction // in, out, both
	MaxHops    int
	Include    IncludeSet
}

func (e Engine) Zoom(ctx context.Context, request ZoomRequest) (Result, error)
```

Zoom adapters must declare the edges they use. Typical paths are:

```text
business capability -> bounded context -> activity -> relation
relation -> activity -> Go symbol/source span -> execution observation
evidence -> verification activity -> generated source -> semantic declaration
```

The links between these resolutions are projection facts such as `contains`,
`implements`, `sourceSpan`, `executes`, or `evidenceFor`. They need an explicit
source, stable IDs, and a deterministic adapter. They are not silently substituted
for PROV predicates. If a link is only suggested by a Go name or text similarity,
the adapter returns it as a candidate at most.

`zoom in` follows an adapter toward a finer resolution; `zoom out` follows its
declared inverse toward a coarser resolution. Both directions must preserve the
focus identity and obey `MaxHops`, `MaxFacts`, and the selected candidate policy.
The default result should show the immediate neighborhood, not an unbounded graph
walk. A caller asking for a path must receive the edge sequence and origin for each
step so that a high-level answer can be traced back to a source span or rule.

For example, a provenance view of `billing://activity/pay-order` can show its
`used` and `wasGeneratedBy` neighborhood, while an implementation view can follow
the source map to the handwritten slot. These are two projections of the same
identity, not two competing identities.

## 7. Proposed conformance query fixture

The fixture should be proposed as a future `examples/conformance/query.fixture`
alongside the existing `.gooo` examples. It is shown here only; this research PR
does not add the file or a query implementation.

The source declarations are intentionally compact:

```gooo
package billing
namespace billing

entity Order id "billing://entity/order"
entity Payment id "billing://entity/payment"
entity Receipt id "billing://entity/receipt"

activity PayOrder(Order) -> Payment
activity IssueReceipt(Payment) -> Receipt
```

The query fixture adds explicit, namespace-safe view facts and one unresolved
observation:

```text
fixture billing-query/v1

fact billing://activity/pay-order belongsTo billing://context/billing
fact billing://entity/order belongsTo billing://context/ordering
candidate billing://entity/payment wasDerivedFrom billing://entity/order
    reason "Go implementation reads Order fields; no semantic assertion"

rule contextDependsOn(owner, dependency) <=
    belongsTo(activity, owner),
    used(activity, entity),
    belongsTo(entity, dependency),
    owner != dependency

query inputs {
    focus billing://activity/pay-order
    match ?activity used ?entity
    include deterministic
    limit 10
}

query inverse_inputs {
    focus billing://entity/order
    match ?entity usedBy ?activity
    include deterministic inverse
    limit 10
}

query context_dependencies {
    derive contextDependsOn(?owner, ?dependency)
    include deterministic derived
    limit 10
}

query unresolved_derivation {
    focus billing://entity/payment
    match ?entity wasDerivedFrom ?source
    include candidate
    limit 10
}
```

The expected canonical facts from the two activity signatures are:

```text
billing://activity/pay-order used billing://entity/order
billing://entity/payment wasGeneratedBy billing://activity/pay-order
billing://activity/issue-receipt used billing://entity/payment
billing://entity/receipt wasGeneratedBy billing://activity/issue-receipt
```

The expected query assertions are:

| Query | Expected result |
| --- | --- |
| `inputs` | one deterministic declared match: `pay-order used order` |
| `inverse_inputs` | one deterministic inverse match: `order usedBy pay-order`; canonical graph hash unchanged |
| `context_dependencies` | One derived `billing contextDependsOn ordering` match with rule ID and three supports |
| `unresolved_derivation` | One candidate `payment wasDerivedFrom order`; excluded from default closure |

The fixture must assert more than row counts:

1. IDs from another namespace do not match the billing focus.
2. Identical input, rule set, and query produce byte-for-byte identical ordered
   results across repeated runs.
3. Reversing `used` is a query projection and does not add a canonical fact.
4. The derived dependency has a stable rule ID and a complete support trace.
5. Candidate inclusion changes only the returned view; it does not change the IR
   semantic fingerprint or the derived closure.
6. A candidate with the same triple as a deterministic fact is shadowed in normal
   reads, while its observation remains available to evidence inspection.
7. A missing source span, unsafe rule, invalid PROV type signature, or exceeded
   limit is a deterministic conformance error rather than an empty result.

## 8. Implementation sequence and non-goals

The recommended implementation order is: (1) a snapshot-based query boundary with
exact matching, inverse views, namespace checks, and stable ordering; (2) bounded
positive rules with proof traces; (3) recursive monotonic rules with fixed-point
limits; (4) zoom adapters for source maps, evidence, and runtime observations; and
(5) CLI/query-file conformance using the fixture in this document.

This proposal intentionally does not choose RDF storage, a graph database, a
full-SPARQL implementation, unrestricted Datalog, fuzzy text search, or automatic
candidate promotion. A text index may later accelerate name search, but the
semantic query result must still be explained by stable IDs, canonical facts, rules,
and evidence.
