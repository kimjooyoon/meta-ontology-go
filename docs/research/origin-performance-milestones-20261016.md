# 출처 조회와 보조 보기의 성능 계약

2026-10-16. [구현 입구](../language/advisory-origin-views.ko.md)와 새 로컬 관찰을
기준으로 정리합니다. 목표는 유용한 출처를 유지하면서 원래 프로그램과 에이전트의
작업을 방해하지 않는 것입니다. 지표는 적용 여부를 결정하기 위한 계약입니다.

## 후보를 좁힌 기준

평균 압축률만 보면 작은 파일의 블록 비용을 놓칩니다. 평균 지연만 보면 꼬리 지연을
놓칩니다. 선택 횟수는 실제 독해나 만족을 설명하지 못합니다. 원본 출처 수를 줄여
시간·용량을 개선한 결과는 비교 가능한 개선으로 세지 않습니다. 이 때문에 의미
보존, 조회 지연, 실제 보관 비용 세 가지를 우선 지표로 두었습니다.

| 우선 지표 | 정의·데이터 원천 | 판단 |
| --- | --- | --- |
| 의미가 달라진 사례 수 | 같은 원문·입력·도구의 짝에서 힌트 유무/오류로 원본 보고서·의미 IR·생성물·기존 종료 상태가 달라진 수. 각 출력의 원래 바이트 해시와 관찰 범위를 보관합니다. | 0이 원칙입니다. 현재 로컬 확인은 원본 출처 보고서와 CLI 상태에 한정됩니다. |
| 출처 조회 p95 지연 | 동일한 노드·간선·입력 영역에서 조회 진입부터 canonical 보고서 완료까지의 시간 분포. 냉간·예열, 도구·기계·소스·표본 수를 붙입니다. | 실측 기준선 뒤 SLO를 정합니다. 보기 직렬화 시간과 저장 시간을 섞지 않습니다. |
| 복원 가능한 원문 대비 실제 저장량 | 보존 대상 전체의 실제 디스크 할당 바이트 / 바이트 복원이 확인된 원본 바이트 합. 사건·프로필·인덱스·메타데이터 범위를 함께 명시합니다. | 모든 원본이 유지되는 조건에서 개선을 판단합니다. 작은 파일 수와 중복 프로필 보관도 비용입니다. |

고정 가중치로 합친 종합 점수는 두지 않습니다. 속도 개선이 출처 손실을 가릴 수
있기 때문입니다. 구현 변경의 원래 CI에서 의미 보존을 확인하고, 성능 측정은
고정된 새 측정 집합의 출처를 따로 남깁니다.

## 진단 지표와 보존 조건

- **힌트의 추가 지연:** 같은 조건의 짝마다 `표시 포함 시간 - 기본 시간`을 구한
  분포의 p95·p99. 두 독립 분포의 분위수 차이와 구별합니다. 음수도 남깁니다.
  렌더링의 CPU·출력 바이트 비용은 측정 대상이며 0으로 가정하지 않습니다.
- **대기 경계:** 컴파일·생성·실행 경로가 힌트 저장·잠금·큐를 기다리는 경로 수는
  0이어야 합니다. 현재 경로는 저장을 호출하지 않습니다. 별도 저장 명령은 busy를
  바로 반환합니다. 이 구조 확인을 시간 실측으로 바꾸어 설명하지 않습니다.
- **메모리:** 요청당 할당 수/바이트, 처리 노드당 바이트, 최대 RSS를 원본 규모와
  함께 기록합니다. `sizeof`는 참조된 문자열·슬라이스 저장 공간을 제외합니다.
  코드의 작은 구조체 크기로 전체 RSS 개선을 주장하지 않습니다.
- **보관:** `저장된 논리적 바이트 / 원래 바이트`를 압축 진단으로 둡니다.
  디스크 할당량과 별개입니다. 복원 바이트 해시 일치율은 해당 전체 보관 집합에서
  100%가 수용 조건이며, 읽지 못한 원본을 분모에서 빼지 않습니다.
- **보조 실패:** 잘못된 힌트·낡은 스냅샷·busy·아카이브 읽기 실패를 코드별로
  셉니다. 호스트가 기록하지 않은 제안은 수용된 사건으로 세지 않습니다. 외부
  큐를 붙인다면 큐 상한·만료·드롭 수·재시도 수를 별도로 기록해야 합니다.

## 현재 관찰과 한계

[원래 로그 해시와 단계별 사례](../observations/advisory-origin-views/observations.json)를
보관합니다. 로컬 소스는 개발 도중 바뀌었고 각 단계의 성공을 최종 합친 소스의
검증으로 합산하지 않습니다. 공개 후 고정된 PR head의 원래 CI가 최종 소스의
판단 근거입니다.

| 관찰 대상 | 원래 논리적 바이트 | 포장 후 논리적 바이트 | 복원 확인 |
| --- | ---: | ---: | ---: |
| 서로 다른 선택 사건 40개 | 45,520 | 25,230 | 40/40 원본 바이트 일치 |
| 그 단계의 현재 프로필 1개 | 18,660 | 891 | 크기·원본 해시 확인 |

이 수치는 생성한 선택 기록 집합의 결과입니다. 보관 파일의 고정 헤더를 포함하고,
파일시스템 메타데이터와 과거 프로필 아카이브 전체는 포함하지 않습니다.
모든 저장량이나 저장소 전체의 절감률로 일반화하지 않습니다. 이후 별도 사례에서
프로필 세 버전의 이전 해시가 보존된 바이트까지 도달하는 것을 확인했습니다.

다른 작은 원문 684바이트는 포장 후 109바이트가 됐지만, 로컬 파일시스템의 실제
할당량은 두 파일 모두 4,096바이트였습니다. 작은 사건마다 파일을 만들면 압축률이
좋아도 물리적인 용량 개선은 작을 수 있습니다.

Go 구조체의 인라인 크기는 Snapshot 120바이트, Choice 136바이트였습니다.
전체 힌트 JSON, 참조 문자열, allocator 비용과 RSS를 포함한 수치가 아닙니다.
원본 출처 조회의 p95·p99·전체 RSS 기준선은 아직 측정하지 않았습니다.

| --- | --- | --- |
| M1 보조 보기 경계 | Gooo가 보기와 이유를 정하고, JSON 힌트를 원본 보고서 뒤에 적용하는 입구 구현 | 오류·미지원 보기·범위 초과에도 canonical과 기존 상태 유지. 생성·실행 경로의 힌트 의존 0. 최종 소스의 원래 CI 확인. |
| M2 분리된 기록과 복원 | 명시적 load/record/read, 낡은 상태 거부, 원본 바이트 포장과 프로필 버전 보관 구현 | 마지막 사건 중복 수용 0, busy 대기 반복 0, 전체 선언 보관 집합의 복원 일치. 실제 디스크 비용도 계상. |
| M3 블록 아카이브 | 다음 보관 형식 설계 | 여러 사건을 불변 블록으로 묶고 인덱스로 읽기. 기존 사건·프로필의 원래 바이트·해시·기원 연결 유지. 혼합 버전·중단 복구·단일 원문 조회를 확인한 뒤 이행. |
| M4 출처 그래프 배치 | 다음 측정 후 선택 | 반복 ID/문자열 사전, 32바이트 해시, 연속 노드·간선 배열을 후보로 비교. 같은 값의 서로 다른 출처를 합치지 않기. 순서·좌표·안정 ID와 원본 복원 유지. |
| M5 성능 기준선과 SLO | 측정 전 | 같은 소스·원본 집합의 짝을 기계·도구·냉간/예열별로 기록. p95/p99·할당·RSS·논리/물리 저장량을 함께 보고 수용 예산 결정. 단일 실행에서 개선율 추정하지 않기. |

각 단계는 별도의 변경으로 판단합니다. M3~M5는 아직 구현·측정을 완료한 기능으로
설명하지 않습니다. 현재 CI 제한 시간을 줄이거나 검사를 생략해서 성능 목표를
맞추지 않습니다. 사용성이 실제로 좋아지는지를 확인하면서 필요한 범위만 확장합니다.
