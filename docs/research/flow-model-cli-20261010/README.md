# 값 흐름 모델로 대입문을 조립한 기록

2026-10-10 macOS arm64에서 공개된 자체 모델을 Gooo 컴파일러에 직접 연결했습니다.
생산자는 깨끗한 소스 `5f4c73b9801c80ed6c1ebbbbf6200eca933538fb`,
Go1.27.2, 공개 SDK0.2.33입니다. 공개 컴파일러0.6.25 설치본과는 구분되는 개발 소스입니다.

사용한 [공개 가중치](https://github.com/kimjooyoon/gooo-decision-runtime/releases/tag/v0.2.33-experimental)는
`model-flow_on.json`입니다. 파일108,446바이트, FP32 가중치37,160바이트이며,
SHA256은 `8380505096525a640a06418526530cbc7f76d3efebc2923ee04b018539c5c13f`입니다.
다시 학습하거나 가중치를 조정하지 않았습니다. 모델이 소스의 경로 순서를 고르면
Gooo가 본문을 만들고 선언 사례를 검사합니다.

## 사용한 Gooo 코드

[실행 예제](../../../examples/body-codegen/source-value-flow.gooo.fixture)는
`max(input, 10)`을 지역 변수와 대입문으로 구성합니다.

```text
let value = input
let limit = 10
let result = input
if value < limit { result = value } else { result = limit }
return result
```

소스에는 비교 순서와 분기 배치를 고르는 두 선택, 한영 의도, 출력6개·조건3개 사례와
최대4개 후보 예산이 있습니다. 위의 기본 본문은 작은 값을 반환하므로 조립 과정에서
분기를 바꿔야 합니다. 모델 입력의 뒤64칸에는 대입·복사를 따라 추적한 반환값과
비교 피연산자가 들어갑니다. 아직 실행하지 않은 후보의 정답이나 실패는 넣지 않습니다.

[실행 전 계획](protocol.txt)에 정한 여섯 명령을 한 번씩 실행했습니다.
학습에는 관련된 최대·최소 과제가 포함되므로 이 기록은 실제 연결과 사용 비용을 보여줍니다.
독립적인 문제의 정확도는 별도의 자료가 필요합니다.

## 실제 결과

| 방식 | 검사한 본문 | 모델 호출 | 추가 피드백 호출 | CLI 내부 전체 조립 |
| --- | ---: | ---: | ---: | ---: |
| 모델 없음 | 3 | 0 | 0 | 1.068333ms |
| 첫 판단만 사용 | 2 | 1 | 0 | 3.437041ms |
| 출력 피드백 허용 | 2 | 2 | 1 | 3.551709ms |

세 방식 모두 선언 출력6/6개·조건3/3개를 만족했습니다. 모델의 첫 선택은 틀렸습니다.
두 모델 실행은 후보0을 검사한 뒤 후보2로 완성했습니다. 피드백을 켜면 실제 실패
`input=-9007199254740995, expected=10, actual=-9007199254740995`를 전달했지만,
모델은 다시 후보0에 가장 높은 점수를 줬습니다. 이미 검사한 후보를 반복하지 않는
탐색기가 남은 후보2를 검사했습니다. 이번 예제에서 피드백의 추가 이득은 없었습니다.

첫 판단만 쓴 실행의 판단 시간은24.375µs였습니다. 피드백 실행은 첫 판단16.875µs,
추가 판단13.875µs였고, 두 실행의 모델 읽기는 각각2.080500ms·2.137834ms였습니다.
한 번씩의 관측이며 평균이나 백분위수가 아닙니다. 작은 본문에서는 모델을 읽는 비용이
후보 한 개를 덜 검사한 이득보다 컸습니다.

`body-context`는 판단·후보 검사0회로384개 FP32 값을 내보냈습니다.1,536바이트 해시가
실제 첫 판단의 입력과 같았고, 조건·출력 관측 구간은 비어 있었습니다. 정적 값 흐름은
분기 선택에만 들어가며, 비교 순서 선택의 해당 구간은0으로 남습니다.

## 저장한 프로그램 실행

`Main`이 조립된 `Choose`를 호출하도록 구성한 뒤 별도 실행 사례8개를 통과했습니다.
모델 사본을 지우고 저장된 구성을 재실행했을 때도8/8개를 통과했고 새 판단은0회였습니다.
큰 정수 `9007199254740993`, `±9007199254740995`, `18014398509481990`도 그대로 확인했습니다.
사례 일부는 소스·호출자 조립 사례와 겹칩니다.

| 처음 구성·실행 | 0.81초 | 0.28초 | 0.22초 | 87,932,928바이트 |

재실행은 저장된 실행 파일을 사용해 빌드를 새로 시작하지 않았습니다. CPU 합/벽시계는

RSS에는 Go 빌드와 실행 도구가 포함됩니다. 짧은 조립 명령의 최대 RSS는22,364,160바이트와
22,036,480바이트였고 외부 벽시계는0.00초로 반올림됐습니다.

## 기록 확인

원본 stdout·소스·저장 구성은 `gzip -n`으로 압축하고 해제한 바이트를 원본과 비교했습니다.
`result/`에는 생산자·입력 해시, 시각, 명령별 시간과 완료 목록을 함께 둡니다.
모델은 위의 공개 파일과 해시로 식별합니다. 실행 전 빌드 신원 조회에서 `--build`를 빠뜨린
사전 점검은 실험 시작 전에 멈췄습니다. 여섯 실행 명령을 다시 실행하지 않았습니다.

```sh
go run ./docs/research/flow-model-cli-20261010/audit \
  docs/research/flow-model-cli-20261010/result
```

이 도구는 저장 기록만 읽어 정확한 정수·입력 해시·모델 신원·호출 수·사례 결과와
저장 재실행을 재집계합니다. 모델 판단이나 프로그램 실행을 추가하지 않습니다.
첫 감사 구현은 피드백의 최고 점수 후보를2로 예상했으나 실제 기록은0이었습니다.
감사 코드를 실제 기록에 맞춰 고쳤으며 위의 불리한 결과를 그대로 보존했습니다.

컴파일러 연결의 전체 bodycodegen·CLI race 검사는37.998초·147.557초에 통과했습니다.
정적 검사와 새 예제 검사도 통과했고, 실제 소스 분해기로 확인한 변경 파일의 생성 조각은
각74줄 이하였습니다. 원격 CI와 다음 컴파일러 배포 상태는 해당 PR에서 확인합니다.
