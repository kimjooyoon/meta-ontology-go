# 같은 프로그램의 문법 프로필을 바꾸기

2026-10-16, PR #1621 소스 `9c1b231522b01a1dbcb414591c184967f6f7a745`에서
시작한 조사와 후속 구현 기록입니다. 프로필 변경의 후보 생성 입구를 구현했습니다.
여섯 필드 정책 레코드의 실제 적용과 네이티브 소비는 다음 작업입니다.

## 구체적인 문제

현재 미등록 연산의 해상도·이유·다음 단계는 Gooo 활동 세 개가 정합니다. 반환 기록의
준비도·쓰기·승격 필드는 Go 구조체의 거짓 기본값으로 채웁니다. 다음에는 이 여섯
값을 Gooo 레코드 생성식에서 함께 읽을 수 있게 하려 합니다.

```gooo
activity DescribeOperation(registered Boolean, originRecorded Boolean) -> OperationDisposition
    id "gooo://metric-operation-origin/describe-operation" computes `
return OperationDisposition{
    resolution: OperationResolution(registered, originRecorded),
    reason: OperationReason(registered, originRecorded),
    next_operation: OperationNextStep(registered, originRecorded),
    readiness_credit: false,
    repository_workspace_writes: false,
    promotion_authorized: false,
}
`
```

여기서 `OperationDisposition`은 안정 ID가 있는 문자열 필드 세 개와 불리언 필드
세 개를 가진 원본 레코드입니다. 본문 생성기는 이 표현과 고정된 세 보조 활동을
이미 처리합니다. Go 연결기는 필드의 안정 ID·타입을 대응시켜 전송합니다.

## 실제로 확인한 경계

새 검사 `TestSourceDispositionProfileFresh1751`의 서로 다른 사례 세 개가 통과했습니다.
기존에 끝난 검사나 실행 집합은 재실행하지 않았습니다.

| 진입점 | 새 레코드를 넣은 입력의 결과 |
| --- | --- |
| 일반 파서 | `parse.entity-fields-deferred` 유지 |
| 명시적인 EntityFields V3 프로필 | 구문 해석 성공 |
| 본문 생성기 | 레코드 1개·필드 6개·고정된 보조 활동 3개, 타입 검사와 결정론적 재생성 성공 |

이것은 해당 소스 입력과 세 진입점의 확인입니다. 등록된 문법 사례의 프로필 변경,
실제 프로그램 실행, 독립 소비자의 변경된 기록 수용을 확인한 결과는 아닙니다.

현재 `unresolved-operation-source-origin` 사례는 일반 프로필로 등록돼 있습니다.
레코드를 붙인 소스를 이 사례로 검사하면 기존의 프로필 거부가 발생합니다.
`RegisterSyntaxCapability`는 새 ID·경로의 사례를 추가하고 평가 집합을 한 개
늘리는 연산입니다. 이미 등록된 ID·경로를 주면 `REGISTRATION_CASE_ALREADY_EXISTS`로
거부합니다. 기존 사례의 프로필 변경을 새 사례 추가로 처리할 근거가 없습니다.

## 후속 연산의 요구사항

프로필 변경에는 별도의 명시적 요청과 원본에 연결된 후보가 필요합니다.

1. 변경 전 사례의 ID·경로·판단 계열·메타 연산을 정확히 지정합니다.
2. 변경 전·후의 프로필 ID를 지정하고, 지원하는 프로필의 실제 소스 해석을 수행합니다.
3. 사례 ID 집합과 평가 대상 수는 유지합니다. 무관한 사례와 과거 분모 기록도 보존합니다.
4. 실제 원본, 원본 스냅샷, 요청, 생성 후보를 각각 바이트 해시로 연결합니다.
5. 후보는 JSON 등록과 네이티브 등록에서 같은 사례의 프로필만 변경합니다.
   소스 단위의 위치는 구문 구조에서 찾으며 특정 파일명이나 행 번호로 고정하지 않습니다.
6. 원본의 충돌·누락·낡은 요청·모호한 사례는 서로 다른 미해결 원인으로 남깁니다.
7. 준비도·저장소 쓰기·승격 권한은 부여하지 않습니다. 후보 검증과 실제 적용을 구분합니다.
8. 원래 CI가 프로필 변경의 실제 생산·소비와 기존 원본 집합 보존을 확인해야 합니다.

기존 신규 등록 연산의 9개 산출물 계약은 유지합니다. 프로필 변경은 자체 산출물과
보존 법칙을 정의해야 합니다. 프로필 선택을 위해 일반 파서의 기본 지원 범위를
넓히는 변경도 이 작업에서 자동으로 도출되지 않습니다.

이 경로를 구현한 뒤 원래 정책 파일에 결과 레코드를 적용합니다. 레코드의 표시 이름을
바꿔도 필드 ID로 연결되고, 독립 소비자가 source-owned 여섯 값을 확인하는 것이
실제 사용 경로의 완료 조건입니다.

## 고정된 본문에 기대 결과를 붙이기

레코드 제안에 `value_case` 네 개와 `attempts "1"`을 붙이는 과정에서 별도 제약을
재현했습니다. 기대 결과가 있어도 선택지가 없으면 `assembly requires 1..16 choices`로
거부했습니다. 고정된 본문을 검사하려고 불필요한 선택지를 만들 필요는 없습니다.

후속 개발의 명세 검증기는 선택지 없는 고정 레코드 본문에 유한한 `value_case`를
허용합니다. Integer 경로 사례·관찰·탐색·선택 상태와 혼합하지 않습니다. 기존 사례 수
1..128, 시도 예산 1..64와 타입·홀드아웃 검사는 유지합니다. 후보는 원래 본문 하나이고,
모델 순위를 요청하지 않습니다. 기존 선택지 경로의 오류 메시지와 검사 우선순위도
유지합니다.

새로 실패했던 `TestDispositionFiniteSourceFresh1753`만 수정 뒤 다시 실행했습니다.
불리언 입력 두 개의 네 조합에서 여섯 필드, 총 24개 필드값이 맞았습니다. 이것은
제안한 유한 입력 영역의 확인이며 실제 정책 파일 적용이나 프로그램 실행 결과는
아닙니다. 원본의 권한 필드는 각 사례에서 명시적으로 거짓입니다.

후속 새 경계 사례 19개는 시도 예산·빈 사례·입력과 출력 타입·단일 후보·모델 순위
생략을 확인했습니다. 기대값이 틀린 고정 본문은 `PARTIAL_FINITE`와 맞은 필드 수를
남깁니다. 검사 우선순위 보존은 별도 새 사례 2개로 확인했습니다. 각 로컬 단계는
당시 소스의 관찰로 보관하며 먼저 끝난 단계들을 재실행하지 않았습니다. 최종 합친
소스는 이 후속 변경의 원래 CI가 확인할 대상입니다.

## 플래그에서 정확한 프로필 ID로

후속 구현을 읽으면서 추가 제약을 확인했습니다. 기존 `entity_fields=true`는
`EntityFieldsV1Support()`를 선택합니다. V1의 문자열 필드에 이어 V2는 불리언,
V3는 정수, V4는 선택 필드, V5는 반복 필드를 더합니다. 위 제안의 세 문자열·세
불리언 필드는 타입 범위상 V2부터 표현할 수 있습니다. 앞선 V3 검사는 그대로
해당 관찰이며, 전체 정책의 V2 생산·소비는 별도로 확인할 대상입니다.

새 개발 입구는 사례에 `entity_fields_profile` ID를 명시할 수 있게 합니다.
커널에 있는 정확한 V1~V5 ID만 해석하고 실제 선택한 프로필의 다이제스트를
해석 결과에 남깁니다. 명시적 ID와 기존 플래그를 함께 주면 모호한 해석으로
거부합니다. 명시적 ID가 없으면 기존 경로와 전송 필드 모양을 유지합니다.
일반 파서의 기본 지원 범위도 유지합니다.

새 로컬 사례 12개는 불리언·정수·선택·반복 필드의 프로필 경계, 알 수 없는 ID,
혼합 지정, 기존 V1 경로와 네이티브 등록 소스의 ID 투영을 확인했습니다.
이 단계에서 실제 사례의 ID·경로·개수·분모나 정책 파일을 바꾸지는 않았습니다.
이 관찰 당시에는 프로필 변경 후보·명령·실제 정책 연결이 구현 전이었습니다.

문법 프로필은 소스를 해석하는 계약입니다. 잘못된 ID와 모호한 지정은 해석을
거부하고, 그 원인을 보존합니다. 보조 보기 힌트는 원래 해석 결과 뒤에 적용하며
오류가 나면 기본 보기를 사용합니다. 각 도메인이 갖는 효과와 오류 경계를
입구에서 구분합니다.

## 구현한 프로필 변경 입구

[`profile_migration.gooo`](../../internal/meta/syntaxregistration/profile_migration.gooo)가
요청 고정, 변경 후보, 등록 JSON·네이티브 등록·프로그램 원문의 세 산출물 역할을
선언합니다. Go 연결기는 표시 이름 대신 안정 ID와 `used`·`wasGeneratedBy` 관계를
확인합니다. 이 계약은 기존 `meta_sources` 영역에 등록했으며, 언어 능력 사례나
평가 분모를 새로 추가하지 않았습니다.

`syntax-profile-migration` 명령은 현재 입력과 교체할 Gooo 원문을 읽고 외부의 새
디렉터리에 후보를 만듭니다. 같은 ID·경로의 기존 사례를 유지하면서 두 등록의
프로필만 바꾸고, 원문은 호출자가 지정한 정확한 바이트로 담습니다. 기존 프로그램과
새 프로그램은 각자의 프로필에서 AST·바이트·의미 왕복 및 Get-Put·Put-Get을 검사합니다.
이 검사는 두 프로그램 사이의 의미가 같다는 주장이 아닙니다.

후보에는 세 파일의 변경 전·후 바이트, 각 바이트 해시, 요청·입력·도구 실행 정체성,
실제 프로필 ID와 다이제스트, 두 소스의 해석 결과가 있습니다. 독립적인 후보 검증은
현재 입력에서 예상 후보를 다시 구성해 전체를 비교합니다. 분모 이력은 읽어서
고정하며 산출물에 넣지 않습니다. 저장소 적용·쓰기·승격 권한은 부여하지 않습니다.

실제 등록 소스에서는 마지막 필드와 닫는 중괄호가 붙은 한 줄 사례를 확인했습니다.
쉼표와 새 필드를 같은 바이트 위치에 따로 넣으면 잘못된 순서로 조립되는 문제가
있었습니다. 이 위치는 한 삽입으로 구성하도록 수정했습니다. 수정 뒤 실제 131개
사례의 ID·개수를 유지하는 후보를 생성·검증했습니다. 이 과정에서 Gooo 원문은
대상 하나의 변경 전후 두 개만 해석했으며, 131개 프로그램을 실행한 것은 아닙니다.

[명령 사용법](../language/syntax-profile-migration.ko.md)과
[단계별 관찰](../observations/syntax-profile-migration/observations.json)에 범위를 남깁니다.
개발 중 끝난 검사를 다시 실행하지 않고 새 경계나 실제 실패만 추가 확인했습니다.
최종 합친 소스는 공개한 변경의 원래 CI에서 판단합니다. 정책의 여섯 필드 실제 적용,
프로그램 실행과 독립 소비까지는 이 후보 입구의 성공에서 추론하지 않습니다.

원래 PR #1627의 CI에서는 새 메타 계약 파일을 넣은 뒤 원본 파일 수 확인값이
149에 남아 있는 문제를 찾았습니다. 원본 파일 수는 150으로 갱신하고, 언어 사례 수
131과 평가 분모는 유지했습니다. 새 map 복사 코드를 `maps.Clone`으로 정리해 CI의
코드 정리 고정점도 맞췄습니다. 실패한 원본 목록 검사 하나만 로컬에서 다시 실행해
통과했으며, 다른 완료 집합을 재실행하지 않았습니다. 공개한 원래 PR의 소스와 본문은
보존하고 별도 수정 소스의 원래 CI에서 전체 결과를 판단합니다.
[실패와 수정 관찰](../observations/syntax-profile-migration/original-ci-repair.json)을 남깁니다.
