# Text 값과 실행 전송 용량의 경계

## 해결하려는 문제

Text는 값 하나의 UTF-8 바이트 수를 제한한다. JSON 전송 바이트는 다르다.
NUL 한 바이트는 `\u0000` 여섯 바이트로 직렬화된다. 1,024바이트 Text 여섯 개가
들어간 레코드는 한 행이어도 기존 32 KiB 입력 제한을 넘을 수 있었다.
입력 해석만 바꾸면 정규화된 사례의 재직렬화나 64 KiB 네이티브 출력에서 다시
막힐 수 있다. 이 변경은 그 경계를 함께 조정한다.

Gooo 예제는 [`wire-capacity.gooo.fixture`](../../internal/bodyexecution/testdata/wire-capacity.gooo.fixture)다.
안정 ID가 있는 레코드를 `First → Second`로 전달한다. 두 본문은 값을 그대로
반환한다. 정수의 정확한 전달과 Text의 손실 없는 전달을 검사하며 새 모델을 쓰지 않는다.

## 공개하는 계약

| 경계 | 최대값 | 단위 |
| --- | ---: | --- |
| 단일 composition 입력 JSON | 1,048,576 | 원본 전송 바이트 |
| 정규화한 사례 집합 JSON | 1,048,576 | 재직렬화 바이트 |
| 시리즈 JSON | 16,777,216 | 전체 전송 바이트; 최대 16개 집합 |
| 네이티브 composition stdout | 1,048,576 | 한 실행의 전송 바이트 |
| Text 하나 | 1,024 | 디코딩한 UTF-8 바이트 |
| 사례 집합의 행 | 128 | 입력 행 |
| 기록한 origin의 export 페이지 | 32,768 | 별도 페이지 JSON 바이트 |

1 MiB는 기존 package 입력 읽기의 유한한 용량과 맞춘 값이다. 각 최대값의 모든
조합을 허용한다는 뜻은 아니다. 원본과 정규화 JSON은 크기가 다를 수 있어 둘 다
검사한다. 값이나 행을 잘라서 통과시키지 않는다. 네이티브 결과 한도를 넘으면
부분 바이트를 성공한 값으로 반환하지 않는다.

`gooo package inspect --json <workspace.json>`과 composition inspection의
`transport_capacity`는 실제 검사에서 사용하는 상수를 보고한다. 이 표시는
실행·모델 호출을 하지 않으며, 표시 객체를 수정해도 허용 범위가 바뀌지 않는다.
새 명령이나 워크플로는 추가하지 않았다. compiler stdout·stderr, provenance
파일과 saved receipt는 별도의 기존 제한을 유지한다. 네이티브 2초와 상위 60초도
유지한다. 값 출력에 사용한 버퍼는 실제 쓰기 때 자라며, 1 MiB를 선할당하지 않는다.
한도 변경은 전체 프로그램의 RSS나 처리량이 개선됐다는 측정값이 아니다.

## 새 관찰과 남은 확인

새 로컬 사례 20개를 세 단계로 한 번씩 실행했다. 이전에 완료한 사례 집합은
다시 실행하지 않았다. 각 단계의 원본·소스 고정 기록은
[`observations.json`](../observations/composition-wire-capacity/observations.json)에 연결했다.

- 새 네이티브 입력 한 행은 37,005바이트다. 여섯 Text는 각각 실제 NUL 1,024개,
  정수는 정확한 signed64 최솟값이다.
- 두 활동의 출력은 73,884바이트다. 실제 네이티브 두 실행의 stdout 해시와
  14개 필드의 값·안정 ID를 독립 기대값과 비교했다.
- 모델 호출과 기대 출력에 따른 정확도 분모는 모두 0이다. 입력 관찰과 필드 전달의
  성공을 모델 정확도로 바꾸지 않는다.
- 초과 입력·정규화 집합·시리즈·출력·진단, 중복 필드, decoded Text 한도도 검사했다.
  준비 명령에서 한도를 읽는 CLI 경로는 별도로 검사했다.

이 기록은 개발 소스의 새 관찰이다. 최종 공개 소스의 원래 CI 수용은 별도로 필요하다.
외부 소비자의 원래 37,282바이트 실패와 49,855바이트 복합 입력은 이 로컬 합성
사례로 대체해 성공 처리하지 않는다. 새로운 compiler 버전을 고정한 해당 입력의
관찰 전까지 외부 전체 ABI 수용은 미확인으로 남긴다.

Saved replay는 기존 소스·선택을 재구성한 뒤 새 실행 관찰을 만든다. 과거 출력의
모든 표시 필드를 인증하는 동작과 구분한다. 두 부모 해시가 각각 어떤 바이트를
가리키는지는 [사용 예제](../../examples/workspace-input-observations/README.md)에 명시했다.

## 의미 계획과 표시 힌트의 분리

첫 공개 후보 #1634의 원래 투영 검사 `38919600787`, 작업 `117035787496`에서
`TestPlanInspectionReleaseRejectsMissingCountersAndChangedSource`가 실패했다.
`CompositionInspection`에 추가한 용량 필드가 원래 구조 계획과 함께 동등성 비교에
들어갔다. 과거 검사 자료에는 이 필드가 없어 비교가 달라졌다. 원래 로그 해시는
`efa940cf9824e24e381560195014453b9b5d6613017dba9b580f093ea4f33b7f`다.

후속 변경은 용량을 `body-plan --json`의 표시층에 둔다. 정규화된 구조 계획에는
넣지 않는다. 기존 릴리스 검증기와 과거 검사 자료는 수정하지 않는다. 유효한 JSON
안에서 힌트가 없거나 타입·버전·내용이 잘못돼도 구조 계획의 해석과 입력 템플릿은
유지된다. 원본 해시, 계획, 필수 카운터의 누락·변경은 계속 거부한다. 전체 JSON이
깨진 경우까지 유효한 구조 계획으로 취급하는 동작은 제공하지 않는다.

새 힌트 경계 사례 12개와 원래 실패 검사의 기존 반례 8개를 구분해
[`hint-boundary/observations.json`](../observations/hint-boundary/observations.json)에 기록했다.
이 로컬 확인에는 새 네이티브 프로그램·모델 실행이 없다. 원래 실패 후보의 소스와
관측 기록을 유지하고 후속 소스의 원래 CI를 별도로 확인한다.
