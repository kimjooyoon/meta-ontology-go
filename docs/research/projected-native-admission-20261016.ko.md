## 원래 관찰

`TestWorkspacePureCallsRecordNamespacesAndValueCopies`는 네임스페이스가 다른
레코드의 값 복사와 두 입력의 기대값을 확인한다. 첫 번째 실행은 값을 반환했고,
같은 실행 파일·입력의 두 번째 실행은 `EXECUTE_2`, `WAIT` 단계에서 종료됐다.

- 두 번째 자식의 관찰 벽시계 시간: 4,260,273,700ns.
- 보고된 사용자 CPU 시간: 0ns, 시스템 CPU 시간: 1,731,000ns.
- 표준 출력·오류 해시는 빈 바이트의 해시였다.
- 오류는 `context deadline exceeded: signal: killed`였다.
- 소스의 네이티브 Wait 제한은 2초, 구성 실행의 상위 제한은 60초다.
- 원래 작업 로그 SHA-256:
  `08c5cfeafd4f07ce8b8f8dd3542b8a9a219d67e9be1afd9036bc3205219a679e`.

이 기록은 실행을 완료하지 못했다는 사실을 보여준다. 실행되지 않은 결과를
네임스페이스나 값 복사의 반례로 확정할 수 없다. 짧은 CPU 시간만으로 운영체제
스케줄링·호스트 부하·파이프 대기 중 어느 원인이었는지도 확정할 수 없다.
현재의 텍스트 실패 출력은 타이밍 구조체와 종료 코드의 포인터 값을 풀어 쓰지 않아
그 차이를 조사하는 데 제약이 있었다.

## 이번 변경

의미 검사의 투영된 작업공간에서는 테스트 패키지 하나만 동시에 실행한다.
패키지 안의 검사는 별도의 Go 도구와 네이티브 자식을 만들 수 있다. 다른 패키지의
빌드·검사가 이 자식 작업과 겹치는 경로를 줄이기 위한 보수적인 자원 배치다.

실제 명령은 `go test -p=1 ./...`다. 전체 패키지·테스트를 유지한다. 네이티브 2초,
상위 60초, CI 작업 제한과 거부 조건도 유지한다. 명령 배열 하나를 실행과 관측
기록에 함께 사용해, 기록된 인수가 실제 실행과 달라지는 것을 막는다.

실패한 레코드 검사에는 전체 런타임의 JSON 출력을 붙인다. 이후 같은 실패가
발생하면 프로세스의 종료 코드·Start/Wait 시간·출력 해시·실패 단계를 원래
관측값으로 읽을 수 있다. 성공으로 바꾸는 분기나 재시도는 추가하지 않는다.

새로운 두 경계 사례는 실제 언어 프로그램을 다시 실행하지 않고, 원래 셸 함수에
가짜 도구를 연결해 다음을 확인한다.

1. 전체 검사 인수와 패키지 동시성 인수가 실행·관측 기록에 일치한다.
2. 한 번만 호출한다. 성공 0과 실패 23의 종료 상태를 그대로 전달한다.
3. 표준 출력·오류의 바이트 수와 해시를 실제 파일에서 계산한다.

## 확인해야 할 한계

패키지 순서화는 겹치는 작업을 줄이는 변경이다. 호스트 지연이 완전히 없어졌다는
증거나 CI가 더 빨라졌다는 측정값은 아직 없다. 순서화로 전체 검사 시간이 늘 수도
있다. 최종 새 소스의 원래 CI에서 수용 여부와 시간을 확인한다.

실행 용량, 실행 관찰의 누락, 실제 값의 불일치는 서로 다른 도메인이다. 이후에는
의미 검사 결과가 이 차이를 원래 프로세스·입력·소스 기원과 함께 표현하도록
개선해야 한다. 이번 변경만으로 시간 예측이나 미해결 프로그램 구성을 완료했다고
설명하지 않는다. 실패한 #1631의 소스·본문·원래 실행은 그대로 보존한다.
