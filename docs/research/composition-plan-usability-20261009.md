# 조립하기 전에 입력과 연결을 읽기

Gooo 프로그램을 처음 실행할 때는 어디에 값을 넣어야 하는지부터 알 수 있어야
합니다. `body-plan`은 호출자 입력, 활동 연결, 먼저 조립해야 할 호출 본문을
같은 구조 계획에서 보여줍니다. 입력 양식도 만들 수 있습니다. 생성·실행 결과와
구조 조회 결과는 별도로 기록합니다.

## 이번에 가져온 원리

2026-10-09에 Hacker News와 GeekNews의 목록, GitHub Trending을 확인하고
아래 원문을 읽었습니다. Trending 페이지에서는 저장소 목록이 제공되지 않아
현재 순위나 인기도에 관한 판단은 하지 않았습니다.

| 원문 | 읽은 내용 | Gooo에 적용할 판단 |
| --- | --- | --- |
| [Meadows](https://github.com/lorezzed/meadows), HN에서 발견 | 작은 텍스트 언어를 그래프 JSON으로 컴파일하고, 별도 도구가 그 그래프를 표시하고 시뮬레이션합니다. | 실행 결과를 얻기 전에도 도구가 읽을 수 있는 계획을 내보냅니다. Gooo는 기존 stable ID와 bind 의미를 유지합니다. |
| [Dan Cohen의 Zotero 회고](https://newsletter.dancohen.org/archive/the-slow-formation-of-durable-software/), 2026-10-06, GeekNews에서 발견 | 연구자의 실제 작업과 기존 도구를 연결하는 과정에서 제품의 형태를 구체화했습니다. | 입력 작성 → 실행 → 저장 재생 → 기대값 검사라는 지금의 작업을 연결합니다. 새로운 서비스 설치를 시작 조건으로 늘리지 않습니다. |
| [tinyjs](https://github.com/tarwin/tinyjsapp), GeekNews에서 발견 | 기본 시작 경로와 확장 템플릿을 함께 제공합니다. | 기본 조회와 입력 양식은 모델이나 새 의존성 없이 사용합니다. 모델 연동은 별도 명시적 단계로 둡니다. |

이 표는 원문에서 내린 적용 판단입니다. 자료가 Gooo의 완전성이나 성능을
검증한 것은 아닙니다. 외부 구현을 가져오거나 실행하지 않았습니다.

## 줄이는 것

입력 키를 알아내려고 먼저 조립을 실행하는 절차를 줄입니다. `Main`과
`Main.input0`의 차이, bind로 이미 연결된 포트, 호출되는 조립 본문을 같은
계획에서 확인합니다. 입력 양식에는 실제 호출자의 루트 입력만 들어갑니다.

관측한 결과를 양식의 정답으로 자동 복사하는 경로는 넣지 않습니다. 기본값은
수정할 자리이며, 정답률은 실제 기대값이 제공된 다음에 셉니다. 구조 조회는
본문 타입 검사도 수행하지 않으므로 오류가 있는 본문도 계획을 가질 수 있습니다.

## 다음 연결 기준

여러 조립 본문과 추가 루트 입력을 저장 조립의 반례 루프에 연결할 때 이
계획을 기준으로 삼습니다. 실패한 원래 호출 행은 그대로 다음 구성에 넘기고,
중간 입력이나 호출 본문의 인수를 역산해 루트 사례를 만들지 않습니다.
소스에 작성한 본문별 사례는 native 생성기가 계속 별도로 검사합니다.

이 변경은 그래프 조회와 입력 양식까지 구현합니다. 작업장의 다중 조립 반례
루프는 아직 이 export를 소비하지 않습니다. 소스와 계약 digest, 준비 본문의
순서, 입력 키가 실제 생성 계획과 일치하는지 확인한 뒤 연결할 수 있습니다.

## 실제로 이어 실행한 결과

[관측 파일](composition-plan-dogfood-20261009.json)은 다섯 예제에서 새 계획과
입력 양식을 만들고, 입력 전용 실행 뒤 기대값을 제공해 같은 생성물을 재생한
결과입니다. 다섯 계획 모두 실제 생성 계획과 정확히 같았습니다. 조회는 모델
호출·후보 검사·실행이 각각 0회였고, 입력 전용 실행의 정답 수는 0/0입니다.

| 예제 | 초기 생성 모델 호출 | 이후 작성한 호출 기대값 | 재생의 새 모델 호출 |
| --- | ---: | ---: | ---: |
| 여러 루트와 입력 연결 | 0 | 49/49 | 0 |
| 자체 모델의 세 필드 조립 | 1 | 4/4 | 0 |
| 두 source_search 활동 | 0 | 15/15 | 0 |
| 두 source_fill 활동 | 0 | 15/15 | 0 |
| 본문 안에서 호출되는 예산 계산 | 0 | 1/4 | 0 |

예산 계산은 약한 본문별 사례를 만족하는 첫 후보를 선택했습니다. 별도로
제공한 호출 기대값에서는 세 번 실패했습니다. 구조 조회와 실행 성공만으로
기능이 맞았다고 계산하면 이 차이가 사라집니다. 다음 구성에서는 이 원래
호출 행들을 반례로 쓰는 것이 필요합니다.

자체 모델은 기존 가중치 446바이트를 사용했고, 로더가 관측한 해석된 텐서는
2,096바이트였습니다. 전체 프로그램 메모리나 일반화 성능을 뜻하지 않습니다.
이번 작업에서 모델을 새로 학습하거나 다운로드하지 않았습니다. 여러 검사가
함께 실행됐으므로 속도 개선이나 독립된 지연 시간 수치는 보고하지 않습니다.
