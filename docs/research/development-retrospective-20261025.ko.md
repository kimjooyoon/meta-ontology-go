## 구조적으로 남은 문제

현재 기능별 기록·계획·CLI가 늘고 있습니다. 코드 줄 수만으로 낭비를 판단하기보다
새 의미 하나를 추가할 때 기존 안정 모듈을 얼마나 수정하는지 봐야 합니다.
워크스페이스 로더처럼 여러 소비자가 실제 같은 계약을 쓰는 부분부터 공유합니다.
도메인별 원본 의미가 다른 기록을 이름이 비슷하다는 이유로 합치지는 않습니다.

출처는 결과의 점수보다 어디서 왔고 어떤 변환을 거쳤는지 설명해야 합니다.
실제 실행 결과, 과거 실행의 읽기, 새 소스의 제안은 서로 다른 기원을 갖습니다.
현재 반례를 새 구현에 넣어 통과해도 원본 CI의 실패는 그대로 남습니다.

공유 소스는 변화의 단위를 다시 보게 합니다. 같은 파일을 아홉 워크스페이스가
사용하면, 파일 하나의 분할 성공은 아홉 문맥의 보존을 뜻하지 않습니다. 출처와
소비자 관계를 따라 수정할 선언을 묶고, 각 문맥의 진입점·타입·실행 결과를 확인해야
합니다. 내용 해시가 같다는 사실과 같은 소스 발생을 가리킨다는 사실도 구분합니다.

`ecf07409c31be3e59700b042618c864bb03f21ca`의 추적 파일 감사에서는 80줄을 넘는
Gooo 파일 21개 중 10개가 외부 JSON 워크스페이스에 선언됐습니다. 검사한 정의는
111개이며 `examples/recorded-use-origins/inspect.gooo`의 선언 소비자는 9개였습니다.
이는 명시적인 파일 목록에서 확인한 참조 수입니다. 임베드·동적 로딩까지 포함한
전체 소비자 수나 메타 연산의 완료율로 사용하지 않습니다.

별도의 Go 1.27.3·darwin/arm64 조회에서는 공개 커밋 `67c1675ec`의 패키지 460개에서
직접 임베드하는 Gooo 소스 21개를 확인했습니다. Go의 `go list -json`이 제공하는
`EmbedFiles`·`TestEmbedFiles`·`XTestEmbedFiles`를 사용했습니다. 다른 플랫폼·태그와
동적 파일 읽기는 이 조회 범위에 포함되지 않습니다. 언어가 소비자를 찾는 다음 단계는
이런 기존 생태계의 관측을 출처와 함께 연결하고, 미관찰 범위도 유지하는 것입니다.

Gooo 저장소 전체를 자동 재포장하는 경로는 아직 완료되지 않았습니다.
공통 분할 기반의 다섯 소비자 중 네 경로가 준비된 실험 브랜치가 있고,
Gooo 저장소 소비자는 추가 연결이 필요합니다. 이번 파일 분할 CLI를 이 전체
연산의 구현으로 바로 등록하지 않습니다. 단일 파일·임베드 입력·물리 저장소 투영의
후속 계약도 각각 닫아야 합니다.

## 다음 기능의 순서와 완료 기준

1. **Gooo가 자신의 소스를 나누는 경로.** 공통 로더와 분할 결과를 실제 저장소 소비자에
   연결합니다. stable ID·import·실행 결과·정확한 원본 바이트 구간이 보존돼야 합니다.
   지원하지 않는 입력은 원인과 다음 작업을 반환하고, 처리한 것처럼 세지 않습니다.
2. **선언에서 후속 소비자를 찾는 변경 계획.** 도구 버전이나 의미 선언 변경이 어떤
   투영·검사에 닿는지 출처 관계로 찾아냅니다. 누락 소비자는 전체 범위를 유지합니다.
   새로운 기능 하나를 넣을 때 손으로 연결해야 하는 기존 모듈 수를 기록합니다.
3. **에이전트가 바로 사용할 제안과 반영.** 하나의 실행 가능한 작은 예제로 시작해
   계획·적용·변경된 입력 거부·재실행 거부를 같은 공개 경로에서 설명합니다.
   사람에게 보여주는 렌즈의 설정 오류는 실행 의미나 필수 검사를 바꾸지 않습니다.
4. **작은 decision 모델의 제한된 선택.** 소스가 허용한 후보 중 선택할 곳이 실제로
   여러 개인 경우에 연결합니다. 모델 없는 결정론적 경로, 호출 수, 선택 후 독립
   평가의 분모를 유지합니다. 현재 시간 계산과 파일 분할은 모델 호출이 필요 없습니다.

새 CLI를 추가하기 전에는 기존 선언·IR·계획·반영 경로가 그 일을 표현할 수 있는지
확인합니다. 첫 목표는 손으로 쓰는 연결 코드가 줄고, 에이전트가 실패 원인을 읽고
다음 작업을 고를 수 있는 것입니다. 사용자의 CI에 추가 학습이나 무거운 모델,
자동 업로드를 기본 요구하지 않습니다.

## 출처를 변경의 범위까지 연결하기

현재 전문화 방향은 **출처가 있는 변경의 영향 범위와 동시 수정**입니다.
반복 구현을 함수로 모으는 것에서 더 나아가, 한 선언을 바꿀 때 어느 소비자가 함께
바뀌어야 하는지 Gooo의 기존 의미 이미지와 선언 관계로 확인하려 합니다.

이번 공유 소스 반례에서는 두 패키지가 한 파일을 읽고 있었습니다. 파일을 나누면서
첫 패키지의 목록만 바꾸면 두 번째 패키지의 선언 일부가 사라졌습니다. 그런데 해당
선언이 현재 진입점에서 쓰이지 않으면 남은 프로그램은 여전히 유효했습니다.
따라서 컴파일 성공과 기존 의미 보존은 별도 관측입니다. 전체 소비 패키지를 함께
계획하고, 실제 파일 목록을 다시 읽은 이미지와 독립된 실행 기대값까지 비교합니다.

같은 내용을 읽었다는 관측도 충분하지 않았습니다. 폴더 별칭과 대소문자 별칭은
다른 문자열 경로로 같은 쓰기 대상에 도달할 수 있었습니다. 파일 교체 전에 실제
쓰기 후보를 읽기 관점에 투영해 기존 컴파일러로 다시 검사합니다. 하드링크는 원래
내용과 inode가 같아도 별도 디렉터리 항목의 교체에는 영향을 받지 않아 구분합니다.
주소 해석은 Go 호스트의 파일 기능이고, 선언 보존은 기존 Gooo 의미 검사가 담당합니다.

앞으로도 원본 바이트의 해시, 안정된 의미 ID, 읽은 문맥, 변경이 도달하는 파일 항목을
하나의 식별자로 합치지 않습니다. 각각 무엇을 식별하고 어느 관측에서 얻었는지 남깁니다.
지표도 명시된 소비자 수, 계획에 포함한 수, 실제 재로드한 수, 독립된 출력 조건 수를
각자의 분모로 유지합니다. 아직 발견하지 못한 소비자를 0개로 계산하지 않습니다.

다음 단계는 여러 workspace의 공동 변경을 실제 저장소 메타 작업에 연결하고,
단일 파일 생성기와 embed 사용처의 후속 변경을 표현하는 것입니다. 작은 decision
모델은 안정된 ID로 표현된 여러 합법적인 분할 후보의 순서를 고를 수 있습니다.
출처 누락을 추정으로 채우거나 검사되지 않은 경로를 완료로 바꾸는 역할은 부여하지 않습니다.

## 실제 파일 작업의 실패를 숨기지 않기

공유 소스 작업을 검토하면서 Go 호스트의 기존 두 경로에서도 반례가 나왔습니다.
임시 파일 쓰기의 오류 변수가 안쪽 범위에 가려져, 쓰기에 실패한 빈 파일을 원본에
덮어쓰고 성공으로 보고했습니다. 실제 읽기 전용 파일로 두 준비 위치를 각각 실패시켜
재현했고, 첫 오류를 전달해 원본 교체 전에 멈추도록 고쳤습니다. 정상 분할과 실패 시
원본 바이트·새 대상 부재·임시 파일 정리를 별도로 검사합니다.

또한 메타 실행의 읽기 전용 Git 사본은 이미 공통 정리 함수가 있었지만, 한 실행 경로가
일반 삭제를 사용해 사본을 남겼습니다. 작은 실제 Git 저장소에서 작업 실패 후 누수를
재현하고 기존 정리 함수에 연결했습니다. 출처를 남길 자료와 작업이 소유한 임시 사본의
수명을 구분해야 저장 공간 비용도 반복 실행 횟수에 따라 계속 쌓이지 않습니다.

## 이번 연결 작업에서 배운 점

공동 분할 예제는 실제 계산과 재실행 검사를 통과했지만 첫 전체 검사에서 소스 등록
누락이 발견됐습니다. 예제를 `examples/shared-source-consumers/main.gooo`로 두고
Gooo 등록 생성기가 아홉 멤버를 제안하도록 했습니다. v100의 136개 문법 사례는
그대로 보존하고 v101에 한 사례를 추가했습니다. 이 등록 수와 실제 활동 출력 여섯
개의 검사는 다른 질문에 답합니다. 사례 수를 올렸다는 이유로 기능 보존이 확인되지는
않습니다. 생성기는 필요한 연결을 함께 만들고, 독립 실행 검사는 결과를 확인합니다.

정리 회귀 테스트에서도 문맥의 혼동이 드러났습니다. 테스트는 임시 Git 저장소를
만들었지만 CI가 전달한 `GIT_DIR`을 조회해 다른 저장소의 스냅샷을 만들었습니다.
같은 환경 변수로 로컬 실패를 재현한 뒤, 테스트를 만든 저장소의 경로에 연결했습니다.
CI의 원래 실패를 남기고 수정된 소스의 결과를 따로 기록합니다.

두 경우 모두 한 도구 내부의 성공만으로 연결 전체를 설명하기 어려웠습니다.
다음 기능에서도 원본 ID, 소스 발생 위치, 소비자 문맥, 실제 실행 관측을 이어 읽는
작은 경로부터 완성하겠습니다. 반복되는 연결의 소유권을 Gooo 선언으로 옮기고,
Go에는 파일·프로세스·주소 해석 같은 호스트 동작을 남기는 방향입니다.

## 실제 소비자와 다음 전문화 단계

`249546c9e648dc47c6b5f9140e01491c89ca4ce3`에서는 실제 저장소의 유효한 워크스페이스
정의 111개를 읽고, `examples/recorded-use-origins/inspect.gooo`를 참조한 9개를
공동 계획에 연결했습니다. 새 정의를 다시 읽은 9개 의미 이미지는 각자의 계획과
일치했고, 계획 재생도 같았습니다. 소스 출력은 2개, 정의 출력은 9개이며 실제 쓰기는
0개였습니다. 계획 구성 147ms는 한 번의 로컬 관측입니다. 추적된 1MiB 이하 JSON 중
현재 워크스페이스 스키마를 선언한 파일만 조사했으며, 임베드·동적 읽기는 별도입니다.
이 9개 이미지 검사를 앞서 확인한 독립 기대 출력 6개와 합쳐 완료율로 계산하지 않습니다.

연결의 다른 쪽에서는 정상 보고서를 거부하는 문제가 나왔습니다. 소스 생산기는 중첩
Go 모듈의 소유 위치와 처리 불가 사유를 기록했지만 소비자는 그 필드를 몰랐습니다.
[후속 수정 #1795](https://github.com/kimjooyoon/meta-ontology-go/pull/1795)는 실제 생산기와
Gooo 메타 바인딩을 거친 입력으로 소유자 미확인·모듈 경계를 넘는 링크·필요한 도구
버전 부재를 검사합니다. 원래 파일 수와 줄 수, 적용 불가 사유를 함께 유지합니다.
새 사유를 지원할 때 정상 입력뿐 아니라 사유 불일치와 거짓 성공도 확인해야 합니다.

다음 언어 기능은 **원본 위치를 유지하는 명시적 소스 묶음**에 집중합니다. 현재 임베드
계약을 읽는 일부 Go 소비자는 한 파일을 전제로 합니다. 작은 읽기 전용 실험에서는
`operation-input-contract.gooo`를 두 구문 트리로 나누고 기존 변환기에 연결했습니다.
엔티티 10개와 활동 12개의 실제 파일·바이트 구간이 유지됐고 의미 IR 해시도 같았습니다.
이 실험은 임베드 소비자 이전이나 전체 ABI 검사의 완료를 뜻하지 않습니다.

구현 완료 기준은 명시한 멤버의 원본 바이트와 선언 위치를 보존하고, 기존 계약 검사를
그 묶음에 그대로 적용하는 것입니다. 누락 멤버·서로 다른 헤더·중복 ID·지원하지 않는
import 문맥은 빈 결과와 원인을 반환해야 합니다. 그 뒤 실제 임베드 소비자 하나를
연결해, 파일 분할 때문에 Go 연결 코드를 반복 수정하는 비용이 줄었는지 확인합니다.

에이전트에게는 원본 ID와 통과 여부에 더해 확인한 입력의 역할과 문맥도 전달해야 합니다.
같은 함수나 옵션이 다른 위치·타입·소비자에서 쓰일 때 기존 결과의 적용 범위가 달라집니다.
현재 표현이 담지 못하는 문맥은 미확인으로 남기고, 새 문맥의 기대 결과를 별도로
검사합니다. 사전빌드 도구 배포도 소스 revision·실제 Go 빌드 버전·필수 입력 계약을
함께 연결해야, 빠른 설치가 오래된 실행 경로의 재사용으로 이어지지 않습니다.

## 이름을 바꿔도 연결되는 의미

소스 묶음을 첫 임베드 소비자에 연결한 뒤, 같은 ID를 유지한 이름 변경이 네이티브
검사에서 거부되는 반례를 발견했습니다. 의미 IR은 같은데 Go 소비자가 예전 이름을
타입으로 판단하고 있었습니다. [문제 #1797](https://github.com/kimjooyoon/meta-ontology-go/issues/1797)의
수정에서는 열 개 엔티티의 역할을 ID로 찾고, 실제 소스 이름은 별도로 전달합니다.
컴파일러 자신이 사용하는 `FunctionInput`도 `FunctionSource`로 바꾸었습니다.

이름표를 새로 붙여도 같은 대상을 찾을 수 있어야 하지만, 어떤 이름표를 읽었는지는
기록에 남아야 합니다. 그래서 의미 해시는 유지하고 원본 해시는 새로 계산합니다.
과거 실행 기록은 고치지 않고, 새 준비에서 읽은 선언과 결과를 연결합니다. 실제 코드
추출 결과가 메타 실행 소비자까지 도달하는 검사와, ID·검사 단계 연결을 잘못 바꾼
반례를 함께 둡니다. 테스트용 과거 기록의 스키마 적응과 실제 새 실행도 구분합니다.

전문화의 다음 기준은 **출처를 따라 의미를 유지하며 구조를 바꾸는 비용**입니다.
작은 변경에 필요한 수작업 Go 수정 수, 선언 소비자 중 실제 확인한 문맥 수, 새 실행과
과거 결과의 적용 범위를 따로 봅니다. 언어 기능 하나를 추가할 때마다 새 프로토콜과
CLI를 만들기보다 기존 ID·입력 계약·출처 연결을 확장하겠습니다. 모델이 후보 순서를
돕는 경우에도 이 연결은 결정론적으로 확인할 수 있어야 합니다.

## 패키지 목록과 실제 소비 선언을 구분하기

임베드 소비자를 조사하면서 패키지 전체의 파일 목록이 충분하지 않은 반례를 얻었습니다.
같은 패키지의 두 변수가 한 Gooo 파일을 읽었고, 하나는 파일 묶음, 다른 하나는 단일
파일을 선언했습니다. 분할 뒤 패키지 목록에는 두 멤버가 모두 나타났지만 단일 파일
변수에는 첫 멤버만 남았습니다. 이 입력도 의미 검사를 통과할 수 있으므로, 검사의 성공과
원래 선언의 보존을 다시 구분해야 했습니다.

파일 패턴 해석기를 별도로 만들지 않고 Go의 임시 투영과 변수별 조회를 연결했습니다.
원본 Go 선언의 위치·바이트 해시, 제안된 Gooo 멤버, 선택된 빌드 문맥을 함께 남깁니다.
테스트 선언의 패턴이 표시돼도 일반 `go list`에서는 실제 테스트 임베드 목록이 비어
있을 수 있어 `-test`를 사용합니다. 앞선 21개 관측도 전체 소비자가 없다는 결론으로
확장하지 않습니다. 임시 경로의 별칭 때문에 투영이 적용되지 않았던 원본 실험도 남기고,
요청 주소와 도구가 실제 사용하는 물리 주소를 구분했습니다.

이번 네이티브 API는 변수의 파일 포함을 관측합니다. 이후의 동적 읽기, 런타임 설정,
권한 문맥까지 그 관측으로 대신하지 않습니다. 생태계 작업에서도 당시 수집하지 않은
런타임 문맥은 소스 ID만으로 복원할 수 없었습니다. 또한 한 기능의 출처가 바뀌면 이를
소비하는 프로필과 거부 검사까지 재검토 대상이어야 한다는 실제 재작업 사례가 나왔습니다.
이 영향 관계를 찾고 필요한 변경을 함께 준비하는 것이 다음 연결의 기준입니다.

## 소비자 관측을 실제 분할 계획에 연결하기

이제 임베드 관측은 별도로 만든 분할 문자열 대신 기존 워크스페이스 분할기와 같은
바이트 분할을 받습니다. 원본에서 ID로 경계를 찾고, 복사한 바이트 구간을 남기며,
각 소비자가 실제로 받는 소스 묶음을 다시 비교합니다. 원문과 의미가 보존되는지,
소비자에서 선언이 빠지는지, 현재 문맥으로는 해석하지 못하는지를 따로 보입니다.

실제 컴파일러 계약을 사용한 연결 검사에서는 묶음 소비자가 22개 선언과 기존 네이티브
계약을 유지했습니다. 단일 파일 소비자의 소스도 문법상 유효했지만 활동 12개가 빠졌고
네이티브 계약은 거부됐습니다. 같은 소스의 파싱 성공을 보존의 성공으로 대신하지
않아야 한다는 사례입니다. 새 파일을 처음 선택하게 되는 다른 패턴 소비자도 영향
목록에 들어갑니다. 읽지 못하는 소비자는 빈 결과로 지우지 않고 미확인 사유를 남깁니다.

공통화의 기준도 여기서 구체화됩니다. 워크스페이스와 임베드의 읽기 문맥은 서로
다르지만, 원본 선언을 자르고 출처 구간을 유지하는 동작은 같습니다. 이 부분만 공유하고
각자의 의미 해석과 네이티브 계약 검사는 유지했습니다. 다음 단계는 명시한 소비자들과
실제로 발견한 소비자를 연결하고, 전체 쓰기 집합과 복구를 같은 계획에서 다루는 것입니다.
이번 계획 API가 그 쓰기 권한이나 저장소 전체의 소비자 발견을 대신하지는 않습니다.

## 소스 묶음을 실제 코드 생성에 연결하기

분할 계획을 만들 수 있어도 생성기가 한 파일만 읽으면 개발자가 Go 연결 코드를 다시
맞춰야 합니다. 이 비용을 줄이기 위해 기존 순수 본문 생성기에 명시적인 소스 묶음을
연결했습니다. 엔티티와 고정 함수를 다른 멤버에서 찾고, 각 선언의 실제 파일·위치를
유지합니다. 같은 패키지·네임스페이스, 타입, 호출 깊이와 순환 검사는 기존 경로를
사용합니다. 필수 필드와 선택 필드의 프로필도 단일 파일에서 사용하던 규칙을 따릅니다.

컴파일러의 실행 연속 정책을 직접 두 Gooo 멤버로 나누었습니다. 재시도 시 관측할
대상을 정하는 두 활동을 `source_recovery.gooo`로 옮기고, 기존 생성기와 임베드가
같은 파일 계열을 읽게 했습니다. 아홉 Go 생성물은 그대로입니다. 파일 구성이 바뀐
출처 식별값은 새로 계산하므로 과거 출처 기록을 현재 소스 기록으로 재사용하지 않습니다.

추가 검토에서는 아직 선택이 필요한 `assembling` 활동을 고정 생성기에 넣었을 때
초기 본문이 그대로 출력되는 반례를 찾았습니다. 이제 선택한 진입 활동이나 호출한
활동에 미해결 조립이 있으면 결과를 내보내지 않습니다. 같은 소스 묶음에 있는 별개의
미완성 활동은 고정된 진입 활동의 생성을 막지 않습니다. 이 구분은 파일 전체에 같은
상태를 붙이는 대신 실제 호출 관계에서 미완성의 영향을 찾는 데 필요합니다.

전체 검사에서는 문법 소스 목록도 파일 구성의 소비자임이 확인됐습니다. 새 회복
멤버의 등록을 빠뜨리자 그 목록을 읽는 문법·의미 검사가 함께 거부했습니다. 회복
멤버를 기존 메타 소스 목록에 등재하고, 두 파일에서 세 타입과 아홉 활동의 ID 및
Get-Put/Put-Get 법칙을 별도로 검사했습니다. 등록된 문법 사례 139개와 언어 사례
137개·거버넌스 사례 2개의 분모는 그대로입니다. 파일을 나눈 일을 새 언어 기능 수로
세지 않습니다. 저장소 전체의 자동 분할은 이런 등록 소비자까지 계획에 담아야 합니다.

계속 전문화할 방향은 **의도를 옮기거나 다듬어도 연결이 유지되는 메타프로그래밍**입니다.
에이전트가 구조 변경을 제안하면 영향받는 소비자와 실제 적용 범위를 알 수 있어야 하고,
사람은 그 제안의 이유와 원본 위치를 읽을 수 있어야 합니다. 작은 성공을 저장소 전체의
성공으로 확장하지 않고, 새로 표현할 수 있는 Gooo 행동·유지된 소비자·남은 수작업을
각각 봅니다. 이번 작업은 고정 본문 생성기의 연결을 닫습니다. 동적 소비자 발견, 전체
쓰기 계획과 복구, 묶음 소스의 조립·표현식 조회는 계속 남아 있습니다.

## 실제 등록 누락을 다음 변경의 사전 관측으로 돌려놓기

회복 소스를 나눈 뒤 발생한 등록 누락은 반복 가능한 개발 문제입니다. 이제 기존 분할
계획을 문법 소스 목록에도 적용해, 쓰기 전에 새로 등록할 파일을 알 수 있습니다. 원본과
제안된 구성을 같은 목록으로 비교하며 기존의 누락·미등록 항목도 함께 유지합니다.
실제 정책의 `NextObservation`을 별도 파일로 옮기는 검사에서는 새 파일 하나가 등록
대상으로 나타납니다. 예측 결과는 원본 바이트를 복사해 구성한 메모리 파일시스템을
기존 관측기로 다시 읽은 결과와 비교합니다.

이 과정에서 파일 경로의 정렬도 출처 기록의 일부임을 확인했습니다. 전체 경로를 단순히
정렬하면 디렉터리를 방문하는 기존 관측 순서와 달라질 수 있습니다. 새 형식을 하나 더
만드는 대신 기존 관측 순서를 보존했습니다. 검사 도중 원본이 바뀌면 제안을 다시
준비하도록 반환하고, 제안된 관측을 이미 설치된 파일의 기록으로 취급하지 않습니다.

제가 앞으로 줄이려는 것은 기능마다 새 도구를 붙이는 횟수보다, **같은 의도 변경을 여러
소비자에게 따로 설명해야 하는 횟수**입니다. 분할 의도와 원본 구간은 하나로 유지하고,
임베드·코드 생성·등록 목록이 각자의 관점에서 영향을 계산하게 합니다. 전체 저장소를
읽는 비용과 수작업 등록은 아직 남습니다. 다음 연결은 각 관측의 적용 범위를 유지하면서
필요한 수정과 복구를 한 쓰기 계획으로 준비하는 것입니다.


## 10월 26일: 실행 범위와 기원을 계획에 넣기

이번 단계에서 선택한 전문화 방향은 **출처를 따라 함께 바뀌어야 할 것을 구성하는
메타프로그래밍**이다. 파일을 작게 만들었다는 점수에 그치지 않고, 원래 선언의 ID와
바이트, 그 선언을 읽는 워크스페이스, 컴파일러의 등록 정보, 별도 실행 사례가 같은
변경을 가리키는지 확인한다.

기존 `SplitGoooSections(FileInput)` 활동에 명시적인 워크스페이스·소비자 범위·사례
입력을 연결했다. 이 입력은 이미 관찰한 파일 지표에 결합되며, 범위를 바꾸면 계획의
정체성도 바뀐다. 선택된 작업은 기존 CLI의 준비·반영 경로를 호출한다. 새로운 파일
수정 엔진을 만들지 않았으며, 결과는 임시 사본에서 구성한다. 에이전트의 실제 작업
폴더에 자동 반영하는 권한은 별도다.

재실행은 같은 Git 커밋을 서로 다른 임시 폴더에 복원해 확인한다. Git archive의
메타데이터와 실제 소스 파일을 구분하고, 파일 목록과 blob 바이트도 확인한다.
`export-ignore`나 `export-subst`로 원본 일부가 사라지거나 바뀐 사본은 해당 커밋의
완전한 실행 입력으로 받지 않는다. 원시 명령 출력의 해시는 남기고, 임시 주소를
정규화한 비교 값은 별도로 만든다. 이 구분이 없으면 동일한 작업도 실행한 폴더마다
다른 작업으로 기록될 수 있었다.

현재 실동작 관찰은 inventory 예제 한 건, 각 실행의 독립 사례 8개, 두 개의 새 사본을
범위로 한다. 전체 저장소의 자기개선 완료율로 확대하지 않는다. 입력 누락이나 중단은
미해결 상태로, 실제 실행에서 나온 실패는 반례로 유지한다. 작은 decision 모델은
소스가 허용한 후보 중 시도 순서를 정할 수 있고, 이 실행 경로는 모델 없이 동작한다.

앞선 PR의 원본 CI 실패에서는 추가 교훈 두 가지가 나왔다.

- 검사 자체가 원래 파일명을 전제로 하면 선언을 올바르게 재배치해도 깨진다. 검사도
  실제 선언과 필드 값의 출처를 따라가도록 수정했다.
- 패키지 하나의 읽기 예산과 여러 패키지의 의존 묶음 예산은 범위가 다르다. 파일
  1MiB·패키지 8MiB 한도를 유지하고, 전체 묶음에는 별도 16MiB 한도를 적용했다.
  이는 허용하는 입력량을 늘린 변경이며, 메모리 절감으로 표현하지 않는다.

Mac에서 전체 투영을 재현할 때에는 Linux 전용 namespace publisher가 지원되지
않는다는 제한도 확인했다. 로컬에서는 실제 생성기의 staged 결과를 별도 사본에 놓고
실패했던 컴파일·등록 검사를 확인했다. 이 관찰은 Linux의 원본 CI를 대신하지 않는다.

범위를 명시한 분할 실행의 첫 CI에서는 Git 목록과 archive가 다른 경로 범위를 읽었다.
CI의 `GIT_WORK_TREE`와 호출한 하위 폴더가 archive에 섞여, 전체 커밋 파일 목록과
맞지 않는 사본이 만들어졌다. 같은 환경으로 로컬 실패를 재현하고 두 조회 모두 지정한
Git 저장소에서 실행하도록 고쳤다. 원본 바이트·전체 파일 목록 검사는 유지한다.
호출자의 경로 설정을 넣은 상태의 독립 사례 8개와 두 새 사본의 재실행도 검사한다.

다음에는 다음 비용을 각각 관찰한다.

1. 새 입력 종류를 연결할 때 손으로 고치는 기존 모듈 수와 추가되는 Go 구현량.
2. 명시한 소비자, 실제 발견한 소비자, 다시 읽은 소비자와 실행 사례의 각각의 분모.
3. 대상 선택부터 제안·반영·평가까지의 단계별 시간과 미해결 원인.
4. 사람이 보는 이름·주소·설명 변경 때문에 불필요하게 다시 실행한 작업 수.

PR 설명 수정도 현재 `edited` 이벤트의 CI 대상이다. 이번 동일한 소스에 대해 두
CI 실행이 만들어지고 앞 실행이 취소된 이력도 남겼다. 다음 게시에서는 설명을 먼저
준비하고 소스를 한 번 올리는 순서를 사용한다. 장기적으로는 소스·대상 브랜치·승격
요청의 변화와 설명만의 변화를 구분하되, 승격에 필요한 기존 호출 경로를 보존해야 한다.

새 기능의 수보다 이 경로를 다른 실제 사용처가 재사용할 수 있는지가 다음 판단 기준이다.
[범위 입력과 실행 계약](../language/workspace-manifest.md#binding-a-source-split-into-a-metric-plan)에
현재 입구와 제한을 함께 기록했다.

전체 검사에서는 실행기 등록을 바꾼 뒤 `examples/self-improvement/main.gooo`가 이전
실행기를 계속 요구하는 불일치도 발견했다. 관측기는 실제 등록 목록과 Gooo 선언의
`Execute` 입력을 비교해 이를 거부했다. 현재 선언을 새 실행기에 연결하고, 입력이나
정체성이 빠지면 여전히 거부하는 회귀 검사를 유지했다. 앞으로의 동시 변경 계획에는
파일의 직접 사용처뿐 아니라 이렇게 기능을 설명하는 계약의 사용처도 포함해야 한다.

스냅샷 실행의 여섯 필수 검사와 출처 증명이 통과한 뒤, 같은 소스의 CodeQL 결과에서
압축 해제의 파일 접근 경고를 확인했다. 각 검사가 관측한 범위가 달랐다. 작은 임시
디렉터리 반례에서는 추출 대상 안의 부모 링크가 외부 폴더를 가리킬 때 파일과
디렉터리 생성이 그 링크를 따랐다. 재현 범위는 추출 함수에 이미 링크가 있는 입력이다.

추출은 Go의 [`os.Root`](https://go.dev/blog/osroot)를 열어 실제 파일 접근을 해당
디렉터리 안에 묶도록 바꿨다. Git의 파일 목록·blob 바이트 검사는 유지하며, 디렉터리
이름은 점 경로나 중복 구분자를 정규화해 받아들이는 대신 원래 표기가 유효한지 검사한다.
외부 링크의 파일·폴더 생성 거부와 정상 중첩 파일의 원본 보존을 별도로 확인한다.

다음 제출부터는 새 소스의 필수 실행 검사와 별도 정적 진단을 초기에 함께 수집한다.
긴 실행 검사 뒤에 정적 실패를 처음 발견하는 지연을 줄이고, 수정은 그 진단의 원본
소스와 반례에 연결한다. 성공한 검사와 아직 해결되지 않은 진단을 각각 유지하며,
수정된 소스는 새 CI에서 다시 확인한다.

## 마지막 변환본에 검사를 연결하기

의미 검사 파이프라인을 읽다가 전체 Go 검사가 첫 투영 뒤에 실행되고, 그 뒤의
고정점 반복에서도 소스를 변경하는 순서를 확인했다. 실제 셸의 실행 순서와 검사
함수를 사용한 작은 재현에서, 통제된 후속 변환이 함수 결과를 0에서 1로 바꿨다.
앞선 검사 기록은 성공으로 남았고 마지막 소스의 독립된 Go 검사는 실패했다.
이 재현은 변환 콜백을 통제한 파이프라인 범위이며, 원래 추출기가 같은 의미 변경을
만들었다거나 전체 CI가 그 변경을 승인했다는 관측을 포함하지 않는다.

기존 전체 검사를 마지막 변환 뒤로 옮겼다. 실행 횟수는 한 번으로 유지하며, 반례가
남은 경우의 보고서도 현재 검사 결과가 생긴 뒤 작성한다. 고정점이 닫히는 경우와
반례가 남는 경우에서, 동작을 보존한 변환과 독립 기대값을 깨뜨린 변환을 각각
검사한다. 반례의 상태와 검사 성공 여부는 계속 별도로 남긴다.

출처는 원본 커밋만으로 끝나지 않는다. 같은 커밋에서 출발해도 변환 전후의 프로그램은
서로 다른 검사 대상이다. 후속 변경 계획에서도 어떤 소스 상태를 읽고 검사했는지를
연결하고, 마지막으로 쓰인 결과 뒤에 검사가 놓이는지 확인해야 한다.

## 기대와 관측을 서로 다른 소유자로 두기

생태계의 실제 세 검증기에서 같은 여덟 개 import path가 반복됐다. 처음에는 이들을
의존 모듈 목록으로 묶으려 했지만, 실제 내용은 한 애플리케이션의 Go 패키지 구성이다.
원본 Gooo에서 생성기로 이어지는 관계와 배포할 소스 목록도 각각 다른 범위였다.
이 셋을 같은 목록으로 합치면 원래의 변경 의도를 잃는다.

[runtime-package-surface](../../examples/runtime-package-surface/README.md)는 기대하는
패키지와 비교 규칙을 Gooo로 선언한다. Go의 기존 조회가 실제 패키지를 관측하고,
Gooo가 누락·추가·중복을 분류한다. 관측 결과로 기대 목록을 생성하지 않으며 입력의
순서·대소문자·공백은 그대로 보존한다. 출처 참조는 원본 출력에 연결하는 어댑터의
책임이고, 모델 호출이나 새로운 생산 Go 비교 알고리즘은 추가하지 않았다.

독립 기대값 14개는 실제 실행과 저장 실행의 재생을 확인한다. 기대 선언을 잘못
바꾸는 반례에서는 기존 기대값이 실패해야 한다. 실제 도구 관측은 기대값이 없는
`OBSERVED`이며, 이 관측을 테스트 정답률의 분자에 더하지 않는다.
[소비자 연결 #237](https://github.com/kimjooyoon/gooo-go-ports/pull/237)은 세 검증기의
실제 관측을 같은 Gooo 평가기로 전달한다. 소비자의 컴파일러 고정, 생성 바이트와
CI는 그 저장소에서 검증한다. 이는 내부 소비 사례 하나이며 외부 채택 수로 세지 않는다.

다음 전문화는 **선언·관측·소비자 관계를 구분한 동시 변경**이다. 한 소스에서 모든
답을 생성하는 것보다, 의도의 소유 위치를 줄이면서 독립 검사가 잘못된 변경을 잡게
하는 것이 중요하다. 원본과 연결 관계를 남기면 에이전트도 무엇을 바꿀지와 무엇을
다시 확인할지를 구분할 수 있다. MMO의 문맥·버전·출처를 가진 매핑은 이런 관계를
설명하는 데 적용하며, 의미 동일성이나 실행 권한은 각 계약에서 별도로 판단한다.

## 자기개선 계약도 의미 ID로 읽기

계약을 검사하는 코드에는 `Measure`, `Execute`, `SourceTree` 같은 표시 이름에
의존하는 부분이 남아 있었다. 원래 ID와 PROV 관계가 같아도 한글 이름으로 바꾸면
검사가 실패하는 반례를 먼저 재현했다. 이는 기원이 같은 선언을 다른 표현으로 보는
것과 실제 기능을 변경하는 것을 관측기가 구별하지 못한 문제다.

Gooo 활동에 기존의 자동 생성 ID를 명시하고, 관측기는 내려진 의미 IR의 ID,
`used`, `wasGeneratedBy` 관계를 읽도록 바꿨다. 여러 입력의 순서는 기존 IR의 입력
순서에서 읽는다. PROV의 집합 관계만으로 순서나 반복 입력을 지우지 않는다.
표시 이름은 보고서에 남기고, 실행기마다 입력 사실의 원본 파일·바이트 구간을 함께
반환한다. 구간은 그 보고서가 가리키는 소스 해시 안에서 해석해야 한다.

검사 범위는 자기개선 계약의 29개 선언을 개별로 바꾸는 경우와 모두 바꾸는 경우다.
의미 ID와 관계를 보존한 30개 이름 변경에서 같은 의미 해시를 요구한다. ID, 입력
순서, 결과나 관측 사용 관계를 바꾼 반례와 중복 ID도 별도로 거부한다. 이 결과를
다른 모든 native 소비자가 임의의 이름 변경을 지원한다는 주장으로 넓히지 않는다.

생태계 쪽에서도 새 Gooo 커널 하나를 연결할 때 의존 목록 세 곳과 번들·소스 사본
두 곳을 함께 고쳐야 한다는 사용 피드백이 나왔다. 이 중복을 다음 실제 적용 대상으로
삼는다. 버전·입력 한도·선언의 소비자를 먼저 읽고 필요한 수정을 계산하는 흐름이
필요하다. 첫 native 실행에서 입력 경계를 넘은 여섯 사례를 활동의 결과와 혼동했던
피드백도 있어, 입력 수용 여부와 활동 동작의 분모를 나누는 원칙을 유지한다.

첫 전체 검사에서는 계약 README의 설명을 갱신한 뒤 시각 자료가 이전 문서 해시를
가리킨 불일치도 발견했다. 현재 설명과 장면의 의미를 확인하고 참조 해시를 갱신했다.
이미지나 검사의 판정 규칙은 바뀌지 않았다. 이 참조도 소스 소비자의 한 종류다.
앞으로 변경 계획은 실행 코드뿐 아니라 명시적인 문서 참조를 함께 찾아야 하며,
해시 갱신 가능 여부와 해당 설명이 여전히 맞는지는 서로 다른 판단으로 남겨야 한다.

별도 호환성 검토에서는 정책 선언이 entity/activity 그래프 밖에 있다는 점도 확인했다.
구문 선언 수와 그래프 노드 수를 같다고 본 새 검사는 유효한 `policy`를 거부했다.
이 가정을 제거하고 정책의 의미 해시·이름 변경·잘못된 상태 참조를 별도로 검사했다.
