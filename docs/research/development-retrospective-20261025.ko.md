## 구조적으로 남은 문제

현재 기능별 기록·계획·CLI가 늘고 있습니다. 코드 줄 수만으로 낭비를 판단하기보다
새 의미 하나를 추가할 때 기존 안정 모듈을 얼마나 수정하는지 봐야 합니다.
워크스페이스 로더처럼 여러 소비자가 실제 같은 계약을 쓰는 부분부터 공유합니다.
도메인별 원본 의미가 다른 기록을 이름이 비슷하다는 이유로 합치지는 않습니다.

출처는 결과의 점수보다 어디서 왔고 어떤 변환을 거쳤는지 설명해야 합니다.
실제 실행 결과, 과거 실행의 읽기, 새 소스의 제안은 서로 다른 기원을 갖습니다.
현재 반례를 새 구현에 넣어 통과해도 원본 CI의 실패는 그대로 남습니다.

공유 소스는 변화의 단위를 다시 보게 합니다. 같은 파일을 아홉 워크스페이스가
사용하면, 파일 하나의 분할 성공은 아홉 문맥의 보존을 뜻하지 않습니다. 출처와
소비자 관계를 따라 수정할 선언을 묶고, 각 문맥의 진입점·타입·실행 결과를 확인해야
합니다. 내용 해시가 같다는 사실과 같은 소스 발생을 가리킨다는 사실도 구분합니다.

`ecf07409c31be3e59700b042618c864bb03f21ca`의 추적 파일 감사에서는 80줄을 넘는
Gooo 파일 21개 중 10개가 외부 JSON 워크스페이스에 선언됐습니다. 검사한 정의는
111개이며 `examples/recorded-use-origins/inspect.gooo`의 선언 소비자는 9개였습니다.
이는 명시적인 파일 목록에서 확인한 참조 수입니다. 임베드·동적 로딩까지 포함한
전체 소비자 수나 메타 연산의 완료율로 사용하지 않습니다.

별도의 Go 1.27.3·darwin/arm64 조회에서는 공개 커밋 `67c1675ec`의 패키지 460개에서
직접 임베드하는 Gooo 소스 21개를 확인했습니다. Go의 `go list -json`이 제공하는
`EmbedFiles`·`TestEmbedFiles`·`XTestEmbedFiles`를 사용했습니다. 다른 플랫폼·태그와
동적 파일 읽기는 이 조회 범위에 포함되지 않습니다. 언어가 소비자를 찾는 다음 단계는
이런 기존 생태계의 관측을 출처와 함께 연결하고, 미관찰 범위도 유지하는 것입니다.

Gooo 저장소 전체를 자동 재포장하는 경로는 아직 완료되지 않았습니다.
공통 분할 기반의 다섯 소비자 중 네 경로가 준비된 실험 브랜치가 있고,
Gooo 저장소 소비자는 추가 연결이 필요합니다. 이번 파일 분할 CLI를 이 전체
연산의 구현으로 바로 등록하지 않습니다. 단일 파일·임베드 입력·물리 저장소 투영의
후속 계약도 각각 닫아야 합니다.

## 다음 기능의 순서와 완료 기준

1. **Gooo가 자신의 소스를 나누는 경로.** 공통 로더와 분할 결과를 실제 저장소 소비자에
   연결합니다. stable ID·import·실행 결과·정확한 원본 바이트 구간이 보존돼야 합니다.
   지원하지 않는 입력은 원인과 다음 작업을 반환하고, 처리한 것처럼 세지 않습니다.
2. **선언에서 후속 소비자를 찾는 변경 계획.** 도구 버전이나 의미 선언 변경이 어떤
   투영·검사에 닿는지 출처 관계로 찾아냅니다. 누락 소비자는 전체 범위를 유지합니다.
   새로운 기능 하나를 넣을 때 손으로 연결해야 하는 기존 모듈 수를 기록합니다.
3. **에이전트가 바로 사용할 제안과 반영.** 하나의 실행 가능한 작은 예제로 시작해
   계획·적용·변경된 입력 거부·재실행 거부를 같은 공개 경로에서 설명합니다.
   사람에게 보여주는 렌즈의 설정 오류는 실행 의미나 필수 검사를 바꾸지 않습니다.
4. **작은 decision 모델의 제한된 선택.** 소스가 허용한 후보 중 선택할 곳이 실제로
   여러 개인 경우에 연결합니다. 모델 없는 결정론적 경로, 호출 수, 선택 후 독립
   평가의 분모를 유지합니다. 현재 시간 계산과 파일 분할은 모델 호출이 필요 없습니다.

새 CLI를 추가하기 전에는 기존 선언·IR·계획·반영 경로가 그 일을 표현할 수 있는지
확인합니다. 첫 목표는 손으로 쓰는 연결 코드가 줄고, 에이전트가 실패 원인을 읽고
다음 작업을 고를 수 있는 것입니다. 사용자의 CI에 추가 학습이나 무거운 모델,
자동 업로드를 기본 요구하지 않습니다.

## 출처를 변경의 범위까지 연결하기

현재 전문화 방향은 **출처가 있는 변경의 영향 범위와 동시 수정**입니다.
반복 구현을 함수로 모으는 것에서 더 나아가, 한 선언을 바꿀 때 어느 소비자가 함께
바뀌어야 하는지 Gooo의 기존 의미 이미지와 선언 관계로 확인하려 합니다.

이번 공유 소스 반례에서는 두 패키지가 한 파일을 읽고 있었습니다. 파일을 나누면서
첫 패키지의 목록만 바꾸면 두 번째 패키지의 선언 일부가 사라졌습니다. 그런데 해당
선언이 현재 진입점에서 쓰이지 않으면 남은 프로그램은 여전히 유효했습니다.
따라서 컴파일 성공과 기존 의미 보존은 별도 관측입니다. 전체 소비 패키지를 함께
계획하고, 실제 파일 목록을 다시 읽은 이미지와 독립된 실행 기대값까지 비교합니다.

같은 내용을 읽었다는 관측도 충분하지 않았습니다. 폴더 별칭과 대소문자 별칭은
다른 문자열 경로로 같은 쓰기 대상에 도달할 수 있었습니다. 파일 교체 전에 실제
쓰기 후보를 읽기 관점에 투영해 기존 컴파일러로 다시 검사합니다. 하드링크는 원래
내용과 inode가 같아도 별도 디렉터리 항목의 교체에는 영향을 받지 않아 구분합니다.
주소 해석은 Go 호스트의 파일 기능이고, 선언 보존은 기존 Gooo 의미 검사가 담당합니다.

앞으로도 원본 바이트의 해시, 안정된 의미 ID, 읽은 문맥, 변경이 도달하는 파일 항목을
하나의 식별자로 합치지 않습니다. 각각 무엇을 식별하고 어느 관측에서 얻었는지 남깁니다.
지표도 명시된 소비자 수, 계획에 포함한 수, 실제 재로드한 수, 독립된 출력 조건 수를
각자의 분모로 유지합니다. 아직 발견하지 못한 소비자를 0개로 계산하지 않습니다.

다음 단계는 여러 workspace의 공동 변경을 실제 저장소 메타 작업에 연결하고,
단일 파일 생성기와 embed 사용처의 후속 변경을 표현하는 것입니다. 작은 decision
모델은 안정된 ID로 표현된 여러 합법적인 분할 후보의 순서를 고를 수 있습니다.
출처 누락을 추정으로 채우거나 검사되지 않은 경로를 완료로 바꾸는 역할은 부여하지 않습니다.

## 실제 파일 작업의 실패를 숨기지 않기

공유 소스 작업을 검토하면서 Go 호스트의 기존 두 경로에서도 반례가 나왔습니다.
임시 파일 쓰기의 오류 변수가 안쪽 범위에 가려져, 쓰기에 실패한 빈 파일을 원본에
덮어쓰고 성공으로 보고했습니다. 실제 읽기 전용 파일로 두 준비 위치를 각각 실패시켜
재현했고, 첫 오류를 전달해 원본 교체 전에 멈추도록 고쳤습니다. 정상 분할과 실패 시
원본 바이트·새 대상 부재·임시 파일 정리를 별도로 검사합니다.

또한 메타 실행의 읽기 전용 Git 사본은 이미 공통 정리 함수가 있었지만, 한 실행 경로가
일반 삭제를 사용해 사본을 남겼습니다. 작은 실제 Git 저장소에서 작업 실패 후 누수를
재현하고 기존 정리 함수에 연결했습니다. 출처를 남길 자료와 작업이 소유한 임시 사본의
수명을 구분해야 저장 공간 비용도 반복 실행 횟수에 따라 계속 쌓이지 않습니다.

## 이번 연결 작업에서 배운 점

공동 분할 예제는 실제 계산과 재실행 검사를 통과했지만 첫 전체 검사에서 소스 등록
누락이 발견됐습니다. 예제를 `examples/shared-source-consumers/main.gooo`로 두고
Gooo 등록 생성기가 아홉 멤버를 제안하도록 했습니다. v100의 136개 문법 사례는
그대로 보존하고 v101에 한 사례를 추가했습니다. 이 등록 수와 실제 활동 출력 여섯
개의 검사는 다른 질문에 답합니다. 사례 수를 올렸다는 이유로 기능 보존이 확인되지는
않습니다. 생성기는 필요한 연결을 함께 만들고, 독립 실행 검사는 결과를 확인합니다.

정리 회귀 테스트에서도 문맥의 혼동이 드러났습니다. 테스트는 임시 Git 저장소를
만들었지만 CI가 전달한 `GIT_DIR`을 조회해 다른 저장소의 스냅샷을 만들었습니다.
같은 환경 변수로 로컬 실패를 재현한 뒤, 테스트를 만든 저장소의 경로에 연결했습니다.
CI의 원래 실패를 남기고 수정된 소스의 결과를 따로 기록합니다.

두 경우 모두 한 도구 내부의 성공만으로 연결 전체를 설명하기 어려웠습니다.
다음 기능에서도 원본 ID, 소스 발생 위치, 소비자 문맥, 실제 실행 관측을 이어 읽는
작은 경로부터 완성하겠습니다. 반복되는 연결의 소유권을 Gooo 선언으로 옮기고,
Go에는 파일·프로세스·주소 해석 같은 호스트 동작을 남기는 방향입니다.

## 실제 소비자와 다음 전문화 단계

`249546c9e648dc47c6b5f9140e01491c89ca4ce3`에서는 실제 저장소의 유효한 워크스페이스
정의 111개를 읽고, `examples/recorded-use-origins/inspect.gooo`를 참조한 9개를
공동 계획에 연결했습니다. 새 정의를 다시 읽은 9개 의미 이미지는 각자의 계획과
일치했고, 계획 재생도 같았습니다. 소스 출력은 2개, 정의 출력은 9개이며 실제 쓰기는
0개였습니다. 계획 구성 147ms는 한 번의 로컬 관측입니다. 추적된 1MiB 이하 JSON 중
현재 워크스페이스 스키마를 선언한 파일만 조사했으며, 임베드·동적 읽기는 별도입니다.
이 9개 이미지 검사를 앞서 확인한 독립 기대 출력 6개와 합쳐 완료율로 계산하지 않습니다.

연결의 다른 쪽에서는 정상 보고서를 거부하는 문제가 나왔습니다. 소스 생산기는 중첩
Go 모듈의 소유 위치와 처리 불가 사유를 기록했지만 소비자는 그 필드를 몰랐습니다.
[후속 수정 #1795](https://github.com/kimjooyoon/meta-ontology-go/pull/1795)는 실제 생산기와
Gooo 메타 바인딩을 거친 입력으로 소유자 미확인·모듈 경계를 넘는 링크·필요한 도구
버전 부재를 검사합니다. 원래 파일 수와 줄 수, 적용 불가 사유를 함께 유지합니다.
새 사유를 지원할 때 정상 입력뿐 아니라 사유 불일치와 거짓 성공도 확인해야 합니다.

다음 언어 기능은 **원본 위치를 유지하는 명시적 소스 묶음**에 집중합니다. 현재 임베드
계약을 읽는 일부 Go 소비자는 한 파일을 전제로 합니다. 작은 읽기 전용 실험에서는
`operation-input-contract.gooo`를 두 구문 트리로 나누고 기존 변환기에 연결했습니다.
엔티티 10개와 활동 12개의 실제 파일·바이트 구간이 유지됐고 의미 IR 해시도 같았습니다.
이 실험은 임베드 소비자 이전이나 전체 ABI 검사의 완료를 뜻하지 않습니다.

구현 완료 기준은 명시한 멤버의 원본 바이트와 선언 위치를 보존하고, 기존 계약 검사를
그 묶음에 그대로 적용하는 것입니다. 누락 멤버·서로 다른 헤더·중복 ID·지원하지 않는
import 문맥은 빈 결과와 원인을 반환해야 합니다. 그 뒤 실제 임베드 소비자 하나를
연결해, 파일 분할 때문에 Go 연결 코드를 반복 수정하는 비용이 줄었는지 확인합니다.

에이전트에게는 원본 ID와 통과 여부에 더해 확인한 입력의 역할과 문맥도 전달해야 합니다.
같은 함수나 옵션이 다른 위치·타입·소비자에서 쓰일 때 기존 결과의 적용 범위가 달라집니다.
현재 표현이 담지 못하는 문맥은 미확인으로 남기고, 새 문맥의 기대 결과를 별도로
검사합니다. 사전빌드 도구 배포도 소스 revision·실제 Go 빌드 버전·필수 입력 계약을
함께 연결해야, 빠른 설치가 오래된 실행 경로의 재사용으로 이어지지 않습니다.
