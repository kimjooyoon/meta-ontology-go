# 작은 판단 모델을 Gooo에서 쓰기 쉽게 만들기

확인일: 2026-10-10. HN·GeekNews의 당일 목록과 GitHub 주간 페이지를 살펴보고,
관련 구현과 원문을 읽었습니다. GitHub 웹 조회는 3주 전 캐시가 섞여 있어 순위나 증가량을
최신 수치로 인용하지 않습니다.

## 이번에 적용한 것

일반 분기의 `body-context --model` 사전 확인을 구현했습니다. 선택지와 입력 규격을 먼저
확인하고, 실제 조립 때의 입력과 지문을 비교할 수 있습니다. 기존 자체 모델은 세 레코드
필드를 고르는 데 맞춰져 있습니다. 분기 하나가 그 규격에 맞지 않으면 이유를 남기고
결정론적 조립을 이용합니다. Gooo 소스는 후보와 사례를 정의하고 모델은 그 범위의 순서를 제안합니다.

| 읽은 자료 | 가져온 관점 | Gooo에 반영하거나 이어서 확인할 부분 |
| --- | --- | --- |
| [Microsoft-Decision-1, 10월 9일](https://commandline.microsoft.com/microsoft-decision-1-model-foundry/) | 고정 답안의 확률을 소프트웨어에서 바로 소비함; 별도 평가와 입력 변형을 고려함 | 선택지·입력 지문을 공개하고, 모델 입력 가능 여부와 실제 기능 사례 점수를 분리함 |
| [pg-jev](https://github.com/realZachi/pg-jev) | 의미 판단을 기존 연산에 조합하고, 결과 분포와 실제 요청 수를 관찰함 | 조건·변수·분기 안의 제한된 선택을 유지하고, 새 예측과 저장 재생의 횟수를 따로 셈 |
| [RAD Debugger](https://github.com/EpicGames/raddebugger) | 도구가 공통 debug 정보를 변환·읽고 원문 dump를 제공함 | 안정 ID, 원문, 정규화한 IR, 소비한 모델 입력을 연결해 확인함 |
| [Michael Lynch의 개발 글쓰기, 10월 7일](https://refactoringenglish.com/blog/anti-patterns-software-blogging/) | 독자가 바로 얻을 것을 먼저 보여 주고 필요한 배경을 짧게 설명함 | 새 안내를 실행 예제와 결과 필드부터 읽도록 씀 |

Microsoft의 속도·품질 수치는 공급자의 해당 모델 평가입니다. Gooo 실험의 수치로 옮기지 않습니다.
pg-jev의 배치 크기와 성능도 그 확장의 관측 범위입니다. Gooo의 작은 배열 모델에 같은 한계를
가정하지 않습니다. RAD의 debug 구조는 참고 아이디어이며 새 디버거를 가져오지 않았습니다.

## 없앤 제한, 이번에 추가하지 않은 것

사전 확인에서 모델을 레코드에만 지정하게 하던 CLI 제한을 없앴습니다.
이미 생성이 지원하던 경로별·두 선택·세 선택 계약을 같은 준비 코드로 확인합니다.
모델에 실제 입력 규격이 맞지 않는 이유는 유지합니다.

대형 범용 모델 설치나 새 네트워크 API는 이번 작업 범위에 추가하지 않았습니다.
가변 선택 수에 기존 세 선택 가중치를 그대로 재해석하는 변경도 하지 않았습니다.
구조의 숫자가 같더라도 레코드 필드 특징과 분기 특징은 서로 다릅니다. 입력을 억지로
세 개로 채우면 모델이 원래 배운 판단을 보존하는지 확인하기 어렵습니다.

## 다음 소형 모델의 판단 단위

일반 경로에 필요한 것은 변수 이름 고르기, 대입 대상 고르기, 피연산자 순서,
분기 배치, 실행 순서입니다. 현재 경로별 모델 계약은 선택 수 1..16을 이미 처리합니다.
그 계약의 소스 특징과 한글·영어 의도를 학습 단위로 쓰는 쪽을 먼저 실험할 수 있습니다.
기존 레코드 전용 모델의 결과가 그 학습 품질을 대신하지 않습니다.

후속 실험은 기존에 개발에 사용한 예제를 계속 개발 자료로 표시하고, 새 본문 계열을 별도
평가로 남깁니다. 첫 선택의 사례 만족도, 정해진 예산 안에서 조립한 만족도, 다른 입력의
실행 점수, 선택·의도 문장 변형에 따른 일관성, 실제 예측 수를 각각 기록합니다.
이 단계에서는 새 모델을 학습·업로드했다고 주장하지 않습니다.
