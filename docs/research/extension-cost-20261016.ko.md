# Gooo의 확장 비용: 최근 변경에서 확인한 것

2026-10-16. 최근 PR의 추가량이 크다는 지적을 실제 병합 이력과 구현으로 확인했다.
현재 판단은 **확장 비용을 줄일 필요가 있고, 아직 감소 추세를 입증하지 못했다**는
것이다. 추가·삭제 비율만으로 컴파일러의 개발 단계나 구조의 건강함을 판정하지 않는다.

## 집계 단위와 원본

GitHub에서 조회한 최근 PR 25개 중 `dev`에 병합된 11개를 사용했다.
`main` 승격 8개와 미병합·교체된 `dev` PR 6개는 이 집계에서 제외했다.
승격은 이미 수용한 소스의 전달이며 새 기능의 구현량으로 다시 세지 않는다.

- 기준 커밋: `814f4dd75828732348e6c114443236c1f899db94`
- 마지막 커밋: `5322c6fc58a6ad661b80f7229bbce54e88d6ca84`
- 수용한 PR: #1603, #1605, #1608, #1611, #1614, #1616, #1617,
  #1621, #1624, #1625, #1629.
- 각 PR의 첫 부모와 병합 커밋 사이의 추가·삭제가 GitHub의 PR 메타데이터와 일치했다.
- 전체 순변화는 위 두 커밋의 트리 차이로 별도 계산했다.

본문으로 전달받은 대표 PR 11개의 합계 `+25,216 / -1,035`는 전체 11개 번호가
제공되지 않아 같은 표본으로 재현할 수 없다. 명시된 6개 PR의 수치는 일치한다.
또한 #1629는 이번 확인 시점에 `dev` 병합을 마쳤다.

| 범위 | 추가 | 삭제 | 차이 |
| --- | ---: | ---: | ---: |
| 위 11개 수용 PR의 개별 diff 합 | 21,287 | 999 | 20,288 |
| 기준 트리 → 마지막 트리 | 21,071 | 783 | 20,288 |

개별 diff 합에는 같은 기간 다시 고친 줄도 들어간다. 두 트리의 차이는 최종 상태의
증가를 보여준다. 둘은 같은 기간의 서로 다른 측정값이다.

원본은 [GitHub 비교](https://github.com/kimjooyoon/meta-ontology-go/compare/814f4dd75828732348e6c114443236c1f899db94...5322c6fc58a6ad661b80f7229bbce54e88d6ca84)와
각 [PR](https://github.com/kimjooyoon/meta-ontology-go/pull/1629)의 메타데이터다.
아래 명령으로 고정된 두 트리의 파일별 원자료를 읽을 수 있다.

```sh
git diff --no-renames --numstat \
  814f4dd75828732348e6c114443236c1f899db94 \
  5322c6fc58a6ad661b80f7229bbce54e88d6ca84
```

| 파일 분류 | 파일 수 | 추가 | 삭제 |

| Go 테스트 | 114 | 6,235 | 14 |

| 문서 | 15 | 1,129 | 17 |

분류 순서는 `docs/observations/**`, 문서, `*_test.go`, `testdata`, 생성 Go,
나머지 Go, `.gooo`, 워크플로, 예제 데이터, 기타다. 생성 Go는 파일명
`.generated.go` 또는 `Code generated`와 `DO NOT EDIT` 표식으로 식별했다.
이번 범위에서 별도 testdata 분류는 없었다. 한 파일 안에 섞인 생성 영역까지
분리한 수치는 아니므로 첫 행을 정밀한 수작업 Go 측정값으로 사용하지 않는다.

`.gooo`의 `computes`에는 개발자가 작성하는 본문 로직도 있다. Go 텍스트를
원문으로 옮긴 양을 자동화 성과로 계산하지 않는다. 후속 비교에서는 생성 영역 외
Go와 원문의 수작업 본문을 함께 기록하고, 원문이 의미를 소유하는 범위는 별도로
평가한다. 이번 표는 그 본문까지 분해한 수작업 총량 지표가 아니다.

추가분의 약 51.1%는 테스트와 관측 기록이다. 생성 파일 외 Go도 약 33.2%를
차지한다. 테스트·원본 기록에는 유지 이유가 있지만, 이 비율이 구현의 복잡도를
설명하거나 정당화하지는 않는다. 압축 파일 12개는 행 수가 없으며 실제 바이트와
기록의 보존 비용은 별도로 봐야 한다.

## 구조에 대한 판단

### 1. 파일 수를 결합도로 읽으면 과장된다

#1629의 55개 파일 중 생성 파일로 식별되지 않은 Go는 21개다. 이 중 기존 파일을
수정한 것은 7개, 패키지 경계는 3개다. 테스트 15개, 관측 기록 14개도 전체 파일
수에 포함된다. 작은 선언·테스트를 파일로 나눈 효과가 있어 55개를 모두 안정된
핵심 모듈의 변경으로 해석하기 어렵다. 기존 파일이라는 사실만으로 안정성도 확정할
수 없다.

실제 diff에는 두 곳의 프로필 분기 복제를 `ReplayCase`로 모은 변경과 기존
`Cases` 원본 탐색을 재사용한 변경이 있다. 신규 기능과 구조 개선이 함께 들어갔다.

### 2. 연결·검사 설정의 전파는 실제 문제다

11개 중 10개 병합이 워크플로를 수정했다. 사용자용 `cmd/` 명령은 1개,
개발용 `scripts/` 실행 입구는 7개 새로 생겼다. 서로 다른 실행 효과와 플랫폼
관찰 때문에 필요한 부분도 있지만, 다음 기능에서도 별도 실행 입구와 검사 설정을
계속 추가해야 한다면 확장 비용이 커진다.

#1627·#1628의 원래 CI에서 소스 파일 수 `149 → 150`, 메타 소스 목록의 과거
기록 비교, Go 고정점 검사 문제가 드러났다. 특히 새 메타 소스를 추가할 때 현재
목록과 과거 목록의 동등성을 요구한 것은 도메인 보존 법칙이 맞지 않았던 경우다.
수용한 수정은 과거 순서를 보존하면서 현재 목록에 원본을 추가하는 경우를 구분한다.
전체 검사를 약하게 만들거나 원래 실패 기록을 지워서 해결하지 않았다.

고정된 현재 소스 집합과 독립 소비자의 기대값은 가치가 있다. 목록을 하나로 합쳐
생산자와 소비자가 같은 오류를 공유하게 만들면 이 가치가 줄어든다. 다음 단계는
원본 역할·버전·변경 법칙을 선언하고 기계적인 투영을 생성하되, 다른 경로에서
원본 집합과 보존 법칙을 검사하는 것이다.

### 3. 공통 IR은 이미 있다. 수용 경로가 아직 특수화돼 있다

Gooo는 이미 `bidir`·`semantic` IR과 안정 ID를 사용한다. 별도의 거대한 공통 IR을
만드는 것보다 기존 IR이 실제 생성·소비까지 반복 없이 전달되는 범위를 넓히는
편이 현재 문제에 맞는다.

`profile_migration.gooo`의 역할 선언은 20줄이지만 프로필 변경 PR에는 Go 구현
1,083줄이 추가됐다. 이 원문은 역할·기원을 선언하고 Go가 AST 수정과 바이트 보존을
수행한다. 선언만으로 새 변경 엔진 전체를 생성하는 상태는 아직 확인되지 않았다.
이 비대칭은 다음 개발에서 줄여야 할 구체적인 대상이다.

신규 등록은 9개 의미 산출물과 분모 이행을 다룬다. 프로필 변경은 같은 사례와
분모를 유지하는 3개 산출물을 다룬다. 요청·해시·파일이라는 모양이 비슷해도 이 두
연산의 보존 법칙을 하나로 취급하지 않는다. 공유할 부분은 원본 고정, 안정 ID 대응,
소유 파일 판별과 기계적인 전송이다.

## 진행 중인 여섯 필드 정책에 반영한 결정

[`policy.gooo`](../../internal/meta/metricprogram/unresolvedpolicy/policy.gooo)가 문자열
세 개와 불리언 세 개의 실제 값을 모두 정하도록 개발했다. Go의 기본 불리언 값에
의존하던 부분을 원문 생성식으로 옮겼다. 같은 안정 ID를 가진 소스·네이티브 필드의
표시 이름을 바꿔도 값이 전달되는 실제 네이티브 관찰을 별도로 보관했다.

반복이 확인된 두 소비자에서 다음 구현을 공유한다.

- `internal/recordbridge`: Go 필드의 안정 ID·타입·전체 태그 구문 해석.
- `internal/projectionbundle`: 이전 manifest가 소유한 퇴역 파일 판별과 파일 교체.

레지스트리 생성기와 정책 생성기가 이를 사용한다. 도메인별 반환 형식과 완전성
조건은 각 소비자가 유지한다. 공통 기록 프레임워크·신규 CLI·새 CI 게이트는 이
분석을 위해 추가하지 않았다.

분석 시점의 미게시 Go diff는 구현 파일 `+446/-180`, 테스트 `+421/-26`,
생성 파일 `+55/-15`였다. 공유 구현을 만들었어도 구현의 순증가는 266줄이다.
이번 한 사례만으로 수작업 Go 비용이 줄어드는 추세를 주장할 수 없다. 개발 중
별도 단계의 새 사례 25개는 통과했으며, 최종 통합 소스의 원래 CI 수용은 별도다.

## 다음에 측정할 확장 비용

지표는 같은 종류의 작업끼리 비교한다. 새로운 문법 의미의 구현과 기존 레코드에
연산 하나를 선언하는 작업을 같은 분모에 넣지 않는다. 기능 하나의 정의는 작업을
시작할 때 고정한 원문 예제·입출력·보존 법칙으로 남긴다.

| 지표 | 기록할 값 | 해석 |
| --- | --- | --- |
| 수작업 구현 변화 | 생성 영역을 제외한 Go 추가·삭제·기존 선언 수정, 새 연결 코드 | 같은 확장 유형의 다음 사례에서 비교. 테스트·생성물과 분리. |
| 전파 범위 | 기존 구현 패키지, 프로토콜, 레지스트리, CLI, 워크플로의 변경 경로 | 각 변경이 요구되는 원본 의미를 연결. 파일 수만 점수화하지 않기. |
| 원문 소유 범위 | 각 출력 필드·역할·분기의 원본 선언 및 Go의 의미 기본값 | 출력 값의 출처를 따라갈 수 있는지 확인. 전체 언어 비율로 확대하지 않기. |
| 재사용 비용 | 초기 공통 구현과 후속 소비자 연결의 Go 변화 | 추출 직후 순증가도 그대로 기록. 후속 사례에서 이득을 확인. |
| 독립 확인 | 원문 기대값과 별도 네이티브 소비자의 결과·경계 사례 | 같은 생성기가 만든 기대값만으로 완전성을 판정하지 않기. |
| 전달 비용 | 원래 CI의 실행 수·대기·수행 시간, 실패·교체 이유 | 승격과 재실행을 기능 구현 비용에 중복 집계하지 않고 별도로 기록. |

바로 이어갈 순서는 다음과 같다.

1. 여섯 필드 원문과 기존 두 생성기의 공유 경계를 최종 소스 CI로 확인한다.
2. 다음 동일 유형의 연산·필드 확장에서 기존 생성기를 재사용하고 새 연결 코드의
   필요량을 기록한다. 새로운 의미 규칙이 필요한 부분은 원문과 IR의 책임을 명시한다.
3. 반복된 등록 목록·워크플로 수정이 어떤 원본 역할에서 발생하는지 좁혀 선언과
   투영의 경계를 개선한다. 독립적인 원본 집합·이력 보존 검사는 유지한다.
4. 두 후속 사례가 생긴 뒤 같은 유형의 비용이 줄었는지 비교한다. 원래 사례와
   원본 커밋을 남기고, 삭제량이나 생성 비율에 단독 목표를 두지 않는다.

이 순서는 언어의 새 표현력과 확장 비용을 함께 보려는 선택이다. 사용자가 적은
현재 단계에서 개발 단계나 장기 비용 곡선을 확정할 자료는 아직 부족하다.

## 2026-10-17 재검토: 지적에 동의하는 범위와 다음 판단 기준

원래 분석의 문제 제기는 유효하다. 다만 추가·삭제 비율에서 언어의 개발 단계를
추론하거나, 이후 전체 Go 코드가 감소해야 성숙한다고 판단하기에는 근거가 부족하다.
새로운 의미를 구현하는 비용과 이미 지원하는 의미를 조합하는 비용을 구분해야 한다.
후자의 같은 유형 사례에서 수작업과 변경 전파가 줄어드는지를 확인한다.

고정된 원래 기간을 다시 읽어 위 표의 `+21,071/-783`, 개별 PR 합계
`+21,287/-999`, 워크플로 변경 `10/11`을 재확인했다. 원문에 제시된 대표
11개의 전체 번호는 여전히 없어 `+25,216/-1,035`의 동일 표본 재현은 하지 못했다.
현재 #1629는 병합됐으므로 이를 미병합으로 부른 설명에는 시점 차이가 있다.

### 원래 기간 뒤의 수용 변경

이후 `dev`에 병합된 [#1630](https://github.com/kimjooyoon/meta-ontology-go/pull/1630),
[#1633](https://github.com/kimjooyoon/meta-ontology-go/pull/1633),
[#1635](https://github.com/kimjooyoon/meta-ontology-go/pull/1635)를 별도 기간으로
읽었다. 승격 #1636과 병합되지 않은 #1631·#1634는 구현량에 더하지 않았다.

| 두 트리의 차이 | 추가 | 삭제 |
| --- | ---: | ---: |
| 전체 | 2,815 | 261 |
| 생성 파일로 식별되지 않은 Go | 487 | 196 |
| Go 테스트 | 963 | 25 |
| Gooo 원문 | 27 | 0 |

이 범위에는 워크플로 수정과 새 `cmd/`·`scripts/` 실행 디렉터리가 없다.
기존 구현 Go 파일은 19개, 그 파일이 속한 패키지는 6개다. 필드 정책 확장,
네이티브 검사 자원 조정, 전송 경계 수정이 섞인 기간이므로 원래 기간과의 행 수
차이를 추상화 효율의 개선율로 읽지 않는다. 재현 범위는 다음 두 트리다.


유지한다. 이번 재검토에서는 소스와 병합 이력을 읽었으며 검사를 다시 실행하지 않았다.

### Gooo가 실제 동작을 소유하는지 확인하기

`profile_migration.gooo`는 역할과 연산의 기원을 선언하고, Go가 AST 수정과
원본 바이트 보존을 구현한다. 역할 선언의 존재만으로 변경 알고리즘이 Gooo에서
생성됐다고 평가하지 않는다. 반면 `unresolvedpolicy/policy.gooo`는 출력 문자열
세 개와 불리언 세 개의 실제 값·분기를 정한다. 두 사례는 원문이 소유하는 범위가
다르다. `.gooo` 파일 수나 생성 코드 비중만으로 이 차이를 나타낼 수 없다.

다음 같은 유형 확장에서는 다음 질문에 답을 남긴다.

1. **동작 변경의 출처**: 값이나 분기를 원문에서 바꾸면 기존 투영·소비 경로로
   전달되는가? Go에도 같은 결정을 다시 적어야 하는가?
2. **추가 수작업**: 생성 영역 밖 Go와 `.gooo`의 수작업 본문을 합쳐 무엇을
   작성했는가? 본문의 위치만 옮긴 것을 자동화 이득으로 세지 않는다.
3. **변경 전파의 이유**: 기존 패키지·프로토콜·등록 목록·CLI·워크플로 수정마다
   어떤 새로운 의미나 실행 효과가 이를 요구하는가? 기계적인 투영은 따로 센다.
4. **의미 보존**: 안정 ID, 원본 기원, 기존 사례의 의미와 분모가 유지되는가?
   이름이 비슷한 기록이나 변경 계획에도 서로 다른 보존 법칙을 남긴다.
5. **독립 기대값**: 생성된 산출물과 별도로 작성한 기대값·반례가 있는가?
   생산자와 검사가 같은 실수를 공유할 가능성을 확인한다.

이 분석 때문에 별도 점수 체계·CLI·필수 CI를 추가하지 않는다. 기존 PR 설명과
관측 기록에 위 답을 남기고, 두 후속 동일 유형 사례가 쌓이면 초기 공통화 비용과
후속 연결 비용을 함께 비교한다. 현재 확인한 개선은 두 생성기의 공통 경계와
원문 소유 필드의 확장이다. 수작업 비용의 지속적인 감소는 아직 입증되지 않았다.

### 후속 구현에서도 비용을 그대로 세기

관측 집합의 결합·누락·중복 판단을 Gooo 원문에서 실행하는 변경은
[#1638](https://github.com/kimjooyoon/meta-ontology-go/pull/1638)로 `dev`에,
[#1639](https://github.com/kimjooyoon/meta-ontology-go/pull/1639)로 `main`에
반영됐다. 비교 범위는 `0f19a7d53b8a9af4689451fbf085e42ef9160187`에서
`2ac41bf496556d7f1cf39abbe10572b6e520b1af`까지다. 승격은 다시 더하지 않는다.

| 변경 범위 | 추가 | 삭제 |
| --- | ---: | ---: |
| 전체 32개 파일 | 1,573 | 23 |
| `internal/`의 생성 표식 외 Go | 436 | 17 |
| 기존 CLI의 Go 연결 | 29 | 0 |
| 기존 CI 실행기의 Go | 305 | 2 |
| Go 테스트 | 348 | 1 |
| Gooo 원문 | 89 | 0 |

새 CLI·실행 디렉터리는 없고, 기존 워크플로 한 곳의 입력 전달이 바뀌었다.
Gooo가 열 개 출력 필드의 실제 판정을 소유하게 됐지만, 원문·입력·영수증을 연결하고
독립적으로 재구성하는 Go는 늘었다. 표의 구현량과 원문 본문을 개발 비용에 포함한다.
한 번의 의미 확장으로 같은 유형의 후속 연결 비용이 감소했다고 말할 수는 없다.

이후 확인한 빈틈은 새 관측 영수증의 경계 검사 범위다. 기존 16개 반례는 이전
영수증 형식을 대상으로 하므로 새 형식의 모든 거부 경로를 확인한 수로 사용할 수
없다. 이를 보완하는 13개 검사는 기존 실행기·입력 저장·수신 경로를 재사용한다.
원문·IR·생성기에 새 기능을 넣는 작업과 검사 비용을 구분해 기록한다. 원본 묶음은
유지하고 변경된 멤버만 저장하며, 보고서는 저장된 영수증의 식별 해시를 참조한다.
이 보완의 새 소스 CI 결과는 별도로 확인할 단계다.

이후 보완은 [#1640](https://github.com/kimjooyoon/meta-ontology-go/pull/1640)으로
수용됐고, [#1641](https://github.com/kimjooyoon/meta-ontology-go/pull/1641)을 거쳐
`main`의 `969eb8c07fa3984d5287d049e2ffec1b2ce6a077`에 반영됐다. 새 영수증의
13개 수신 경계 검사는 기존 16개와 구분해 확인했다. 이 결과는 해당 경계의 확인이며,
전체 언어의 완전성이나 같은 유형의 후속 개발 비용 감소를 뜻하지 않는다.

확인 중 기존 PR 워크플로의 변경 경로 목록에 이 실행기 디렉터리가 빠진 점을
찾았다. 실행기 내부를 바꿔도 실제 생산자·수신자 검사가 선택되지 않던 누락이다.
기존 워크플로에 디렉터리 전체를 한 번 선언해 이후 같은 실행기의 사례 추가가
검사 선택으로 이어지게 한다. 새 작업이나 별도 게이트를 만드는 변경은 없다.

다음 개선의 판단 기준은 같은 의미를 두 곳에 다시 적는 결정의 수와, 같은 유형의
확장에서 수정해야 하는 기존 경계다. 원문의 결정을 보존하는 전달은 공통화하고,
독립 기대값과 도메인마다 다른 보존 법칙은 각각 유지한다. 전체 삭제량이나 생성
비율에 목표를 두면 필요한 검사·출처까지 줄이는 방향으로 흐를 수 있다.

### 후속 언어 기능: Text 필드의 크기 조건

`max_utf8_bytes`는 기존 수신 제한을 일괄 변경하는 대신 원문 필드가 값의 범위를
정하도록 만드는 새 의미다. 기존 IR의 필드에 조건을 전달하고 형식·의미 해시·
Go 투영·실행 경계에서 이를 보존한다. 이 첫 구현에서 필요한 커널 비용과 같은
조건으로 다른 필드를 선언하는 비용을 구분한다.

프로필 ID 목록과 지원 기능을 여러 소비자에서 반복하던 부분은 하나의 정확한
커널 조회로 모은다. 서로 다른 두 JSON 수신 경로에서 드러난 문자 해석 차이는
기존 Gooo 이스케이프 정책과 원본 바이트 검사를 공유하도록 정리한다. 과거 생성
기록과 생성 영역의 원래 바이트는 보존한다.

공개 예제 한 개를 구문 레지스트리에 추가하고, 공개 CLI의 실행 원본은 기존 CI
산출물에 보관한다. 새 CLI·워크플로·작업은 추가하지 않는다. 커널과 검사 소스는
증가하며, 전달할 필드와 실제 새 의미가 늘어난 비용을 그대로 기록한다. 이 변경의
원래 CI 수용과 다음 같은 유형 선언의 비용 비교가 후속 확인 대상이다.

이번 검토의 판단은 다음과 같다. 전체 행 수가 늘어도 새로운 의미가 원문 한 곳에서
정해지고 기존 경로로 전달될 수 있다면 표현력의 진전이다. 반대로 같은 종류의
선언을 하나 더 쓰는 데 의미 판정과 연결 코드를 다시 작성해야 한다면 확장 비용이
남아 있다. 새 커널을 만드는 첫 비용·후속 선언 비용·독립 검사와 원본 보존 비용을
각각 기록하고, 동일 유형의 후속 사례로 공통화의 효과를 판단한다.

## 소스 구성 배지

README의 두 배지는 기존 `scripts/line-metrics` CI 집계에서 프로젝트 루트의
`go_lines`, `gooo_lines`를 읽은 스냅샷이다. 현재 기준은 공개된 `0.6.39-dev`의
소스 [`4bfb816`](https://github.com/kimjooyoon/meta-ontology-go/commit/4bfb81640fcf485a022abc3b0484b2fd7bcb9f65)다.

| 집계 | 파일 | 물리적 행 |
| --- | ---: | ---: |
| Go (`.go`) | 9,074 | 619,112 |
| Gooo (`.gooo`) | 191 | 9,236 |
| 두 언어 합계 | 9,265 | 628,348 |

Gooo 비중은 `9,236 / 628,348 × 100 = 1.469886…%`를 소수 둘째 자리로
표시한 **1.47%**다. 주석·빈 행·테스트·생성 Go를 포함한다. 집계에서
`directories`의 `path="."`, `subject_kind="PROJECT_ROOT"` 행을 읽었으며,
별도의 변환 저장소를 나타내는 `storage_directories`는 사용하지 않았다.
파일별 행 수 합계와 루트 합계가 일치하고, Go/Gooo 파일 수는 해당 커밋의 Git 트리와도 일치했다.

원본은 [CI run 41049546849, attempt 1](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/41049546849)의
[producer artifact 12974783787](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/41049546849/artifacts/12974783787)에
담긴 `source-metrics.json`이다. ZIP SHA256은
`b0e21109ae7734c0ba1e04e80f4c68b6f521f8695ab3a2debb0f82a0288d2cb4`,
멤버 SHA256은 `24e2dd46ee30c3f65e129c3017d6abde25bfb6026887c1ab872113fe694254cc`다.
소스 SHA는 산출물 메타데이터와 보고서의 `commit_sha`에서 함께 확인했다.
이번 확인에서는 592,697바이트의 원본 ZIP만 보관하고,
38,865,625바이트의 확장 JSON 사본을 디스크에 추가로 저장하지 않았다.
이 수치는 소스 구성의 관찰값이며, 원문 의미 소유와 수작업 확장 비용은 앞 절의 기준으로 따로 읽는다.
