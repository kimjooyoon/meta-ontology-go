# Gooo가 만들고 있는 언어와 작은 모델

업데이트: 2026-10-11. Gooo 소스 안에서 유한 IR 후보 문법, 훈련·홀드아웃 사례와 시도 예산을 함께 선언해 실행할 수 있습니다.

다음 개발은 작은 업무 규칙의 변경, 결과 설명, 저장한 프로그램의 재사용에 집중합니다.
개발 소스는 같은 입력의 이전·이후 결과를 비교하고 분모를 명시한 Markdown 보고서로 내보냅니다.
[도입 계획](adoption-plan.ko.md)에 외부 반복 사용, 초기 작성 비용, 지불 의사를 확인할 기준을 정리했습니다.

**지금의 위치:** Gooo로 허용된 코드 조립 경로를 표현하고, 자체 소형 모델이
시도할 순서를 제안하며, 실행 결과를 다음 판단과 개발에 연결하고 있습니다.
공개 0.6.26은 선택별 사례 모델을 연결하며, 0.6.27 후보는 저장 결과 비교를 준비합니다.
초기 V3·V4 계약의 생성 400회·실행 800회 관측은 당시 범위의 기록으로 남깁니다.
아래에서 사용 가능한 경로, 실제 측정 범위와 다음 언어 과제를 설명합니다.

이번 방향의 연구 가설과 현재 증거의 한계, 결정론 경로와 모델 순위를
공정하게 비교하는 방법은 [검증 가능한 코드 조립 연구 계획](research/verified-construction-thesis.md)에
정리했습니다.

성장은 다른 개발자가 직접 따라 할 수 있는 작은 예제에서 시작합니다.
한 작업의 선언·선택·생성·실행을 보여주고, 같은 후보와 검증 조건에서
결정론 경로와 모델 순위를 비교한 뒤, 다른 도메인과 외부 사용 사례로
넓힙니다. 공개 결과에는 실패와 미관측도 함께 남깁니다. 예를 들어
4건을 관측해 0건을 충족한 `0/4`는 측정된 미완성(`PROGRESS`)이고,
관측 자체가 없으면 `UNKNOWN`입니다. `PROGRESS`라는 상태만으로
이전보다 나아졌다고 판단하지 않으며, 같은 기준의 이전 결과와 비교합니다.
공개할 자료와 확인할 증거는 연구 계획의 성장 단계 표에 정리했습니다.

### 다음 성장 단계: 작은 도구가 다음 프로그램을 구성하게 하기

Gooo의 차별점을 확인할 중심 과제는 **의미를 선언하는 언어와 선택을 돕는 모델을
독립적으로 발전시키면서, 실제로 쓸 수 있는 프로그램을 구성하는 것**입니다.
모델을 교체해도 허용된 선택지와 검사 기준은 같은 상태로 비교합니다.
유한 예산 안에서 선택한 프로그램과 동작은 달라질 수 있으므로 그 차이도 기록합니다.
도메인 선언을 바꿀 때는 바뀐 개념·타입·조건과 공통으로 사용하는 컴파일러 규칙을
함께 보여줍니다. 공방의 설계도와 부품, 조립 순서를 제안하는 역할을 따로 살펴보는 셈입니다.

현재 [Gooo 조립 정책](../examples/package-assembly-policy/README.md)은 후보의 실제 검사 결과를
읽고, 지원하는 레코드 선택 경로에서 계속 탐색할지 멈출지를 결정합니다.
정책도 다른 Gooo 패키지의 조건 함수를 재사용합니다. 저장한 일반 조립은
남은 예산으로 이어갈 수 있습니다. `body-compose`의
[보조 함수 조립 이어가기](../examples/dependent-continuation/README.md)는 보조 함수를 먼저
구성하고, 그 변경에 영향을 받은 호출자의 기존 후보를 같은 사례로 재검사합니다.
과거 정책과 점수는 당시 소스로 재현하며, 기존 후보·재검사·새 후보 수를 구분합니다.
이 경로는 레코드 선택 조립을 지원합니다. `package resume`에서도 저장한 패키지 조립을
명시적인 Gooo 정책으로 이어갑니다. 이전 정책의 소스 패키지와 앞서 채운 본문을
보존하고 새 모델 호출 없이 진행합니다. 다른 조립 프로필의 이어가기는 다음 과제이며,
선택지 안에 답이 없는 결과도 그대로 남깁니다.

이 과정에서 드러난 표현의 한계가 언어 개발의 우선순위가 됩니다. 진단 규칙의
반복 조건을 줄이기 위해 [타입이 있는 순수 함수 호출](../examples/pure-activity-calls/README.md)과
[패키지 사이의 호출](../examples/package-body-calls/README.md)을 추가했습니다.
조건문 안에서 보조 함수를 부르고, 그 보조 함수의 본문도 소스의 선택지로 조립할 수 있습니다.
호출 관계는 유한하며 재귀는 지원하지 않습니다. 학습 자료도 이런 구체적인 선언,
후보, 실패 사례와 실행 결과를 중심으로 쌓습니다.

공개 자료는 따라 할 수 있는 한글·영문 예제, 결정론·모델 비교, 저장된 프로그램의
재실행 순으로 구성합니다. 직접 설치해 본 관측과 다른 개발자의 재현을 구분하고,
외부에서 발견한 실패와 실제로 쓰인 작업을 다음 개발에 연결합니다.
[현재 증거와 다음 구현 범위](research/verified-construction-thesis.md#october-8-checkpoint-and-next-deliverable)에
시작 템플릿·도메인 도구·설명 도구의 위치를 모았습니다.

### 최근 실제 사용에서 확인한 내용

[별도 표준 라이브러리](https://github.com/kimjooyoon/gooo-standard-library)에 숫자·논리·문자열
함수 17개를 Gooo로 작성하고 세 패키지를 함께 사용하는 앱을 공개했습니다.
기존 자체 모델을 재학습 없이 썼으며, 이번 앱은 모델·고정 순서 모두 여덟 후보에서
완료됐습니다. 별도 열 입력과 부분 결과를 공개했고 로컬·Linux 실행을 대조했습니다.

가져다 쓰는 과정에서 Gooo의 패키지 이름과 import를 작업공간에 반복 작성하는
불편이 드러났습니다. 현재 개발 소스는 두 항목을 생략하면 Gooo 선언에서 읽습니다.
패키지 위치·소스 파일·진입점은 명시하고, 직접 적은 메타데이터는 소스와 대조합니다.
새 라이브러리·진단 프로젝트도 이 형식을 사용합니다. 기존 명시형과 같은 그래프가
만들어지고 실제 호출·재실행·조립 이어가기가 유지되는지 검사합니다.
[사용법](language/workspace-manifest.md#resolve-and-execute).

[0.6.10 개발 안내](releases/0.6.10-dev.md)는 패키지에서 문자열 길이를 계산하고
실제 입력을 처리하는 경로를 설명합니다. 이 수정으로 Gooo 소스를 고치는 도구를
패키지로 실행했습니다. 기존 그래프 모델은 후보 네 개, 고정 순서는 여덟 개를
시도해 완성했고, 별도 입력 542개와 저장 재실행을 확인했습니다. 모델의 첫 제안과
적은 시도 한도에서는 실패·부분 충족도 남았습니다. 결과 소스로 Gooo 함수를
수정한 뒤 다시 컴파일해 실행했습니다. 공개 파일의 배포 상태와 소스는 릴리스
페이지에서 확인할 수 있습니다.

[0.6.8 개발판 안내](releases/0.6.8-dev.md)는 계산한 지역 변수를 후보별로 결과에 연결하는
방법과 정수 나눗셈·나머지를 설명합니다. 작은 재시도 정책으로 고정 순서와 자체 모델의
조립, 저장 재실행을 비교할 수 있습니다. 초기화·대입·분기에서 발생하는 오류도 유지합니다.

[0.6.7 개발판 안내](releases/0.6.7-dev.md)에 조립 이어가기와 소스에 적힌 탐색 방법을
바꾸는 흐름을 모았습니다. Gooo 정책이 실행 결과를 읽고 다음 방법을 고르며,
열 입력에 공통으로 쓸 식을 후보 목록에 담는 제곱식 문법을 추가했습니다.
[원본 관측](research/quadratic-fit-feedback-20261008/README.md)은 기능 사례 10/10과
후보 목록 16/108을 따로 기록합니다. 레코드 필드 조립에는 자체 소형 모델을
연결해 같은 입력에서 고정 순서와 비교했습니다.

[0.6.6 개발 후보의 실행 기록](research/release-066-dogfood-20261008/README.md)은
새 실행 파일로 만든 진단 도구, 직접 호출하는 보조 함수, 이전 버전의 조립 기록 재실행을
함께 확인합니다. 진단 도구는 활동 출력 8/8, 보조 함수 호출 앱은 4/4를 충족했습니다.
조립을 일찍 멈춘 경우에는 보조 함수 사례 3/5와 앱 출력 2/4가 남았고,
Gooo 설명 도구가 이 기록을 읽어 다음 후보 탐색을 제안했습니다.
이 관측은 로컬 개발 후보에서 수행했으며, 제안을 자동 실행하는 단계와 외부 재현은 포함하지 않습니다.

이번 성장 방향을 확인하는 작은 사례로, 자체 모델로 만든 진단 도구의 기록을
다시 Gooo 설명 도구에 전달했습니다. [0.6.5 개발 후보 관측](research/release-065-dogfood-20261008/summary.json)에서
모델의 첫 제안은 조립 사례 3/5를 맞혔고, 다음 후보가 5/5를 충족했습니다.
결정론 경로는 네 후보, 모델 경로는 두 후보를 시도해 같은 실행 코드를 만들었으며,
활동 출력 8/8과 조립 관측에 겹치지 않는 고유 입력 4/4를 별도로 기록했습니다.
모델 추론은 19.9마이크로초, 준비는 0.497밀리초였습니다. 호스트 CPU 표본은
사전 7.6%, 실행 세션 6.3~17.3%였으며 다른 앱과 컴파일·대기 구간을 포함합니다.
단일 순차 관측이므로 모델 자체의 CPU 증가량이나 일반적인 속도 우위는 미측정입니다.

이 과정에서 모델의 제안 표시가 빠지는 오류를 발견해 수정했습니다. 이제
모델이 처음 추천한 후보와 검사를 거쳐 선택한 후보를 구분해서 보여줍니다.
수정 전후 기록과 재현 검사를 함께 남겼고, 설명을 만드는 동안 새 모델 호출은
0회였습니다. 이런 실제 사용을 통해 표현이 부족하거나 설명이 틀리는 지점을
찾고, Gooo 도구와 컴파일러의 다음 개발 과제로 연결합니다.

### Gooo로 만든 작은 도구를 바로 사용하기

`gooo init --template diagnostic my-diagnostic`으로 진단 도구 프로젝트를
바로 만들 수 있습니다. 조건식·변수 할당·레코드 선택지는 생성된 Gooo 소스에
있고, 기본 경로는 모델 없이 실행합니다. 한 번 조립한 기록을 저장하면 새 입력에
모델 호출 없이 재사용할 수 있습니다. [시작 템플릿 안내](language/project-starters.md#start-a-reusable-diagnostic-tool)는
선택적으로 자체 모델을 연결하는 방법과 각 검사의 범위를 함께 설명합니다.
이 템플릿을 실제로 만든 [자체 모델 관측](research/diagnostic-starter-20261008/summary.json)에서는
결정론·모델 경로와 폴더 이동 후 재실행이 각각 활동 출력 8/8을 맞혔습니다.
모델은 두 후보를 시도했고, 추론은 19.0마이크로초, 준비는 0.770밀리초였습니다.
추가 입력 세 건은 새 모델 호출 없이 값을 반환했습니다. 단일 로컬 관측이며,
추가 입력에는 기대 정답을 주지 않아 정답률은 미관측으로 남겼습니다.

조립 결과를 설명하는 [독립 Gooo 패키지](../examples/assembly-explainer/README.md)를
추가했습니다. 입력은 맞춘 사례 수, 전체 사례 수, 관측된 최선의 후보와 남은
평가 예산입니다. Gooo 소스에 선언한 조건이 “더 나은 후보 사용”, “다른 후보
계속 탐색”, “선택지 확장”, “아직 관측하지 않음”을 구분하고 설명을 반환합니다.
필드 타입과 판단 규칙, 메시지를 같은 소스에서 읽고 수정할 수 있습니다.

`package execute --construction-receipt`는 저장된 레코드 조립 기록을 이 도구에
직접 연결합니다. 후보 점수와 생성물을 먼저 재계산해 확인하고, 각 시도 당시의
충족 사례 수와 남은 예산을 입력으로 만듭니다. 자체 모델의 실제 문서 진단 기록에서
첫 후보의 2/3에는 “계속 탐색”, 다음 후보의 3/3에는 “새 입력 관측”을 반환했습니다.
기록 해석 중 새 모델 호출은 0회이며, 판단 규칙은 Gooo 소스에 그대로 있습니다.
반환한 제안이 실제 수정을 실행하는 단계와는 별도입니다.

레코드 조립에서는 [패키지 정책 도구](../examples/package-assembly-policy/README.md)를
실행 경로에 직접 연결할 수 있습니다. `--assembly-policy-workspace`로 지정한
Gooo 진입 활동이 각 후보의 실제 점수를 읽고 다음 후보를 시도할지 결정합니다.
판단에 쓰는 작은 함수도 다른 패키지에서 가져다 씁니다. 정책의 원본 소스와
가져온 함수, 변환된 프로그램을 결과에 저장하며, 재실행은 그 저장본을 다시
구성합니다. 모델은 후보 순서를 제안하고, 사례 충족률은 실행한 검사에서 계산합니다.

[호출되는 본문 조립](../examples/called-body-construction/README.md)은 이 흐름을
보조 함수 안으로 확장합니다. 보조 함수가 선언한 선택지를 먼저 조립하고,
선택된 본문을 고정 함수로 연결한 뒤 호출하는 쪽을 생성합니다. 여러 번
호출해도 조립은 한 번이며, 각 부품의 시도·미충족 사례를 별도로 보존합니다.
새 네이티브 실행에서는 실제 호출 인자를 기록해 기존 조립 사례와 비교합니다.
후보 평가 중 다른 보조 함수를 부른 이력은 아직 미관측으로 남으며, 그 경로의
새 입력 여부와 최종 출력 검사는 구분합니다.

이 연결을 소스의 IR 탐색과 여러 빈칸을 채우는 본문 조립까지 확장했습니다.
탐색 기록은 각 시점까지 채점한 후보만 보여주고, 후보 전체를 먼저 채점하는
본문 조립은 이미 확인된 전체 집합을 보여줍니다. 타입 오류로 채점하지 못한
후보는 사유를 남기며, 실제로 관측한 0점과 구별합니다. 작은 공방에서 부품을
하나씩 시험하는 기록과, 모두 시험한 부품 목록을 구분하는 셈입니다.
[실행 예제](../examples/construction-observation/README.md)는 Gooo가 이 기록을
읽고 “이미 관측한 더 나은 후보 사용” 같은 다음 작업을 반환하는 과정을 보여줍니다.
공개 실행에서는 두 입력의 활동 출력 4/4를 확인하고, 조립 관측 다섯 건을
Gooo가 해석했습니다. 이 실행의 모델 호출은 0회입니다. 이 관측에서 드러난
단계 간 입력 누락을 수정해, 현재 패키지 실행과 재실행은 앞선 본문 채우기의
사례·보류 사례·추가 관측 입력까지 합산합니다. 새 루트 입력도 중간에 이미
본 값으로 바뀌면 중복 관측으로 구분합니다.
[전체 단계 예제](../examples/workspace-input-observations/README.md)는 출력 8/8과
새 고유 입력 사례 1/1을 서로 다른 단위로 기록합니다.
같은 예제의 저장된 프로그램을 다시 실행하고 Gooo 설명 도구에 연결한
[공개 관측](research/workspace-inputs-20261008/replay-summary.json)도 추가했습니다.
재실행은 1.16초, 설명은 0.38초였으며 각각 네이티브 실행 두 번과 모델 호출
0회를 기록했습니다. 한 번의 로컬 관측이고 빌드 캐시 조건은 통제하지 않았습니다.
Gooo는 조립 사례 3/3인 후보에 “새 입력 관측”, 0/3인 후보에 “관측한 더 나은
후보 사용”을 제안합니다. 이 제안은 다음 도구가 사용할 데이터로 반환합니다.

외부 파일로 조립 계획을 전달한 경우도 같은 Gooo 설명 도구로 연결했습니다.
[패키지 가져오기 예제](../examples/package-imports/README.md)는 패키지 두 개의
후보 네 개를 읽고 다음 작업을 제안합니다. 기록에 저장된 계획으로 사례 점수를
재계산하며, 외부 계획은 `external_fill`, 소스 선언은 `source_fill`로 출처를
표시합니다. [실제 실행](research/external-construction-20261008/summary.json)은
활동 출력 2/2와 설명 네 건을 기록했고, 생성·실행 1.03초와 설명 0.40초,
모델 호출 0회였습니다. 실행 입력은 조립 사례와 겹치므로 새 입력의 충족률은
미관측입니다. 시간은 캐시 조건을 통제하지 않은 로컬 단일 관측입니다.

`package execute --inputs`는 기대 정답을 미리 적지 않고 실제 값을 받는
사용 경로입니다. 활동 하나만 있는 패키지도 바로 실행합니다. `--json`으로
기록을 받으면 실행 상태는 `OBSERVED`, 정답 검증은 미관측으로 남습니다.
`--cases`는 별도의 테스트 경로로 유지하며, 이 도구의 명시된 10개 사례를
확인했습니다. 다음 작업 제안은 데이터로 반환하므로 실제 수정을 수행하는
도구는 그 결과를 따로 소비해야 합니다.

그 다음 연결을 [Gooo 피드백 예제](../examples/assembly-feedback/README.md)로
구현했습니다. `body-refine`은 실제 실행에서 맞춘 수를 Gooo 정책에 전달하고,
정책이 반환한 다음 예산으로 선언된 선택지·문법 범위에서 다시 조립합니다.
실패한 직접 입력과 기대값을 소스의 명시적 사례로 추가할 수도 있습니다. 어떤 결과를
보관할지도 Gooo가 결정합니다. 원본 소스, 수정된 선언, 모델 판단과 매 단계의
실행 결과가 남으며, 선택한 프로그램을 모델 없이 다시 실행할 수 있습니다.
반복 판단에 쓴 사례의 충족률과 마지막에만 실행하는 평가 결과는 따로 기록합니다.

이 루프에 기존 자체 QAT 모델을 연결한 [실제 관측](research/assembly-feedback-20261007/summary.json)에서는
결정론 경로가 3라운드·선택 시도 13회, 모델 경로가 2라운드·6회로
피드백 출력 14/14와 마지막 평가 출력 6/6을 맞혔습니다. 양쪽 모두 실패한
직접 입력 하나를 소스 사례로 추가했습니다. 모델 판단은 약 16·21마이크로초,
전체 실행은 각각 2.81·1.74초였습니다. 같은 작업의 순차 관측 한 쌍이며,
빌드 캐시 조건을 통제한 반복 실험은 아직 남아 있습니다. 현재 문법으로
필요한 식을 표현할 수 없는 예제는 계속 `PROGRESS`로 남기는 검사도 추가했습니다.

### 같은 조건으로 비교하고 자체 모델을 사용하기

두 결과를 비교할 수 있는 조건도 Gooo 활동으로 선언합니다. 양쪽 결과의
관측이 끝났고 미확인·반증 단위가 없어야 증감량을 계산합니다. 비교 근거가
부족한 축은 JSON의 `numerator_delta`에 `null`을 남깁니다. 따라서 `0/4`에서
`2/4`로 나아진 결과, 그대로인 결과, `4/4`에서 `1/4`로 내려간 결과를
미관측 상태와 구분해 다음 작업에 사용할 수 있습니다.

이번 개발에서는 기존 자체 QAT 모델로 Gooo 진단 프로그램도 실행했습니다.
기록된 부분 충족 입력(17/21필드, 타입 탈락 1개)에 대해 두 경로 모두
`partial / repair-and-replay`를 반환했습니다. 모델 경로는 후보 2개,
결정론 경로는 4개를 평가해 같은 진단 본문을 골랐습니다. 모델 추론은
1회·22.334마이크로초, 모델 준비는 0.327밀리초로 관측됐습니다.
한 작업의 단일 관측이며, 전체 실행 속도 비교에는 빌드 캐시 차이가 남습니다.
[원본 리비전·모델 해시와 측정 범위](research/comparison-dogfood-20261007.json)를
함께 공개합니다. 이 진단은 기존 결과를 읽고 다음 작업을 고르는 도구입니다.

같은 기록의 원래 레코드 조립도 다시 실행했습니다. 후보 8개 중 4회만
시도하도록 고정하면, 자체 모델 경로는 14/14개 활동 출력이 기대값과
일치했고 결정론 경로는 6/14개였습니다. 양쪽 모두 타입 탈락 후보 1개를
거쳐 탐색을 계속했습니다. 7개 실행 입력 중 5개는 선택 사례와 겹치며,
서로 다른 입력 2개에서의 활동 출력은 모델 4/4, 결정론 2/4입니다.
이 입력 분리는 모델 학습 자료와의 독립성을 뜻하지 않습니다. 단일 작업의
유한 관측이며, 위 JSON의 `bounded_record_follow_up`에 별도로 기록했습니다.

후속 컴파일러 리비전 `5c9556e1`에서는 같은 실험의 입력 구분을 런타임이
자동 계산했습니다. 고유 입력 7건 중 5건은 이미 관측한 입력이며, 새 입력
2건의 요구 출력을 모두 맞힌 사례는 모델 2/2, 결정론 1/2입니다. 여기서 단위는
여러 활동의 출력을 묶은 한 입력 사례입니다. 모델 예측은 1회·22.292마이크로초,
네이티브 전체 구간은 각각 691.01·489.60밀리초였습니다. 반복 표본과 동일한
캐시 조건을 확보하기 전까지 속도 우위는 미확인입니다. 정확한 리비전과 새 관측은
같은 JSON의 `automatic_input_separation_follow_up`에 보존했습니다.

재현할 때는 공개된 컴파일러 리비전 `91fbb04b`를 빌드한 뒤 다음 소스를
사용합니다. 같은 명령에서 `--model`을 생략하면 결정론 경로입니다.

```sh
sed 's/attempts "8"/attempts "4"/' examples/body-codegen/record-candidate-continuation.gooo.fixture > /tmp/bounded-record.gooo
gooo body-compose --source /tmp/bounded-record.gooo \
  --cases examples/body-codegen/record-field-updates-cases.json \
  --model /path/to/gooo-ecosystem-workbench/models/shared-qat/model.json
```

Gooo가 선언한 IR 후보 탐색은 생성 결과를 저장한 뒤 `body-execute`로 이어갈
수 있습니다. 실행기는 원본 후보 집합, 선택된 식, 훈련·홀드아웃 결과를 다시
계산하고 실제 Go 실행으로 연결합니다. 이 재생 단계의 모델 호출은 0회입니다.
[생성과 실행을 나누는 예제](source-assembly.md#declare-a-typed-ir-search-in-the-gooo-source).

`assembling` 블록은 한정된 IR 후보 탐색을 Gooo 소스에 직접 선언합니다. 이제
여러 코드 구멍(hole)에 각각 다른 타입의 문법을 지정할 수 있습니다. 예를 들어
조건 구멍에는 입력과 훈련 입력값을 비교하는 불리언 문법을, 반환값 구멍에는
정수 상수·오프셋 문법을 지정합니다. 컴파일러는 각 구멍의 후보를 조합하고,
완성된 바디를 타입 검사한 뒤 선언된 사례로 채점합니다. 모델이 연결되면 이
완성된 후보 조합의 순위를 정하고, 연결되지 않으면 같은 집합에서 결정론적으로
선택합니다. 홀드아웃 사례는 선택 문맥에 넣지 않습니다.

새 조건부 예제는 선언된 세 입력에서 3/3을 만족합니다. 동시에 조건 문법이
열거할 수 있는 후보 중 일부만 예산 안에서 만들었으므로 문법 완전성은
`PROGRESS`로 기록됩니다. 이 결과는 선언된 사례의 정확도이지, 자연어 의도
충족률이나 전체 정수 영역의 정확성을 증명하지 않습니다. 지원 문법과 조립
예제는 [소스 조립 안내](source-assembly.md#when-holes-need-different-expression-types)에
있습니다.

### IR 탐색 결과를 다음 활동으로 연결하기

소스에 선언한 `search hole`을 이제 `body-compose`의 활동으로 연결할 수
있습니다. 음수 보정 → 오프셋 조립 → 불리언 검사 예제에서 두 번의 탐색 결과가
명시된 연결을 따라 전달되고, 완성된 그래프를 곧바로 빌드해 두 번 실행합니다.
다섯 입력의 기대 출력 15개와 큰 정수의 전달을 검사하는
[실행 예제](native-body-composition.md#source-ir-search-across-activities)를 추가했습니다.
저장한 결과를 재생할 때는 원본 후보 집합과 선택·홀드아웃 결과를 확인하며
모델을 다시 호출하지 않습니다. 완성된 소스는 다음 작업에서 일반 Gooo 바디로
사용할 수 있습니다. 이 경로의 IR 후보 탐색은 현재 결정론 순서를 사용하고,
같은 그래프의 기존 선택지 조립에는 소형 모델을 연결할 수 있습니다.

### 여러 빈칸을 채운 프로그램을 이어서 쓰기

`source_fill`로 변수 식과 조건 식 등 여러 빈칸을 채운 결과도 이제
`body-compose`의 다음 활동으로 전달할 수 있습니다. 두 활동에서 각각
두 빈칸을 채우고 불리언 검사까지 연결하는
[실행 예제](native-body-composition.md#source-owned-multi-hole-construction)는
다섯 입력의 기대 출력 15개를 확인합니다. 레코드의 조건과 반환값을 함께
조립한 결과도 타입이 맞는 후속 활동에 연결할 수 있습니다.

`--fill-model`은 이 경로에 자체 TinyGo 연산 판단 모델을 연결합니다.
그래프에서 모델을 한 번 읽고, 각 조립 활동이 준비되면 판단을 호출합니다.
모델이 제안한 후보와 선언된 사례로 채점해 실제 선택한 후보를 모두 남깁니다.
저장한 결과는 모델 파일 없이 후보 점수와 홀드아웃을 재계산해 재생합니다.
완성된 소스는 일반 Gooo 프로그램으로 다시 실행할 수 있습니다.

잘못된 연산을 제안하도록 만든 테스트 모델로 선택 보정과 재생을 확인했습니다.
이는 연결 구조에 대한 검사이며 학습된 모델의 정답률 측정과 구분해 기록합니다.
문법에서 아직 탐색하지 않은 조합과 테스트에서 맞지 않은 사례는 계속
완전성 기록에 남깁니다. 이런 실행 가능한 예제와 원본 기록을 함께 공개하며
외부에서 재현하고 개선할 수 있는 언어로 키워갑니다.

실제 학습한 QAT 연산 모델도 같은 예제에 연결했습니다. 이번 한·영 혼합 의도
두 건의 연산 예측은 0/2였고, Gooo가 후보 범위와 사례 점수로 보정한 최종
출력은 모델 사용·미사용 모두 15/15였습니다. 판단 호출은 약 25–28µs였지만
이 예제에서 모델의 이득은 확인되지 않았습니다.
[측정 기록](research/source-fill-dogfood-20261007.json)과
[원본 실행 결과](research/source-fill-native-20261007/model-native.json)를
함께 공개합니다. 다음 모델 개선에서는 한글·영어·혼합 의도를 분리하고,
컴파일러의 보정 전 예측과 보정 후 동작을 각각 측정할 필요가 있습니다.

## 성장 방향: 교체 가능한 조립 과정과 실제 사용 예제

먼저 Gooo로 실패한 조립을 설명하고, 반례에서 허용된 수정 경로를 제안하며,
선언한 타입과 조건으로 실행 예제를 만드는 작은 언어 도구들을 키웁니다.
각 도구의 입력·Gooo 결과·실행 기록을 함께 공개해 다른 개발자가 따라 할 수
있게 합니다. 그 과정에서 표현하지 못한 기능이 다음 언어 개발 과제가 됩니다.

모델을 바꾸는 실험에서는 소스·온톨로지·후보 집합·검증 기준을 고정합니다.
모델은 어떤 후보부터 시도할지 제안합니다. 같은 예산에서 선택된 프로그램과
실제 동작은 달라질 수 있으므로, 그 차이를 실행 결과로 비교합니다.
온톨로지를 바꾸는 실험은 바뀐 의미와 조건을 별도로 기록하고 같은 컴파일러가
어디까지 처리하는지 확인합니다. [두 도메인 도구 예제](../examples/domain-tools/README.md)는
코드 조립 관측과 문서 관측에 서로 다른 입력 타입·규칙·조립 사례를 선언하고,
결과 타입과 출력기를 공유합니다. 사용자가 제공한 관측을 해석하는 Gooo 도구로,
각각 7개 입력과 14개 기대 출력의 실행 사례를 제공합니다. 같은 도구 안에서는
모델 순위와 결정론 순서를 바꿔도 후보·규칙·실행 기준을 유지합니다.

이 두 도구에 기존 자체 QAT 모델을 연결한 [실제 관측](research/domain-tools-20261007/summary.json)에서는
조립 진단의 후보 평가가 8회에서 1회로, 문서 진단은 6회에서 2회로 줄었습니다.
네 실행 경로의 최종 출력은 각각 14/14로 일치했습니다. 문서 진단에서 모델의
첫 후보는 요구 필드 하나를 틀렸고, 선언된 사례를 평가한 뒤 다음 후보를
선택했습니다. 각 판단은 약 21µs였으며, 단일 실행의 비용과 실패를 함께 공개합니다.
이것은 두 도구의 유한 관측이고, 더 넓은 작업의 성과와 외부 재현은 다음 과제입니다.

이번 `body-compose`의 `input_separation`은 선택 과정에서 관측한 입력과
새 실행 입력을 구분합니다. 중간 활동에 전달된 실제 값까지 비교하며,
중복 입력은 한 건으로 셉니다. 새 입력에서 요구한 출력이 전부 맞은 사례 수를
분자로 남깁니다. 모델의 학습 데이터와 독립적인지는 별도의 미확인 항목입니다.
[지표의 분모와 상태 정의](native-body-composition.md#input-separation)를 공개합니다.

외부에는 작은 실행 예제, 같은 조건의 비교 결과, 언어 설계 순서로 설명합니다.
소스·모델·데이터·라이선스 기록과 실행 증거를 연결하고, 실제 재현과 사용 사례를
쌓습니다. 사업 방향은 그 사용 경험을 바탕으로 판단합니다. 구체적인 개발 순서는
[성장과 교체 실험 계획](research/verified-construction-thesis.md#grow-through-a-replaceable-construction-system)에 있습니다.

지금은 이 순서를 작은 도구에 적용하고 있습니다. Gooo로 조립 결과를 설명하는
[실행 예제](../examples/assembly-explainer/README.md), 실행 반례를 받아 다음
시도를 정하는 [피드백 관측](research/assembly-feedback-20261007/summary.json),
두 패키지가 같은 `Result` 이름을 사용해도 안정 ID로 구분해 연결하는
[패키지 예제](../examples/package-record-namespaces/README.md)가 그 출발점입니다.
패키지 예제의 4개 입력·12개 출력은 모두 기대값과 일치했고 모델 호출은 0회였습니다.
이 결과를 토대로 다음에는 같은 컴파일러에 두 도메인의 선언과 판단 규칙을
넣어보고, 새로 필요한 언어 기능을 구체적인 실패 사례에서 고릅니다.
외부 개발자의 독립 재현과 실제 사용 성과는 관측이 생기는 대로 별도로 기록합니다.

## 어떤 작업을 쉽게 만들고 싶은가

“이 조건에서는 이 값을 쓰고, 다른 조건에서는 저 연산을 하며, 결과는 이
예시들을 만족해야 한다”는 의도를 코드와 연결하고 싶습니다. 그 연결이
변경과 반복 생성 과정에서도 남아 있어야 다음 작업을 자동으로 이어갈 수 있습니다.

설계도와 작은 조립 작업장을 떠올리면 이해하기 쉽습니다. Gooo 선언은
부품의 의미와 연결 규칙을 표현합니다. 소형 모델은 허용된 조립 경로 중
시도할 순서를 제안합니다. 컴파일러는 타입과 조건을 확인하고 Go 코드를
만듭니다. Go로 만든 실험 실행기는 그 결과를 빌드하고 실행합니다.
실패한 예시는 다음 시도에 전달되고, 작업 기록에는
성공한 부분과 아직 확인하지 못한 부분이 함께 남습니다.

현재 경로 계획에는 원본 Gooo, 한국어·영어 의도, 허용된 대안, 유한한 입출력
예시가 들어갑니다. 원본과 계획 문서는 해시로 연결됩니다. 조건식, 변수
할당, 참조, 중첩 분기, 연산 순서를 조합하는 제한된 정수 함수부터 실험하고
있습니다. 이제 `computes` 뒤의 `assembling` 블록에 의도, 선택 위치,
유한 입출력 예시와 시도 예산을 함께 적을 수 있습니다. 같은 선언으로 모델을
연결하거나 결정론적으로 탐색하고, 실제 Go 실행까지 이어갑니다. 선언의 변경은
의미 IR의 지문에도 남습니다. 외부 JSON 계획은 해당 블록이 없는 활동에서
계속 사용할 수 있습니다. [구문과 실행 예제](source-assembly.md).

### 한 번의 조립을 따라가 보면

설명을 위한 예로 “값이 기준보다 작으면 보정하고, 마지막에 두 배로 만든다”는
함수를 생각할 수 있습니다. 계획은 비교 조건, 보정 연산, 마지막 연산에 각각
두 대안을 줍니다. 세 선택을 조합하면 여덟 개의 함수 바디가 생깁니다.
모델은 원본 구조와 의도를 보고 먼저 시도할 조합을 고릅니다. 입출력 예시에서
실패하면 실제 입력·기대값·결과가 다음 판단의 문맥이 됩니다. 이 선택 단계는
유한 평가기로 바디를 평가합니다. 선택된 바디를 Go로 생성한 뒤 실험 실행기가
별도로 빌드하고 실행하며, 각각의 결과가 원본 선언에 연결됩니다.

이 예시는 현재의 유한 경로 조립 방식을 풀어 쓴 것입니다. 실제 호출 계약과
실행 가능한 자료는 [바디 생성 안내](language/body-codegen.md)와
[세 선택 모델 안내](three-choice-path-model.md)에 있습니다. 현재는 대안과
예시를 계획에 제공하며, 자연어에서 계획 자체를 찾는 능력은 다음 연구 범위입니다.

## 언어·모델·실행기가 맡는 일

IR은 원본 선언을 컴파일러가 다루기 쉬운 구조로 옮긴 중간 표현입니다.
예를 들어 조건, 대입할 변수, 두 분기의 연산을 각각 이름 있는 부품처럼
다룹니다. 모델은 선언된 부품의 조합에 순위를 주고, 타입 검사와 예시 평가가
조립 결과를 확인합니다. 이 과정을 언어의 기능으로 다루는 것이 여기서 말하는
메타프로그래밍입니다.

| 구성 | 현재 역할 | 살펴볼 곳 |
| --- | --- | --- |
| Gooo / meta-ontology-go | 의미 ID, 선언, IR, Go 생성, 실제 실행, 관측 기록 | [컴파일러](https://github.com/kimjooyoon/meta-ontology-go) |
| 자체 소형 모델 | 세 개의 이진 선택으로 이루어진 여덟 경로의 순위 제안 | [Hugging Face 모델](https://huggingface.co/asketeddy/gooo-shared-judgment-tiny-v1) |
| Go 실행 라이브러리 | 모델 로딩, 배열 기반 계산, 요청별 작업 메모리, 피드백 탐색 | [gooo-decision-runtime](https://github.com/kimjooyoon/gooo-decision-runtime) |
| 실험 저장소 | 데이터 생성, GPU 학습, 품질·속도·메모리 비교, 원본 증거 공개 | [연구 저장소](https://github.com/kimjooyoon/gooo-neural-decision-experiments) |

## 서로 다른 타입의 IR 구멍 조립 — 2026-10-06

새 예제에서는 `condition` 구멍에 `integer-predicate/v1`, `yes` 구멍에
`integer-offset-constant/v1`을 지정합니다. Gooo가 조건과 반환값을 따로
생성한 뒤 전체 조합을 평가하므로, 모델은 문장이나 코드 조각을 따로 이어
붙이는 대신 컴파일러가 검사할 수 있는 완성된 후보 중에서 선택합니다.
후보 수가 선언된 예산보다 많으면 남은 후보가 있다는 사실과 실제 탐색 비율을
영수증에 기록합니다. 지표 설명과 재현 가능한 예제는
[조건부 IR 조립](source-assembly.md#when-holes-need-different-expression-types)에서
확인할 수 있습니다.

### 드문 훈련 사례 사이의 경계 찾기

훈련 입력이 `-10`과 `10`뿐이면 `input < 0`과 `input <= 0`은 둘 다
훈련 사례를 통과합니다. `integer-predicate-cutpoint/v1`은 관측 입력 사이의
정수 중간점을 후보로 만들어 두 식을 모두 남깁니다. 예제는 `0`과 `5`를
홀드아웃으로 두므로 결정론적 첫 후보의 결과는 훈련 2/2, 홀드아웃 1/2로
나옵니다. 허용 후보 중 `input <= 0`을 선택하면 홀드아웃 2/2입니다. 이는
작은 유한 사례에서 후보 간 동률이 남을 수 있고, 홀드아웃이 그 차이를 드러낼
수 있음을 보여줍니다. 전체 정수 범위나 자연어 의도의 완전한 충족을 증명하는
수치는 아닙니다.

회귀 테스트에서는 Laya API와 같은 형식으로 동작하는 테스트 서버가
`input <= 0`을 반환하도록 하여 후보 전달, 소스 구성, 홀드아웃 분리 측정을
확인합니다. 실제 Laya 모델의 품질이나 속도 측정은 아닙니다. 직접 실행하는
방법과 지표 해석은 [경계 조건 예제](source-assembly.md#when-holes-need-different-expression-types)에
있습니다.

선택 전에 Gooo는 훈련 입력만으로 주변 정수와 내부 중간점 탐침을 최대 128개
만듭니다. 선언된 홀드아웃 입력과 겹치는 탐침은 제외하고, 남은 지점에서 각
후보의 출력을 계산해 Laya 선택 문맥에 전달합니다. 탐침의 정답값은 없고,
홀드아웃 행과 기대값도 모델에 보내지 않습니다. 따라서 Laya는 의도와 후보별
행동 차이를 함께 보고 선택할 수 있으며, 이 관측은 정답 증거가 아닙니다.

새 `body_fill_candidate_probe_coverage` 지표는 생성된 탐침 공간에서 실제
실행한 후보·입력 조합의 비율을 나타냅니다. 영수증에는 후보 간 출력 차이가
관측된 입력 수, 비교된 후보 쌍의 구별 비율, 탐침 입력·출력 서명 해시와 탐침
실행 시간도 기록됩니다. 이는 후보의 행동 차이와 측정 범위를 보여주는 값이지,
후보의 정답률이나 의도 충족률을 뜻하지 않습니다.

[행동 프로필 예제](../examples/body-codegen/source-ir-fill-probe-choice.gooo.fixture)는
훈련 `-10 -> 0`, `10 -> 1`로 `input > 0`과 `input >= 0`을 동률로 남기고,
홀드아웃 `5 -> 1`과 별도로 훈련에서 유도한 탐침 `0`으로 두 후보의 행동을
구별합니다. Laya 형식의 테스트 서버가 프로필을 받고 포함 경계 후보를
선택하는 코드 경로를 검증합니다. 이 테스트는 실제 모델이 한국어 의도를
이해하는 능력을 측정하지 않습니다. Laya가 없으면 선언된 후보 순서에 따른
결정론적 선택을 유지합니다.

학습에는 로컬 GPU의 MPS와 오프라인 PyTorch를 사용합니다. 모델 로딩과
추론, 탐색, 코드 조립, 측정 도구는 Go로 구성합니다. 모델이 연결되지 않거나
입력이 모델의 지원 범위를 넘으면 전체 입력을 보존하고 결정론적 경로로
이어갑니다. 이때 모델 호출 수는 0으로 기록됩니다.

## 기록의 어느 시점 값을 읽는지 전달하기 — 2026-10-05

지역 레코드의 필드를 순서대로 갱신하고, 그 전에 복사한 레코드·문자열의
값을 보존할 수 있습니다. 예를 들어 작업 중인 메모의 상태를 바꾸어도
옆에 찍어 둔 사진의 상태는 그대로입니다. 이 차이를 컴파일러가 정의·복사·
쓰기·읽기 관계로 기록합니다. 분기에서 달라진 정의는 합류 관계로 남기고,
조기 반환 뒤 계속 실행될 조건도 함께 보존합니다.

`body-context --value-flow`로 실행 전의 관계를 살펴볼 수 있습니다. 별도
소형 모델 입력 버전은 이 관계를 선택당 두 개의 16칸 배열로 요약합니다.
기존 표현에서 같은 배열이었던 현재값·저장값 쌍은 새 회귀 예제에서 구분됩니다.
이 단계의 지표는 입력 구분이며, 새 가중치의 기능 충족률은 후속 학습·실행
실험에서 측정합니다. 모델이 연결되지 않거나 출처 분석 한도를 넘으면

## 차별점으로 발전시키려는 부분

1. **의도와 생성물의 연결을 언어에 남기기.** 이름이 바뀌어도 의미 ID로
   같은 대상을 추적하고, 생성된 구조와 실행 결과를 원본 선언에 연결합니다.
2. **작은 판단을 반복해서 프로그램을 조립하기.** 모델의 역할을 조건 선택과
   세부 경로 순위처럼 좁게 잡아 저사양 환경에서도 실험할 수 있게 합니다.
3. **완전성을 여러 축으로 관찰하기.** 생성률, 예시 충족률, 실행 여부,
   원본으로의 역추적, 미관측 경계를 각각 기록합니다. 다음 단계가 무엇인지
   시스템이 읽을 수 있도록 첫 미해결 항목과 원인을 보존합니다.
4. **바뀐 이유를 재현할 수 있게 만들기.** 입력, 모델, 도구, 소스 리비전,
   시도한 경로와 실패 예시를 연결합니다. 비교 조건이 같을 때 수치 증감을
   계산하고 조건이 바뀌면 그 변경을 드러냅니다.

이 네 가지를 함께 구현하는 것이 프로젝트의 목표입니다. 다른 언어와의
비교는 앞으로 같은 과제·도구·예산으로 수집한 증거를 바탕으로 확장합니다.

### 차별점을 어떤 수치로 확인할 것인가

| 발전시키려는 성질 | 확인할 지표 | 현재 근거와 다음 질문 |
| --- | --- | --- |
| 의도에서 동작까지 연결 | 전체 예시를 충족한 함수 비율, 개별 예시 충족률 | 유한 정수 함수에서 관측했으며 새 과제와 타입으로 확장 예정 |
| 작은 판단으로 조립 비용 줄이기 | 추가 후보 수, 모델 호출 수, 생성·실행 시간 | 고정된 여덟 경로에서 비교했으며 더 큰 계획으로 확장 예정 |
| 한·영 의도를 일관되게 받기 | 양쪽 모두 유효한 경로를 고른 쌍, 함께 틀린 쌍 | 전체 입력을 보존한 표현 비교 진행 |
| 바뀐 이유를 추적하기 | 원본·모델·결과 연결, 미해결 항목의 변화 | 내용 해시와 `completeness-delta`로 관측 연결 |
| 작은 장치에서도 실행하기 | 저장 크기, 상주 배열, 전체 RAM, 지연 시간 | 각 비용을 따로 측정하며 새 모델과 실행 환경의 재현성 확인 중 |

완전성은 작업 지시서의 항목별 체크 기록에 가깝습니다. 여기서 “368/512”는
512개 입력 중 첫 후보가 제공된 16개 예시를 모두 만족한 수입니다. 일부
예시만 맞은 정도, 다음 시도에서 완성된 수, 실행 권한처럼 아직 관측하지 못한
조건도 별도로 남깁니다. 이 기록이 다음 개발 작업을 고르는 재료가 됩니다.

숫자는 다음처럼 읽으면 됩니다. 모델이 어떤 경로에 준 0.8이라는 점수는
선택 분포의 값입니다. 16개 예시 중 12개를 통과했다면 그 예시 집합의
충족률은 75%입니다. 원본 연결이나 실행 권한을 아직 관측하지 못했다면
해당 항목은 `UNKNOWN`으로 남습니다. 서로 다른 질문에 답하는 세 기록을
함께 보여주어야, 다음에 무엇을 고칠지 판단할 수 있습니다.

## 최근 언어 기능: 필요한 관측을 골라 조립하기

### 여러 본문을 하나의 실행으로 연결하기

`body-compose`는 Gooo의 `bind` 선언에 따라 여러 활동의 실제 본문을 연결합니다.
정수 본문을 조립하고 범위를 제한한 뒤 불리언 판단으로 전달하거나, 같은 결과를
두 활동에 보내는 작업을 한 번의 Go 빌드로 실행합니다. 별도 텍스트 입력도 같은
계획에 놓을 수 있습니다. 조립 작업장에서 완성한 부품을 연결선에 꽂고 전체
동작을 확인하는 과정입니다.

두 결과를 받아 합산하거나 서로 비교하는 본문도 연결할 수 있습니다.
`Add(Integer, Integer)`의 `input0`, `input1`은 원문 순서대로 구분합니다.
`Label(Integer, Boolean, Text)`처럼 타입을 섞고 첫 입력만 연결한 경우에는
나머지 두 입력을 실행 예시에 명시합니다. IR에는 순서와 반복 타입을 보존하고,
실행 기록에는 각 입력의 실제 값과 생산자를 남깁니다. 하나의 본문은 현재
최대16개의 입력을 받으며, 조립 모델은 단일 정수 입력 활동에서 후보를 제안합니다.

기존 `fields` 선언의 필수 문자열 기록도 실제 값으로 만들고 전달합니다.
`Candidate{title: input1, state: "ready"}`처럼 모든 필드를 명시해 구성하고,
다음 본문에서 `input.title`을 읽습니다. 생성된 프로그램은 선언 순서의 Go
구조체를 사용하며, 관측에는 각 필드의 안정적 식별자와 실제 값을 남깁니다.
레코드 본문 조립은 V1의 필수 문자열, V2의 필수 Boolean, V3의 필수 Integer를
지원합니다. 이 버전 구분은 기존 기록의 해석을 바꾸지 않습니다. V4는 선택형
단일 문자열·Boolean·Integer 필드를 Go 투영에 반영하며, `gooo run --record-input`
의 `record.forward` 경로도 이를 전달합니다. 누락 키는 누락으로
남고 빈 문자열·`false`·`0`은 실제 값으로 보존됩니다. 본문 생성과 `body-compose`도
V4 선택형 단일 스칼라 필드를 포인터 값으로 읽고, 레코드 복사와 명시적 `bind`로
전달합니다. 관측 기록에는 안정 ID와 별도로 존재 여부가 남습니다. 선택형 필드를
새로 합성하는 학습 조립은 아직 지원하지 않습니다.
[선언·본문·실제 값 관측](native-record-values.md).

이제 모델 선택 경로도 같은 도메인 기록을 다룹니다. `source_fill` 안에
후보 본문과 record `value_case`를 선언하면, Gooo가 각 후보의 타입과 사례
결과를 먼저 확인하고 Laya는 선언된 후보 중 하나만 고릅니다. 예를 들어
`Candidate.state`를 읽어 `Review.decision`을 만드는 작은 예제가 있습니다.
Laya가 고른 내용은 다시 생성·평가되며, 결정론적 실행에서는 사례 점수가
가장 높은 후보를 선택합니다. 이는 선언된 사례의 기록 결과가 맞는다는
증거이며 임의의 자연어 의도나 모든 도메인 값에서의 정확성을 뜻하지 않습니다.
[record IR 본문 조립 예제](language/body-codegen.md#model-guided-record-body-fill).

이제 record 사례에서 본문 후보를 자동 파생하는 문법도 선언할 수 있습니다.
입력 필드의 관측값으로 동등·비동등 조건을 만들고, 기대 출력 record의
문자열·정수·불리언 값에서 타입이 맞는 리터럴 후보를 얻습니다. Gooo가
후보 조합의 크기와 잘라낸 범위를 기록하고 완성된 본문을 타입검사·재생한
뒤 모델에 선택을 맡깁니다. 그래서 기본 후보 목록을 사람이 일일이 작성하지
않아도 되며, 정확도 주장은 선언한 문법과 사례 범위로 한정됩니다.
[자동 파생 예제](../examples/body-codegen/source-ir-fill-record-derived.gooo.fixture).
`record-field-predicate-composition/v1`은 서로 다른 필드의 원자 조건을
두 개씩 `&&` 또는 `||`로 묶습니다. 임의의 중첩 논리를 만들지는 않으며,
생성 가능한 유한 공간과 보유한 후보 수를 별도로 표시합니다.
새 `record-field-relation/v1` 문법은 여러 record 입력의 서로 다른 필드끼리
직접 비교합니다. 문자열·불리언은 동등/비동등, 정수는 순서 비교까지 후보로
만듭니다. 관측된 특정 리터럴을 외우는 대신 실행 입력 사이의 관계를 조건으로
표현할 수 있습니다. 선언된 입력 순서와 필드 순서를 유지하며, 전체 비교 후보와
잘라낸 후보 수를 완전성 기록에 남깁니다. 학습 예시 네 쌍과 보류 예시 두 쌍에서
키 동등 조건을 만들고 별도로 평가하는
[record 관계 fixture](../examples/body-codegen/source-ir-fill-record-relations.gooo.fixture)를
추가했습니다. 이 점수는 그 유한 사례의 동작만 설명하며 모든 키나 데이터에 대한
정확성을 뜻하지 않습니다.
`record-field-relation-composition/v1`은 두 필드 관계를 `&&` 또는 `||`로
결합하고, 네 개의 서로 다른 필드를 비교하는 조합을 먼저 제안합니다. 전체
원자 관계와 쌍별 조합 수를 분모에 두고 `max_expressions`로 보유한 접두 후보를
제한하므로, 조합 공간과 대입 공간의 완전성을 따로 볼 수 있습니다. 새
[관계 조합 fixture](../examples/body-codegen/source-ir-fill-record-relation-composition.gooo.fixture)는
키와 활성 상태가 모두 같은 경우만 승인하고, 학습 4건과 보류 2건을 별도로
측정합니다. 이 문법은 중첩 조건을 만들지 않으며 보류 점수도 전체 입력에 대한
정확성을 뜻하지 않습니다.
세 입력 관계를 위한 `record-field-relation-composition/v2`도 추가했습니다.
서로 다른 관계 원자 세 개에 두 가지 괄호 구조와 네 가지 `&&`/`||` 조합을
적용하고, v1의 두 항 조합과 단일 원자도 fallback 후보로 포함합니다. 서로 다른
입력 필드 관계를 많이 사용하는 후보를 먼저 두며, `max_expressions`로 자른 경우
전체 196개 조건 중 보유한 8개 접두 후보를 별도로 기록합니다. 3개 키를 비교하는
fixture는 조건/값 16개 대입을 모두 평가하고 보류 사례 결과도 분리해 보여줍니다.
[세 입력 관계 fixture](../examples/body-codegen/source-ir-fill-record-relation-triples.gooo.fixture).
`holdout_value_case`는 후보 생성과 Laya 요청에서 제외하고 선택한 본문을
확정한 뒤 별도로 평가합니다. 따라서 학습 사례 점수와 보류 사례 점수를
구분하지만, 보류 사례 몇 건만으로 모든 입력에 대한 정확성을 주장하지 않습니다.

`record-field-relation-composition/v3`을 추가했습니다. 서로 다른 네 관계 원자를

후보만 보유하고 전체 분모와 생략한 범위를 기록합니다.

네 레코드의 키가 모두 같을 때만 승인하는 [실행 예제](../examples/body-codegen/source-ir-fill-record-relation-quads.gooo.fixture)는
21,704개 조건 중 8개를 탐색합니다. 네 훈련 사례와 별도 보류 사례 두 건에서 본문을
타입 검사하고 재생하며, 후보 문법 완전성과 전체 대입 공간 완전성을 각각
보고합니다. 이 결과는 선언된 사례의 근거이고 다른 입력 영역의 정확성을
주장하지 않습니다.

모델은 정수 `assembling` 활동에 선택 순서를 제안하며 요청 안에서 한 번 로드합니다.
현재 일반 본문의 Integer·Boolean·Text 타입은 선언한 연결을 따라 전달합니다.
각 단계의 실제 입력과 출력을 남겨 마지막 값만 맞은 경우와 중간 의미까지
충족한 경우를 구분할 수 있습니다. 저장한 전체 조립 기록은 추가 추론 없이
다시 실행하고, 선택된 Gooo는 다음 조립의 입력으로 사용할 수 있습니다.
[선언·실행 명령·유한 완전성의 분모](native-body-composition.md).

처음 제공한 예시에서 두 바디가 같은 값을 내면, 어느 쪽을 사용할지 아직 결정하기
어려울 수 있습니다. `input-2`와 `2-input`은 입력 2에서 모두 0입니다.
컴파일러는 선언된 관측 입력 중 두 바디의 차이가 드러나는 입력 3을 추천하고,
같은 Gooo 소스의 별도 기준 함수에서 기대값을 얻습니다. 새 사실을 예시에 더하면
후보가 하나로 줄어듭니다. 작업자가 부품을 다른 각도에서 확인하는 과정과 비슷합니다.

`body-codegen --path-observation`에 연결된 현재 기능은 다음 세 단계입니다.

1. **관측 선택:** 남은 후보의 출력이 가장 잘 갈리는 입력을 고릅니다.
2. **출력 재사용:** `reuse_probe_outputs`로 이미 계산한 출력을 요청 소유 배열에 보관합니다.
3. **바로 조립:** `resolve_unique_candidate`로 전체 후보 중 하나가 남으면 해당 바디를 구성합니다.

세 번째 단계는 새 모델 판단과 탐색을 생략합니다. 타입 검사, 생성한 바디의 유한 평가,
실행 전 원본 관측 재현은 이어집니다. 후보가 여럿이거나 관측 예산이 부족하면 기존 탐색으로
진행하고, 기대값을 주는 기준 함수가 없으면 추천 입력과 미해결 상태를 기록합니다.

### 한 번의 모델 판단으로 여러 IR 본문 구멍 채우기

`body-codegen --fill-plan`의 v2는 Gooo 본문에 `seed`, `step` 같은 표현식
구멍을 여러 개 두고, 모든 구멍을 채우는 후보 조합을 선언합니다. 컴파일러가
각 완성 후보를 먼저 타입 검사하고 같은 유한 입출력 예시로 점수를 냅니다.
모델은 조합 중 하나만 고르며, Gooo가 그 조합을 본문에 반영하고 선택된 식과
각 후보의 점수를 기록합니다. 따라서 모델이 임의의 코드를 작성하지 않고도
서로 연관된 세부 선택을 한 번에 판단할 수 있습니다.

현재 v2 범위는 `Integer -> Integer` 본문과 표현식 구멍 2~8개입니다. Laya는
완전한 후보 조합 하나를 선택하고, 연결하지 않으면 선언 순서를 사용합니다.
소형 모델도 v2의 수동 후보 계획에서 제한적으로 쓸 수 있습니다. 각 완성 후보의
첫 번째 구멍 표현식이 서로 다른 지원 연산으로 시작해야 하며, 모델의 8개 연산
분류를 그 구멍으로 후보 ID에 대응합니다. 따라서 나머지 구멍까지 함께 추론하는
일반 조합 모델은 아닙니다. 중복·미지원 연산 후보와 문법에서 자동 생성한 큰
후보 집합은 Laya 또는 결정론 경로를 사용합니다.
[실행 가능한 다중 구멍 예제와 JSON 계약](language/body-codegen.md#filling-typed-body-ir-holes).

## 자체 모델 개발과 이전 실행 관측

공유 판단 모델은 256→8→2 네트워크를 세 번 재사용하며 학습 파라미터는

### 실행 환경이 바뀌었을 때 발견한 문제

완성했습니다. 더 넓은 기존 개발 집합의 수치는 368/512로 유지합니다.
압축 모델의 판단 중앙값은 8.33µs, 전체 코드 생성은 10.00ms,
컴파일러 프로세스 최대 RSS의 중앙값은 17.78MiB였습니다. 모델을 끈 경로도
추가 후보 96개를 거쳐 완료됐고, 코드 생성 중앙값은 9.80ms였습니다.
후보 수 감소가 전체 시간 개선으로 이어지는 정도는 더 큰 조립 과제로 살펴봅니다.
모든 기록의 첫 미해결 항목은 `permission_boundary`였습니다.
[전체 수치·각 변형·원본 기록](https://github.com/kimjooyoon/gooo-neural-decision-experiments/blob/main/docs/full-input-native-results-20261003.md).

### 활동 하나를 바로 실행하기

데이터 흐름이 없는 Gooo 활동 하나를 실행할 때 인위적인 `bind`를 요구하지
않습니다. `gooo body-compose`는 한 활동의 입력 계약과 본문을 그대로 계획으로
만들고, Go로 투영한 뒤 빌드와 두 차례 실행을 이어서 기록합니다. 활동 여러 개를
조합할 때는 각 데이터 흐름을 계속 명시적 타입 `bind`로 연결합니다. 예제의
세 유한 입력은 `0/3`이 아닌 실제 Go 실행 결과 `3/3`으로 관측되며, 이 비율은
선언된 입력 범위에 한정됩니다. [실행 예제와 기록 형식](native-body-composition.md#one-activity-without-a-synthetic-bind).

### 이름 붙인 판단을 본문에서 재사용하기 — 2026-10-08

같은 소스에 선언한 순수 활동을 `IsPartial(input0, input1)`처럼 조건식 안에서
호출할 수 있습니다. 지역 변수 초기화, 레코드 필드와 반환식에도 같은 규칙을
적용합니다. 호출 대상의 타입·본문·안정 ID·호출 관계를 생성 결과에 남기며,
컴파일러가 재귀와 호출량을 확인합니다. 작은 판단을 복사하지 않고 다시 쓰는
언어 기능입니다. [예제와 실행 명령](../examples/pure-activity-calls/README.md).

진단 도구는 부분 완료 판단을, Gooo 조립 정책은 계속 시도할 수 있는지 판단을
보조 활동으로 분리했습니다. `--entry`는 실제 실행할 활동을 지정하고, 보조
활동은 본문의 인자를 받아 동작합니다. [패키지 호출 예제](../examples/package-body-calls/README.md)는
`rules.IsPartial(...)`로 가져온 함수와 그 함수의 지역 보조 함수를 연결합니다.
원래 패키지·이름·안정 ID·본문 해시와 실행용 이름 사이의 대응을 기록합니다.
앱, 진단 도구, 판단 라이브러리를 각각 Gooo로 구성하는 작은 생태계 예제입니다.

이 [실행 기록](research/pure-activity-calls-20261008/summary.json)에서는 자체 모델이
2개 후보, 결정론적 순서가 4개 후보를 시도해 같은 프로그램에 도달했습니다.
각각 선언 사례 5/5개, 필드 15/15개, 별도 실행 기대값 4/4개를 충족했습니다.
첫 모델 후보만 저장했을 때는 본문 변환 단위 105/105개를 보존하면서도 사례는
3/5개였습니다. “선택한 코드를 모두 옮겼는가”와 “요구 기능을 얼마나 충족했는가”를
따로 보여주는 작은 예제입니다. 모델의 일반적인 성능 우위는 아직 측정하지 않았습니다.

### 조립 기록을 이어 쓰는 언어 도구 — 2026-10-08

Gooo의 `Checkpoint` 규칙으로 첫 후보를 저장한 뒤, `Explain` 규칙으로 남은
후보를 이어서 조립할 수 있습니다. `body-compose --resume-composition`은 이전
관측을 다시 계산해 확인하고, 원래 후보 순서와 총 시도 예산을 이어받습니다.
자체 모델을 사용해 시작했어도 이어하기에는 모델 파일이나 새 추론이 필요하지
않습니다. 정책의 소스, 이전 판단, 새 판단과 실제로 추가한 후보 수를 기록합니다.
[한국어 설명과 실행 명령](../examples/assembly-policy/README.md#continue-a-saved-partial-construction).

지원 범위는 레코드 선택으로 조립하는 활동과 고정 본문을 연결한 그래프입니다.
작업 호출은 실행기가 시작하며, 선언된 후보 안에 답이 없거나 예산을 소진한 경우
부분 충족을 그대로 남깁니다. 이런 작은 도구의 재현과 재사용을 쌓아, 다음 언어
기능과 학습 과제를 실제 미해결 사례에서 고르는 방향으로 발전시키겠습니다.

기능 설명에서 실제 산출물까지 연결하는 사용 흐름을 먼저 완성하고 있습니다.
`discover --generation`은 저장된 코드 생성 결과를 원본 Gooo의 허용 경로와
대조합니다. 별도 계약이 요구하는 기능 두 개 중 하나의 산출물만 재현되면
생성 범위는 1/2입니다. 조립 설명서에서 완성된 부품까지 연결하는 단계이며,
입력에 따라 제대로 동작하는지는 실행 관측으로 따로 기록합니다.
[실행 방법과 지표 해석](language/capability-discovery.md#connect-an-existing-generation).
여기에 `--execute-cases`를 추가하면 지정한 입력으로 생성된 프로그램을 실제로
두 번 실행합니다. 생성 범위 1/2와 새로운 입력의 기대값 충족 6/6을 각각 표시하고,
실행 결과를 원본 활동까지 역으로 연결합니다. 반복 입력은 한 번만 세며,
생성 과정에서 이미 관측한 입력은 독립 입력 분모에 포함하지 않습니다.

- **작은 조립법의 재사용:** 조건부 보정·범위 제한·두 연산 순서를 매개변수로
  표현해 긴 경로 계획의 반복을 줄입니다. 같은 의미를 표현한 선언 크기,
  생성·실행 결과와 미해결 항목을 먼저 비교합니다.
- **계산과 순서의 재현성:** 컴파일러에 연결한 계산 규칙을 더 넓은 입력에서
  관측합니다. 문장의 연산 순서를 구별하면서 작은 배열로 표현하는 방법도
  비교합니다. 새 모델을 연결할 때 원문·후보·관측의 연결을 유지합니다.
- **한국어·영어와 Gooo 의미 연결:** 남은 데이터 분할·표현 조건을 평가하고
  새 과제로 확장합니다. 번역 쌍의 유효한 선택, 같은 오답, 추가 탐색 비용을
  함께 측정합니다.
- **완전성 변화 비교:** 현재 `completeness-delta`가 제공하는 이전·이후
  관측 비교를 자연어 탐색과 더 넓은 실행 프로필까지 확장합니다.
- **더 풍부한 언어 표현:** 더 다양한 타입과 조합을 표현하고 생성·역관측
  규칙을 함께 늘립니다. 각 기능은 실행 가능한 예시와 연결합니다.
- **반복 사용 비용:** 모델을 한 번 로드한 요청 처리의 지연, 동시성,
  프로세스 RAM을 분리 측정합니다. 원본 실험 기록에는 저장 예산을 둡니다.

자연어 capability discovery의 선언 범위는 대상 파일의 선언 수로 계산하지
않습니다. 대상 파일이 자기 분모를 정하면 모든 선언이 자동으로 충족된 것처럼
보일 수 있기 때문입니다. 별도 Gooo 파일에 기대하는 안정 ID와 타입 경계를
선언하고, 실제 파일이 이를 얼마나 갖췄는지 비교합니다. 계약을 제공하지 않으면
완성도는 `UNKNOWN`이며, 계약이 있으면 누락된 ID와 분모를 영수증에 남깁니다.
이 수치는 선언 범위만 설명하며 바디의 정확도나 도메인의 철학적 완전성을
대신하지 않습니다. [실행 예제](../examples/capability-discovery/README.md).

최근 조사에서 우선하는 원리는 다음 관측 선택, 실행 사실 보존, 필요한 단계만 수행하기입니다.
[LAVOIR](https://arxiv.org/abs/2609.30706)의 정보 가치,
[OpenAI의 실행 문맥 분석](https://openai.com/index/how-two-settings-tripled-our-arc-agi-3-scores/),
[Meta의 조립식 절차](https://engineering.fb.com/2026/09/02/ml-applications/organizational-second-brain-ai-learns-from-experts/),
[Context Language Models](https://arxiv.org/abs/2609.37725v1)에서 작은 설계 질문을 가져옵니다.
Gooo에서는 선언된 기준 함수와 실행 결과로 개선 근거를 자동 수집합니다.
[원문별 채택 이유와 적용 범위](https://github.com/kimjooyoon/gooo-neural-decision-experiments/blob/main/docs/agile-language-research-20261003.ko.md).

## 레코드의 불리언 필드 — 2026-10-05

기존 레코드는 문자열 필드만 표현할 수 있어 `ready`나 `enabled` 같은 상태도
문자열로 저장해야 했습니다. 이 제약을 풀기 위해 기존 계약을 바꾸지 않고
필수 단일 `boolean` 필드만 추가하는 EntityFields V2를 만들었습니다. Gooo의
필드 타입은 안정적인 `urn:gooo:type:boolean`으로 IR에 들어가고, 생성된 Go
구조체에서는 `bool`이 됩니다. Gooo 선언에 둔 참·거짓 사례를 통해 후보 선택,
타입 검사, JSON 관측을 확인합니다.

V2는 `gooo generate`의 Go 구조 투영, 독립 본문 생성, `body-compose` 레코드
전송에서 사용합니다. 입력·바인딩 전달·실제 필드 관측·기대값에서도 Boolean을
JSON Boolean으로 유지합니다. 새 타입이 기존 V1 기록을 조용히 다시 해석하지
않도록 버전을 분리했습니다.
[Gooo 예제와 실행 방법](native-record-values.md#typed-fields-across-source-driven-execution).

## 레코드의 정수 필드 — 2026-10-05

레코드에서 수량이나 점수 같은 수치를 문자열로 표현하지 않도록 EntityFields
V3에 필수 단일 `integer` 필드를 추가했습니다. 이 타입은 안정적인
`urn:gooo:type:integer`로 의미 모델에 기록되고 Go에서는 `int64`가 됩니다.
Gooo의 조립 사례는 입력값을 계산해 레코드에 넣고, 2^53을 넘는 값의 JSON
입력부터 연결 실행까지 정밀도가 유지되는지 확인합니다.

V3은 V1의 문자열과 V2의 불리언을 유지하면서 정수 타입을 더합니다. V1/V2
프로필 기록은 그대로 구분됩니다. [정수 레코드 예제와 실행 안내](native-record-values.md#typed-fields-across-source-driven-execution).

## 선택형 레코드 필드 — 2026-10-07

도메인 값에는 없을 수도 있는 정보가 있습니다. V4는 `optional one` 문자열,
Boolean, Integer 필드를 Go의 `*string`, `*bool`, `*int64`로 투영합니다.
따라서 부재와 `""`, `false`, `0`을 구별할 수 있습니다. 의미 투영의 source map은
원본 필드 span·안정 ID·프로필 지문을 보존하고 생성 manifest는 그 source map
지문과 Go 산출물을 연결합니다. 현재는 `gooo check`, `gooo generate`,
`run --record-input`과 record 본문 복사·조합에서 사용할 수 있으며 capability
discovery, 활동 bind 계획, 다중 패키지 `package execute`도 이 프로필을 읽습니다.
패키지 실행은 선택 필드를 가져온 활동에서 다음 활동까지 보존합니다. 생략된 키는
부재로, 명시한 빈 문자열·`false`·`0`은 값으로 남습니다. 실제 패키지 실행과 재생은
[선택 필드 예제](../examples/package-optional-record-flow/README.md)에서 확인할 수
있습니다. `record-field-assembly`는 `nil`로 부재를 선택하고 타입이 맞는
지역값의 주소로 문자열·불리언·정수 값을 만들 수 있습니다. 유한 사례별
`expected_present`와 `actual_present`를 기록하므로 빈 문자열·`false`·`0`과
부재를 구별합니다. 이는 선언된 사례에서 확인한 범위이며 모든 입력의 정확성을
뜻하지 않습니다. `null` 입력은 거부합니다.
[V4 예제](../examples/entity-fields-v4/main.gooo.fixture)와
[V4 지원 범위](entity-fields-v4.md),
[V1 지원 관측](entity-fields-support.md)을
확인할 수 있습니다.

## 기록형 IR 본문에서 자체 모델 사용 — 2026-10-07

`source_fill`은 Gooo의 선언된 사례에서 기록형 본문 후보를 만듭니다. 작은
로컬 모델은 후보를 직접 쓰지 않고, 한 IR 구멍의 연산 종류를 예측합니다.
예를 들어 `&&`를 고르면 Gooo는 해당 구멍에 `&&`를 쓰는 완성 후보만 남기고,
그 안에서 학습 사례 점수가 가장 높은 후보를 선택합니다. 같은 연산을 쓰는
후보가 여럿이어도 나머지 구멍을 채운 완성 후보를 점수로 구분할 수 있습니다.
모델에는 의도만 전달하고 사례 값은 보내지 않습니다. Gooo는 모든 후보를 타입
검사하고 학습 사례 점수를 계산하며, 선택 결과와 별도 보류 사례를 다시
평가합니다. 전체 후보 중 더 높은 학습 점수의 후보가 있으면 Gooo가 교체합니다.

추론은 한 구멍에 둘 이상의 지원 연산 종류가 있을 때만 수행합니다. 모든
구멍에서 연산 종류가 같거나 지원 범위 밖이면 추측하지 않고 추론 전에
실패합니다. 모델을 생략하면 선언된 후보 점수로 결정론적 선택을 합니다.
이 점수는 선언한 유한 사례에서만 유효하며 전체 입력 영역의 정확도는
보장하지 않습니다. [기록형 IR 생성 예제](language/body-codegen.md#model-guided-record-body-fill).

## 정수 레코드 경계 조건 — 2026-10-07

레코드 입력의 정수 필드는 기존 문법에서 관측값에 대한 `==`·`!=` 조건만
후보로 만들 수 있었습니다. 새 `record-field-predicate/v2` 문법은 정수 입력과
정수 필드에 `<`, `<=`, `>`, `>=`를 추가합니다. v1 문법의 후보 공간은 그대로
유지해 기존 생성 결과와 지표 분모를 바꾸지 않습니다. 후보 기준값은 선언한
훈련 사례에서 가져오고, 잘린 후보 수와 완전성은 영수증에 기록합니다.

새 예제는 다섯 훈련 기록에서 양수 조건을 구성하고 음수·양수 보류 기록 두
건에서 선택된 본문을 다시 평가합니다. 이 실험은 유한 후보 중 경계 조건을
조립할 수 있음을 보일 뿐, 선언하지 않은 임계값이나 모든 정수 입력에 대한
정확성을 보장하지 않습니다. [실행 가능한 Gooo 선언](language/body-codegen.md#model-guided-record-body-fill).

## 정수 범위 조건 조합 — 2026-10-07

새 `record-field-predicate-composition/v2` 문법은 이 정수 비교들을 두 개씩
`&&`·`||`로 묶습니다. 작은 후보 한도에서도 레코드 필드 간 조건과 같은 정수
필드의 범위 조건을 함께 탐색하도록 두 종류 후보를 교차 배치합니다. 전체
문법 크기와 실제 보유한 후보 수를 따로 기록하며 v1 순서는 바뀌지 않습니다.
[범위 조건 fixture](../examples/body-codegen/source-ir-fill-record-integer-range.gooo.fixture)는
훈련 사례와 별도 보류 사례에서 타입검사·재생·정확도를 측정합니다. 이는 유한
사례 안의 증거이며 모든 정수 입력에 대한 완전성 주장은 아닙니다.

## Gooo 도구를 조립한 뒤 반복 사용하기 — 2026-10-07

`package replay`는 저장한 패키지 조립 결과를 현재 소스와 다시 연결하고,
선택된 본문을 새 입력으로 실행합니다. 모델이 처음 조립에 참여했어도 이후
실행에는 모델 파일이 필요하지 않습니다. 같은 도면으로 만든 공구를 가져다
쓰는 방식입니다. 원래 모델의 판단 기록과 이번 실행에서 발생한 호출 수는
서로 구분합니다.

기존 자체 QAT 모델을 실제로 연결한 [관측 기록](research/workspace-replay-20261007/summary.json)에서는
첫 제안이 훈련 필드 13/15를 맞혔고, Gooo의 유한 탐색이 두 번째 후보에서
15/15를 맞혔습니다. 결정론 순서는 네 후보를 시도했습니다. 두 경로의 실제
출력 기대값은 8/8, 모델 없이 저장 결과를 재실행한 기대값도 8/8이었습니다.
모델은 약 19마이크로초에 제안했으며, 첫 제안의 높은 확률값과 실제 부분
충족을 함께 기록했습니다. 단일 과제의 관측으로 전체 성능을 일반화하지 않습니다.

[진단 도구 예제](../examples/package-diagnostic-replay/README.md)는 Gooo 라이브러리가
완료·부분 충족·관측 부족·잘못된 수를 분류하고, 다른 패키지가 설명을 만드는
작은 생태계 도구입니다. 새 입력만 전달하면 실제 값을 반환하며 정답률을
만들지 않습니다. 기대값이 있는 사례에서 미충족 항목이 남으면 `PROGRESS`로
표시합니다. 모델과 언어의 역할 분리를 사용자가 실행해 볼 수 있는 경로입니다.

## 본문의 맥락으로 빈칸 구성하기 — 2026-10-07

`input + 빈칸`에 대해 `2 → 3`, `10 → 11`을 선언하면 빈칸에는 `1`이
필요합니다. 기존 문법은 최종 출력에서 상수 후보를 가져와 이 값을 놓쳤습니다.
새 `integer-hole-residual/v1`은 빈칸에 0과 1을 넣은 출력 차이를 관측하고,
필요한 상수와 입력에 따른 일차식을 후보로 만듭니다. 조립대에서 부품을 끼울
자리를 먼저 살펴보는 방식입니다.

관측에는 훈련 사례만 쓰고, 제안된 식을 전체 본문에 넣어 다시 평가합니다.
분기·비선형식·정수 오버플로 때문에 제안이 틀릴 수 있으며, 실패와 생략한
후보도 기록합니다. 모델 없이 같은 순서로 재생할 수 있습니다.
[세 활동을 연결한 실행 예제](native-body-composition.md#contextual-hole-construction)는
상수와 지역변수 계산을 함께 구성합니다.

이 발전은 모델의 정답률 상승과 구분해 측정합니다. 후보를 표현하지 못한
실패는 언어의 구성 능력으로 해결하고, 모델은 그 공간에서 탐색 순서를 돕도록
키웁니다. 공개 결과에는 훈련·보류·실제 실행의 분모를 각각 남기며, 다음
성장 기준은 외부 개발자가 예제를 재현하고 자신의 과제로 확장할 수 있는지입니다.

## 패키지별 레코드 이름과 안정 ID — 2026-10-07

서로 다른 라이브러리가 각자 `Result`를 선언해도 함께 실행할 수 있도록
레코드 이름의 범위를 패키지에 연결했습니다. 외부에 보이는 이름은 그대로
두고, 실행 코드에서는 안정 ID로 서로 다른 타입을 구분합니다. 같은 이름의
서랍에 패키지와 ID라는 주소를 붙이는 방식입니다.

본문 생성자, 함수 입출력, 조립 후보와 계획 본문이 이 대응을 함께 사용합니다.
문자열이나 지역 변수에 나온 `Result`는 타입 이름으로 바꾸지 않습니다.
같은 안정 ID를 여러 이름으로 부를 때는 필드 선언이 일치하는 하나의 타입으로
연결합니다. 원래 패키지·이름·ID와 실행용 이름은 결과에 기록합니다.
[실행 예제](../examples/package-record-namespaces/README.md)는 서로 다른 두 레코드를
거치는 세 활동을 연결하고, 네 입력의 열두 출력 기대값을 확인합니다.
