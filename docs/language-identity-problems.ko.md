# Gooo의 의미를 중심으로 개발하기

2026-10-13 개발 소스 기준. 앞으로 구현의 단위는 **Gooo 소스로 표현하고 실행할 수 있게 된 문제**로 잡습니다.
컴파일러 코드의 분량과 실험 파일 수는 구현 비용을 설명합니다. 언어의 진전은 사용자가 작성한
개념·조건·선택이 실제 동작과 설명으로 이어지는지 확인해서 판단합니다.

## 우리가 풀려는 문제

프로그램을 만드는 과정에는 서로 다른 질문이 있습니다. 어떤 일을 하려는가, 어떤 구현을
허용하는가, 지금 결과를 받아들일 근거가 무엇인가, 아직 무엇을 모르는가입니다.
Gooo는 이 질문들을 소스에 남기고 컴파일과 실행까지 이어가려 합니다.

작업 지시서에 부품, 조립 순서의 선택지, 확인 방법을 함께 적는 모습에 가깝습니다.
자체 소형 모델은 그 안에서 먼저 시도할 선택을 제안합니다. 기준과 후보를 바꾸는 일은
Gooo 프로그램의 변경으로 드러납니다. 모델을 생략해도 같은 선언으로 작업을 진행합니다.

## 현재 코드에서 확인한 과제

| 문제 | 확인한 현재 상태 | Gooo에서 발전시킬 방향 |
| --- | --- | --- |
| 추가로 확인할 내용을 프로그램과 함께 전달하기 어렵다 | `assembling`은 선택과 사례를 소유하지만 추가 관측은 `--path-observation` JSON으로 전달했다 | `observe`에 입력, 기준 활동, 관측 한도를 선언하고 IR·소스 출력·재실행에 보존한다 |
| 사례를 모두 맞혀도 의도가 하나로 결정되지 않을 수 있다 | 서로 다른 후보가 초기 사례에 같은 답을 내며, 기존 관측기가 차이가 나는 입력을 찾을 수 있다 | 원래의 모호함, 새로 얻은 답, 미관측 후보를 함께 보여 준다. 기준 활동이 없으면 질문을 남긴다 |
| 조립 단계를 옮기면 확인한 조건을 잃을 수 있다 | 호출자에 맞춘 typed-path 후보 검사는 처음의 `case`만 검사하고 관측으로 얻은 답을 누락했다 | 새 답을 지역 계약에 보존하고 호출자 요구와 충돌하면 각 조건의 결과를 나누어 남긴다 |
| 아직 고르는 중인 구현이 다른 구현의 정답이 될 수 있다 | 관측의 기준 활동 자체에 `assembling`이 있어도 원래 바디에서 답을 얻었다 | 기준은 고정된 `computes`로 선언하고 미결정 조립을 기준으로 삼으면 이유를 보고한다 |
| 소스의 표현 방식에 따라 평가 기능이 다르다 | Integer 경로의 `holdout_case`에 이어 레코드의 필드 선택·갱신에서도 `holdout_value_case`를 사용할 수 있게 했다 | 선택·이어 조립·호출자 조립의 평가를 나누고, 실제 호출 입력과 겹치는지도 기록한다 |
| 모델 연구 결과와 언어의 지원 범위가 쉽게 섞인다 | 작은 모델은 일부 정수 비교·반환 선택에 연결돼 있고, V4의 별도 평가에서는 첫 선택이 악화됐다 | 먼저 필요한 Gooo 작업을 정하고, 그 작업의 선언과 실패 기록을 바탕으로 판단 모델을 개선한다 |
| 개념을 고칠 때 관련 선언을 함께 읽어야 한다 | `context`는 안정적인 ID 주변의 선언을 내보내고, `impact`는 변경 전후의 호출·관측 기준·타입 관계를 비교한다 | 다시 확인할 범위와 아직 해석하지 못한 의존 관계를 함께 표시한다. 실제 동작은 별도로 확인한다 |

## 첫 구현: 소스가 다음 관측을 소유하기

[작은 수수료 예제](../examples/source-owned-observation/README.md)는 `11 -> 0`만으로는
뺄셈의 방향을 구분할 수 없는 상황을 사용합니다. Gooo에 추가 입력 두 개와 기준 활동을 적으면,
기존 관측기가 후보를 구별하는 입력을 골라 답을 얻고 그 답을 기록합니다.
소스를 다른 개발 환경으로 옮겨도 같은 확인 계획을 읽을 수 있습니다.

`observe`의 내용은 문법 노드와 의미 IR에 보존됩니다. 입력·기준·한도를 바꾸면 의미 식별값도
바뀝니다. 외부 옵션은 이 선언을 덮어쓸 수 없고, 저장된 관측도 원래 선언과 맞아야 합니다.
기준 활동의 답이 초기 사례와 충돌하면 조립을 진행하기 전에 그 충돌을 보고합니다.
워크스페이스에서는 다른 소스 파일의 기준 활동도 의존 대상으로 보존하고 패키지 이름을 함께 변환합니다.

호출자가 다른 결과를 요구하며 후보를 다시 고를 때에도 이미 얻은 답은 지역 조건에 포함됩니다.
현재 조합의 기준 활동으로 그 답을 다시 확인하고, 다른 후보를 편하게 선택하려고 정답을 바꾸지 않습니다.
초기 관측의 기록은 그대로 보존하며, 후보의 기록에는 어느 관측에서 답을 가져왔는지 남깁니다.
이 단계는 새로운 질문을 고르거나 모델을 다시 호출하지 않습니다.

예를 들어 기준이 `Fee(17) = -6`이라고 답했는데, Fee를 그대로 반환하는 호출자가 `6`을 요구하면
둘을 동시에 만족시킬 수 없습니다. 예제의 두 후보는 각각 지역 조건 `2/2`·호출자 `0/1`,
지역 조건 `1/2`·호출자 `1/1`로 구분됩니다. 결과는 `PARTIAL_FINITE`로 남습니다.
이렇게 무엇을 지켰고 무엇이 충돌하는지 드러내는 것이 Gooo에서 다루려는 완전성의 한 부분입니다.
전체 입력에 대한 증명이나 자연어 의도의 충족률로 이 수치를 확대하지 않습니다.

이 변경의 성공 기준은 문법 파싱만으로 끝나지 않습니다. 소스 왕복, 실제 후보 구별,
기준 없는 미해결 결과, 한도에 가려진 후보, 별도 입력의 네이티브 실행과 저장 결과 재사용을
각각 확인합니다. 테스트 결과는 해당 기능과 사례 범위의 증거로 읽습니다.

## 두 번째 구현: 선택한 이유와 별도 평가를 나누기

경로 조립에서도 `case`와 `holdout_case`를 함께 적을 수 있습니다. 전자는 후보를 고르는 데
사용하고, 후자는 선택이 끝난 바디를 평가합니다. 평가 정답만 바꾼 합성 검사에서 선택 문서,
모델 입력 배열, 선택 결과가 그대로 유지되고 평가 점수만 바뀌는 것을 확인했습니다.
평가 입력은 초기 사례·조건 사례·추가 관측 입력과 겹칠 수 없습니다.

[수수료 예제](../examples/source-path-holdouts/README.md)는 두 후보가 초기 사례를 모두 맞히는
상황에서 시작합니다. 초기 바디의 별도 평가가 `0/1`이어도 그 점수로 다시 고르지 않습니다.
호출자의 요구로 선택이 바뀐 뒤 최종 바디를 평가하면 `1/1`이 됩니다. 출력에는 두 시점의
평가와 호출자 선택에 쓴 사례를 구분해 남깁니다. 평가 중 연산 오류가 나면 정확도는 미측정으로 남습니다.

평가 입력이 호출자 조립 중 이미 쓰일 수도 있습니다. 예제에서 Main에 54를 주면 Fee에는
59가 전달됩니다. 최종 결과는 함수가 실제로 받은 입력을 따라가며 이 겹침을 표시합니다.
호출 기록이 없으면 겹침 여부도 미상입니다. 다른 지역 함수 평가나 모델의 과거 학습 데이터까지
독립성을 확인한 수치로 확대하지 않습니다.

## 세 번째 구현: 일부 필드가 맞는 것과 결과 전체가 맞는 것을 구분하기

레코드 조립에는 필드 값을 채우는 `field_value`와 기존 값을 고치는 `field_update`가 있습니다.
두 방식 모두 `value_case`로 선택 사례를, `holdout_value_case`로 별도 평가 사례를 적습니다.
문자열·정수·불리언을 함께 담은 결과에서 전체 결과와 개별 필드의 성공 수를 따로 기록합니다.
선택 필드의 생략과 값 0도 구분합니다.

예를 들어 반품 처리에서 금액·승인 여부·설명을 반환한다고 해 봅시다. 승인 여부와 설명을
제대로 채워도 금액의 부호가 틀리면 해당 반품 결과는 틀린 것입니다. 필드의 성공 비율은
어느 부분이 구현됐는지 알려 주고, 사례 전체의 성공 비율은 함께 작동했는지 알려 줍니다.
이 비율을 자연어로 적은 의도의 충족률로 확대하지 않습니다.

[레코드 예제](../examples/record-field-holdouts/README.md)에서는 지역 선택 직후의 별도 평가,
보조 함수가 바뀐 뒤 이어 조립한 평가, 호출자 요구로 고른 최종 바디의 평가를 구분합니다.
앞선 결과는 당시의 바디와 함께 보존합니다. 같은 답을 나중 바디에 적용해 결과가 달라졌다면
어느 조립 단계에서 변했는지 확인할 수 있습니다. 현재는 대상의 선언을 유지한 채 의존 함수를
바꾸는 연속 조립을 지원합니다. 대상의 의도나 선택지를 고쳤다면 새 비교와 조립이 필요합니다.

이 기능에서 모델은 소스가 허용한 선택지의 순서를 제안합니다. 별도 평가의 입력과 정답은
지원하는 다섯 가지 레코드 모델 입력 형식에서 제외됩니다. 이번 기능 검사는 결정론적 경로와
입력 분리를 확인했으며, 모델의 새 학습이나 예측 성능을 측정하지 않았습니다.

## 네 번째 구현: 레코드가 확인할 질문을 함께 갖기

환불 금액이 0인 사례만으로는 금액 유지와 부호 변경을 구별할 수 없습니다.
[추가 관측 예제](../examples/source-record-observation/README.md)는 `observe`에 승인된 반품과
승인되지 않은 반품을 질문으로 적습니다. 컴파일러는 허용된 후보들이 다른 답을 내는 입력을
고르고, 고정된 기준 활동에서 답을 얻습니다. 질문 목록, 기준, 한도는 Gooo 프로그램에 남습니다.

문자열·불리언·정수·선택 필드를 담은 레코드와 여러 인자를 그대로 다룹니다. 기준이 없으면
질문을 남기고, 후보나 질문 한도에 도달하면 확인하지 못한 범위를 기록합니다. 후보가 계산에
실패한 경우에도 그 후보를 없었던 것으로 취급해 유일한 구현을 찾았다고 판단하지 않습니다.

새로 얻은 답은 이어 조립과 호출자 조립에도 전달됩니다. 현재 기준 활동이 앞선 답과 충돌하면
충돌을 보고하고, 기존 답을 바꾸는 대신 사용자가 고친 선언을 드러냅니다. 성공한 부분과
충돌한 부분을 함께 표현하는 것이 이 기능의 목적입니다. 평가 사례는 계속 별도로 남습니다.

기존 모델 입력 형식은 유지합니다. 이번 추가 관측은 유한한 사례 검사와 후보 구별에 쓰이며,
새 답을 학습 입력으로 넣거나 모델 성능이 좋아졌다고 주장하는 근거로 쓰지 않습니다.

## 다섯 번째 구현: 결과를 판단할 조건을 언어가 연결하기

반품의 금액, 승인 여부, 설명 보존은 서로 다른 조건입니다. 결과 전체를 한 번에 비교하면
어느 조건을 만족했는지 알기 어렵습니다. 각 조건의 집계까지 사용자가 직접 작성하면
같은 평가 배선이 여러 프로그램에 반복됩니다.

[`criteria` 예제](../examples/source-behavior-criteria/README.md)는 판단 조건을 Gooo의 고정된
`computes` 활동으로 정의하고, 조립 대상에 이름으로 연결합니다. 조건 활동은 원래 입력과
후보의 실제 결과를 받아 불리언을 반환합니다. 컴파일러가 입력 전달, 후보별 조건 평가와
결과 기록을 담당합니다. 따라서 금액 37을 반대로 바꾸는 관계나 사용자의 설명을 그대로
보존하는 관계를 소스에서 읽고 수정할 수 있습니다.

각 입력과 조건의 쌍을 만족·불만족·미확인으로 나눕니다. 세 조건 중 둘을 만족했다면
`2/3`으로 기록하고, 계산 오류가 난 조건은 미확인으로 남깁니다. 이 수치는 선언한 조건과
입력에 대한 측정입니다. 조건 자체가 충분한지, 더 넓은 입력에서 어떤지는 후속 과제입니다.

호출자 조립에서도 같은 조건을 다시 확인합니다. 호출 결과가 맞아도 지역 조건을 잃으면
전체 완료로 판단하지 않습니다. `holdout_input`은 선택 뒤의 별도 평가에 쓰고, 호출자가
이미 사용했던 입력인지도 표시합니다. 고정된 조건의 구현이 바뀌면 앞서 시도한 후보를
다시 확인하며 이전 소스와 결과를 함께 보존합니다.

자체 소형 모델은 현재 선언된 선택지의 순서를 제안하는 역할을 이어갑니다. 기존 입력
형식에는 조건 활동의 바디가 포함되지 않습니다. 앞으로 모델을 발전시킬 때는 어떤 조건이
남았고 어떤 선택이 그 조건에 영향을 주는지를 소스 구조로 표현하는 문제를 연구할 수
있습니다. 이번 기능에는 새 학습이나 예측 성능 향상을 주장할 근거가 포함돼 있지 않습니다.

## 여섯 번째 구현: 정답 레코드 없이 다음 조건 입력을 고르기

[`criteria_input` 예제](../examples/source-criteria-questions/README.md)는 후보 출력의 차이로
추가 입력을 고르고, 그 입력을 소스의 조건 활동으로 판단합니다. 처음 준 입력과 추가로
얻은 입력을 구분하며, 추가 입력도 이어 조립과 호출자 조립의 조건으로 유지합니다.

## 일곱 번째 구현: 후보가 같은 답을 내도 조건을 다시 확인하기

모든 후보가 같은 답을 낸다는 사실만으로 그 답을 받아들이기는 어렵습니다. 반품 금액을
그대로 두는 두 구현은 금액 0에서 부호 반전 조건을 만족하고, 다른 금액에서는 함께
잘못된 답을 낼 수 있습니다.

[공통 오답 예제](../examples/source-criteria-challenges/README.md)는 소스에
`criteria_strategy "distinguish_then_check"`를 적습니다. 후보를 구분하는 질문을 우선하고,
차이가 없으면 남은 입력에서 관측 가능한 결과를 조건에 대입합니다. 후보를 구분하려고
고른 입력인지, 공통 결과를 확인하려고 고른 입력인지 기록합니다. 확인할 수 없는 출력은
같은 답이라는 증거로 취급하지 않습니다.

추가 입력에서 모든 허용 후보가 조건을 위반하면 그 사실을 남깁니다. 선택지를 소스에
추가하거나 조건을 수정하면 새로운 프로그램으로 다시 조립할 수 있습니다. 이 구분으로
현재 선택지로 조립 가능한 범위와 더 표현해야 하는 요구를 확인할 수 있습니다.

## 여덟 번째 구현: 선택지가 실패한 이유를 소스의 조건으로 설명하기

[가격 예제](../examples/source-criteria-explanations/README.md)는 원가 18과 예산 25 사이에서
가격을 고릅니다. 소스가 허용한 가격 10과 30은 각각 원가 조건과 예산 조건을 어깁니다.
가격 20이라면 두 조건을 만족하므로, 이 실패를 조건 자체의 모순으로 설명해서는 안 됩니다.

조립 보고서는 각 후보를 탈락시킨 조건 이름, 입력, 실제 출력과 소스 식별값을 연결합니다.
어떤 후보까지 확인했는지, 확인하지 못한 후보가 있는지, 실패 이유를 연결할 기록이
부족한지도 구분합니다. 원래의 상세 기록은 그대로 두고 읽을 수 있는 설명을 도출합니다.

이 예제에서는 두 번째 선택지를 20이 나오도록 수정한 소스로 별도 평가 1/1을 관측했습니다.
조건은 그대로 유지했습니다. 이후 조건을 수정한 경우에도 앞선 실패 기록은 당시 소스의
설명으로 남고, 현재 조건의 결과는 별도로 표시됩니다. 저장된 보고서를 읽는 동안에는
모델 호출이나 프로그램 재실행이 발생하지 않습니다.

## 아홉 번째 구현: 정수 계산도 자신의 조건으로 경로를 고르기

“입력에서 11을 뺀다”는 관계는 Gooo로 적을 수 있습니다. 입력마다 정답을 하나씩 작성할
필요는 없습니다. [`Integer -> Integer` 예제](../examples/source-scalar-criteria/README.md)는
원래 입력과 계산 결과를 받아 `결과 == 입력 - 11`을 판단하는 활동을 연결합니다.
처음 입력 11에서는 두 경로가 모두 0을 냅니다. 선언한 다음 질문 17을 관측하면
어느 경로가 조건에 맞는지 구분됩니다. 함수의 입력·결과 타입도 그대로 유지합니다.

같은 조건을 피연산자 순서, 분기 배치, 지역 변수 참조, 대입 대상, 문장 순서에 적용할 수
있습니다. 질문으로 얻은 조건은 호출자 조립과 이어 조립에서도 유지합니다. 실제 호출
결과가 맞더라도 앞서 얻은 조건에 어긋나면 부분 완료로 남깁니다. 현재 지원 범위는
인자 하나를 받는 정수 함수와 기존의 제한된 바디 문법입니다.

예제의 올바른 경로는 조건 2/2, 별도 조건 1/1, 추가 네이티브 실행 1/1을 통과했습니다.
선택지 두 개가 모두 같은 계산 오류를 내는 예제는 조건 1/2, 추가 실행 0/1로 남았습니다.
각 결과의 입력과 분모를 따로 남겼으며 모델 호출은 모두 0회입니다. 현재 모델의
레코드용 입력 형식으로는 이 프로필을 표현할 수 없어 결정론적으로 선택합니다.

이 기능의 언어적 변화는 판단 기준을 함수의 사용 방식과 함께 운반할 수 있게 된 점입니다.
Go 구현은 그 연결과 실행을 담당합니다. 앞으로 자체 결정 모델의 학습 항목도 이 소스가
허용한 선택, 아직 충족하지 못한 조건, 다음에 물어볼 입력을 기준으로 설계할 수 있습니다.
조건의 품질과 새 입력에서의 동작은 계속 따로 살펴야 합니다.

## 열 번째 구현: Gooo 프로그램이 다른 Gooo 구현의 관계를 판단하기

[관계 예제](source-relational-callers.ko.md)는 여러 결과 사이의 조건을 Gooo 활동으로
작성합니다. 증가 관계에서는 같은 함수를 두 번 호출하고, 왕복 관계에서는 서로 다른
두 함수를 합성합니다. 호출자 조립이 이 관계를 기준으로 지역 구현을 선택하며 각 함수의
기존 조건도 유지합니다.

성공 가능한 두 프로그램은 별도 관계 검사에서 각각 1/1을 통과했습니다. 올바른 선택지가
없는 두 프로그램과 지역·호출자 조건이 충돌하는 프로그램은 부분 완료로 남았습니다.
다섯 프로그램을 각각 한 번 실행했고 모델 호출은 0회였습니다. 새 컴파일러 로직 없이
현재 Gooo로 판단 활동 자체를 구현한 사례입니다. 이 결과를 더 넓은 입력의 증명이나
자체 모델의 성능 개선으로 확대하지 않습니다.

## 다음 작업을 고르는 기준

- 먼저 실패하거나 표현하기 어려운 `.gooo` 프로그램을 남깁니다.
- 그 프로그램의 의미 중 무엇이 외부 코드에 흩어져 있는지 확인합니다.
- 새 문법·IR·실행 기능이 사용자의 선언을 끝까지 보존하는지 검사합니다.
- 기능 사례와 별도 평가를 나누고, 미지원·모순·미관측 결과도 보존합니다.
- 자체 모델의 학습은 이 언어 기능에 필요한 판단을 기준으로 설계합니다.

우선순위는 관측·평가 선언의 실행 범위 확장, 조립 방식 간 평가 의미의 일관성, 개념 변경의 영향 설명입니다.
자연어 이해 범위, 더 넓은 바디 조립, CAP04/05와 100가지 독립 실험의 완수 여부는 별도로
검증해야 합니다. 이번 관측 선언 하나로 그 요구 전체를 완료했다고 판단하지 않습니다.

## 모듈 타입으로 실제 결과를 만드는 다음 과제

활동 서명의 `module.Value`와 본문의 `module.Value{...}`는 같은 entity ID를 가리켜야 한다.
새 테스트에서 서명은 해석됐지만 본문의 별칭이 남는 문제를 확인했고,
원래 파일의 import를 값 생성자에 적용하는 수정안을 준비했다.
같은 표시 이름과 별칭을 사용하는 다른 파일의 업무 타입은 구분한다.

후보가 쓰일 실제 빈자리의 변수 범위도 읽는다. 소스·외부 fill plan에서
지역 값이 import 별칭을 가린 두 경우를 거절했고, 다른 블록의 지역 값은 보존했다.
새 API 관찰과 실제 CLI에서 선택 사례, 별도 평가와 호출 입력의 결과를 각각 확인했다.
[가져온 레코드 생성자 안내](language/package-qualified-record-constructors.ko.md)에
원래 생산자, 결과와 현재 표현 범위를 기록했다.
