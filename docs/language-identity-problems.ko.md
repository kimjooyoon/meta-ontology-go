# Gooo의 의미를 중심으로 개발하기

2026-10-12 기준. 앞으로 구현의 단위는 **Gooo 소스로 표현하고 실행할 수 있게 된 문제**로 잡습니다.
컴파일러 코드의 분량과 실험 파일 수는 구현 비용을 설명합니다. 언어의 진전은 사용자가 작성한
개념·조건·선택이 실제 동작과 설명으로 이어지는지 확인해서 판단합니다.

## 우리가 풀려는 문제

프로그램을 만드는 과정에는 서로 다른 질문이 있습니다. 어떤 일을 하려는가, 어떤 구현을
허용하는가, 지금 결과를 받아들일 근거가 무엇인가, 아직 무엇을 모르는가입니다.
Gooo는 이 질문들을 소스에 남기고 컴파일과 실행까지 이어가려 합니다.

작업 지시서에 부품, 조립 순서의 선택지, 확인 방법을 함께 적는 모습에 가깝습니다.
자체 소형 모델은 그 안에서 먼저 시도할 선택을 제안합니다. 기준과 후보를 바꾸는 일은
Gooo 프로그램의 변경으로 드러납니다. 모델을 생략해도 같은 선언으로 작업을 진행합니다.

## 현재 코드에서 확인한 과제

| 문제 | 확인한 현재 상태 | Gooo에서 발전시킬 방향 |
| --- | --- | --- |
| 추가로 확인할 내용을 프로그램과 함께 전달하기 어렵다 | `assembling`은 선택과 사례를 소유하지만 추가 관측은 `--path-observation` JSON으로 전달했다 | `observe`에 입력, 기준 활동, 관측 한도를 선언하고 IR·소스 출력·재실행에 보존한다 |
| 사례를 모두 맞혀도 의도가 하나로 결정되지 않을 수 있다 | 서로 다른 후보가 초기 사례에 같은 답을 내며, 기존 관측기가 차이가 나는 입력을 찾을 수 있다 | 원래의 모호함, 새로 얻은 답, 미관측 후보를 함께 보여 준다. 기준 활동이 없으면 질문을 남긴다 |
| 조립 단계를 옮기면 확인한 조건을 잃을 수 있다 | 호출자에 맞춘 typed-path 후보 검사는 처음의 `case`만 검사하고 관측으로 얻은 답을 누락했다 | 새 답을 지역 계약에 보존하고 호출자 요구와 충돌하면 각 조건의 결과를 나누어 남긴다 |
| 아직 고르는 중인 구현이 다른 구현의 정답이 될 수 있다 | 관측의 기준 활동 자체에 `assembling`이 있어도 원래 바디에서 답을 얻었다 | 기준은 고정된 `computes`로 선언하고 미결정 조립을 기준으로 삼으면 이유를 보고한다 |
| 소스의 표현 방식에 따라 평가 기능이 다르다 | IR search/fill의 `holdout_case`를 Integer typed-path에서도 표현하고 초기·최종 바디를 따로 평가하도록 확장했다 | 선택에 평가 답이 섞이지 않는지 검사하고, 호출자 조립에서 이미 본 입력과 겹치는지도 기록한다 |
| 모델 연구 결과와 언어의 지원 범위가 쉽게 섞인다 | 작은 모델은 일부 정수 비교·반환 선택에 연결돼 있고, V4의 별도 평가에서는 첫 선택이 악화됐다 | 먼저 필요한 Gooo 작업을 정하고, 그 작업의 선언과 실패 기록을 바탕으로 판단 모델을 개선한다 |
| 개념을 고칠 때 관련 선언을 함께 읽어야 한다 | 개발 중인 `context`는 안정적인 ID 주변의 선언과 조립 계약을 내보낸다 | 실제 변경 사례를 통해 의존 관계, 남은 의무와 수정 범위를 언어 수준에서 연결한다 |

## 첫 구현: 소스가 다음 관측을 소유하기

[작은 수수료 예제](../examples/source-owned-observation/README.md)는 `11 -> 0`만으로는
뺄셈의 방향을 구분할 수 없는 상황을 사용합니다. Gooo에 추가 입력 두 개와 기준 활동을 적으면,
기존 관측기가 후보를 구별하는 입력을 골라 답을 얻고 그 답을 기록합니다.
소스를 다른 개발 환경으로 옮겨도 같은 확인 계획을 읽을 수 있습니다.

`observe`의 내용은 문법 노드와 의미 IR에 보존됩니다. 입력·기준·한도를 바꾸면 의미 식별값도
바뀝니다. 외부 옵션은 이 선언을 덮어쓸 수 없고, 저장된 관측도 원래 선언과 맞아야 합니다.
기준 활동의 답이 초기 사례와 충돌하면 조립을 진행하기 전에 그 충돌을 보고합니다.
워크스페이스에서는 다른 소스 파일의 기준 활동도 의존 대상으로 보존하고 패키지 이름을 함께 변환합니다.

호출자가 다른 결과를 요구하며 후보를 다시 고를 때에도 이미 얻은 답은 지역 조건에 포함됩니다.
현재 조합의 기준 활동으로 그 답을 다시 확인하고, 다른 후보를 편하게 선택하려고 정답을 바꾸지 않습니다.
초기 관측의 기록은 그대로 보존하며, 후보의 기록에는 어느 관측에서 답을 가져왔는지 남깁니다.
이 단계는 새로운 질문을 고르거나 모델을 다시 호출하지 않습니다.

예를 들어 기준이 `Fee(17) = -6`이라고 답했는데, Fee를 그대로 반환하는 호출자가 `6`을 요구하면
둘을 동시에 만족시킬 수 없습니다. 예제의 두 후보는 각각 지역 조건 `2/2`·호출자 `0/1`,
지역 조건 `1/2`·호출자 `1/1`로 구분됩니다. 결과는 `PARTIAL_FINITE`로 남습니다.
이렇게 무엇을 지켰고 무엇이 충돌하는지 드러내는 것이 Gooo에서 다루려는 완전성의 한 부분입니다.
전체 입력에 대한 증명이나 자연어 의도의 충족률로 이 수치를 확대하지 않습니다.

이 변경의 성공 기준은 문법 파싱만으로 끝나지 않습니다. 소스 왕복, 실제 후보 구별,
기준 없는 미해결 결과, 한도에 가려진 후보, 별도 입력의 네이티브 실행과 저장 결과 재사용을
각각 확인합니다. 테스트 결과는 해당 기능과 사례 범위의 증거로 읽습니다.

## 두 번째 구현: 선택한 이유와 별도 평가를 나누기

경로 조립에서도 `case`와 `holdout_case`를 함께 적을 수 있습니다. 전자는 후보를 고르는 데
사용하고, 후자는 선택이 끝난 바디를 평가합니다. 평가 정답만 바꾼 합성 검사에서 선택 문서,
모델 입력 배열, 선택 결과가 그대로 유지되고 평가 점수만 바뀌는 것을 확인했습니다.
평가 입력은 초기 사례·조건 사례·추가 관측 입력과 겹칠 수 없습니다.

[수수료 예제](../examples/source-path-holdouts/README.md)는 두 후보가 초기 사례를 모두 맞히는
상황에서 시작합니다. 초기 바디의 별도 평가가 `0/1`이어도 그 점수로 다시 고르지 않습니다.
호출자의 요구로 선택이 바뀐 뒤 최종 바디를 평가하면 `1/1`이 됩니다. 출력에는 두 시점의
평가와 호출자 선택에 쓴 사례를 구분해 남깁니다. 평가 중 연산 오류가 나면 정확도는 미측정으로 남습니다.

평가 입력이 호출자 조립 중 이미 쓰일 수도 있습니다. 예제에서 Main에 54를 주면 Fee에는
59가 전달됩니다. 최종 결과는 함수가 실제로 받은 입력을 따라가며 이 겹침을 표시합니다.
호출 기록이 없으면 겹침 여부도 미상입니다. 다른 지역 함수 평가나 모델의 과거 학습 데이터까지
독립성을 확인한 수치로 확대하지 않습니다.

## 다음 작업을 고르는 기준

- 먼저 실패하거나 표현하기 어려운 `.gooo` 프로그램을 남깁니다.
- 그 프로그램의 의미 중 무엇이 외부 코드에 흩어져 있는지 확인합니다.
- 새 문법·IR·실행 기능이 사용자의 선언을 끝까지 보존하는지 검사합니다.
- 기능 사례와 별도 평가를 나누고, 미지원·모순·미관측 결과도 보존합니다.
- 자체 모델의 학습은 이 언어 기능에 필요한 판단을 기준으로 설계합니다.

우선순위는 관측·평가 선언의 실행 범위 확장, 조립 방식 간 평가 의미의 일관성, 개념 변경의 영향 설명입니다.
자연어 이해 범위, 더 넓은 바디 조립, CAP04/05와 100가지 독립 실험의 완수 여부는 별도로
검증해야 합니다. 이번 관측 선언 하나로 그 요구 전체를 완료했다고 판단하지 않습니다.
