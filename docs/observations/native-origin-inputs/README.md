# 기원 기록을 Gooo 입력으로 읽은 관찰

2026-10-14 개발 변경. 새 CLI 입력 어댑터와 네 가지 `.gooo` 설명 프로그램을 실행했다.
기준 컴파일러 소스는 `5aef6eca1e43080240e7e5bac0f14cac2353b63e`다.

## 실제 결과

| 입력 | 행 수 | 기대한 설명·개수 일치 | 원래 관찰 |
| --- | ---: | ---: | --- |
| 빈 목록을 포함한 생성 | 4 | 4/4 | COMPLETE |
| 외부 입력과 생성 원소 읽기 | 8 | 8/8 | COMPLETE |
| 생성 원소를 읽은 연결 | 4 | 4/4 | COMPLETE |
| 원소 읽기 구간의 새 페이지 | 5 | 5/5 | COMPLETE |
| 중단된 원소를 포함한 새 페이지 | 2 | 2/2 | PARTIAL |

실제로 실행된 새 설명 프로그램의 입력 23행에서 설명과 개수가 23행 모두 일치했다.
기록을 만든 과거 프로그램의 재실행은 0회, 모델 호출도 0회다.
CLI 결과는 정답 없는 입력 모드의 `OBSERVED`, `finite_total=0`을 유지한다.
위 23/23은 별도 테스트에 적은 이 예제의 기대값과 비교한 수치다.

## 처음 막힌 지점

[9719 로그](run9719.log)에서 원소 예제 두 호출이 Go식 `:=` 변수 선언으로
생성 단계에서 실패했다. 같은 실행에서 목록·읽기·연결 설명은 통과했다.
Gooo의 `let`으로 고친 뒤 [9743 로그](run9743.log)의 새 입력 구간 두 개를 실행했다.
각각 5행과 2행이 통과했다. 앞선 실패 결과를 성공으로 바꿔 기록하지 않았다.

새 입력 옵션의 충돌·범위, 다섯 저장 형식, 빈 페이지, 32KiB 초과 진단,
잘못된 참조·집계 12종도 9719에서 확인했다. 이 검사는 원래 프로그램을 실행하지 않는다.
원래 관찰 요약과 영수증 해시, 다음 페이지가 새 결과에 남는지도 확인했다.

구형 v1 읽기 기록도 [9767의 새 입력 어댑터 검사](run9767.log)에서 20행 중 2행을
골라 읽었다. PARTIAL을 유지하고, 없는 생성 기록의 조회를 거절하며, 반환 요약을
수정해도 원래 기록이 바뀌지 않는 것을 확인했다. [최종 Go 소스](producer9767.tar.gz)와
[해시 목록](producer9767.json)을 보관했다. 이 검사에서도 프로그램 실행은 0회다.

## 시간과 용량

이번 단일 관찰에서 새 소비 프로그램의 전체 runtime 구간은 약 315~670ms였다.
빌드 시간은 약 97~273ms, 첫 네이티브 프로세스의 CPU 시간은 약 7.9~10.7ms,
최대 RSS는 약 4.7~4.9MiB였다. 전체 runtime에는 빌드와 두 번의 실행·관찰이 포함된다.
PC 전체 CPU 사용률은 측정하지 않았다. 반복 성능 비교로 해석할 자료는 아직 없다.
[상세 수치](summary.json)와 각 실행 JSON을 함께 보관했다.

추가 모델이나 도구 체인 다운로드 없이 작업했고 실행 바이너리는 실행기의 임시
디렉터리 정리로 제거된다. 소스 스냅샷은 압축 보관한다.

## 출처와 범위

[9719 소스](producer9719.tar.gz)·[해시 목록](producer9719.json),
[9743 소스](producer9743.tar.gz)·[해시 목록](producer9743.json)에 실제 생성 소스를 보관했다.
최종 예제는 네 종류별 하위 폴더로 옮겼다. 9743의 Gooo와 워크스페이스 바이트는
유지했고, 테스트의 파일 경로만 새 배치로 맞췄다. 옮긴 뒤의 과거 사례는 로컬에서
다시 실행하지 않았다.

원래 데이터는 [목록 생성 관찰](../construction-origins/README.md)의 세 runtime이다.
원소마다 읽기가 없다는 결과에는 앞서 계산한 지역 변수를 사용하는 경우도 포함된다.
전체 데이터 의존성, 중첩 레코드·목록, 외부 사용자의 첫 실행 경험은 후속 범위다.
