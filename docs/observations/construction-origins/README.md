# 새 목록의 원소가 만들어진 곳을 이어 보기

2026-10-14 개발 관찰. 이 디렉터리는 제안 소스와 로컬 실행 기록을 담는다.
이 변경안의 CI와 릴리스 수록 여부는 공개 PR에서 따로 확인한다.

## Gooo로 표현한 문제

```gooo
let previous = input.values[0]
let numbers = []int64{
    Inner(input),
    input.values[0] + input.values[1],
    previous + 2,
}
return Batch{values: numbers[1:], ...}
```

목록을 만든 뒤 일부를 잘라 다음 활동에 넘겨도, 읽은 원소에서 원래 생성 표현으로
돌아갈 수 있어야 한다. 같은 숫자가 입력과 새 목록에 있더라도 각각의 위치와
생성 과정을 유지한다. 새 부품에 조립 위치를 적고, 조립하는 동안 꺼내 쓴 부품의
기록도 함께 붙이는 방식이다. 위 설명의 `...`는 생략 표시이며, 실행 가능한 전체
소스는 [구성·전달 예제](construction9533.gooo.fixture)에 있다.

`body_constructions`는 Gooo 본문에서 목록과 원소의 위치를 잡고 Go 투영까지
같은 구문 노드를 따라간다. 실행에서는 `construction_sites`와
`traces[].constructions`가 실제 생성 횟수와 원소별 계산 구간을 담는다.
읽기에는 외부 입력의 `origin` 또는 새 목록의 `construction`이 붙는다.
생성 번호와 원소 번호는 같은 사례의 생성 기록을 가리킨다.

원소의 `read_start`부터 `read_end` 직전까지는 그 원소를 계산하는 동안 발생한
같은 사례의 `reads`다. 중첩 호출이 만든 목록과 그 목록을 읽은 일도 이 구간에
남는다. 원소 표현을 순서대로 한 번씩 계산하며 새로운 스레드나 잠금을 추가하지 않는다.

출력 일치의 분모는 선언한 예상 출력이다. 생성·읽기 수는 실행에서 기록된 사건 수다.
이를 언어 전체의 완전성이나 모델 정답률로 환산하지 않는다. 모델 호출은 이번 관찰에서 0회다.
Gooo에 선언한 후보와 사례만으로 결정하는 경로를 사용했다.

[프로토콜 관찰](observe9571.log)은 빠진 좌표, 미래 생성 참조, 이중 기원,
미완료 생성 참조, 잘못된 원소 수, 차단된 활동의 생성 등을 거부했다.
생성 4,096회 상한과 원소 65,536개 상한에 도달한 경우의 부분 기록도 별도로 확인했다.
이 두 상한 관찰은 인위적으로 만든 프로토콜 입력이며, 그 규모의 네이티브 성능 측정은 아니다.

## 아직 연결하지 않는 부분

- `previous + 2`의 `previous`를 앞서 읽었던 입력까지 동적으로 추적하는 기능은 남아 있다.
  이 원소의 계산 구간에는 새 읽기가 없고, `previous + 2`라는 소스 위치가 남는다.
- `input.name` 같은 단일 필드는 생성 표현에 보존된다. 현재 원소별 읽기 구간은
  목록의 인덱스·순회 읽기를 기록한다.
- 기록된 읽기가 결과에 영향을 줬다는 인과관계를 모두 증명하지는 않는다.
  원소 계산 중 사용하지 않는 값을 읽는 경우도 해당 구간에 들어간다.
- 소스 위치는 선택된 Gooo 문서 기준이다. 작업공간 원본 파일과 후보 조각까지의
  동적 위치 연결, 중첩 목록, 원소 대입과 목록 증가는 추가 개발 과제다.

상한에 걸리면 값을 만드는 동작은 계속하고 누락 수를 기록한다. 읽기는 실행당
65,536회, 생성은 4,096회 및 예약 원소 65,536개, 각 목록은 256개까지다.
실행 기록 파일은 최대 32MiB로 읽는다. 입력과 생성 목록을 연결할 때 사용한
메모리 주소는 프로세스 안에서만 쓰며 저장하지 않는다.

## 저장된 기록을 Gooo에서 사용하기

`CompositionConstructionFacts`는 생성 원소를 14개 스칼라 필드로 펼친다.
`CompositionConstructedReadFacts`는 사례·읽기·생성·원소 번호를 연결한다.
[설명 프로그램](consumer9593.gooo.fixture)은 실제 저장된 관찰을 레코드 입력으로 받아
조건문으로 분류했다. 미완료·누락·위치 미연결을 별도 결과로 다루는 메타프로그램의
입력으로 사용할 수 있다.

실행 결과 JSON의 `runtime`에서도 같은 정보를 읽는다.

```sh
gooo body-compose --source docs/observations/construction-origins/construction9533.gooo.fixture \
  --cases docs/observations/construction-origins/construction9533-cases.json --entry Read
```

이 명령은 기능 사용법이다. 기존 관찰을 로컬에서 다시 실행해 결과를 갱신하지 않았다.
구조와 성능을 비교할 때는 새로운 소스·입력 묶음과 실행 환경을 함께 기록한다.

## 시간·실패·보관

구성·전달 예제의 첫 네이티브 프로세스는 벽시계 355.62ms, CPU 6.51ms,
최대 RSS 4.95MiB였다. 내장 동일성 확인을 위한 두 번째 프로세스는 4.00ms,
CPU 3.13ms, 최대 RSS 4.89MiB였다. 프로세스 CPU 시간이며 PC 전체 CPU 사용률은
측정하지 않았다. 단일 관찰이므로 일반적인 지연 시간이나 속도 개선으로 해석하지 않는다.
[요약 원본](summary.json)에 다른 프로그램의 측정도 있다.

첫 시도 9473은 리팩토링 중 필요한 `bytes` import를 빠뜨려 컴파일하지 못했다.
9571은 출력 2/2와 위치 연결을 얻었지만, 테스트가 선택 표현의 괄호를 예상하지 않아
실패했다. 두 실패와 각각의 소스는 그대로 보관했다. 수정 후에는 별도 입력과
표현을 가진 새 관찰을 실행했다.

이전 PR #1543의 원본 CI는 `observeCompositionRuns`를 자동으로 분리하는 과정에서
`NO_SAFE_DECLARATION_CAPACITY`를 보고했다. 관찰 상태와 결과 연결을 별도 구성으로
분리해 수정했다. CI를 다시 실행하거나 이미 공개한 소스를 바꾸지 않았으며,
후속 PR의 원본 CI가 이 변경 전체를 검토한다.

[생산 소스 묶음](producers.tar.gz), 각 `producer*.json`, 실행 로그와 종료 기록을 보관한다.
새 모델·워크트리·복제 저장소를 만들지 않았고, 네이티브 실행 임시 파일은 기존 실행기의
정리 경로를 사용한다. 100가지 실험 전체, 모델과 소스 결정의 결합, 외부 사용성 검증은
계속 남아 있는 목표다.
