# 목록을 고르는 계산과 접근 표현의 출처

측정값 목록에서 구간을 자른 뒤, 다른 활동이 그 구간의 특정 위치를 읽는 프로그램을
Gooo로 구성했다. 구간 시작과 끝, 읽을 위치를 소스에서 따라가고, 그 표현들을 다시
Gooo 활동에 전달해 설명하는 것이 이번 관찰의 목적이다.

`source_fill`의 명시적 후보는 레코드 입력에서 정수·문자열·불리언 결과를 직접 반환할 수 있다.
목록 원소를 읽기 위해 출력용 레코드를 따로 만들 필요가 줄었다. 후보는 타입 검사와
선택 사례를 거치고 별도 보류 사례의 결과를 남긴다. 모델을 연결하지 않은 결정론적 경로로 관찰했다.

## 프로그램과 관찰 결과

| 관찰 | 확인한 범위 | 결과 |
| --- | --- | --- |
| 정수 목록 | 구간 선택 → `bind` → helper 호출 → 요청한 위치 읽기 | 새 입력 5개, 활동 출력 10/10 |
| 문자열·불리언 목록 | 소스 타입 ID로 정한 별칭 타입의 원소 선택 | 새 입력 4개, 출력 4/4 |
| 선택 사례 | 정수 2개, 문자열 1개, 불리언 1개 | 각각 2/2, 1/1, 1/1 |
| 별도 보류 사례 | 각 출력 타입에 하나씩 | 각각 1/1 |
| 접근 출처 | 필드·목록·인덱스·구간 경계 | 실제 방문한 표현 16건 |
| Gooo 설명 | 저장된 접근 표현을 읽는 새 Gooo 프로그램 | 16/16, 원래 프로그램 재실행 0회 |
| 구조 한도 | 접근 노드·접근 사실의 상한과 중복 | 각각 256, 범위 오류와 잘림 표시 |

숫자는 이 입력과 예상 출력에 대한 관찰이다. 같은 값이 여러 번 있는 목록과 빈 구간을
포함한다. 결과값이 같다는 이유로 기원을 추정하지 않고 소스 표현과 바이트 위치를 읽는다.

[측정 프로그램](measurements.gooo.fixture), [입력과 예상 출력](measurements-cases.json),
[워크스페이스](workspace.json), [실행과 출처](access8887.json),
[문자열·불리언 결과](scalar8851.json)를 함께 보관한다.
[설명 프로그램](explain.gooo.fixture)은 실제 [접근 사실을 소비한 결과](consumer8933.json)와 연결된다.
`.gooo.fixture` 파일의 내용은 Gooo 소스이며, 실험 입력을 일반 예제 목록과 구분해 보관한다.

## 저장한 결과에서 출처 읽기

이 변경이 포함된 개발 빌드에서 다음 조회를 사용할 수 있다.

```sh
gooo package origins --receipt docs/observations/collection-access/execution8887.json --follow --json
gooo package origins --receipt docs/observations/collection-access/execution8887.json --follow --activity urn:access8887:take
```

JSON의 `report.value_flow.accesses`는 소스 접근 목록이다. 필드 `kind`가 `index_operand`면
위치를 정하는 식, `slice_low`와 `slice_high`면 구간 경계다. 각 항목에는 activity ID,
선택 본문 해시, 원래 본문의 바이트 범위가 남는다. `ProgramAccessFacts`는 같은 정보를
Gooo 레코드로 전달하며 기존 `ProgramOriginFacts`의 레코드 형식을 유지한다.

접근 목록은 후보 필터가 없는 조회에서 최대 256건이다. `--candidate`는 후보 기원 행을
조회하며 접근 목록은 생략한다. `accesses_truncated`, `truncated`, `analysis`, `issues`를
함께 읽어야 한다. 예제의 분석은 조기 반환의 제어 경로와 펼치지 않은 호출 때문에 `PARTIAL`이다.
레코드 구성과 분기에서 가능한 기원이 합쳐지며, 개별 원소의 실행 기원은 후속 범위다.

세 번의 CLI 조회에서 원래 실행 기록의 해시는 유지됐고 프로그램·모델 실행은 없었다.
첫 조회는 약 674 ms, 다음 두 조회는 약 14.5 ms와 12.6 ms였다.
[명령별 관찰](ended8971.json)에 남겼으며, 반복 성능 측정이나 속도 보장으로 해석하지 않는다.
검사용 실행 파일 약 26 MB는 관찰 후 삭제했다.

## 발견한 문제와 수정

첫 프로그램은 레코드 입력에서 정수를 반환하는 후보를 구성하지 못했다. 기존에
레코드 출력만 허용하던 조건을 고치고, 정수·불리언·문자열의 정확한 값 비교 경로를 연결했다.
다음 새 프로그램에서는 출력 10개가 맞았지만 인덱스 접근이 보고서에서 빠졌다.
여러 의존 경로가 합쳐질 때 최단 기원 경로만으로 접근 목록을 만들었던 것이 원인이었다.
조회 중 방문한 접근 표현을 따로 수집해 이 누락을 고쳤다.

이전 실패를 덮어쓰지 않고 [첫 로그](observation8791.log), [두 번째 로그](observation8837.log),
[수정 후 새 프로그램](observation8887.log), [Gooo 소비 프로그램](observation8933.log)을 남긴다.
과거 소스·테스트·모델 코호트의 로컬 재실행은 0회다. 실패 후에는 구분된 새 소스와 입력을 사용했다.
문자열·불리언 관찰은 두 번째 로그 안에서 통과했으며 다시 실행하지 않았다.

[요약](summary.json)과 각 `producer*.json`은 관찰 당시 기준 커밋과 변경 파일 해시를 기록한다.
[소스 묶음](producer-sources.tar.gz)은 당시 변경 파일을 보존한다.
전체 CI와 개발 브랜치 수용 여부는 이 변경의 원래 PR 실행 결과로 별도 확인한다.
