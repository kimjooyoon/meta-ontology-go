# 지역 대입에서 조립 전 소스로 돌아가기

`let seed=__GOOO_BODY_HOLE_seed__`의 빈 부분을 후보 `input+383`으로 채웠다고 하자.
실행 기록에는 `seed`에 대입한 회차가 남고, 그 대입 위치에는 선택된 후보 표현의
원래 문서·해시·바이트 범위가 연결된다. 이후 `seed=doubled+input`은 템플릿에서
온 표현으로 구분한다. 같은 변수여도 대입마다 조립 출처가 다르다.

`local-fill-fragments` 입력은 저장된 대입 기록에서 해당 조립 조각을 선택한다.
원래 생산 프로그램이나 모델을 다시 실행하지 않는다. 분류는 입력을 받은 Gooo
프로그램의 조건문이 담당한다. 직접 선언한 후보, 문법으로 조립한 표현,
유지한 템플릿의 종류를 전달하며, 이번 실제 실행에서 관찰한 종류는 후보와 템플릿이다.

## 범위와 다음 연결

`source_start`와 `source_end`는 조립 입력에 기록된 후보 표현, 문법 또는 템플릿
조각의 범위다. 템플릿 조각은 하나의 대입 표현보다 넓을 수 있다.
`selected_decoded_start/end`는 조립된 본문 안의 해당 대입 우변을 가리킨다.
두 범위를 같다고 해석하면 안 된다.

기록된 조립 출처가 없으면 새 출처를 추측해서 넣지 않는다. `completed`는 그 대입이
실제로 끝났는지를 따로 나타낸다. 조립 출처가 있다는 사실만으로 실행 완료나 값의
최소 원인 집합을 주장하지 않는다. 사용 기록의 `assignment_index`를 같은 실행
사례의 대입 기록과 연결하면, 해당 사용이 읽은 대입의 조립 출처를 따라갈 수 있다.

현재 새 경로는 로컬 후속 구현이다. 공개 예제·문법 등록과 CLI의 저장 기록 읽기를
연결했으며, 전체 기능의 수용 여부는 후속 제출의 원래 통합 CI로 확인한다.

## CLI 연결과 등록 확장

11553에서는 패키지 실행의 조립 출처가 별도 `BodyFills`에 남아 있어 행이 0개로
나오는 문제가 확인됐다. 해당 별도 출처를 지역 대입에 연결했다. 완료된 11553은
로컬에서 다시 실행하지 않았고, 다른 분기 계산과 입력을 가진 11591로 확인했다.
새 생산 결과는 2/2, 실제 CLI 읽기의 두 출력은 `candidate`, `template`과 일치했다.
읽기 실행은 기대값 없는 OBSERVED이며 분모 0을 유지한다.
[추출 출처](record-origin11591.json), [CLI 요약](cli11591-summary.json)을 보관한다.

11503은 합성 메타데이터로 같은 출처의 중복과 서로 다른 후보의 충돌을 구분했다.
출처가 충돌하면 AMBIGUOUS_ASSEMBLY_INPUT을 남기며 임의의 출처를 선택하지 않는다.
선택적인 출처 설명이 없던 기록의 위치 식별자는 유지하고, 이미 있는 설명의 모순은
거부한다. 이 검사는 언어 프로그램을 실행하지 않았다.

등록기에서 새 읽기 소스를 v54→v55로 등록했다. 생성된 9개 역할·9개 파일을 그대로
보관했다. PR #1548 원래 CI에서 드러난 분모 선택 함수의 크기 문제는 생성기에서
16개 항목씩 나누도록 수정했다. 11447에서는 실제 소스 분할기로 선택 함수 6개,
최대 37줄, 분할 파일 7개가 각각 75줄 이하임을 확인했다. 11617에서는 선택 생성만
v55→v56으로 이어지는 경로를 확인했다. 해당 후속 분모를 실제로 등록한 것은 아니다.
