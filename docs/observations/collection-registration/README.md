# 목록 문법을 자체 등록 과정에 연결하기

Gooo 프로그램이 정수·문자열·불리언 목록을 사용하면, 그 문법을 확인하는 설정도
등록 과정에 함께 따라가야 한다. 이번 변경은 Gooo로 선언한 `RegisterSyntaxCapability`가
검사 목록, 네이티브 등록 코드, 기능 수와 버전 기록을 함께 구성하도록 연결한다.

## 관찰한 동작

새 목록 프로그램 3개를 각각 등록했다. 세 프로그램 모두 필요한 9개 산출물 역할을
채웠고, JSON 검사 목록과 생성된 Go 등록 코드에 목록 문법 설정이 남았다.
서로 충돌하는 문법 설정 조합 9개는 거절했다. 등록 후보는 입력 소스와 활동 ID에
연결되며, 원래 입력을 변경하지 않는다.

[관찰 요약](summary.json), [원본 로그](observation8551.log),
[종료 기록](ended8551.json), [생산 소스 목록](producer8551.json),
[생산 소스 묶음](producer.tar.gz)을 함께 보관한다.
실행 전체는 약 6.59초였으며 컴파일 시간이 포함된다. 모델 호출은 0회다.

## 이전 CI에서 고친 연결 문제

목록 예제 두 개를 추가하면서 언어 기능 수가 80개에서 82개가 됐다.
등록 과정이 읽던 기준은 80개여서 다음 등록을 진행할 수 없었다.
v49 기록은 82개를 명시하고 v48의 원본 바이트와 다른 다섯 경계의 수치는 유지한다.
이후 새 프로그램 등록은 그 기준에서 다시 한 개씩 증가한다.

자동 함수 분리에는 이미 다른 파일로 옮긴 `registryPaths`를 다시 옮기려는
옛 규칙도 남아 있었다. 해당 규칙의 내용과 출처는 이력에 남기고 실행 목록에서
제외했다. 현재 소스 구조를 읽는 일반 분리 경로가 후속 변경을 처리한다.

읽기 전용 Git 임시 사본은 하위 디렉터리의 쓰기 권한 때문에 정리되지 않았다.
이제 소유한 임시 디렉터리의 권한을 복구한 뒤 삭제한다. 새 사례에서 외부 경로를
가리키는 링크의 대상은 유지되는 것을 확인했다.

이 관찰은 등록 산출물과 임시 파일 수명에 관한 범위다. 생성 후보를 적용한 전체
컴파일러 검사와 목록 전달의 최종 출처 연결은 공개 후 해당 PR의 원본 CI로 확인한다.
