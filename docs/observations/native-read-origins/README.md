# 목록을 읽은 위치와 원본 입력의 기원

같은 숫자가 여러 번 있는 목록에서 두 번째 항목을 읽었다면, 값만 비교해서 어느
항목이었는지 알아내기는 어렵다. 이번 구현은 프로그램이 실제로 읽은 위치를 기록한다.
구간을 잘라 다른 활동에 넘겨도 `구간의 1번 → 입력 목록의 2번`처럼 연결한다.
소스에 있는 읽기 표현과 입력 원소에 각각 꼬리표를 붙이는 방식이다.

Gooo가 선언한 목록, `bind`, 함수 호출, `for … in`을 사용한 새 프로그램으로 관찰했다.
`source_fill`은 소스에 있는 후보와 사례를 이용해 읽을 위치를 선택했다. 모델 호출은 0회다.

## 이번에 사용할 수 있는 것

- `[]int64{input.amount, 0}`, `[]string{"기본", input.name}`, `[]bool{true, false}`로
  본문에서 목록을 만든다. 빈 목록도 가능하며 한 목록의 상한은 256개다.
- `input.items[index]`와 `for item in input.items`가 실행된 위치를 기록한다.
- 슬라이스, 레코드 복사, `bind`, helper 호출을 통과한 원소를 원본 입력에 연결한다.
- 기록을 평평한 레코드로 바꾸고, 다시 Gooo 프로그램에 입력해 해석한다.

원소 대입과 목록 증가는 기존의 읽기 전용 목록 규칙을 따른다. 중첩 목록, 고정 길이
배열 표기, 원소별 키를 붙인 리터럴은 현재의 목록 생성 범위에서 제외한다.

## 실행과 기원 연결을 각각 읽기

| 새 관찰 | 예상 출력 | 실행 중 읽기 | 원본 입력 원소에 연결 |
| --- | --- | --- | --- |
| 구간 → bind → helper → 후보로 고른 위치 | 7/7 | 20건 | 19건, 새 목록 1건 미연결 |
| 문자열·불리언 목록 조립과 빈 문자열 목록 | 9/9 | 6건 | 새로 구성한 목록 6건 미연결 |
| 생략·빈 값·값이 있는 optional 목록을 함께 받기 | 3/3 | 3건 | 3건 |
| 중첩 인덱스와 원소 주소 전달 | 4/4 | 6건 | 6건 |
| Gooo가 저장된 읽기 기록을 설명 | 20/20 | 원래 프로그램 재실행 0회 | 위치 이동 10건, 유지 9건, 미연결 1건 |

기원 관찰은 35건 중 28건이 입력 원소에 연결됐고, 새 목록의 7건은 미연결이다.
이 비율의 분모는 기록한 읽기 횟수다. 각 프로그램의 예상 출력 일치율은 표의 별도 열에 있다.
읽기 표현 12곳은 모두 선택한 Gooo 소스의 해시와 바이트 위치에 연결됐다.

[구간 프로그램](read-window.gooo.fixture), [입력](read-window-cases.json),
[실행 기록](native9059.json), [읽기 레코드](read-facts9059.json)를 함께 제공한다.
[설명 프로그램](explain-reads.gooo.fixture)과 [소비 결과](consumer9127.json)는 그 레코드를
Gooo에서 다시 사용하는 예다. 원래 프로그램을 실행하지 않고 저장된 runtime에서 읽었다.

[목록 조립](literal-decisions.gooo.fixture), [그 결과](literal9281.json),
[optional 입력](optional-input.gooo.fixture), [그 결과](optional9311.json),
[중첩 인덱스](nested-index.gooo.fixture), [그 결과](order9361.json)도 보관한다.
`.gooo.fixture`는 실험 자료를 일반 예제 목록과 구분한 파일 이름이며 내용은 Gooo 소스다.

## 결과를 읽는 방법

이 변경이 포함된 개발 빌드에서는 기존 `body-compose` 결과에 기록이 포함된다.
아래 명령은 사용자가 새로 실행할 때의 예이며, 이번 작업에서 저장된 프로그램을 다시 돌리지는 않았다.

```sh
gooo body-compose --source docs/observations/native-read-origins/read-window.gooo.fixture \
  --cases docs/observations/native-read-origins/read-window-cases.json --entry Run > execution.json
```

결과 JSON에서 다음 항목을 함께 읽는다.

| 위치 | 내용 |
| --- | --- |
| `runtime.read_sites` | 읽기 종류, 활동 ID, Go 표현 위치, 선택한 Gooo 표현 위치 |
| `runtime.read_inputs` | 외부 입력의 활동·포트·엔티티·필드 ID |
| `runtime.traces[].reads` | 실제 읽은 인덱스, 그때의 목록 길이, 입력 원소의 번호 |
| `runtime.read_observation` | 기록·연결·미연결·누락 수와 기록 파일 해시 |
| `runtime.traces[].reads_dropped` | 기록 상한 이후 생략된 읽기 수 |

`origin.input_collection`은 `read_inputs`의 번호이고 `origin.element_index`는 원본 입력
목록의 번호다. 두 번호 모두 0부터 시작한다. 슬라이스 안의 `index`와 원본의 번호가
달라질 수 있다. 건너뛴 분기는 읽기 이벤트를 남기지 않는다. 주소를 얻는 표현에서는
실제로 값을 읽는 내부 인덱스만 기록한다.

컴파일러 내부의 `CompositionReadFacts`는 Gooo 레코드에 넣을 수 있는 스칼라 필드를
반환한다. [설명 프로그램의 입력](explain-reads-cases.json)에는 그 형태를 그대로 담았다.
기존 `package origins --follow`의 정적 경로와 함께 사용하면 선택한 표현과 실제 입력 위치를
각각 살펴볼 수 있다.

## 기록 방식과 현재 범위

실행 시 JSON 입력을 읽은 직후, 실제 배열 원소를 내부의 타입이 있는 포인터로 등록한다.
슬라이스와 레코드 복사는 같은 원소를 참조하므로 입력 기원이 이어진다. 이 포인터는
실행 중에만 사용하며 파일에는 입력 번호와 원소 번호를 기록한다. 같은 값을 비교해
연결하는 단계는 없다. 각 입력 사례를 시작할 때 등록표를 새로 만든다.

새 목록은 그 목록을 만든 Gooo 표현의 출처를 가진다. 현재 실행 기록에서 원본 입력
원소와의 연결은 미연결로 남긴다. 목록 안에 입력값을 복사하거나 산술 계산을 넣었을 때의
원소별 파생 관계는 후속 구현 범위다. 여러 패키지의 원본 파일·후보 조각으로 이어지는
상세 위치는 기존 정적 기원 조회를 함께 사용한다. 이번 동적 표현 위치는 선택된 Gooo 문서를 가리킨다.

성공한 정수·문자열·불리언 목록 읽기를 관찰한다. 인덱스 범위 밖의 접근은 기존 실행
오류 흐름을 따른다. 읽기 지점은 최대 4,096개, 이벤트는 실행별 최대 65,536개,
입력 원소 등록은 사례별 최대 65,536개다. 누락과 미연결은 `PARTIAL` 및 개별 카운트로 남긴다.
관찰은 동기식이며 별도 작업 큐나 잠금을 추가하지 않는다. 기존 실행 시간 제한을 따른다.

새 네이티브 실행은 기존 런타임의 두 번 실행 절차에서 출력과 읽기 기록을 각각 비교했다.
과거 소스·테스트·모델 코호트의 로컬 재실행은 0회다.

## 실패와 자원 관찰

첫 시도에서는 본문 목록 리터럴이 거절됐다. 제한된 스칼라 목록의 검증과 평가를
추가한 뒤 구분된 새 소스와 입력으로 확인했다. 이후 예제 작성 과정에서는 후보 ID의
하이픈·대문자, 빠진 bind, 테스트 코드 치환 오류가 각각 드러났다. 마지막 예제는
소문자 후보 ID와 명시적인 입력 전달을 사용했다. 컴파일러 결함과 예제 작성 오류를
같은 성공률 분모에 섞지 않고 로그별로 남겼다.

[첫 제한](observation9023.log), [구간 실행](observation9059.log),
[소비·한도 검사와 ID 오류](observation9137.log), [테스트 빌드 오류](observation9173.log),
[bind 오류](observation9203.log), [대문자 ID 오류](observation9241.log),
[문자열·불리언·optional 결과](observation9311.log), [인덱스 순서 결과](observation9361.log).
후보 ID 진단에서 허용 문자를 더 구체적으로 알려 주는 사용성 개선도 필요하다.

구간 프로그램의 해당 관찰에서 네이티브 프로세스 시간은 약 401 ms와 7.37 ms,
CPU 시간(user+system)은 약 10.25 ms와 5.69 ms, 최대 RSS는 약 5 MiB였다.
전체 실행 준비를 포함한 런타임 호출은 약 714 ms였다. 첫 실행 지연의 원인 분해와
컴퓨터 전체 CPU 사용률은 이 관찰에 포함하지 않았다. 한 번의 관찰값으로 기록한다.
임시 네이티브 실행 폴더는 실행이 끝나면 제거된다.

[요약](summary.json)에 실행별 분모, 시간, 메모리와 공개 내보내기 내역이 있다.
각 `producer*.json`, [생산 소스 묶음](producer-sources.tar.gz),
[원래 결과 묶음](original-results.tar.gz)은 실패를 포함한 당시 입력을 보존한다.
`native9059.json`은 runtime을 유지하고 복사 분리 실험용 `facts` 필드를 생략한 공개본이다.
전체 CI와 개발 브랜치 수용 여부는 이 변경의 원래 PR 실행 결과로 확인한다.
