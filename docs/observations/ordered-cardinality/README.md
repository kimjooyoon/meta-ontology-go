# 단일 값과 목록 선언의 입력 규칙 확인

Gooo 소스의 타입, 필수 여부, `one`과 `many`에 따라 같은 JSON 값의 사용 가능 여부가
달라진다. JSON을 읽는 단계는 스칼라와 순서 있는 스칼라 목록을 받아들이고,
실행 계획은 필드 선언과 맞는지 확인한다. `required many`의 빈 목록은 제공된 값이며,
`optional many`의 생략은 값이 없는 상태로 남는다.

## 새 소스에서 확인한 결과

| 범위 | 결과 | 기록 |
| --- | --- | --- |
| Integer·Text·Boolean × required·optional × one·many | 새 소스 12개, 각각 입력 형태 10개. 예상된 처리 결과 120/120 일치 | [입력별 결과와 소스](observations/cardinality8017.json), [실행 로그](observation8017.log) |
| JSON 읽기와 소스 타입 확인 | 84개를 읽음. 그중 선언과 맞는 30개 실행, 나머지 54개 실행 전 거부. null·중첩 목록·객체 36개는 읽기 단계에서 거부 | 같은 입력별 기록 |
| 실행한 값과 기원 | 실행 30개에서 순서, 생략 상태, 정확한 int64, 소스 digest와 루트 입력 digest 보존 | 같은 입력별 기록 |
| 조건 분기와 목록의 정적 기원 | 새 본문 3개에서 분기 양쪽 값, 이름이 겹친 지역 변수, 한글 바이트 위치와 목록 입력 연결 확인 | [기원 결과](observations/origins8123.json), [분석 로그](observation8123.log) |
| 출처 분석 메서드의 자동 분해 입력 | 실제 helper 렌더러로 7개 메서드를 읽음. 최대 본문 44줄, 렌더링된 helper 49줄 | [렌더링 로그](observation8161.log) |

120개는 이 입력 규칙의 유한한 사례 집합이다. 원래 계획한 다양한 메타프로그래밍 실험의
개수와는 별도로 센다. 모델 호출은 0회다. 기원 분석의 3개 본문은 실행하지 않고 정적으로
읽었으며, 반복문의 원소별 실제 경로는 `PARTIAL` 범위로 남는다.

## CI에서 발견한 문제와 수정

[앞선 변경안](https://github.com/kimjooyoon/meta-ontology-go/pull/1538)의 기존 레코드 테스트가
목록 선언과 빈 목록 입력을 모두 거부하도록 기대했다. 목록을 지원하는 현재 의미에 맞춰
그 기대를 바꾸고, 단일 값 필드에 목록을 전달하는 경우는 소스 타입 확인에서 계속 거부한다.
null과 중첩 목록의 거부도 유지한다.

같은 변경안의 [저장소 변환](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/38423086423)은
길어진 출처 분석 메서드를 자동 분해하지 못했다. 선언 처리와 조건 분기의 환경 합치기를
별도 메서드로 옮겼다. 노드 생성과 순회 순서는 유지한다.

수정된 기존 테스트는 로컬에서 재실행하지 않았다. 각 새 관찰은 저장된 해당 소스에서
한 번 수행했으며, 전체 변경안의 호환성 판단은 새 공개 커밋의 원래 CI 결과를 따른다.
렌더링 회귀 검사는 이후의 파일 분할에도 대응하도록 파일명 대신 receiver와 메서드 이름으로
대상을 찾게 보완했다([최종 검사 변경 기록](final-capacity-test.json)). 이 최종 검사 코드의 실행 결과는 후속 CI에서 확인한다.
