# CI를 검증 작업의 도메인으로 다루기

수정한 줄 수는 작업량을 설명하는 입력 하나입니다. 실행 시간은 그 입력을
사용하는 코드, 필요한 검사, 선행 작업과 실행 환경에도 달려 있습니다.
공용 선언 한 줄을 바꾸면 많은 검사가 필요할 수 있고, 문서 여러 줄의 수정은
작은 검증으로 닫힐 수도 있습니다. 소비자를 확인하지 못한 입력은 전체 범위를
유지해야 합니다.

## 지금 연결한 흐름

1. 원본 CI 생성 시각과 실행기가 준비 작업을 받아들인 시각을 함께 관찰합니다.
2. 작업 예산은 준비 작업 수락부터 공유합니다. Go 설치와 도구 컴파일도 이 시간에 포함합니다. 도구는 한 번 컴파일해 공유합니다.
3. 각 단계가 실제 실행할 명령과 현재 소스의 출처를 묶습니다.
4. 접근 가능한 비용 저널에서 명령·환경·자원·이벤트 문맥이 맞는 표본을 찾습니다.
5. Gooo 정책이 남은 시간 안에서 실행 여부와 다음 행동을 결정합니다.
6. 완료와 실패, 중단된 비용을 외부 저널과 원본 실행의 산출물로 남깁니다.

허용 조건과 실행 결과의 분류는 공개 도구의
[policy.gooo](https://github.com/kimjooyoon/gooo-ci-domain/blob/8b621c007a988a1490c31f60d5bdd8818b91e583/policy.gooo)에
있습니다. 실제 Gooo 컴파일러가 생성한 Go 코드와 생성 출처도 함께 공개했습니다.
현재 연결은 해당 도구의 리비전을 고정합니다.

도구 버전은 CI 워크플로의 `GOOO_CI_DOMAIN_REVISION` 한 곳에서 고릅니다.
설치와 원본 출처, 소비자 검증, 비용 캐시가 이 값을 함께 사용합니다.
새 버전의 캐시는 별도 이름을 사용하며, 이전 버전의 관측 기록은 그대로 남습니다.

명령이 완료된 뒤 마지막 기록 저장이 실패하면, 이미 얻은 `WorkReceipt`와
원래 오류를 함께 전달합니다. 완료된 명령의 결과 필드는 유지하고 CLI 종료 상태는
실패를 알립니다. 호출자는 이 결과와 오류를 함께 읽고 후속 행동을 정해야 합니다.

명령이 성공하지 못하면 같은 receipt의 결정·수락 여부·다음 행동·예측값·경과 시간을
stderr에도 표시합니다. [main 원본 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39084671023)에서는
race 명령의 예상 비용 1,870,434ms가 남은 1,540,277ms보다 커서 실행 전에
`OVER_BUDGET`으로 거부됐습니다. 이 경우 `REFINE_REQUIRED_WORK`를 함께 읽어
테스트 결과와 실행 전 거부를 구분할 수 있습니다. 명령 인자와 원문은 이 요약에 복사하지 않습니다.
stdout의 기록 형식, 공유 시계와 검사 의무는 유지합니다.

[도구 #5의 원본 CI](https://github.com/kimjooyoon/gooo-ci-domain/actions/runs/39087875323)는
초기 대기 90초를 별도로 보존하고 수락 이후 45,932ms를 기록했습니다.
이 중 실제 검사 명령은 25,409ms였습니다. 해당 도구의 작은 검사 범위에 대한 값이며,
컴파일러 CI의 단축률은 새 소스의 원본 실행에서 확인해야 합니다.

## 의무와 시간의 관계

소스 관찰·메타 연산은 포맷·정적 검사·테스트와 함께 시작합니다.
최종 정책 판단 직전에 같은 실행 ID·원본 회차·소스 버전의 다섯 검사가
모두 성공했는지 합류 기록으로 확인합니다. 관찰을 만드는 작업과 그
관찰을 승인하는 작업의 선행 관계를 구분합니다. 이 합류는 처음의 공유
시계와 남은 예산을 사용하며 새 예산을 만들지 않습니다.

마지막 재현 단계는 앞선 증거 작업의 따뜻한 빌드에서 만든 컴파일러와
증명 도구를 사용합니다. 도구의 소스 버전·실행 ID·회차·Go 버전·내용
해시를 확인한 뒤, 예제 코드를 새로 생성하고 증명도 새로 계산합니다.
도구 산출물은 1일 보관하고 출처와 합류 기록은 원본 실행에 남깁니다.
이 변경의 CI 시간 단축량은 새 원본 실행에서 관찰할 항목입니다.

여섯 정식 검사는 현재 소스의 같은 검사 의무를 유지합니다. 각 작업의
실제 명령 본문은 원본 출처와 비교할 수 있습니다. 준비 작업 하나가
앞에서 도구를 만들고, 이후 단계들은 같은 작업 수락 시각과 명시한 실행 예산을 사용합니다. 이번 전체 소스 발견·검증 요청은 40분으로
두었고, 3분은 개선 목표입니다. 각 단계가 예산을 새로 받지는 않습니다.

예측값이 없는 새 작업은 남은 시간으로 첫 비용을 관찰할 수 있습니다. 시간을
넘긴 작업은 미완료와 중단 비용으로 기록합니다. 완료된 비용과 예측 오차는 다음
소스의 계획에 들어갑니다. 단축하려면 필요한 작업의 구조나 실행 자원을 바꿔야
하며, 아직 닫히지 않은 검증 의무는 계속 표시됩니다.

전체 의무를 유지하면서 고정된 자원으로 임의 크기의 변경을 언제나 3분 안에
끝낸다고 보장할 수는 없습니다. 현재 구조는 이 충돌을 계획 단계와 실제 실행
단계에서 드러냅니다. 변경 범위의 닫힘, 비용 예측의 가용성, 완료된 의무의 비율,
예측 오차, 전체 시각의 초과량을 각각 관찰해야 합니다.

## 출처의 단위

명령 출처에는 현재 커밋과 트리, 추적된 작업 파일, 실행 파일의 내용, 명령 인자,
환경과 자원 문맥이 들어갑니다. 논리 작업공간의 Git 설정은 그대로 사용합니다.
활성화 기록의 내용은 해시로 연결되며, 기존 활성화·정식 검증·승격 출처가
각자의 판단 범위를 담당합니다.

비용 저널은 소스 폴더 바깥에 있고 4 MiB 한도가 있습니다. 원본 실행의 기록은
다음 실행이 해당 캐시에 접근하고 비용 키가 같을 때 이어받습니다. 실패와 시간 초과도
보존 대상입니다.
도구 바이너리는 실행당 한 번 준비하고 임시 산출물은 하루만 보관합니다.

같은 커밋의 PR 설명 수정이나 워크플로 재실행은 새 GitHub 실행입니다. 비용 키가
같다는 이유로 이전 실행의 검증 결과를 현재 실행의 결과로 읽을 수 없습니다.
명령 어댑터는 실행 ID와 회차를 별도 출처로 전달합니다. 이전 저널의 완료 비용은
예측에 쓰되, 명령 시작 중복은 현재 실행 ID 안에서만 거부합니다. 출처 파일에는
실행 ID가 남고, 여섯 정식 검사는 새 실행에서 다시 수행합니다.

## 비용 이력을 사용할 수 있는 조건

같은 소스 트리라도 이벤트와 캐시 접근 범위가 다르면 예측 표본이 없을 수 있습니다.
2026-10-17의 [PR 원본 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39007202985)은
race 명령의 선행 표본이 0개, 예측값이 미확정이었습니다. 같은 트리의
[dev 원본 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39009450298)은
25개 표본에서 1,565,078ms를 예측했고 1,327,313ms가 기록됐습니다.
PR의 실제 기록은 1,426,663ms였습니다. 명령·환경·도구가 같아도 이벤트를 포함한
비용 키가 달랐습니다. 이 두 관측으로 전체 CI의 단축률을 계산하지 않습니다.

[GitHub 캐시의 접근 범위](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching#restrictions-for-accessing-a-cache)도
전달 가능성을 제한합니다. 현재 저널은 예측과 같은 소스의 중복 실행 거부에 함께
쓰이고, 예측은 작업 수락에도 영향을 줍니다. 다음 개선에서는 과거 비용의 참고 범위와
현재 작업의 실행 권한을 따로 다룹니다. 캐시를 통째로 다른 이벤트에 복사하거나
과거 성공 기록을 현재 검사 완료로 읽지 않습니다. 표본 수·키·캐시 가용성·예측값과
실제 비용을 함께 남겨 예측 실패와 이력 전달 실패를 구별합니다.

## 현재 관찰과 다음 문제

첫 연결에서 기록한 공개 도구의 원본 PR CI는 명령 실행 20.257초, 전체 범위 43.181초로
완료됐습니다. 이 값의 대상은 작은 도메인 도구입니다. 컴파일러의 전체 소스에
대한 원본 CI 결과는 별도 출처가 필요합니다.

후속 [도구 PR #4의 원본 실행](https://github.com/kimjooyoon/gooo-ci-domain/actions/runs/39048356392)은
43,686ms, [실제 main 원본 실행](https://github.com/kimjooyoon/gooo-ci-domain/actions/runs/39048431901)은
50,843ms의 요청 범위를 기록했습니다. 각 값은 해당 receipt의 `ScopeElapsedMS`이며,
산출물 전송까지 포함한 GitHub 전체 시간이나 컴파일러의 성능 개선율을 뜻하지 않습니다.

새 로컬 입력으로 실제 단계 어댑터의 로그와 GitHub 출력 전달, 명령 본문 보존을
확인했습니다. 완료한 과거 로컬 코호트는 재실행하지 않았습니다.

다음 개선 대상은 `.gooo` 입력의 실제 소비자 연결과 현재 전역 입력의 범위입니다.
관찰된 파일 읽기는 관계 후보가 됩니다. 그 관계의 출처와 수집 범위를 닫아야
검사 제외에 사용할 수 있습니다. 다른 observer 워크플로의 중복 실행과 외부
서비스·전송 비용도 같은 도메인에 연결해야 합니다. 작은 결정 모델은 소스가
허용한 동일 의무의 일정 후보를 고르는 곳에 적용할 수 있습니다.

초기 GitHub 대기는 실제 작업의 예산과 구분합니다. 원본 생성 시각을 지우거나 전체
경과 시간을 줄여 표시하지 않습니다. 각 작업의 `scope-origin.json`에 두 시각과
`admitted_source_work` 범위를 함께 보관합니다.

GitHub 대기열, 액션과 산출물 전송은 외부 경계입니다. 작업의 활성 시간 한도와
명령의 공통 시각과 요청별 예산은 구현했으며, 전체 원격 완료 시간은 원본 기록으로 계속
관찰합니다. [GitHub 실행 한도](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax)는
이 경계를 이해하는 기준입니다.

## 성공 출처와 실패 보고의 실행 조건

산출물이 없을 때는 같은 소스·실행 ID·회차의 생산 작업 상태를 함께 읽는다.
증명 입력을 받는 단계는 선행 `CI policy` 작업의 종료 결과를 먼저 확인해,
이미 실패·취소·생략된 생산자의 다운로드를 시도하지 않는다.
생산 작업이 건너뛰어졌는지, 실패·취소됐는지, 성공했지만 산출물 게시가
빠졌는지를 별도 이유와 다음 조사 대상으로 남긴다. 작업 상태를 읽지 못했거나
여러 작업이 같은 이름으로 관찰되면 성공으로 간주하지 않는다. 이전 회차의
산출물은 현재 회차의 성공 근거로 승격하지 않는다. 이 분류는 실패 원인의
진단을 돕고, 실제 첫 실패는 원본 작업과 단계 기록에서 확인한다.

여섯 정식 검사와 증명 작업이 성공하면 `ci-proof.json`과 provenance receipt가
그 소스의 완료 출처입니다. CI 전체의 최종 상태는 GitHub 원본 실행에서 읽습니다.
실패 보고는 이 일곱 선행 작업 중 하나라도 성공하지 못했을 때 실행합니다.
실패·생략·취소·미확정 결과는 보고 경로에 남깁니다. 워크플로 전체 취소에 대한
기존 조건도 유지합니다.

[#1581](https://github.com/kimjooyoon/meta-ontology-go/pull/1581)의 원래 실행에서는
여섯 검사와 증명 묶음이 성공한 뒤, 추가 실패 요약이 새 작업공간을 만들다가
공통 예산의 마지막 1초를 소진했습니다. 이 결과는 원래 실행의 실패로 보존합니다.
이후 성공 경로에서는 원래 증명 묶음을 사용하고, 추가 실패 보고 작업은 생략합니다.
실행 예산과 검증 의무는 그대로 두었습니다.

기존 `ci-closure/v2` CLI와 그 명시적 호출은 유지합니다. 자동 CI의 성공 경로는
별도 closure 산출물 대신 기존 증명·receipt를 사용합니다. 실패 경로의 원본 작업
수집과 분류, 실패 manifest의 형식과 출처 검사는 같은 코드로 이어갑니다.

### 예산을 소진한 뒤의 실패 관찰

[#1672의 원본 실행](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39076890730)은
여섯 검사를 통과했지만 마지막 증명 작업이 공유 시계를 연결할 때 남은 예산이
없어 실패했습니다. 실패 보고 작업도 같은 지점에서 멈춰 원인 수집을 생략했습니다.

실패 수집은 앞 단계가 실패한 뒤에도 현재 실행·회차의 작업 API를 읽습니다.
원본 작업 행과 단계 결과를 먼저 저장하고, 내려받은 도구의 `origin.json`이 있으면
바이트 그대로 보관합니다. 기존 분류기가 만든 입력도 함께
`ci-failure-observations-<run>-<attempt>` 산출물로 14일간 남깁니다.
이 기록은 에이전트가 시간 부족과 소스 실패를 구별하는 입력입니다.

공유 시계와 검사 의무, 증명의 성공 조건은 계속 적용됩니다. 원본 기록을
보관했다고 실패가 성공으로 바뀌지 않으며, 실행기 자체의 종료나 GitHub API·전송
실패까지 기록 보존을 보장하지는 않습니다. 로컬 검사는 실패 뒤 수집 조건,
정확한 회차 선택, 원본 값 보존을 확인합니다. 새 워크플로에서 실제 예산 소진 뒤
업로드까지 성공하는지는 별도 원본 실행 관찰이 필요합니다.

## 실행 명령도 자신의 출처를 갱신하기

기존 dev 관측에서는 race 검사가 성공했지만, 관측 선언이 이전의
`go test -race ./...`를 가리켜 해당 명령을 `COMMAND_CONTEXT_MISSING`으로 남겼습니다.
실제 명령에는 JSON 출력과 extractor 패키지 선택이 추가돼 있었습니다.

관측 선언을 현재 명령과 단계 이름에 맞췄습니다. 새 정적 검사는 7개 선언의 PR·push
문맥을 실제 워크플로에서 읽고, 이전 명령이 새 문맥에 연결되지 않는지 확인합니다.
명령이나 소스가 달라지면 문맥 해시도 달라집니다. 이후 비용 관측의 완성 여부는
새 소스의 원래 CI 결과에서 확인합니다. 이 검사는 기존 프로그램이나 비용 실험을
재실행하지 않습니다.

## 외부 도구를 가져오는 단계의 출처

[#1582](https://github.com/kimjooyoon/meta-ontology-go/pull/1582)는 여섯 검사와
네이티브 실행을 통과했지만, 마지막 증명 작업이 `setup-go`를 내려받기 전에
실패했습니다. 같은 공식 리비전이 앞선 작업에서는 실행됐고, 이후 직접 조회한
아카이브는 404를 반환했습니다. 원래 실행은 실패로 보존하고 병합하지 않았습니다.

후속 소스는 아카이브를 확인한 공식 `v6.4.0`과 해당 커밋을 사용합니다. Node 24와
Go 1.27.3, 캐시 입력, 검사 의무는 유지합니다. 새 정적 검사는 모든 워크플로의
소비자가 [선택한 도구 출처](observations/action-origin/observations.json)에 연결되는지
확인합니다. 이후 원격 가용성은 새 소스의 원래 실행으로 관찰합니다.

## 현재 구현과 과거 진단의 대상을 나누기

함수 추출기 진단은 특정 과거 커밋과 산출물을 조사하는 도구입니다. 파일 변경을
계기로 그 과거 대상을 자동 실행하던 경로에서, 보관이 끝난 산출물 조회가 404로
실패했습니다. 이 결과는 그 진단 요청의 실패로 남깁니다.

PR은 현재 워크플로의 요청 계약과 셸 본문 문법을 검사합니다. 과거 프로그램을
실행하는 경로에는 커밋·실행·산출물·해시 네 입력을 모두 명시해야 합니다. 숨은
기본 대상은 제거했습니다. 산출물의 실재 여부와 해시·계획 검사는 실제 진단 시
계속 확인합니다. 구현 파일의 변경과 과거 프로그램 재실행은 각각 자신의 대상을
가집니다. [첫 계약 검사](observations/diagnostic-request/observations.json)는 이 경계만
확인하며, 과거 프로그램과 모델을 실행하지 않습니다.

고객의 검사를 생략하지 않았으며, 시간 단축량도 아직 측정하지 않았다.

## 계획상의 미해결 항목과 실행 실패를 구별하기

[#1655의 원본 CI](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39017267224)에서
source-repacker가 계획하지 못한 1,035개 항목은 정상적으로 수집됐고, 이후 단계도
진행됐다. CI policy의 실제 실패는 마지막 정식 검사 합류에서 `gofmt` 실패를 읽은
지점이었다. 그런데 계획 안내의 `파일.go: 사유` 표현도 오류 annotation으로 보였다.
해당 실행의 [setup-go 오류 감지 규칙](https://github.com/actions/setup-go/blob/b7ad1dad31e06c5925ef5d2fc7ad053ef454303e/matchers.json)은
줄 번호가 없는 이 표현도 인식한다.

계획 안내는 기존 `repackBlocked`의 대상과 사유를 각각 인용된 필드로 표시한다.
계획 가능·미해결 개수와 쓰기 없음의 의미는 유지한다. 쓰기 요청의 거부, 파일 읽기와
구문 오류는 기존 오류 반환 경로를 따른다. 검사에는 현재 다섯 사유의 표시, 기존
오류 정체성, 감지 규칙과의 경계, 계획 가능·불가·누락 파일·선택 대상 없음 및
계획 중 원본 보존을 포함한다. 이 작은 출력 경계의 개선은 새로운 오류 체계나
고객 검사 생략 권한을 만들지 않는다. 결과 해석에는 실제 단계의 종료 상태와
구조화된 계약을 함께 사용한다.

## 실패 관측이 보고서 생성까지 이어지도록 하기

[원본 콜백 39086489606](https://github.com/kimjooyoon/meta-ontology-go/actions/runs/39086489606)은
소스 실행 `39084727702`의 포맷 검사 실패를 읽은 뒤, 실패 관측에도 성공한 검사
연결을 요구해 보고서를 만들지 못했다. 대상 소스는 `c2840bff`이며 콜백을 실행한
`dev` 커밋과 구별한다. 관측기는 성공·미관측·중복·실패를 각각 보존하도록 수정했다.

해시를 확인한 원본 산출물의 작업 행과 소스 워크플로를 새 읽기 코드에 전달하자
7개 작업이 실행 관측 4개, 생략 2개, 거부 1개로 보존됐다. 보고서는 `REFUTED`,
`READ_ONLY`이며 원래 실행의 `cancelled` 상태와 포맷 실패를 유지한다. 재사용과
승격은 허용하지 않는다. 이 확인은 저장된 기록의 읽기이며 원본 검사 재실행이나
GitHub 콜백 수정본의 실행 결과가 아니다.
