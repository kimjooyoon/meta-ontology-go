# 변수를 거쳐 온 조건의 기원

[자격 계산](eligibility.gooo)은 후보에서 고른 기준값을 `eligible`이라는 변수에
담고, 그 변수를 조건으로 금액을 계산한다. 조건에 직접 숫자가 나오지 않아도
`후보의 기준값 → 변수 대입 → 조건`을 따라 최초 파일로 돌아갈 수 있다.

`let eligible = input > 53; if eligible ...`에서 `eligible`이라는 이름만 검색하면
안쪽 블록의 같은 이름이나 나중에 바뀐 값을 잘못 연결할 수 있다. 이 구현은
구문의 변수 선언을 식별하고, 각 사용 위치에 도달할 수 있는 대입을 연결한다.

## 읽는 정보

- `body_fills[].generation.report.body_fill.source_origin.data_flow`: 선택된 본문의
  대입·조건·반환식 노드, 값의 입력 `inputs`, 분기를 만든 조건 `controls`
- `runtime.condition_sites[].source.construction.data_flow`: 해당 조건으로 이어지는 부분 그래프
- `construction.input_source.fragments[].relation`: `direct`, `static_dependency`,
  `direct_and_static_dependency` 중 해당하는 관계
- `construction.input_source`: 후보와 빈칸이 처음 선언된 패키지 파일의 해시와 위치

노드 ID는 본문 해시 안에서 사용하는 위치 식별자다. 언어의 안정된 activity·후보·빈칸 ID는
기존 선언에서 이어받는다. 반복문에서는 의존 관계에 순환이 생길 수 있다.

분기 뒤의 값에는 양쪽에서 도달 가능한 대입이 함께 들어간다. 이는 소스에서 가능한
정적 의존 관계이며, 특정 입력으로 실제 실행한 경로는 기존 실행 기록에서 읽는다.
조건별 그래프에도 본문 분석의 제한 사항을 보수적으로 함께 남긴다.

## Gooo가 직접 해석하기

[`ConditionDependencyFacts`](../../internal/bodyexecution/condition_dependency_facts.go)는
실제 후보 조각의 기원을 11개 필드의 record로 전달한다.
[설명 프로그램](explain.gooo.fixture)이 `analysis_status`와 `relation`을 읽어
“자격.gooo에서 변수를 거쳐 연결됨” 같은 문장을 만든다.
다른 기준으로 출처를 분류하려면 이 `.gooo` 활동을 바꾸면 된다.

파일 위치를 찾은 상태 `source_status`와 의존 관계를 분석한 상태 `analysis_status`는
각각 전달한다. 파일의 위치를 알아도 함수 내부까지 추적했는지는 별도의 질문이기 때문이다.

| 5107 | 실행 결과 2/2, 후보→변수→조건→최초 파일 연결, 저장 구성 읽기 |

이는 나열한 사례의 관찰이다. 언어 전체의 지원률이나 프로그램 정확도에 대한 백분율은 아니다.
각 로컬 관찰은 `f1d6ab92831408acd0b559a1e2e1a740cbc5e19a`와 해당
`producer*.json`의 파일 조합으로 실행했다. 나중 공개한 커밋의 결과로 바꾸어 표기하지 않는다.
변경된 초안 파일은 `snapshots/`에 함께 남겼다. 과거 테스트나 모델 자료는 로컬에서 재실행하지 않았다.
모델 호출과 학습은 모두 0회다.

## 명령행에서 읽기

`cli5381`은 기준값을 변수에 담아 금액에 세 배를 적용하거나 8을 빼는 별도 규칙이다.
새 구성의 입력 79·59와 저장한 구성에 전달한 새 입력 83·61에서 각각 결과 2/2를 확인했다.
두 호출 모두 후보가 변수를 거쳐 조건으로 이어지는 관계와 원본 위치가 남았다.

```sh
gooo package execute --json --cases cases.json workspace.json > receipt.json
gooo package replay --json --cases next-cases.json --receipt receipt.json workspace.json
```

첫 호출은 약 1.12초, 저장 구성을 읽는 호출은 약 0.87초였다. 한 번씩 관찰한 명령행
전체 시간이며 처리량 비교는 하지 않았다. 두 임시 실행 파일은 제거했다.
[실행 기록](execute5381.json), [새 입력 기록](read5413.json),
[실행 결과 조회](inspection5381.json), [저장 구성 조회 결과](ended5413.json)를 함께 남긴다.

첫 결과 수집 코드는 `result.runtime`을 최상위 `runtime`으로 잘못 읽어 실행 후 멈췄다.
그 종료 기록은 [ended5381.json](ended5381.json)에 보존했다. 실제 실행 결과를 다시 읽어
확인한 뒤, 아직 실행하지 않았던 입력 83·61로 저장 구성을 읽었다. 기존 입력은 재실행하지 않았다.

## 추적의 경계

본문은 128 KiB, 노드는 256개, 분석 방문은 8,192회, 반복문 합류는 16회로 제한한다.
한도에 닿으면 이유와 `PARTIAL`을 남긴다. 분석 결과가 프로그램 실행을 막지는 않는다.

호출한 다른 함수의 내부, 배열·포인터의 별칭, 조기 반환 이후의 제어 의존성,
반복문을 빠져나오는 모든 경로는 추가 구현 범위다. `switch`, `range` 등 현재
분석기가 펼치지 않는 구문도 이유와 함께 부분 결과로 남긴다.
반환식 노드는 조립 기록에서 읽을 수 있으며, 다른 activity의 `bind` 입력까지 잇는 작업은 남아 있다.

저장 기록에 `data_flow`가 없으면 해당 정보의 부재를 유지한다. 이미 기록된 그래프는
저장 구성과 비교하며, 새로운 위치 추정으로 과거 내용을 덮어쓰지 않는다.

다음에는 이 연결을 바탕으로 “이 후보를 바꾸면 어떤 조건과 반환값을 다시 살펴봐야 하나”를
Gooo 활동으로 묻는 범위를 확장할 수 있다.
