# Proof-carrying artifact

This experiment makes the combination of a generated artifact and its
justification evidence a language-level object. The Gooo source declares the
operation that produces a `ProofCarryingArtifact`; the producer emits three
typed evidence records and carries a four-step verification recipe with them.

The artifact is deliberately not an authorization. It is emitted as
`subject_artifact_decision=CARRIED`, with
`artifact_use_authority=NONE` and
`INDEPENDENT_CONSUMER_VERIFICATION_REQUIRED`. The consumer may derive only the
narrow capability `artifact_use_authority=READ_ONLY_CONSUMPTION` after
independently reading the source bytes, rechecking the operation receipt,
checking the invariant, and matching the carried recipe to its own canonical
recipe. Mutation, promotion, and semantic authority remain false; generated
bytes alone have no authority path.

## Evidence language

| kind | claim | proof choice | meta-operation | independently rechecked against |
| --- | --- | --- | --- | --- |
| `SOURCE` | source bytes are bound | `FOUNDATION` | `bind-source-bytes` | raw `.gooo` bytes and source digest |
| `OPERATION` | the operation receipt is bound | `COHERENCE` | `bind-operation-receipt` | receipt digest, entry projection, and event sequence |
| `INVARIANT` | generated bytes do not grant authority | `REGRESSION` | `preserve-no-byte-authority` | zero writes, no mutation authority, consumer-required flag |

The recipe has an explicit version and digest and contains the four steps
`verify-source`, `verify-operation`, `verify-invariant`, and
`grant-read-only-consumption`. The producer and trusted consumer each carry a
copy; the consumer's copy is authoritative for conformance, while the
expected case table is validator expectation only. The last step is a
consumer action, not a producer claim. Its capability transition is recorded
as `NONE -> READ_ONLY_CONSUMPTION` only after the three evidence claims
transition from `CARRIED -> PRESERVED`.

The artifact carries both the raw source digest and the canonical semantic
digest. The consumer uses the core `syntax.ParseFile -> bidir.Lower` path, so a
comment-only source intervention changes the raw digest but preserves the
semantic digest and consumer decision. A semantic intervention changes the
operation receipt, evidence links, and claim transitions. The verifier package
does not import the producer or source-execution package; its producer import
numerator is measured over a fixed internal-dependency denominator, while
core-parser dependencies are reported separately.

The workflow snapshots all tracked and untracked repository paths before and
after the run. The structured write-set observation is carried into the
artifact and report, including its before/after digests and exact changed-path
list; it is not inferred as `repository_writes=0` merely because outputs live
outside the repository.

## Research decisions

This experiment adopts the following principles from primary specifications and
research:

1. [Necula, *Proof-Carrying Code: Design and Implementation*](https://people.eecs.berkeley.edu/~necula/Papers/marktoberdorf.pdf)
   requires code to carry a precise explanation, while the receiver checks that
   the explanation is acceptable, addresses the receiver's policy, and matches
   the code. We adopt receiver-side matching and a small independent checker.
   We reject the stronger claim that these bounded JSON checks are a formal
   proof of all compiler or program semantics.
2. [SLSA Build Provenance](https://github.com/slsa-framework/slsa/blob/main/spec/build-provenance.md)
   models provenance as an attestation of how a subject was produced, requires
   externally controlled inputs to be verified downstream, and distinguishes
   the trusted builder from the signer. We adopt explicit producer, source,
   operation, and consumer identities plus downstream input rechecks. We do not
   claim SLSA compliance, signer authenticity, or a cryptographic signature:
   this receipt is read-only and unsigned.
3. [in-toto artifact rules and verification](https://in-toto.io/docs/getting-started/)
   chains named steps with materials, products, and verification rules. We
   adopt a fixed recipe whose named steps and inputs must match exactly. We
   reject open-ended or producer-selected rules: an unrecognized or weakened
   recipe cannot grant authority.

## Fixed cases and falsification

The contract has a fixed denominator of six cases and twenty-four indicators.
The case table below is a validator expectation, not a producer-supplied
authority decision:

| case | expected result |
| --- | --- |
| valid artifact | `PASS / EXACT`, read-only consumption capability |
| tampered evidence | `FAIL_CLOSED / INVARIANT_ONLY`, evidence digest mismatch |
| missing operation evidence | `FAIL_CLOSED / LOWER_RESOLUTION`, evidence missing |
| artifact bytes only | `FAIL_CLOSED / LOWER_RESOLUTION`, bytes are not authority |
| independent recipe mismatch | `FAIL_CLOSED / INVARIANT_ONLY`, recipe drift rejected |
| coherent outer+inner reseal | `FAIL_CLOSED / INVARIANT_ONLY`, source/operation reconstruction mismatch |

Proof claims additionally have a canonical OPEN prior ledger. An independently
reverified source, operation, and recipe claim is appended as `DISCHARGED`; a
missing or unknown claim remains `OPEN` with `LOWER_RESOLUTION`; a coherent
contradiction is `REFUTED`. Each append records the previous digest, stage,
step, reason, evidence digest, and provenance. These claim-ledger transitions
are separate from the artifact transport transition `CARRIED -> PRESERVED`.
The fixed report therefore has three preserved transport transitions and four
total transitions after the read-only capability transition is included.

The claim is falsified if generated bytes grant any authority, if the consumer
grants read-only consumption without all three external inputs, if either a
stale or coherently resealed tampering case passes, if a missing evidence case
is treated as exact, or if a recipe different from the canonical consumer
recipe grants authority. It is also falsified if a comment-only intervention
changes the semantic digest or decision, or if a semantic intervention leaves
operation/evidence/claim-transition digests unchanged. The receipt reports
`producer_import_numerator=0` over its fixed denominator,
`semantic_claims=0`, and the observed repository write-set; these are explicit
scope boundaries, not hidden success claims.
