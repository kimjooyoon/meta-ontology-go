# 실제로 평가한 조건을 결과와 함께 읽기

이 예제는 요청 수량과 처리 가능한 수량으로 승인 여부, 이유, 요청 번호를 구성한다.
Gooo 소스가 조건과 반환 후보를 선언하고, 실행 기록은 실제로 평가한 조건을 남긴다.
모델을 연결하지 않은 결정론적 구성으로 관찰했다.

```sh
go run ./cmd/gooo package execute --json \
  --cases examples/native-condition-evidence/cases.json \
  examples/native-condition-evidence/workspace.json
```

패키지 실행의 입력·기대값 이름은 `units1067/contract:Receive`처럼 패키지 경로를 포함한다.
본문의 `계약.Request` 별칭과 외부 입력의 패키지 식별자는 각각 선언한 범위에서 해석한다.
정확한 입력 표기는 [cases.json](cases.json)에서 볼 수 있다.

## 원래 관찰

| 항목 | 관찰 |
| --- | --- |
| 후보 선택 사례 | 1/1. 승인 여부가 같아도 이유가 다른 후보는 0/1. |
| 별도 평가 사례 | 1/1. 선택 사례와 다른 입력. |
| 실제 실행 | 6개 입력, 두 활동의 기대값 12/12. |
| 조건 실행 기록 | 두 `if` 위치에서 평가한 조건 10건. |
| 위치별 참·거짓 | 위치 두 개 × 참·거짓 두 값, 4/4 쌍 관측. 각 위치별 분모. |
| 원본과 재실행 | 입력 파일 네 개 유지, 두 네이티브 프로세스의 출력 일치. |
| 모델·외부 제공자 호출 | 각각 0회. |

[observation.json](observation.json)은 원래 CLI 관찰과 생산자 정보를 담는다.
생산자는 `61a9bdf`와 임시 Go 변경 11개로 구성됐고, 이후 공개 커밋으로 다시 이름 붙이지 않았다.
[trace.json](trace.json)은 그 실행의 소스 해시·조건 위치·입출력을 읽기 위해 발췌한 자료다.
운영체제 프로세스 기록은 발췌에서 생략했다. CI 승인 자료는 해당 공개 소스의 원래 CI에서 얻는다.

`condition_sites`가 활동 ID와 조건의 코드 위치를 보관한다. 각 입력의
`conditions`는 `site_index`와 실제 참·거짓 값으로 그 위치를 가리킨다.
`deliveries`의 입력·결과·필드 ID와 함께 읽으면 조건과 반환 레코드를 대조할 수 있다.
예를 들어 수량 28, 처리 가능 수량 26인 입력은 첫 조건이 거짓, 두 번째 조건이 참이며
`capacity_exceeded`를 반환했다. 실제 필드와 활동 ID도 기록에 남아 있다.

## 관찰의 범위

조건 위치는 관찰기를 넣기 전의 순수 Go 투영에 대한 바이트 위치다.
Gooo 파일의 원래 문자열 위치로 읽으려면 추가 위치 대응이 필요하다.
이유 문구는 소스에서 작성한 값이며, 조건 기록을 보고 사용자가 의미를 대조한다.
전체 조건식의 참·거짓을 기록하므로 개별 피연산자·지역 변수·루프 종료 조건의 값은 후속 범위다.
위치·값 쌍의 관찰을 전체 업무 요구의 완전성으로 환산하지 않는다.

원래 한 번의 CLI 호출은 구성·빌드·두 프로세스 실행을 포함해 약 1.36초였다.
해당 호출의 자식 프로세스 CPU 시간은 사용자 약 0.174초, 시스템 약 0.169초였다.
다른 언어와 같은 조건으로 비교한 속도나 전체 PC 사용률은 아직 관측하지 않았다.
임시 실행 파일은 해시와 크기를 기록한 뒤 제거했다.

[development-observations.json](development-observations.json)에는 처음의 기록 부재,
다른 새 소스의 중첩 호출·산술 실패, 잘못 쓴 CLI 입력명과 이번 새 예제의 관계를 남겼다.
처음 잘못 쓴 `Receive` 입력은 실행 전에 거절됐으며, 그 소스의 결과를 성공으로 바꾸지 않았다.
서로 다른 관찰의 분모와 생산자를 각각 유지한다.
