# 조립된 조건에서 최초 파일로 돌아가기

두 패키지가 각각 `Check`를 선언하고, 자신이 가진 후보로 조건의 빈칸을 채운다.
컴파일러가 이름을 바꾸고 여러 단계를 합친 뒤에도 어느 파일의 어떤 후보가
현재 조건을 만들었는지 읽는 예제다.

`runtime.condition_sites[].source.construction.input_source`에는 최초 패키지의
파일·해시·activity ID, 의도·후보·빈칸의 위치와 조각별 기원이 들어 있다.
그 바깥 `construction`은 해당 조립 단계의 입력과 출력 위치를 보존한다.
각 위치는 자신이 가리키는 문서의 해시와 함께 읽는다.

## Gooo가 해석하는 부분

Go의 `ConditionFillInputFacts`는 파일 위치와 조각 정보를 평평한 record로 옮긴다.
`.gooo`의 `Describe`가 `MAPPED` 여부와 후보·템플릿 종류를 읽고 표시할 문자열을 정한다.
다음에는 같은 선언을 공유하는 조각을 찾거나 변경한 선언의 소비자를 모으는
메타프로그램에 이 입력을 사용할 수 있다.

이 예제는 조건과 직접 겹치는 조각을 관찰했다. 후속 [변수 기원 예제](../value-origins/README.md)는
지역 대입을 거친 조건과 본문의 반환식으로 연결을 확장한다.
함수 간 값 이동과 반복해서 등장하는 빈칸은 추가 구현 범위다.
이름 치환의 중간에 걸린 위치는 `UNMAPPED`로 남긴다.
출처 필드가 없는 저장 기록에는 과거 기원을 새로 써 넣지 않는다.

## 명령행에서 저장한 구성 다시 사용하기

`cli4799`의 배송 규칙은 import한 계산식을 후보에 사용한다.
새 구성을 만들 때 2개 입력, 저장한 구성을 읽을 때 겹치지 않는 2개 입력을 사용했다.
두 호출 모두 결과 2/2와 원래 파일의 후보 표현식 위치가 유지됐다.
전체 명령행 호출은 각각 약 1.29초와 0.29초였다. 단일 실행의 관찰값이며
지속적인 처리량이나 PC 전체 사용률을 뜻하지 않는다. 임시 실행 파일은 제거했다.

```sh
gooo package execute --json --cases cases.json workspace.json > receipt.json
gooo package replay --json --cases next-cases.json --receipt receipt.json workspace.json
```

[실행](execute4799.json), [새 입력으로 읽기](read_new_inputs4799.json),
[관찰 요약](ended4799.json)에 결과를 남겼다.
