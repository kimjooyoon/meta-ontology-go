# Gooo가 다음 확인 입력을 고르는 반품 예제

금액이 `0`이면 금액을 유지해도, 부호를 바꿔도 결과가 같습니다. 이 사례만
통과한 구현으로 반품 기능이 충분히 확인됐다고 말하기는 어렵습니다.

이 프로그램은 금액·승인·설명에 대한 조건을 Gooo 활동으로 적습니다.
`criteria`가 조건을 연결하고, `observe`가 추가로 확인할 입력을 선언합니다.
후보들이 서로 다른 결과를 내는 입력을 고르면, 그 입력도 이후 조립 과정에서
계속 지켜야 할 조건이 됩니다.

개발 버전 컴파일러로 실행합니다.

```sh
go run ./cmd/gooo body-codegen --json --activity Decide examples/source-criteria-questions/main.gooo.fixture
go run ./cmd/gooo body-compose --source examples/source-criteria-questions/main.gooo.fixture --entry Decide --cases examples/source-criteria-questions/evaluation.json --out /tmp/gooo-criteria-questions-example
```

첫 실행에서 확인한 흐름입니다.

1. 허용된 필드 조합은 8개입니다. 금액 `0`의 세 조건을 만족한 후보는 2개였습니다.
2. 추가 입력 `41`과 `-13`에서 두 후보의 출력이 달라졌습니다. 동률이면 소스에
   먼저 적힌 질문을 골라, `41`을 조건 검사에 추가합니다.
3. 두 입력에 대한 여섯 조건을 만족한 후보가 하나 남았습니다.
4. 선택 후 입력 `73`의 세 조건과, 생성된 프로그램의 별도 실행 2건을 확인했습니다.

| 확인 범위 | 관측 결과 |
| --- | --- |
| 최종 후보의 조건 | 6/6 충족 |
| 선택 뒤 별도 입력의 조건 | 3/3 충족 |
| 생성된 프로그램의 추가 출력 | 2/2 일치 |
| 추가 질문 과정 | 후보 평가 12회, 조건 평가 30회 |
| 모델 호출 | 0회 |

`-13`은 후보 출력을 살펴봤지만 조건 평가에는 사용하지 않았습니다. 위 숫자는
이 프로그램의 한정된 입력과 조건에 대한 결과입니다. 질문 과정의 작업 횟수는
최종 후보 재검사, 별도 입력 검사, 네이티브 실행을 합친 총 실행 비용과 다릅니다.

입력이 더 필요하거나 후보를 계산하지 못하면 그 상태도 기록합니다. 호출자가
다른 출력을 원하더라도 이미 확인한 조건이 사라지지 않습니다. 소스가 의도와
판단 기준을 가지고, 컴파일러는 허용된 선택을 좁혀 가는 실험입니다.
